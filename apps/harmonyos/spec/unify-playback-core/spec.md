# Feature Specification: 统一多端播放器内核（TV / 车机 / 平板对齐手机内核）

**Created**: 2026-10-31  
**Status**: Draft  
**Input**: User description: "我手机端的播放器修好了，给我把tv，car，平板的播放器都统一成 app 的播放器内核，不一样就是ui 显示不一样" + "就是所有的不同客户端 app 除了一显示不一样，内核功能都一样，只有 ui 不一样"

## Overview

将 TV 端与车机端的播放器底层从自研旧引擎（仅 AVPlayer、协商/上报/AVSession 一体的 1499 行巨型类）迁移到与手机/平板相同的统一播放内核（双引擎 AVPlayer+MPV、auto 自动降级、统一编排与会话上报），实现**所有客户端内核功能完全一致、仅 UI 形态不同**。平板端已复用手机链路，本特性不涉及平板改造。同时按用户确认，TV/车机 UI 补齐缺失的功能入口（倍速菜单、引擎选择）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - TV 端使用统一内核播放影片 (Priority: P1)

用户在 TV 端打开任意影片，播放走与手机相同的统一内核：默认 auto 模式（AVPlayer 优先），当影片解码不被 AVPlayer 支持时自动降级到 MPV 引擎继续播放，全程会话上报、心跳、进度记忆与手机端行为一致。播放画质、字幕轨、音轨切换能力与手机端完全对齐。

**Why this priority**: 统一内核是本特性的核心目标，TV 端用户量大且旧引擎能力最弱（无法播 AVPlayer 不支持的格式），收益最大。

**Independent Test**: 在 TV 模拟器/真机播放普通 MP4（AVPlayer 路径）与 AVPlayer 不支持的格式（验证降级），核对会话上报与进度。

**Acceptance Scenarios**:

1. **Given** TV 端已登录并打开一部 H.264 MP4 影片，**When** 点击播放，**Then** 走统一内核 AVPlayer 引擎起播，画面/声音正常，服务端会话建立并上报进度。
2. **Given** TV 端播放一部 AVPlayer 无法解码的影片（auto 模式），**When** AVPlayer 起播失败，**Then** 自动降级 MPV 引擎无缝接管播放（真机 arm64；模拟器上确认降级尝试与失败提示行为）。
3. **Given** TV 端播放中途退出再进入，**Then** 进度续播、观看状态与手机端行为一致。

---

### User Story 2 - 车机端使用统一内核播放（保留行车锁与 mini 条） (Priority: P1)

用户在车机端播放影片，底层与 TV/手机完全同一内核；车机特有 UI 行为保留：行车时视频画面隐藏仅播音频（行车锁）、页面收起后 mini 播放条继续播控、上一集/下一集播控指令。

**Why this priority**: 车机与 TV 同为旧引擎，且行车锁是安全合规要求，必须与统一内核并存。

**Independent Test**: 在车机模拟器播放影片，触发/解除行车锁，收起页面验证 mini 条接续播放。

**Acceptance Scenarios**:

1. **Given** 车机端播放影片中，**When** 进入行车状态，**Then** 视频画面隐藏、音频继续，不影响播放会话。
2. **Given** 车机端播放中，**When** 用户收起播放页，**Then** mini 条显示且播放不中断，可继续播控。
3. **Given** 车机端播放中，**When** 触发上一集/下一集播控指令，**Then** 正确换集并接续上报。

---

### User Story 3 - TV/车机 UI 补齐倍速与引擎选择入口 (Priority: P2)

TV 与车机播放页补齐手机端已有但缺失的功能入口：倍速播放菜单；引擎选择（auto/MPV/AVPlayer 三选一，与手机设置页同款选项）。TV/车机目前没有设置页，引擎选择入口放进各端播放器的菜单层，交互形态遵循各端现有 UI 风格（TV 遥控焦点、车机触控）。

**Why this priority**: 用户明确要求"UI 也补齐功能入口"；无入口则统一后的双引擎能力在 TV/车机上不可见、不可控。

**Independent Test**: TV 遥控操作倍速菜单与引擎选择；车机触控操作同两项；切换后播放行为随之改变并持久化。

**Acceptance Scenarios**:

1. **Given** TV 端播放中，**When** 用遥控器打开倍速菜单选择 2.0×，**Then** 播放速度立即生效且菜单焦点行为符合 TV 现有交互。
2. **Given** 车机端播放中，**When** 在菜单里将引擎从 auto 切换为 AVPlayer，**Then** 后续起播仅用 AVPlayer（不再尝试 MPV），偏好持久化。
3. **Given** 任一端选错引擎导致无法播放，**When** 用户切回 auto，**Then** 恢复自动降级行为。

---

### User Story 4 - 换集/连播在统一内核下跨端行为一致 (Priority: P2)

TV/车机现有的换集（上一集/下一集/自动连播）走统一内核完成，语义与手机端一致：换集时会话正常结束并开新会话，进度分别记忆；TV 端自动连播行为不变。

**Why this priority**: 换集是 TV/车机高频操作，回归风险集中在此，必须单独验证。

**Independent Test**: 播放剧集第 1 集，手动下一集、等自动连播、上一集，核对三个会话与进度。

**Acceptance Scenarios**:

1. **Given** TV 端播完第 1 集，**When** 自动连播触发，**Then** 第 2 集自动起播、第 1 集会话正确结束上报。
2. **Given** 任意端手动切上一集/下一集，**Then** 换集起播成功且各集进度独立记忆。

---

### User Story 5 - 后台播控（AVSession）统一 (Priority: P3)

TV/车机的媒体会话壳（后台长时任务、AVSession 播控指令）由统一的播放合规层承接，指令集合与手机端一致（播放/暂停/ seek/上一集/下一集），车机 mini 条与 TV 播控均正常响应。

**Why this priority**: 功能一致性的收尾项；对用户可见度低于播放本身。

**Independent Test**: 播放中从系统播控中心（控制中心媒体卡片）发指令，验证响应。

**Acceptance Scenarios**:

1. **Given** 播放中，**When** 系统媒体卡片下发暂停/播放/seek，**Then** 播放正确响应。
2. **Given** TV/车机播放剧集，**When** 卡片下发上一集/下一集，**Then** 正确换集。

### Edge Cases

- x86 模拟器上 MPV 为 stub（不可用）：auto 模式尝试 MPV 时应按统一降级路径给出与手机端一致的表现（报不可用、保持 AVPlayer 或提示），不得崩溃或卡死。
- 播放中引擎降级需要重建 Surface：TV/车机的 XComponent 重建流程必须与手机端一致，不得黑屏。
- 车机行车锁切换瞬间（显示↔隐藏）：播放不得中断，音频不得出现静音期之外的异常。
- 弱网/会话心跳失败（404/网络错误）：降档与续播行为与手机端一致。
- 离线副本（本机已下载文件）：TV/车机获得与手机一致的"离线优先、失败回退服务器"能力（内核自动获得；UI 不新增下载管理入口）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: TV 端与车机端播放 MUST 完全走与手机端相同的统一播放内核（统一引擎接口、编排层、会话上报、播控合规层），旧的自研引擎类及其别名层 MUST 从 TV/车机播放链路中移除。
- **FR-002**: 统一后的 TV/车机播放 MUST 支持双引擎：默认 auto（AVPlayer 优先、失败自动降级 MPV），与手机端降级语义完全一致。
- **FR-003**: 系统 MUST 保留各端现有 UI 形态与交互（TV 遥控焦点、长按连发快进；车机行车锁、mini 播放条），内核替换不改变这些行为。
- **FR-004**: TV 与车机播放页 MUST 新增倍速菜单（档位与手机端一致）。
- **FR-005**: TV 与车机 MUST 提供引擎选择入口（auto/MPV/AVPlayer 三选一），选择持久化并对后续起播生效。
- **FR-006**: 各端的能力协商 MUST 保留各自的客户端标识与设备形态口径（如 TV/车机的非移动端标识），但编解码能力申报 MUST 按实际引擎动态申报（与手机端机制一致）。
- **FR-007**: 换集/连播/上一集/下一集 MUST 经统一内核完成，会话结束与新建、进度记忆行为与手机端一致。
- **FR-008**: 系统媒体会话（AVSession/后台长时任务）MUST 由统一合规层承接，播控指令集合跨端一致。
- **FR-009**: 统一内核 MUST 在 TV/车机上支持离线副本优先播放（本机文件、失败回退服务器），无需新增 UI 入口。
- **FR-010**: 车机行车锁（行车时仅音频）MUST 在统一内核下保留且不中断播放。
- **FR-011**: 旧的重复实现（播放器模块内无引用的死代码、与共享库重复的片段跳过实现）SHOULD 在本次迁移中一并清理，避免双实现并存。

### Key Entities

- **统一播放内核（已有）**: 引擎接口（AVPlayer/MPV 双实现）+ 编排控制器（降级、seek 队列、音轨/字幕恢复、音频中断处理）+ 会话协调器（上报/心跳）+ 播控合规层（AVSession/后台任务）。
- **设备播放宿主（扩展对象）**: 现有手机播放 viewmodel 的设备无关化抽 取，新增 TV/车机两种宿主形态；对上层暴露与旧引擎等价的播放状态（相位、进度、缓冲、轨道列表、剧集信息）以最小化页面改造。
- **播放请求**: 跨页面/跨入口的起播请求（详情页预建、播放页接管），统一内核 MUST 兼容 TV/车机现有的"预建-接管-结束"生命周期。
- **能力口径**: 按端（手机/TV/车机）+ 按引擎（AVPlayer/MPV）双维度的编解码/容器能力申报。
- **引擎偏好**: 用户级持久化偏好（auto/MPV/AVPlayer），全端共享同一份偏好键。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: TV、车机、手机、平板四端播放走同一套内核代码，项目中不再存在 TV/车机专属的播放引擎实现（旧引擎类及别名文件删除）。
- **SC-002**: TV/车机端可完成与手机端相同的完整播放流程：起播 → 轨道/画质切换 → 倍速 → 换集 → 进度续播，全流程无功能缺失。
- **SC-003**: auto 模式下 AVPlayer 不支持的影片在 arm64 真机上经 MPV 降级后可正常播放（TV/车机与手机行为一致）。
- **SC-004**: 车机行车锁、mini 条、TV 遥控交互等各端既有 UI 行为 100% 保留，回归无缺陷。
- **SC-005**: TV/车机新增的倍速与引擎选择入口可用且偏好持久化，重启后仍生效。
- **SC-006**: 播放会话上报/心跳在四端行为一致（服务端看到的进度与状态不因端而异）。

## Assumptions

- 平板端已完全复用手机播放链路，无需改造；"平板统一"通过手机链路统一自动达成。
- 画中画（PiP）为手机/平板系统特性，TV/车机不适用，不在补齐范围。
- TV 首页大图预告（TvStage）与手机刷片流（ReelsPage）这类不建会话的轻量预览播放保持现状，不纳入统一内核。
- 车机 trickplay 预览缩略图不在本次 UI 补齐范围（倍速与引擎选择优先；车机屏幕尺寸下 trickplay 价值有限）。
- TV/车机没有设置页，引擎选择入口放在播放器菜单层，交互遵循各端现有风格。
- x86 模拟器 MPV 为 stub 不可用，MPV 降级路径只能在 arm64 真机完整验证；模拟器验证降级尝试的容错行为。
- 现有手机端播放内核（playback/player_engine 共享库）的模块配置已声明支持 car/tv 设备类型，无需改模块配置。
