# changelog 写作指南

`docs/changelog/vX.Y.Z.md` 会原文成为 GitHub Release body，并在应用内「设置 →
更新与维护」一个约 256px 高的滚动框里展示。读者是自己部署 movieclaw 的普通用户，
他们读它来决定「要不要点更新、更新后去试什么」。它是**产品更新说明**，不是变更清单。

下面的规则来自 2026-09 对一批顶级产品真实发布说明的调研（Home Assistant、Jellyfin、
Infuse、Immich、Tailscale、Linear、Raycast、Things、Notion、Dia、Figma、Cursor、
Obsidian、Vercel、Telegram、flomo、滴答清单、Bear），括号里是出处，方便理解
「为什么这么写」。

## 多语言维护

- 每个版本只维护一份 `docs/changelog/<tag>.md`：应用用 `vX.Y.Z.md`，模型用
  `torrent-ner-vN.md`，各客户端用与 tag 同名的 `<前缀>-vX.Y.Z.md`（`ios`、`tvos`、`macos`、`transcoder`、
  `android`、`androidtv`、`windows`）。
  同一份文件同步到同一个 GitHub Release，不按语言另建 Release。
- 服务器 changelog 不写客户端版本号：正文末尾的「Apps / 客户端」一节由发版流水线
  自动生成。功能需要新版 App 时，在该功能的段落里写明「需要 Android X.Y.Z 或更新版本」这类要求；
  必须更新的（如转码器协议变化）放开头提示框。
- **英文在前，完整中文在后**，两段之间用 `---` 和 `## 简体中文` 分隔。使用纯 Markdown，
  不用 HTML 折叠区：GitHub 支持折叠，但当前应用内更新日志不解析 HTML。
- 两种语言讲同一组事实，修改功能、升级要求或已知限制时在同一个 PR 里同步修改两段，
  不把中文缩成摘要。翻译保留版本号、命令、文件名、URL、校验值和贡献者账号。
- **固定章节名**（没有内容的节省略，顺序不变）：

  | 英文 | 中文 | 用途 |
  |---|---|---|
  | `Highlights` | 本版亮点 | 1～3 个主角 |
  | `More features and improvements` | 其他新功能与改进 | 合计超过 4 条时拆成 `New features` / 新功能 与 `Improvements` / 体验改进 |
  | `Fixed` | 修好了 | 用户会说「坏了」的问题 |
  | `For administrators` | 管理员须知 | 默认权限、服务器资源占用、成员可见的变化（只有服务器说明需要时才有） |
  | `Before you update` | 升级须知 | 回退、限制、拿走或挪走的入口、已知问题；首发版本改叫 `Before you start` / 开始之前 |
- **英文段的入口名**：界面只有中文（网页与各 App 目前都是），英文段把路径译成英文，只在**最后要点的
  那个控件**后附一次中文原名，如 Settings → Members → Edit member → turn off **Download videos to
  device (下载影片到设备)**。同一个入口第二次出现不再附；一串选项值（如思考档位）不逐个附；
  **已经拿掉的控件**也附中文原名（老用户要靠它对上号）；改名的两个名字都附（Delete (删除影片) is now
  Delete from library (从媒体库删除)）。界面状态文字（如「已思考，执行 2 次命令」）按需附一次。
  只有图标的按钮写「图标描述 + 无障碍名」，如 the ▶ button (片段) / 顶部的 ▶ 按钮（片段）。没有现成英文译名的，沿用以往说明里的译法
  （如 Update & Maintenance），没有就自己译。
- 文末对比链接统一用 `https://github.com/movieclaw/MovieClaw/compare/…`。
- 审核时对照两种语言的 Docker / 客户端升级要求、回退提醒、功能范围、数字与链接。
  `release-notes.yml` 只同步描述；调整语言不改标签、版本号、附件或发布状态。

客户端（iPhone、Apple TV、Mac、转码器、Android、Android TV、Windows）各有自己的 changelog，
规则相同，差别是：

- **先判定是哪种发版**，写法不同：

  | 类型 | 判定 | 写什么 | 对比链接 |
  |---|---|---|---|
  | 常规升级 | 有同前缀的上一个 tag | 按本指南常规写 | 同前缀上一个 tag → 本版 |
  | 渠道首发 | 第一次走正式渠道，但用户可能装过旧版（社区版、随服务器附带的包） | **两部分都要**：给新用户的完整介绍（能做什么、需要什么、怎么装），加「从旧版迁移」一节（对照用户手上的旧版：怎么拿到新版、数据会不会保留、什么变了、旧版怎么处理） | 不放（没有同前缀的上一个 tag） |
  | 全新首发 | 用户手上从没有过任何版本 | 只写介绍 | 不放 |
- **基线**：用户**实际拿到的**上一版。常规升级用上一个同前缀 tag；TestFlight 这类渠道里用户手上的构建
  早于 tag 时，以实际对外的那个构建为准。渠道首发的迁移部分，对照最后一次随服务器发出去的那一版
  （如 Windows 0.1.0 对照随 v0.37.0 发的 1.0.4）。基线 tag 不在主线上时（如打在合并预览提交上），
  改用内容相同的主线提交取提交列表。渠道首发的新用户介绍要盘点整个产品，不只是区间提交：另列一张
  「能力 → 证据」表。
- **范围**：写这个 App 用户会遇到的一切，包括由服务器决定、但直接影响这个 App 用户的事实（如成员默认
  权限、需要服务器能转码、服务器上的资源占用）；这类事实在客户端说明里也可以单列「管理员须知」。
  App 的功能依赖服务器新接口时，对比脚本也要对服务器目录跑一遍。服务器自身的变化留给服务器说明。
- **入口名的依据**：网页以 `apps/web/lib/mock-data.ts` 与组件里的文案为准（多套主题按默认主题写）；
  iPhone / Apple TV / Mac 以 `apps/apple` 的 Swift 字符串为准；Android 以 `apps/android` 的 Kotlin 字符串为准；
  Windows 以 `apps/desktop/ui` 的 HTML / JS 文案为准。
- **设备叫法**：按界面上的叫法写。iPhone App 在 iPad 上以兼容模式运行，正文写「iPhone」，标题按发版命名。
- **致谢**：看这个产品目录下区间内合入的 PR 作者，以及提交作者与 PR 作者不同的提交作者；仓库所有者
  （movieclaw、yipengfei329）与机器人账号（Cursor Agent、github-actions 等）不在致谢之列。渠道首发可以
  感谢这个客户端一路以来的主要贡献者。
- **应用内展示**：App 在更新提示里展示说明时，应只取「## 简体中文」之后、到下一个单独一行的 `---`
  为止（流水线可能在后面追加验证范围等段落）。发现某个 App 截取有误，**在本版修掉**：显示下一版说明的
  正是本版代码，只写进说明帮不到任何人。说明是在打 tag 之后补写或修订的，已经来不及在本版修，
  就记成下一版的必修项，写进 PR 描述。
- **服务器说明的范围**：盘点和致谢只看服务器与网页相关目录（`src/`、`apps/web`、`docker/` 等）；
  客户端换了获取渠道、旧版收不到更新时（如 Windows 1.0.x → 0.1.0），服务器说明要加一句指引和链接，
  因为老用户只会看到服务器的发布。

**重洗已发布的旧版说明**（按新规则重写历史版本时）：
- 基线是上一个同前缀的正式 tag，代码看那个 tag 本身，不看后来的修复。
- v0.38.0 之前各客户端随服务器一起发布，那时客户端的变化写在服务器说明里，和服务器功能一样按本指南盘点；
  需要的客户端版本照当时的写法写在功能段落里。
- 核对时会查出当时就存在、后来才修好的缺陷：只回填会丢数据或会卡死的，写成「已知问题（已在 vX.Y.Z
  修复）」；其余不回填，保持旧说明简洁。当时已经知道并写过的已知问题照常保留。
- 旧说明本身可以当线索（它代表当时想告诉用户什么），但其中每一句都要重新对照那个 tag 的代码核实。

## 一、先盘点，再取舍

盘点的问题不是「这些提交做了什么」，而是**「用户手上那一版 → 这一版，对他来说什么变了」**。
删掉的入口、改掉的默认值、新加的前提条件、回退路径还走不走得通，在提交标题里基本看不出来，
却是用户最会撞上的。所以盘点以**上一个正式版的代码**为基准，对比**本版的最终代码**。

### 1. 收集线索（三路一起看）

1. **提交与 PR**：`git log --first-parent 上一版tag..本版tag --oneline`（跳过 beta/rc；客户端用同前缀的
   上一个 tag，见 SKILL.md 第四节），以合并 PR 为单位过一遍，再用 `git diff --stat` 交叉检查。
2. **界面与门槛的机械对比**：`python3 scripts/release-surface-diff.py 上一版tag 本版tag <产品目录…>`，
   列出消失的界面文字（标「全部消失」的是真拿走了，标「别处仍有」的可能只是挪了位置）、新增的界面文字，
   以及默认值、版本门槛、权限、开关相关的改动行。**每一条消失的文字都要有交代**：用
   `git log -S'<文字>' 上一版tag..本版tag` 找到真正删掉它的提交，看提交说明是不是有意拿掉的。
   提交标题和前缀只是线索：`fix` 前缀的可能只是删重复入口，提交说明描述的也可能是周期中间的状态。
3. **重构过的页面逐屏对比**：提交里有 refactor、抽共用组件、换实现的页面，把上一版 tag 与本版 tag 的
   渲染内容逐项对照：错误提示、按钮、状态、加载与空状态有没有丢、有没有重复、事件有没有接上。
   对比脚本查不出这类问题（文字两边都在，或根本不是字符串），这次 Android 的「附件条显示两遍」
   「新会话页不再显示错误」都是这样漏的。
4. **已知问题的来源**：
   - 代码里的「已知限制」「TODO」「暂不支持」「一期不做」等注释。
   - 新功能在离线、权限不足、旧服务器、多设备时的表现：不只看页面有没有占位，还要把**常驻元素逐个点一遍**
     （顶栏按钮、标签栏附件、页内可点的卡片），看会不会报错。
   - 后台任务：清理和定时任务由谁、多久触发一次，常驻循环会不会提前退出；等待有没有上限，卡住时会不会
     堵住后面的任务；依赖的外部执行者（如转码器）离线时怎样；**客户端取消后，服务器上的作业会不会跟着停**。
   - 新用到的请求字段和选项值：服务端对空串、null、不传三种值分别怎么解释，和其他端实际发的值是否一致
     （这次 Android 选回「默认」不生效就是这样漏的）；「默认」在每个渠道的实际含义（可能就是「关」），
     老用户已选的值升级后落到哪里；「记住上次选择」这类偏好对**已有对象**（旧对话、旧条目）怎么生效，
     会不会悄悄覆盖对象自己的设置。
   - 错误被吞掉的界面：服务端可能拒绝的每种原因（未配置、数量上限、权限）分别会怎样，应对办法要逐一覆盖，
     不能只写「检查网络再试」。
   - 界面文案与实际行为对不上时，说明以代码行为为准，界面文案列为发版前必须修的缺陷。
5. **最终代码**：判断一项变化时看本版 tag 的代码，不看中间提交。周期内来回改过的东西，只按最终状态写；
   本周期内引入、又在本周期内修掉的问题（用户从没遇到过）不写。**每一条「修好了」都要在盘点表里附上
   上一版代码中问题存在的证据**（同一个页面、同一个操作在上一版 tag 里怎么出错）；如果那个页面或功能
   在上一版里根本没有，或者走的是另一套代码，它就不是修复，不写。下面几种也不写成「修好了」：
   - **预防性改动**：上一版代码有隐患，但用户还碰不到（如「发布多了以后会找不到」）；有用户能感知的
     好处就写成改进，否则不写。
   - **说不清上一版有没有出错**：如协议层的请求格式适配，不调真实上游无法确认用户遇到过；可以写成
     兼容性改进，不写症状。
   - **修了但对已经出事的用户不生效**：照写修复，再写一句已出事的人怎么恢复（恢复步骤同样要核实）。

### 2. 按八个维度逐一过（这是防遗漏的核心）

| 维度 | 要回答的问题 | 去代码里找什么 |
|---|---|---|
| ① 新能力 | 现在能做什么了 | 新页面、菜单项、按钮、接口 |
| ② **拿走、挪走、改名** | 什么不能做了，入口去哪了，叫什么了 | 消失的界面文字、删掉的菜单与路由、改名。写「现在到 Z」之前，在本版代码里确认 Z 真的能做同一件事（不是只能做一部分，如「只能整库清，不能只清一部」要照实写），并在上一版代码里确认 Z 是不是**本来就有**——本来就有的，写成「删掉了重复的入口」，不是「挪到了 Z」。还要确认：从用户原来所在的那一页能不能直接到 Z（全局按钮可能只在页签首页）、要不要重新输入或选择、有没有显示条件；其他端（如网页）仍保留原功能的，照实写 |
| ③ **默认行为** | 什么都不设置时，和以前有什么不同 | 迁移脚本的 `server_default`、模型与偏好的默认值、默认开关 |
| ④ **前提与限制** | 谁能用、什么条件下才能用、什么情况下用不了、前提**在哪里满足** | 版本门槛、权限与角色、能力判断、系统/硬件版本判断、试用开关、界面语言。版本门槛按服务器版本区间逐段写清行为（判断依赖的字段在旧服务器上可能根本不存在），「已登录不受影响」要写清到什么时候为止。转码、压缩、低画质这类功能逐项过：HDR、音轨与声道、字幕类型、是否真的更小。依赖插件或附加组件的，写清从哪里获取；没有公开发布渠道的不写成可用功能。「列出这个选项」与「真正执行」是否用同一套判断：列得出、执行不了的是缺陷 |
| ⑤ **副作用与成本** | 会多占什么、多做什么、影响谁 | 新缓存与目录、后台任务、并发与排队、流量、隐私相关字段 |
| ⑥ **兼容与升级** | 要更新什么、谁先谁后、新旧搭配会怎样 | `docker/runtime-version`、最低版本常量、协议号、旧客户端连新服务器（反之亦然）的行为 |
| ⑦ **数据与回退** | 改了哪些数据，出问题怎么退回去 | 迁移脚本、本机存储格式；**沿用户这次实际的升级路径**走一遍：要换 Docker 镜像的版本（runtime 变了），应用内更新会被拦下、**不会自动备份**，回退要写成「先停容器，再备份数据目录（数据库运行中直接拷贝可能不一致），回退时把镜像标签改回旧版本并恢复这份备份」；只走应用内更新的版本才有更新前的自动备份。客户端降级时，写清本机数据（如下载的文件）会怎样 |
| ⑧ 已知问题 | 已经知道哪里不对 | 核对中发现、来不及修的缺陷；实验性开关 |

②③④⑦ 是最容易漏的四个维度：它们改变的是用户「以为不会变」的东西。

### 3. 从三种读者的角度各读一遍

- **老用户升级**：什么变了，什么不见了，我要做什么？（②③⑥⑦）
- **新用户第一次装**：能做什么，需要什么才能用？（①④，含系统要求、界面语言、需要服务器）
- **管理员**：对成员、磁盘、隐私、费用有什么影响？（③⑤）

### 4. 分级决定写不写

| 级别 | 什么样的变化 | 处理 |
|---|---|---|
| **必写** | 不写会让用户做错操作、被卡住、找不到东西、数据或隐私受影响：升级与回退步骤、版本门槛、拿走或挪走的入口、默认值变化（尤其权限与隐私）、首次安装会遇到的拦截、已知缺陷 | 放提示框或对应章节，写成能照做的话 |
| **应写** | 用户会注意到，或不写会问「为什么」：新入口、使用前提、资源占用、破坏性操作、具体新增内容（列出型号、名称，不写「更新了目录」） | 单独一条，或并入相关亮点的末尾 |
| **可并** | 能感知但很小：按钮变大、样式统一、速度略快 | 并成一句，或「以及 N 处细节改进」 |
| **不写** | 内部实现、CI 与测试、周期内引入又修掉的问题、纯重构 | 在盘点表里写省略理由 |

### 5. 每一句都要有证据

写进说明的每个入口名、默认值、限制条件、版本要求、数量，都要能指到本版代码的具体位置
（界面文字以代码里的实际字符串为准）。涉及升级、回退、备份、数据的句子，不能凭「代码里有这个函数」
就写，要确认用户这次走的那条路径上真的会执行到。

行为取决于仓库外的东西（安装器模板、系统弹窗、第三方客户端），又没法在本机实际走一遍时：盘点表里标
「待真机复核」并写清推断依据，正文**一律**用「可能」措辞，发版 PR 里列出来；维护者在真机上确认后再把
措辞改成确定语气，没确认的保持「可能」。不写的话会让用户丢数据的防范性建议（如「卸载旧版时不要勾选
删除数据」），即使待复核也要写，用「建议」措辞。

几条边界：
- **模拟器里跑通不算真机复核**：后台下载、网络切换、锁屏这类系统行为仍按「可能」写。
- **第三方客户端**：服务器会拒绝是确定的，但客户端走不走那条接口不确定，整句用「可能」。
- **操作指引不需要「可能」**（「下载后覆盖安装」），但它的效果属于行为断言（「数据会保留」），照上面的规则判断。
  系统几乎必然出现的提示（未签名安装包触发 SmartScreen）可以写「通常会」。
- **给用户的应对办法与恢复步骤也要核实能用**：沿所有客户端的重试、重建逻辑走一遍（清掉服务端状态后，
  客户端可能自动重建，问题又回来）；写出副作用与波及谁（重启会打断所有人的播放）；入口从「设置」写全，
  页内控件（行尾 ⋯ 里的项）也写出名字。执行那一刻正在进行的任务会怎样、有没有时序竞态，都要想到；
  能二选一时优先结果确定的步骤（停服务 → 清理 → 启动），而不是界面上「先清空、再重启」的组合。
  还要写清不适用于谁：同样的报错，「没有数据的首次安装」可以
  删库重来，「已有数据的升级」照做就会丢数据，必须分开写。
- **界面示例文案**（如折叠行的总结文字）要在用户最常见的状态下核对：回复结束后、重新打开后，不只看进行中。
- **版本门槛让用户「先升级服务器」时**，要看门槛版本和用户实际会升到的最新版本是否需要换 Docker 镜像，
  需要就写上。
- **名单**（新增模型、新增站点之类）：盘点表附机械比对出的完整清单，正文数量要与之一致，略掉的写理由。

数字（体积、速度、比例）要有可复现的依据：只有代码注释里的一次实测时，要么不写数字，要么写成
「在我们的测试中约……」；不能写成普遍结论。

### 6. 盘点表（放在发版 PR 描述里）

| 来源（提交 / PR / 对比脚本条目） | 维度 | 用户可感知的变化 | 级别 | 对应条目或省略理由 | 证据（文件:行） |
|---|---|---|---|---|---|

对比脚本列出的每一条「消失的界面文字」都要在表里逐条交代；默认值与门槛变化可以按文件分组交代
（如「离线接口的 18 个字段默认值：只影响接口返回，用户不可见」），但改变用户默认体验的那几条要单列。
脚本是线索不是答案：它会漏掉不在字符串里的变化，也会把注释或无关代码列进来，判断以代码为准。

### 7. 取舍（保证好读）

挑 1～3 件本版最值得说的事当亮点，其余放进其他改进或修复，每条写清用户会看到什么变化。
不能用「更准」「优化体验」「以及若干修复」代替具体事实，也不能把未提到的用户可感知变化全交给
compare 链接。重构、CI、测试、文档这类用户感知不到的改动不写。代码层面的完整清单交给文末的
compare 链接——所有被调研的产品都是「精选叙事 + 完整清单另放」两层（HA 的 All changes、
Jellyfin / Infuse 链到完整 notes、Dia 另设 changelog 页）。

## 二、结构

照这个顺序，没有内容的节直接省略：

```markdown
## vX.Y.Z: Release theme

One or two sentences about what users gain, mentioning the other highlights.

> ⚠️ **Action required**: What to do, where to do it, and what happens otherwise.
> (When unnecessary: ✅ No Docker image update is required. Update from Settings → Update & Maintenance.)

### Highlights

#### A benefit or user question

The situation → what is possible now → where to start, or that it applies automatically.

### More features and improvements

- **Benefit**: One sentence, with the entry point when needed.

(Split Features and Improvements when their combined count exceeds four.)

### Fixed

- The recognizable problem that no longer occurs.

### Before you update

- Database migration and rollback (only when applicable), limitations and replacement entry points.

Thanks to @someone. Full changes: [vA.B.C → vX.Y.Z](https://github.com/movieclaw/MovieClaw/compare/vA.B.C...vX.Y.Z).

---

## 简体中文

## vX.Y.Z：本版主题

完整中文说明，保持与英文相同的事实、升级提示、功能范围和链接。
```

**客户端的提示框**：写这个 App 对服务器的要求，以及怎么拿到新版。
不需要动服务器时写 ✅：`> ✅ Works with MovieClaw Server 0.33.0 or later. Install from …`（中文
「✅ 搭配 MovieClaw 服务器 0.33.0 或更新版本即可使用。从 … 安装」）；需要新服务器时写 ⚠️，并说清
旧服务器上会怎样（功能隐藏还是登录被拒）。需要的服务器版本本身要求换镜像的，顺带一句「（这个服务器版本需要更新 Docker 镜像）」。

**渠道首发 / 全新首发**（见「客户端」的发版类型表）：主题段说清它是什么、给谁用、需要什么；亮点写它
能做的事（新用户第一次读到这个产品）；用 `Before you start` / 开始之前 交代系统要求、需要服务器、
首次安装会遇到的拦截、界面语言、登录方式、默认关闭需要手动打开的功能。渠道首发再加一节
`Moving from an earlier build` / 从旧版迁移：旧版会不会自动收到这一版（不会时提示框就要说「这一版
需要手动下载」并给出下载地址）、新旧版会不会并存、数据会不会保留、什么入口变了、旧版怎么处理。
不放对比链接。

客户端提示框的几种情况：
- App 能用、只是某个功能要新服务器：✅，在那个功能里写要求。
- **本版新加或提高了登录门槛**（哪怕已登录的人暂时不受影响）、或必须手动下载重装：⚠️。
- App 里没有强制的最低服务器版本：有实测就写「已验证可搭配的服务器版本」；没有实测但能用 diff 证明
  客户端没用到服务器新接口，写「对服务器的要求与上一版（X）相同」，并带上 X 对应的服务器版本
  （「与随服务器 0.37.0 发布的 1.0.4 相同」），新用户才知道自己够不够。不写「搭配你现有的服务器即可」。

**从旧版迁移**一节：开头一句「除以下几点外，功能与 X 相同」，让老用户分清新旧；多步操作按用户实际
的顺序写（退出旧版 → 安装 → 确认能用 → 处理旧版），第一步放进提示框；安装版、便携版等不同装法
分开交代。下载地址写完整网址，不写「本页附件」（同一份文字也会在应用内和官网展示）；发布页有多个相似附件
（安装版与便携版、带构建号的副本）时，每种装法点名确切的文件名。

**第一屏**（主题标题 + 主题段 + 提示框 + 第一个亮点标题）必须能单独成立：用户只看
这一屏，也知道这版最重要的变化和要不要动手。

## 三、写法规则

1. **一期只推 1～3 个主角**，其余降级成一行。（Linear 每期 1～2 个主题，Notion 一个
   主题，Infuse 博客 3～4 个亮点，Dia 每期一个故事）

2. **给这一版起个名字**：标题写成「版本号：主题短语」，让这版有记忆点。
   （Raycast「v2.5 - 🔌 External Model Providers」，HA「2026.9: There's room on this bus」，
   Notion「3.7: Agent skills for your whole team」）

3. **亮点段落三拍：痛点 → 现在 → 入口**，正文不超过 4 句。使用前提、默认值、限制、资源占用不塞进
   亮点正文：和这个亮点相关的放在段后一个短列表（**每条一个事实，最多 6 条**），管理员关心的放
   「管理员须知」，影响全局的放「升级须知」，超出 6 条的先合并同一主题的条目（如「转码版的条件与代价」），
   用户侧的限制（如「原盘不能下」）留在亮点列表里，管理员的事项再往后挪。只写用户能感知的结果，
   不写系统内部按什么顺序、用什么机制实现。
   - 先用一句话说用户以前遇到的处境（HA「What you couldn't see was why.」，
     Infuse「streaming the original file isn't ideal—especially when watching remotely」）。
   - 再说现在能做到什么，讲具体场景而不是讲机制。
   - 最后告诉用户从哪开始：菜单路径、按钮名（Linear「Type /callout to get started.」，
     Notion「Get started at Settings → …」，Infuse 专写「How to use transcoding」）。
     自动生效的就明说「升级后自动生效，不用设置」（HA「nothing changes and there is
     nothing you need to do」）——这句话本身就是在降低升级顾虑。
   - 入口路径要对照前端代码核实真实的菜单名，别凭印象写：设置分区名以
     `apps/web/lib/mock-data.ts` 为准；多套主题下路径不同时，按默认主题（银玻璃）写；
     顺带确认成员账号能不能看到这个入口，只有管理员能用的要注明「管理员」。

4. **标题讲好处或用户问题，不讲功能名**。
   ✅「在外面用 Infuse 看片，调低画质真的有用了」（HA「How full is your network storage?」，
   Things「Repeating To-Dos, Refined」，滴答「书写更简洁：……」）
   ❌「Jellyfin 客户端调低画质时真的会转码」
   例外：主角本身就是用户会在界面上看到的名字（如「Netflix 主题」），标题里要出现
   这个名字，否则用户对不上号——把它和好处写在一起即可（「一键换成 Netflix 的样子」）。

5. **修复写用户能认出来的症状，不写原因**：「在哪、做什么时、出了什么问题」，让遇到过的
   人一眼认出「就是我那个」。（Raycast「Fixed failing requests retrying in the background
   indefinitely during provider outages」，flomo「【修复】点击 Agent 推送返回对话时，
   页面反复跳转的问题。」）只单列用户大概率遇到过的，其余并成「以及 N 处细节修复」——N 要是真实数字，且这 N 处都在盘点表里；
禁止的是不带数字、没有出处的「若干修复」。
   ❌「修复若干问题」「优化产品体验」（微信、小红书的反例：什么都没说）
   中文避免「不再 A，之后 B」这种会读反的句式，写成「……时……的问题已修复」或「不会再出现……」。
   **放「修好了」还是「体验改进」**：用户会说「坏了」的（报错、打不开、显示不出、
   点了没反应）放「修好了」；原本能用、只是不够好的（慢、糊、不顺手）放「体验改进」。

6. **需要用户动手的事：越危险越靠前，每条都能照做**。写清要执行的命令或菜单路径、
   不做会怎样。（Jellyfin 大版本把升级须知放在最顶部的 TL;DR 编号清单，
   Immich 大版本前置 How to update 并给出命令，Telegram 写全菜单路径）
   需要更新 Docker 镜像 / Mac 转码器 / 某个 App 放开头提示框；不需要时也写一行 ✅，
   自托管用户最怕的就是「这次要不要动容器」。
   数据库迁移只在**有迁移时**写回退提示；没有迁移时不写，也不要替用户担保
   「回退不用恢复备份」——兼容性判断出错的代价由用户承担。

7. **各类变化的固定写法**（每句都要能照做或能对上号）：

   | 类型 | 写法 | 例 |
   |---|---|---|
   | 拿走、挪走、改名 | 「X 不再在 Y；现在到 Z」 | 「影片菜单不再有「清除观看记录」；到媒体库首页按库清除」 |
   | 默认值 | 「默认 X；要改到（入口）」 | 「所有成员默认可以下载；在成员设置里关闭「下载影片到设备」即可禁止」 |
   | 前提 | 「需要 X；否则 Y」，X 不是默认满足的再写在哪里打开（界面没有开关、只能靠弹窗开启的也照实写） | 「需要服务器能转码，否则只能下原画」 |
   | 资源与副作用 | 「会占用 X，在 Y 时自动清理」 | 「转码副本暂存在服务器缓存，下完或 72 小时后清理」 |
   | 升级要求 | 提示框：做什么、在哪做、不做会怎样 | 见第 6 条 |
   | 回退 | 能照着执行的步骤，写清用哪个版本、恢复哪份备份、备份从哪来 | 「先停容器并备份数据目录，再拉新镜像；回退时把镜像标签改回 `v0.37.0`，恢复这份备份后启动」 |
   | 已知问题 | 「已知：X 时会 Y；暂时可以 Z」，Z 要核实过真的管用 | 和某个功能有关的跟在那个功能的列表末尾；影响全局的放「升级须知」 |

   英文段入口名的写法见「多语言维护」：只在最后要点的控件后附一次中文原名，如 Me → **Downloads (下载)**。

8. **坦白边界**：已知限制、还没做完的、要下线的，一句话说清。只和某个亮点有关的，
   放在那个亮点段末尾（读者正读到这里）；影响全局的放「升级须知」。坦白反而增加信任。（Cursor「Rollouts does not merge or roll back on its
   own today.」，Infuse 的段末 Note，Dia「Retiring Memory」，Raycast「While there are no
   major new features…」）

9. **纯修复版不硬凑亮点**：主题直说「这是一个稳定性更新」，列 3～5 条用户能感知的修复
   即可，省掉「本版亮点」节。（Raycast v2.4、Bear 3.0 都坦白说明本版没有大功能）

10. **致谢外部贡献者**：区间内有核心维护者以外的人合入 PR，就在文末点名
   「感谢 @xxx 的贡献」。**以 GitHub 上 PR 的作者为准**；`git log --format='%an <%ae>'`
   只用来找线索（`…@users.noreply.github.com` 前的名字通常就是用户名，但用真实邮箱
   提交的外部贡献者会漏掉），拿不到 PR 信息时宁可只写能确认的人。开源项目靠这个留住贡献者。
   （HA 每条带「Thanks, @xxx!」，Immich 列 New Contributors，Dia「Shipped by Alexandra」）

11. **同一个概念全文一个叫法**，并与界面一致（界面叫「思维链」就不写「思考档位」）。

12. **一句话只讲一件事**：避免一句里挂三层括号和两个「并且」；长句拆开。读者是在手机小屏或应用内
    256px 的滚动框里读这段文字的。

13. **语气**：用「我们 / 你」，平实、具体。人格化点到为止——主题标题、一句结语可以有
    温度，正文保持朴素。（Obsidian 把修复节叫「No longer broken」，本项目对应「修好了」；
    Bear、flomo 都只用一句话建立个性）

## 四、不写什么

- **实现细节**：库名与版本号、runtime 编号、协议 / 容器 / 编码参数（MPEG-TS、AAC、
  `hvc1` 标签之类）、文件路径、配置项内部名、原始测量值。HEVC、4K、HDR、MKV 这类用户在
  文件名里天天见的词可以用；用户要下载的安装包文件名可以写；性能改善可以用取整后的对比
  （「约为原来的十分之一」）说明省了多少。
- **故障原因分析与修复过程**：用户只关心现在好了没有。
- **空话和样板话**：「修复若干问题」「优化体验」「感谢您的使用，求五星好评」
  （滴答清单每版一字不差的致谢段占了全文一半）。
- **重复上一版的内容**。

## 五、篇幅与自检

- **每种语言各自**以 50 行左右为目标（含空行），渠道首发和全新首发可到 70 行；不为凑行数删除必写和应写的变化，
  先把可并的合并、把亮点正文压到 4 句以内。
  条目较多时在现有改进与修复章节里按产品或场景分组；亮点之外每条尽量一句话，
  不把几个独立变化塞进一条。第一屏仍保持简短。
- **发版前独立核对**：写说明的人不自己核对。每个产品另起一个子代理，给它上一版 tag、本版代码、这份
  指南、写好的说明和盘点表，让它按第一节的八个维度对照代码找「遗漏 / 写错 / 夸大 / 不该写 / 中英不一致 /
  入口名不对 / 可读性」，并且**专门检查**：
  - 每个「现在到 Z」的替代入口（新旧两版、从原页面可达、其他端）；
  - 每条「修好了」在上一版的证据（依赖服务器时序的，要同时看上一版服务器的行为）；
  - 每个数字、名单、版本区间的依据；
  - 重构过的页面逐屏对比；离线与权限不足时逐个点常驻元素；
  - 后台任务与取消；新请求字段的空值语义；
  - 每个「可能」与确定语气是否用对，每个应对办法是否真的管用。
  有问题就改；核对中发现的代码缺陷要么修好，要么写进已知问题，不带着不知情发出去。
  **已知问题是最后的退路，不是常规出口**：一个产品要写的已知缺陷超过 3 条，或者应对办法需要用户
  停容器、删目录、重启服务，先停下来修代码再发版——说明写得再准，也比不上用户根本碰不到。
  同一个缺陷出现在几份说明里（如服务器说明和 iPhone 说明都写到取消下载），应对办法要一字不差地一致；
  核对时把同期各产品的说明放在一起交叉比对。
  「管理员须知」「升级须知」也遵守每条一个事实，各自以 8 条为上限；超过时合并同类项或按「权限 /
  资源占用 / 已知问题」分组。共用同一个应对办法的已知问题合成一条，应对步骤只写一次。核对结论与
  「待真机复核」清单写进发版 PR 描述。
- 写完逐项回查盘点表：每项用户可感知变化是否有具体条目，两种语言是否覆盖同一组事实？
  识别优化要说明修正的边界或漏识别场景，性能优化要说明哪个操作更省时或省资源，
  不把局部样本结果写成全库准确率，也不把实验或未完成验收的能力写成已发布。
- 写完只读第一屏：能不能让人想更新？知不知道要不要动手？
- 念给一个不写代码的朋友听：有没有哪句需要解释？每个亮点他知不知道去哪儿试？

样板见 `docs/changelog/v0.27.0.md`。
