# 订阅窗口：一季上千集时先订阅一部分

## 问题

一季可以有上千集（名侦探柯南在 TMDB 里一季 1186 集，国产漫剧、日更剧、长寿动画动辄上百上千集）。
订阅创建就把整季展开成上千个工单：

- 磁盘、入库后处理（ffprobe、刮削、缩略图）一次性吃下上千集，用户未必看得完；
- 详情页的分集履历、工单对账都按上千行算；
- 想"先看一部分"，现在没有任何办法表达——`selected_seasons` 的粒度是整季，`episode_floors`
  只能往上补集数、不能往下收。

## 决策

### 1. 窗口是 E 定义的一部分，不是模式，也不是状态

`subscription.episode_caps`：`{季号: {start, end}}`，用户选择「这一季先订阅哪一段」。
期望集合 E 里这一季窗口外的集**一律不在其中**，清除窗口才恢复：

```
E = (勾选季的全部已知集 ∪ 追新 ∪ 占位集) ∩ { start ≤ 集号 ≤ end（end=None 不设上界） }
```

两种窗口，按这一季**在不在播**选（评审定方向：追在播长剧的用户最想要的是最新的几集，
"从第 1 集订起 + 与追新互斥"的默认方向正好反了）：

- **完结的超长季**：`{start: 1, end: N}`——从第 1 集订起，「继续订阅」把 end 往后加；
- **在播的超长季**：`{start: 已播-N+1, end: None}`——订最新的 N 集，**end 不设上界，
  之后播出的集照常进来，上限与追新不再互斥**；想补老集用「往前再订」（start 往前挪）。

- 沿用「引擎里没有模式分支，选项只是 E 的初始化参数」的立场（subscription.md §2.1），
  `expected_units` 多一个参数，创建 / 调整 / 元数据刷新 / 洗版四个调用点一并传入；
- 存**窗口**而不是个数：幂等，库里已有若干集时语义也不歧义；在播季的窗口不随新集
  播出滑动，界面上再说「先订阅最新 20 集」；
- 「在播」的判定：剧还在播（TMDB status 为 Returning Series）且这一季是最近一个开播的季
  （有已播集）。判定只在网页弹层做（文案与默认值），服务端只认窗口本身；
- 两头都收的混合窗口（start>1 且 end 设值）不接受——弹层表达不了，也不给它留歧义；
- 与 `episode_floors` 方向相反，别混：下限纠正「这季其实有 27 集」（事实），窗口是
  「我先订阅这一段」（节奏）。两个「集数」不进同一个弹窗——下限在「更多 → 调整集数」，
  窗口在「调整订阅」；
- **只存确实截断了本季的窗口**：盖住整季（start=1 且 end 不低于总集数或 end=None）的值
  视为不设，服务端丢弃。窗口不存在就是今天的整季行为，存量订阅零影响；
- 旧值兼容：窗口上线前的落库形态是纯集号 `{季号: 集号}`（只订到第 N 集），读取时
  视作 `{start: 1, end: N}`。PR 未合并前没有线上数据，这条只为防御手改的 JSON。

### 2. 状态：被截断的季不算「已收齐」

`completed ⟺ 无未满足工单 ∧ E 不再生长`（不变量④，派生值）。被截断的季本来就不是收齐，
`recompute_subscription_status` 在 `growing`、`hinted` 之外多一个 `truncated`：订阅留在
订阅中，等用户决定要不要继续。不新增任何存储状态，「还有没订到的集」是从
`episode_caps` 与 TMDB 集数现算的（`windows_of`）。

### 3. 继续 / 往前订 / 清除：沿用 update 的 diff

- 窗口往宽调（继续订阅 / 往前再订）：新入域且从未见过的单元补工单，立即发车搜索；
- 往窄调：超出的集只切 `in_scope`，已下载、已入库的内容一律保留，下载器里的任务不动
  （与减季同口径）；
- 清除（「全部」）：回到整季，已有工单复用，不重复建行。

整体替换语义同 `episode_floors`：传 `{}` 清除，不传不变。

## 入口

遵循「最少配置、最少交互」：订阅仍是一次点击，窗口不是必填项。

| 触点 | 做什么 |
|---|---|
| 季选择行（订阅弹层、调整订阅共用） | **只在单季集数 ≥ 100 时出现**，勾选了才有；完结季一行「先订阅前 [20] 集 · 本季共 1,043 集　全部」，在播季一行「先订阅最新 [20] 集 · 本季已播 1,100 集　全部」。预填默认值、一步改回「全部」。存量订阅打开调整弹层时草稿取订阅现在的窗口，不会被默认值悄悄改成「先订阅一批」 |
| 订阅详情页 | 控制台横幅：完结季「已订阅到第 20 集（本季共 1,043 集）[继续订阅 20 集] [订阅全部]」；在播季「已订阅最新 20 集（从第 1,081 集起，之后播出的新集会自动纳入）[往前再订 20 集] [订阅全部]」。每次一步，剩下不足一批就一次订完。「收录范围」写成「第 1 季（前 20 集）」/「第 1 季（最新 20 集）」 |
| 订阅墙 / 媒体页状态行 | 只显示状态，不放操作：留在订阅中，完结季「已订阅到第 20 集 · 可继续」，在播季「已订阅最新 20 集 · 可以往前补」；首页的缺集统计只算窗口之内的集 |

阈值（`EPISODE_CAP_THRESHOLD = 100`）与默认批量（`EPISODE_CAP_BATCH = 20`）是
`lib/subscription-episode-cap.ts` 里的两个常量。下完一批的那一刻不推送——下完不等于看完，
那时问「要继续吗」是噪音；也不新增全局设置，批量记在订阅上（沿用 20）。

文案不用「追」字：「先订阅」「继续订阅」「往前再订」「订阅全部」。

### 起始集：老剧中途上车（issue #950）

「勾了一季不等于整季都要，从第 N 集开始追」不新增字段：`{start: N, end: null}` 就是这个意思，
服务端本来就接受，E、完成判定、洗版自动跟随。补的只是入口与读法：

- **读法按在不在播分**：不设上界的窗口，在播季读作「最新 N 集」（之后播出的照常进来），完结季
  读作「从第 N 集起」——完结季没有新集可等，说「最新」「之后播出的新集」会误导。服务端在
  `episode_windows` 每一项上标 `airing`（剧为 Returning Series 且是最近开播的季，与弹层同口径），
  详情页、收录范围、订阅墙状态行都按它选文案；旧服务端不标时沿用旧读法；
- **完结季的窗口行多一个切换**：「前 N 集 ｜ 从第 N 集起」，切换沿用输入框里的数（前 20 集 ⇄
  从第 20 集起）；选「从第 N 集起」时行下写明「订阅第 120–200 集；前 119 集不会搜索，也不会下载」。
  在播季仍只有「最新 N 集」；
- **调整订阅不看阈值**：每一季（特别季与只有一集的季除外）都能「先订阅一部分」，二十几集的季
  中途上车也用得上；创建订阅的弹层仍只对超长季出现，不给多季剧每季多出一行。草稿里有值就以
  草稿为准、不论季长短，经接口给短季设过的窗口打开调整弹层再保存也原样保留；
- **iPhone / Android 只读**：订阅详情说明「第 1 季从第 120 集起订阅，之前的集不会搜索也不会下载」，
  编辑留在网页。

## 整包

一季上千集的资源常常就是一个整季包。整包是原子种子，窗口只能靠下载器里的**文件选择**落实
（`file_selection`）。两个原有假设在窗口下不再成立，这里补上：

### 严格取舍：不确定也不回落全量

规则模式规划文件取舍失败时原本**回落全量下载**（多下几个 GB 只是浪费）。上千集的整包下，
这个兜底就是灾难。带窗口的规则订阅走严格路径（`torrent_submit` 的 `strict_selection`）：
规划不出结论、写入失败都不恢复下载，抛错让投递退回队列，刚加进来的暂停任务一并移除
（`delete_files=False`，落点上可能预先存在的文件不碰）。智能订阅本来就是严格路径。
已存在的任务照旧不碰。

### 继续订阅：把新单元并进已有的整包

窗口往宽调后下一批搜到的往往还是同一个包。原来对同一 infohash 只合并台账、不碰下载器里的
文件选中集合（已存在的任务可能是用户自己的），新认领的集因此永远下不到：规则模式下工单挂在
GRABBED，智能模式下候选被「与本订阅已有下载记录相同」拒掉。

`pack_extension.extend_owned_pack` 在投递前识别「这个候选就是本订阅自己投递、还在下载器里的包」
（按站点 + 种子 ID 认，所有权只认我们自己的台账 `owned_by_movieclaw`，用户自己的任务照旧
不碰）：选中集合 = 此前认领的单元 ∪ 本次新单元，只增不减，回读校验后恢复下载，返回与
`_submit_real` 同形的结果，台账继续走投递层原有的合并路径。智能订阅下一批的意图并进原来
的尝试后即删除，不残留「提交中」的意图；文件清单对不上抛 `ExtensionRefused`（继承
`SubmissionRejected`），工单回到等待，不会被恢复任务无限重放。「往前再订」补的是同一包里
更早的文件，走的是同一条并入路径。

## 不做

- **跟随观看进度**（始终领先进度 N 集，类似 Netflix 智能下载）：字段不变、写入者从「用户」
  变成「系统」，是更优雅的第二阶段。现在不做，因为订阅全家共享，而观看进度按成员记，
  该跟谁的进度没有明确答案；
- **两头都收的窗口**：机制上服务端只拒不留，真有「从第 X 集到第 Y 集」的需求再说；
- **改条目元数据 / 自动扩缩**：窗口只挂在订阅上，只影响这一个订阅；
- **推送**：见上；
- **原生客户端编辑**：iOS / Android 只读展示完结季的起始集说明（issue #950），设窗口在网页。

## 已知限制

- 窗口按 TMDB 集号算。「汇总在一季」正是 TMDB 与站点季集编号最容易错位的地方：站点若按自己的季
  或绝对集号命名，窗口再合适也匹配不到资源——这是已有的识别问题，与窗口无关；
- 并入已有整包要求任务还在下载器里；已被移除时走原来的投递路径（规则模式重新加种，智能模式仍按
  「与已有下载记录相同」处理）；
- 在播季「最新 N 集」锚定**订阅时刻的已播集数**：之后新集照常进来（不滑动），窗口起点不变；
  想要的从来不是「永远只要最新的 20 集」，那是跟随观看进度的事。
