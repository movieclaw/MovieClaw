# iPhone 离线下载

把影片下到手机上：连不上家里服务器时（飞机、出差）照样能浏览已下载的内容、能播放；回来后，观看进度与观看统计按真实发生的时间补回服务器。

交互定稿（2026-10-13 用户确认）：
- 不单做下载管理页，复用媒体库的展示。离线时媒体库只显示下过的片子，详情页只读。
- 在线时已下载的片子标出来，并优先播本机。
- 下载可选码率。

相关：`member-permissions-v2.md`（下载权限）、`playback-qoe.md`（先落盘再上报的先例）、`image-sizing.md`、`persistent-jobs.md`。

## 0. 总原则

1. **本机副本自包含**：视频、字幕、字体、展示数据、图片放在同一个文件夹里，离开服务器也能完整展示和播放。文件夹本身就是事实来源，删掉文件夹就删干净了。
2. **页面不知道离线**：媒体库的几处读请求收口到一个取数层。在线时走接口，并顺手刷新本机副本；离线或请求失败时读本机。
3. **离线只是界面模式，不影响播放**：本机副本在线时也优先播。网络判断只决定媒体库显示什么。进入离线要强证据，恢复连接立刻退出。
4. **先落盘再发送，服务端按编号幂等合并**：下载状态、观看记录都这样处理，与 `PlaybackReportQueue` 同一做法。
5. **期望状态 + 对账**：要下什么记在本机；后台下载会话里实际有哪些任务，由对账补齐。崩溃、被杀、断网之后都能自愈。

## 2. 网络判断

### 2.1 两层分开

- **可达性**（事实估计）：分「可达 / 存疑 / 不可达」三档，只回答一件事：现在能不能和我家服务器说上话。
- **模式**（界面）：分「在线 / 离线」，由可达性加上切换规则决定。

播放不看模式。

### 2.2 证据

**旁听**：所有页面请求都经过 `APIClient.performReturningHeaders`（APIClient.swift:342）。在这里，在把错误映射成 `APIError` 之前，把原始结果交给可达性，不发额外请求。以下请求不计：
- 不是发往当前服务器的；
- 主动取消的；
- SSE、图片、视频字节；
- 回前台之前就发出、之后才失败的。App 挂起时系统会掐断连接，回前台后报 -1005，这不说明网络坏了。

**探测**：`GET /api/v1/health`，5 秒超时（几百字节，网慢也够）。只在两种时候发，网络健康时一个都不发：
- 存疑或不可达时（见 §2.3）；
- 冷启动、或后台超过 10 分钟回前台后，**3 秒内页面请求一个都没成功**时探一次。黑洞（只超时）时页面请求要 60 秒才报失败，不探的话要等一分多钟才有第一份证据。

探测请求也走同一个出口，结果经旁听回来，判定只有一条证据通道。

**网络通路**：复用 `NetworkCost` 已有的 `NWPathMonitor`（PlaybackRouting.swift:302），让它多发布一个 `path.status`。不另起监视器。

**怎么确认「是我家服务器回的」**：响应要带 `X-Movieclaw-Spec-Hash` 头。所有 `/api/v1` 响应都带这个头，由中间件加上（middleware.py:76）。下面这些都过不了这一关：酒店或机场的门户页、反向代理的 502 页、外地局域网里恰好同 IP 的别的设备。实例号（`health.instance_id`，§9）用来认本机副本归哪台服务器。

| 结果 | 归类 |
|---|---|
| 收到带标记头的响应（任何状态码，含 401、500） | 成功 |
| 通路 `unsatisfied`（飞行模式、没有 Wi-Fi 也没有蜂窝） | 断网，确定 |
| 连接被拒或主机不可达（-1004） | 硬失败 |
| TLS 或证书错误（-12xx，门户劫持） | 硬失败 |
| 不带标记头的响应 | 硬失败 |
| 本 App 的蜂窝被禁、漫游关闭（-1020、-1018） | 硬失败 |
| 超时（-1001）、连接中断（-1005）、DNS 失败（-1003、-1006）、其他错误 | 软失败 |

DNS 失败算软失败，因为信号差的蜂窝网上 DNS 也会超时。

### 2.3 判定规则

- 任何一次成功 → **可达**，清零全部计数。
- 通路 `unsatisfied` → 立即**不可达**。
- 可达时出现一次失败 → **存疑**，开始探测：立即一次，之后每次探完隔 2 秒再探。
- 从存疑转为**不可达**，满足下面任一条即可：
  - 连续硬失败至少两次、从第一次起 ≥ 3 秒，中间没有成功（夹一次软失败就重新数）；
  - 连续失败至少三次（软失败也算），**从第一个失败请求发出起** ≥ 30 秒，中间没有成功——也就是服务器已经 30 秒没回过任何话。
- 判定规则是纯逻辑（`ReachabilityJudge`），单元测试按时刻喂事件。
- 不可达时继续探测：
  - 通路变化、回前台、用户点「重新连接」时立即探；
  - 在前台时按 30 秒 → 60 秒 → 2 分钟 → 5 分钟退避，5 分钟封顶；
  - 在后台不探。

### 2.4 模式切换：进难出易

**自动进入离线**，只有两种情况：
1. 通路 `unsatisfied`：用户开了飞行模式，意图明确。
2. 判定不可达发生在冷启动后 60 秒内，或后台超过 10 分钟回前台后的 60 秒内。这时用户还没在看服务器上的内容。

**使用途中断网，不自动切**。媒体库首页原有的「与后端通信失败」提示条（LibraryHomeView.swift:187）上加一个按钮「看 iPhone 上的 N 部」，用户点了才切。

**恢复连接后自动回在线**：任何一次成功就回，并给一个轻提示「已连上服务器」。已推入的详情页不动，因为有本机副本的条目在两种模式下都能显示。

本机一部都没下过时，永远不进离线模式，维持现状（首页快照 + 提示条）。

离线模式由已登录会话的本地缓存撑着：冷启动有缓存会话时直接进主界面（AppModel.swift:132）。「连不上服务器」整屏卡片只在没有缓存会话时出现，那种情况本机也不会有该账号的副本，所以那张卡片不加入口。

### 2.5 为什么网慢不会误切

1. 慢请求只要最终回来了就算成功，立即清零。网慢时总有请求陆续成功。
2. 单次超时只会进入「存疑」，界面不变。
3. 只有超时这类失败时，要连续三次失败、且服务器已经 30 秒没回过任何话，才判不可达。每次探测只需在 5 秒内传回几百字节，30 秒里一次都做不到就不是慢，而是断了。
4. 就算判了不可达，使用途中也不自动切，只给一个按钮。
5. 切错的代价也小：任何一次成功立即切回，播放完全不受影响。

## 3. 本机存储

### 3.1 选型

用「每个条目一个文件夹 + JSON」，不用 Core Data、SwiftData 或 SQLite。理由：
- 条目只有几十到几百个，唯一的查询是「列出本账号的全部」。
- 展示数据就是接口模型原样存下，不需要任何映射代码。
- 文件夹即事实来源，不存在「索引说有、文件没了」的不一致。

这和 `PageSnapshots` 是同一套路。

### 3.2 目录

```
Application Support/Offline/<sha(实例号|用户名)>/
  owner.json                服务器地址、实例号、用户名（存储页显示「其他账号」用）
  items/<media_item_id>/
    summary.json            建索引用的小文件（自有结构）：类型、片名、年份、海报键、所属库、各单元摘要、总大小、最近下载时间
    detail.json             LibraryItemDetailView 原样
    library.json            LibraryView 原样
    seasons/<季号>.json     SeasonEpisodesView 原样，只存有下载的季
    progress.json           本机续播点（自有结构）：每个单元 {position_ms, played, updated_at}
    images/<键>.<扩展名>
    units/<file_id>/
      unit.json             单元状态机（§5.4）
      media.<扩展名>
      subs/  fonts/
      playback.json         时长、片头片尾段、章节、音轨与字幕清单、下载时的默认音轨和字幕
  viewings/<viewing_id>.json  待同步的观看记录（§7）；删除条目时不删它们
```

- **账号键**用「服务器实例号 + 用户名」，不用服务器地址。这样同一台服务器换了地址（局域网 IP 和域名之间切换），副本也不会丢。
- **单元**以服务器的 `file_id` 为键。一集有多个版本时只下其中一个；洗版后服务器换了文件，本机的旧副本照样能播。
- **图片键**是图片地址去掉服务器前缀和宽度参数（`w`、变体）后的部分，保留 `v`。TMDB 绝对地址还要去掉尺寸段。

### 3.3 写入与读取

- **单写者**：所有改动都经同一个 actor `OfflineStore`，包括下载回调、删除、元数据刷新和进度写入，因此没有并发写竞争。界面读它发布的只读快照。
- **一律原子写**：先写临时文件，再重命名。
- **视频落盘顺序**：在下载回调里同步把文件 `move` 进单元目录（同一卷上只是改名，O(1)），然后原子写 `unit.json`，标为完成。如果在这两步之间崩溃，启动对账会发现文件在、大小对、状态没标，然后补标。
- **启动建索引**：在后台线程扫一遍 `items/*/summary.json`，在内存里建索引。`detail.json` 等打开详情页时才读。
- **文件保护**：用系统默认等级（首次解锁后可读写），这样锁屏时后台下载也能写入。不要设成 `complete`。
- **不进备份**：整个 `Offline/` 目录排除 iCloud 备份。
- **格式版本**：自有结构（summary、unit、playback、progress、viewing）都带 `format` 版本号。遇到不认识的版本就跳过该条目，不崩溃。

**接口模型存档的兼容**：生成器会把带默认值的字段生成为必有字段，所以模型一旦新增字段，旧的 `detail.json` 就会解码失败。对策有两条：
1. App 升级后第一次在线时，在后台按顺序重拉全部副本的展示数据。
2. 离线时如果解码失败，退回只靠 `summary.json` 的极简详情：海报、片名、各单元的播放和删除。

## 4. 取数层

页面里这四处读请求改为经过 `LibraryReads`：`libraryItemsGet`、`libraryGet`、`libraryItemsListEpisodes`、`playbackResume`。

| 情况 | 行为 |
|---|---|
| 离线模式 | 只读本机；没有副本的条目返回「离线不可用」 |
| 在线，有本机副本 | 先用本机数据秒开，再静默拉服务器并写回本机（同首页快照的做法）。拉取失败就停在本机数据上 |
| 在线，有副本，服务器返回 404 | 显示本机版本，注明「服务器上已删除」，仍可播放、删除 |
| 在线，没有副本 | 照旧走接口 |

读本机数据时统一做两个变换（在线请求失败回落本机时也一样）：
- **详情**：`files` 只保留本机有的，`seasons` 只保留有下载的季。
- **分集**：`owned` 改为「本机有没有」，这样没下载的集自然沿用现有的缺集置灰；`positionMs` 和 `played` 取本机进度与存档中较新的一份。

**离线首页和离线海报墙**是新写的薄视图：
- 直接用 `LibraryPosterCell`、`LibraryPosterGrid`。
- 首页的海报行、「接着看」卡片改为非私有，以便复用。
- 不复用 `LibraryHomeStore`，因为它的偏好、指纹、轮询都是为服务器准备的。

**图片**：`AuthorizedDataLoader`（RemoteImage.swift:277）先按图片键查本机。离线模式直接用本机文件，不发请求；在线时只有请求失败才回落本机。

## 5. 下载

### 5.1 档位

| 档位 | 来源 | 两小时电影约 |
|---|---|---|
| 原画 | 原文件字节 | 原文件大小 |
| 1080p | 服务端转码导出：Mac 转码器出 HEVC 4 Mbps（其余 H.264 6 Mbps）+ AAC | 约 2.7 GB（H.264 4.0 GB） |
| 720p | 同上，HEVC 2 Mbps / H.264 3 Mbps | 约 1.5 GB（H.264 2.1 GB） |
| 480p | 同上，HEVC 1 Mbps / H.264 1.5 Mbps | 约 0.9 GB（H.264 1.2 GB） |

（表里的码率是上限，硬件编码实际平均约七成；「两小时电影约」按实际平均算。清单里的预计大小按上限算，
手机据此留空间不会不够。）

**档位怎么来**：
- 码率沿用实时转码的阶梯（ffmpeg_args.py `BITRATE_LADDER`），上限 1080p（`MAX_TRANSCODE_HEIGHT`）。
- **执行者是 VideoToolbox（Mac 转码器）时出 HEVC**，码率阶梯是 H.264 的约 2/3（`HEVC_BITRATE_LADDER`）。
  真片实测（同一无损中间片，VMAF）：1080p 档 HEVC 平均 2.7～3.0 Mbps，与 H.264 平均 4.0～4.4 Mbps
  分数差在 ±0.5 内（4K HDR 颗粒片 −0.5、1080p 片 +0.3）；720p 差 −0.4～−1.3。同画质小三分之一，
  在外面下载（受 NAS 上行限制）快一半，手机全系硬解 HEVC。VideoToolbox 的恒定质量（`-q:v`）
  实测不生效（不同 q 输出逐字节一样大），所以仍用码率上限。NAS 软件与其它显卡继续出 H.264
  （libx265 在 NAS 的 CPU 上太慢）。播放的转码一律 H.264 不变。
- 服务端在清单里给出这个文件**可用**的档位和预计大小，客户端照着列出来。以后加档位（例如 HEVC）不用发 App。

**轨道**：
- 转码档只带一条音轨。默认取服务端按偏好选的那条，下载 sheet 里可以改。
- 文本字幕全部作为单独文件下载，ASS 连同字体一起。
- 图形字幕（PGS）：原画档随文件自带，转码档一期不带。

**什么时候没有可选档位**：
- HDR 片在没有硬件转码（本机显卡、在线的 Mac 转码器都没有）的服务器上没有转码档（`plan_capped_transcode` 会拒绝）。
- 原盘（BDMV 目录、ISO）一期整个不能下载，按钮置灰并写明原因。

**strm 原画**：一期一律由服务端中继（`RemoteRelayResponse`），不 302 到云盘直链——后台下载会话跟跳转时会把我们的设备令牌带给网盘。代价是云盘的字节要过一遍 NAS；以后要省 NAS 流量，再加「先解析直链、客户端不带令牌直连」这一步。

**下载 sheet**：列出可用档位、各档预计大小和本机剩余空间；记住上次的选择作为默认。

### 5.2 服务端接口

新增 `offline` 路由，放在成员区，用 Bearer 设备令牌鉴权，校验 `allow_video_download` 和库访问权限，命令行不可见。

| 接口 | 作用 |
|---|---|
| `GET /offline/manifest?file_id=` | 一次给齐打包所需的一切：`item`（LibraryItemDetailView）、`library`、`season`（SeasonEpisodesView）、单元信息、`playback`（时长、片段、章节、音轨与字幕清单、默认轨）、要下载的字幕/字体/图片地址、可用档位与预计大小 |
| `POST /offline/profiles` | 选档面板用：一批文件（≤500）各自的可选档位与预计大小、季集与容器，不带展示与播放数据。面板打开时把所有范围的文件一次问完，切范围不再请求；点「下载」才取第一集的完整清单（存条目展示数据），其余集先建「准备中」单元、由下载器逐集取清单。旧服务器没有这个接口（404）时退回逐集取清单。真机实测逐集取 43 份清单（每份约 97 KB，服务端串行约 0.3 秒一份）要十几秒 |
| `GET /offline/files/{file_id}/content` | 原画字节，用 `DisconnectAwareFileResponse`，Range、ETag、If-Range 都是现成的（movieclaw_playback/streaming.py:174）。同时登记到活动页「正在下载」，复用 Jellyfin 下载的登记方式（movieclaw_jellyfin/routes/playback.py:796 那段，抽成共用函数） |
| `POST /offline/exports` | 参数 `{file_id, profile, audio_track?}`；新建或复用一个导出，返回 `export_id`、状态、ETag、预计大小 |
| `GET /offline/exports/{id}/content` | 导出文件（§5.3） |
| `DELETE /offline/exports/{id}` | 客户端下完后通知服务端可以回收（尽力而为，服务端另有过期机制） |
| `POST /playback/viewings` | 观看记录批量补传（§7） |

**为什么另做清单接口**，而不让客户端拼现有接口：片段和章节目前只出现在 `POST /playback/sessions` 的响应里，为了拿它们去建一个播放会话是不对的。单独的清单接口让打包内容成为稳定的契约，服务端内部复用现有的视图构造函数。

**新接口要同步的地方**：
- 成员接口白名单（`tests/api/test_member_auth.py`）；
- Swift 与 Android TV 两个生成器；
- 新字段一律可空，因为旧服务器没有。

### 5.3 导出：边转边下

关键场景：睡前点下载一整季，锁屏放着，第二天上飞机。如果先转完再下，转完时 App 多半在后台，没法可靠地发起下载。所以**下载请求本身就挂在导出上**。

**转码走播放的会话层**：导出就是一个「只下载、不看」的 VOD 播放会话（`TranscodeSession.export_id`），
按顺序要分片（`ensure_segment`），拿到一段就把它接到导出文件后面（第一次先接 `init.mp4`）。于是：

- 谁来转与播放同一个函数（`select_execution_backend`）：本机硬件 → 在线的 Mac 转码器 → 软件。NAS 没有
  显卡时整片交给转码器，派单、取源续读、产物回传重试、补片重启、看门狗全部沿用远程转码的那一套。
- 分片的时间戳是文件绝对时间（VOD 的 `-copyts`），同一编码器从任意分片重启转出来的 `init.mp4` 逐字节相同
  （实测），所以会话中途没了（被播放挤掉、转码器掉线、服务重启）就开一个新会话**从下一个缺的分片**接着转，
  拼出来的文件完整解码、帧数一帧不差；接缝处音频最多重叠一个 AAC 帧（实测 7 毫秒）。
- 换了编码器（转码器换成本机、换了一台不同的 Mac），新 `init.mp4` 对不上：整份换代号从头转，并且不再认领
  转码缓存（避免两种编码器的分片混在一起）。
- 分片落在转码缓存里：之后有人在线看同一规格直接命中；反过来同规格已经被看过的片，导出几乎不用转。
- 等硬件：转码器在线但名额被播放占满、或建导出之后转码器掉线时，导出排队等它（内容接口回 503），不退到 NAS
  软转（慢一个数量级），HDR 更不退（同播放的底线）。

**播放优先**：导出占着的名额对播放算空闲（`RemoteWorkerRegistry` 的 `preemptible`、本机名额同理）。播放要
派任务而只剩导出占着的名额时，会话层先停掉那个导出会话（`_evict_export_for_remote` / `_evict_export_for_local`，
标 `preempted`，不算失败），名额空出来后导出从断点接着转。网页播放器与 Jellyfin 协议（Infuse）都经过会话层，
一处实现。外置转码器上的导出不占本机转码名额，也不算「有人在看」（跳片头等后台作业照常跑）；在本机转的导出
降优先级（`nice`）。

**导出作业**（`services/offline/exports.py`）：
- 进程内单路队列干活，状态落在每个导出自己的目录（`<导出号>/meta.json`）；服务重启后没转完的重新排队、换代号从头转。与片段预切同一路数，没有套 jobs 框架：边转边下要直接读产物和状态，作业框架的派发、租约、重试在这里都用不上（实现时的取舍）。
- **导出号**是五项的指纹：文件、文件的 mtime 和大小、档位、音轨、导出格式版本。全家下载同一集同一档时只转一次；洗版换了文件指纹跟着变。
- 产物是 `cache/offline-exports/<导出号>/<代号>.mp4`（init + 按序接上的分片），缓存管理里登记为「离线下载转码」（可清空）。
- 转码计划用 Jellyfin 协议「播放器要求限码率」同一个 `plan_capped_transcode`（视频见 §5.1、立体声 AAC）。
- 清单只列**比原文件明显小**的档位（预计大小 < 原文件 90%）：源本身码率就低时，转出来不比原画小，不提供（端到端时发现 6 分钟 118 MB 的测试片，720p 预计反而 149 MB）。

**内容接口按导出状态响应**：

| 状态 | 响应 |
|---|---|
| 已完成 | 静态文件：带 Content-Length 和 ETag，支持 Range 与 If-Range，可以续传 |
| 进行中 | 200 分块传输，从头开始发，跟着文件增长往后发。只有 ffmpeg 成功退出且全部发完才正常结束；失败就掐断连接，客户端一定会报错，不会把半个文件当成完成 |
| 排队中 | 503 + `Retry-After` |
| 失败 | 422 + 原因码 |

**ETag 与代号**：
- ETag 用「导出号 + 代号」，导出进行中和完成后保持一致。
- 缓存被清、服务重启后重跑，都会换一个新代号。客户端带旧 ETag 来续传时 If-Range 不匹配，服务端返回整份 200，客户端从头下，不会拼出坏文件。

**并发**：
- 全局一次只跑一路导出。
- 只在有空名额时开始，播放来了让路（见上「播放优先」）。原则：宁可导出慢，也不让播放被拒。
- 不把一部片切成几段同时转：M2 Max 实测单路 4K HDR → 1080p 约 8 倍实时，切 3 段并行约 10 倍、切 2 段反而更慢，
  媒体引擎已近上限，收益抵不上复杂度。

**回收**：
- 客户端下完后调 DELETE；
- 没调的，最后一次访问 72 小时后回收；
- 总量计入缓存管理的上限，按最近使用淘汰。

**已实测**（2026-10-13）：
- 真实 uvicorn 上边转边下：响应无 Content-Length（分块），转码进行中就开始发，结束后 480p 文件时长 240.0 秒准确；
- 服务端中途作废（抛错掐断）时，客户端得到「传输未完成」（curl 退出码 18），不会把半个文件当成完成；

本机 FFmpeg 8.1.2，6 分钟测试片，同一组 movflags：
- 写管道与写文件的**字节完全相同**，说明输出只追加、不回头改写，边写边发是安全的。
- 完整文件的时长为 360.0 秒，准确；任意位置拖动约 40 毫秒到位，落点准确。
- 截掉一半的文件也能打开和拖动，以后做「边下边看」有基础。

模拟器上 AetherEngine 打开本机分片 MP4 已验证能播（端到端用例 4）；拖动性能真机待复验。如果有问题，退回 MPEG-TS，它天然只追加。

### 5.4 客户端下载

**后台下载会话**：
- 两个会话：`io.movieclaw.offline`（只用 Wi-Fi）与 `io.movieclaw.offline.cellular`（蜂窝也可以），开 `sessionSendsLaunchEvents`，不设 discretionary。网络策略放在会话上：续传数据里的请求带不了新的网络策略，改设置时把进行中的任务带续传数据取消、在另一个会话里接着下。
- `httpMaximumConnectionsPerHost = 1`，一次只下一个。家里上行有限，串行能让第一集最早可看。
- AppDelegate 补上 `handleEventsForBackgroundURLSession`。

**请求设置**：
- 带 `Authorization: Bearer <该账号的设备令牌>`。设备令牌不过期，不用 12 小时有效的播放签名。切换账号后，其他账号的下载照常继续。
- 默认仅 Wi-Fi（低数据模式、个人热点同样不下）。
- 任务的 `taskDescription` 写入单元身份（账号键、条目、`file_id`、代号），App 重启后据此把任务对回单元。

**单元状态机**：

```
准备中（拉清单、字幕、字体、图片）→ 排队 → 下载中 → 完成
     ↘ 失败（可重试 / 不可重试）   暂停（带续传数据取消）↔ 下载中
```

**对账**（幂等）在这些时机执行：启动、回前台、可达性恢复、后台会话事件唤醒、任务结束、删除、修改设置。每次对账：
- 应该有任务而会话里没有 → 有续传数据就用续传数据重建，否则新建；
- 会话里有任务而对应单元已删 → 取消。

用户强退 App 时，系统会取消全部后台任务（附带续传数据），下次启动由对账重建。

**重试**：
- 网络类错误、5xx、503 按退避重试：30 秒 → 2 分钟 → 10 分钟 → 30 分钟 → 之后每小时。
- 503 的重试用 `earliestBeginDate` 定时，不需要 App 醒着。
- 403（无权限）、404（文件没了）、422（不能转码）和空间不足不自动重试，写明原因，用户可以手动重试。

**空间检查**：开始前查剩余空间（`volumeAvailableCapacityForImportantUsage`），要求 ≥ 预计大小 + 2 GB；不够就提示，不入队。

**完成判定**：状态码是 200 或 206；有 Content-Length 的核对字节数；分块传输靠正常结束来判断。这些都通过后，才移动文件、标为完成。

**其他文件**：字幕、字体、图片、展示数据在「准备中」阶段用普通接口会话拉取（体积小，且在前台），与视频并行。视频和必需文件都齐了才算完成；图片缺了不影响完成，显示占位。

## 6. 播放

**分流点**在 `PlaybackController` 向服务端发起协商之前（`request()`，PlaybackController.swift:571）。这一集（或这部电影）有已完成的本机单元，就走本地源；否则照旧。

**本地源**：
- `NativeEngine` 以 `file://` 打开，引擎的 `FileIOReader` 直接读文件，现已支持。
- 不设字节缓存键。
- 外挂字幕通过 `prepareExternalSubtitles` 传本机文件。
- 片头片尾段、章节、默认音轨和字幕取自 `playback.json`；之后的轨道选择沿用本机的轨道记忆。
- 不建服务端会话，不 ping。

**起播位置**：用详情页传入的续播点（在线时来自服务器，离线时来自本机）；没有传入时，取本机进度与存档中较新的一份。

**自动下一集**：
- 下一集有本机副本 → 播本机；
- 在线且没有副本 → 照常走服务器；
- 离线且没有副本 → 停在片尾。

**异常与暂缓**：
- 引擎打不开本机文件时，把单元标为「已损坏」，提示「重新下载」。
- 预览缩略图（trickplay）一期不打包。

## 7. 进度与观看记录

**本机播放一律走观看记录，在线离线都是同一条路；流式播放保持现状。** 两条通道不混用，免得一次观看被记两遍。

### 客户端

- 每次播放一个单元，生成一个 `viewing_id`（UUID）。
- 记录的字段：`media_item_id, season, episode, file_id, started_at, updated_at, position_ms, watched_ms, completed, duration_ms`。其中 `watched_ms` 只累计实际在播放的墙钟时间。
- 每 10 秒，以及暂停、停止、退到后台时，原子写一次 `viewings/<id>.json`，同时更新该条目的 `progress.json`（离线续播和离线「接着看」靠它）。
- 本机续播点与服务端**同一套阈值**（不足 5% 不记、超过 90% 算看完、短于 5 分钟的片过了开头就算看完）。不同口径的话，离线时显示「继续 0:12」，连上之后服务端却说没看过（端到端时发现）。
- 可达时立即发送最新快照，同一时刻只有一个在途请求；离线时先留着，可达后批量补传，一批最多 100 条。
- 一条记录要同时满足「服务端已确认」和「这次播放已结束」才删除。
- 与 `PlaybackReportQueue` 同一做法：先落盘再发，发成功才删，服务端按编号合并。

### 服务端 `POST /playback/viewings`

请求体为 `{sent_at, records[]}`，逐条按 `viewing_id` 幂等 upsert：

1. **校时**：偏差 = 服务器当前时间 − `sent_at`，记录里所有时间都加上这个偏差，且不得晚于服务器当前时间。偏差超过 7 天，视为手机时钟不可信，一律按服务器当前时间处理。
2. **定位**：先按 `file_id` 找到这个文件现在属于哪个条目、哪一集，这样条目被转移或重新识别过也能对上。找不到再用 `media_item_id`。都找不到返回 `rejected`。
3. **续播状态**（`playback_state`）：
   - 只有记录的 `updated_at` 比该单元现有的 `updated_at` 新，才写入。按发生时间判新旧，不按到达先后。
   - 位置和「已看」按现有阈值判定（movieclaw_playback/progress.py:21）。
   - `last_played_at` 取两者中较晚的。
4. **观看日志**（`playback_log`，新增一个可空的唯一列 `viewing_id`）：
   - 首次插入时 `play_count` 加 1。
   - `started_at`、`ended_at` 用校正后的时间，因此观看统计按时段分摊时用的也是真实时间。
   - `watched_ms` 取新值与已存值中较大的一个，并且不超过 `ended − started + 2 秒`。
5. **事件**：
   - 「已看」从否变为是 → 发 `playback.completed`，时间用记录里的时间。
   - `playback.started`、`playback.progress`、`playback.stopped` 只在记录是新鲜的时才发，即 `updated_at` 在服务器当前时间 2 分钟以内（也就是在线时的本机播放）。补传的旧记录不发，免得落地后收到一串「开始观看」推送。
   - 不调 `activity.*`，也不调 `end_session`：前者会造出假的「正在播放」卡片，后者在 stop 时会掐断这台设备的流。
   - state、watch、events 的写入函数现在把 `utcnow()` 写死了（movieclaw_playback/state.py、services/playback/watch.py、movieclaw_api/events.py:105），需要加 `now` / `occurred_at` 参数。数据库存的是不带时区的 UTC，客户端时间要先转换。
6. **返回**：逐条给出 `applied`、`stale` 或 `rejected`，三种情况客户端都可以删除该记录。`stale` 表示续播状态没有更新，但观看日志已经记下。

## 8. 删除

| 位置 | 操作 |
|---|---|
| **详情页下载按钮**（电影） | 按钮状态依次是：下载 → 进度环（点按可暂停、继续、取消）→ 已下载 ✓（点按弹出菜单：「删除下载（1.4 GB）」「改下其他画质」）。剧集页没有这个按钮 |
| **分集卡**（剧集） | 没下完时剧照叠一条下载状态（同首页「正在下载」）：蓝描边，底部「下载中 N%」+ 右侧实时速度 + 一道进度；暂停 / 继续 / 取消在长按菜单；下完右上角绿箭头「已下载」，刚下完时短暂提示「下载完成」 |
| 剧集详情页右上角「⋯」 | 菜单顶部一排图标「下载 · 加入合集 · 分享」，点「下载」打开选档面板：顶部分段选范围「第 N 集 / 未看 N 集 / 全部 N 集」（本机已有的不算，有没看的默认「未看」），切范围时各档整批大小跟着变，选一次画质整批开始。这部剧有还没下完的集时，菜单顶部临时多一个分区：「取消下载选中的集」（选中的那集在下时）、「取消全部下载（N 集）」（确认后取消，已下完的保留）；菜单只读「各条目还没下完的单元」这一派生值（只在开始 / 完成 / 删除时变），下载进度刷新不会重建开着的菜单（否则点下去的项落空） |
| 分集卡长按 | 「下载这一集」/「暂停」/「继续下载」/「取消下载」或「删除下载」；只有操作，进度看分集卡上的下载条 |
| 海报卡长按（在线、离线都有） | 已下载的条目在菜单里多一项「删除下载」。只进菜单，不加可见控件 |
| 我的 → 下载与存储 | 分组同系统「iPhone 储存空间」：顶部容量条（MovieClaw 下载 / 其他 / 剩余）；「建议」只在有看完的下载时出现（「删除已看完的」）；「已下载」按条目列出，点进媒体库条目，左滑（红色）或长按删除；「其他账号」分组也能删；下载设置在右上角齿轮菜单（只有「使用蜂窝网络下载」一项，菜单里直接勾选） |
| 退出登录 | 询问「同时删除本机下载的 N 部（X GB）？」 |

**删除规则**：
- 都要二次确认，写明能释放多少空间，并说明「观看进度会保留」（待同步的观看记录不随删除走）。
- 离线时同样可以删：只动手机，不碰服务器。
- 删除下载中的单元：先取消任务，再删目录。
- 一个条目的单元全删完后，整个条目目录一起删。

## 9. 账号与权限

**服务器实例号**：
- `/api/v1/health` 新增 `instance_id`，取 Jellyfin 兼容层已经持久化的 `server_id`（settings/schemas.py:641，首次读取时生成）。
- 读取它不依赖兼容层开关。
- 两个用途：作为账号键的一部分（§3.2），以及探测时核对服务器身份（§2.2）。

**下载权限**：
- 按成员权限 v2 已定稿的 `allow_video_download` 实现（member-permissions-v2.md:149、:260）：默认开，儿童预设关；关闭时下载相关接口返回 403，Jellyfin 的 `EnableContentDownloading` 为 false。
- 会话能力快照（`SessionCapabilities`）加上这个字段，并且可空：旧服务器缺这个字段，就视为不支持离线下载，下载按钮不出现。
- 权限后来被关掉：不能再下新的，已下的照常能播。
- 不做 DRM，也不做远程擦除。本机副本就是普通文件，安全边界在服务器。

**令牌被吊销**（例如在别处改了密码）：
- **不自动删除下载**。否则自己在网页上改个密码，手机里的片子就全没了。
- 副本跟着「实例号 + 用户名」走，同一账号重新登录就回来了；也可以在存储页的「其他账号」里手动删。
- 这是修订：第一轮提议的「收到 401 就删」作废。

**离线时不能切换账号**，因为切换需要连服务器验证。

## 10. 性能预算

| 项 | 预算 |
|---|---|
| 网络健康时 | 不发额外请求（只旁听），只用已有的一个通路监视器 |
| 离线模式下 | 外壳的角标轮询、SSE 照旧按各自的退避重试（一期没有专门暂停，失败请求不计入连通性判断）|
| 启动 | 后台线程扫 N 个 `summary.json`（每个约 1 KB），500 部以内不到 10 ms |
| 打开已下载条目的详情 | 解码本机 `detail.json`（几十到两百 KB）不到 5 ms，首帧就是完整页面 |
| 下载进度 | 回调节流到每秒一次，写进单元自己的可观察对象。海报墙只观察「已下载集合」（只在完成、删除时变化），下载过程中不重绘 |
| 本机播放 | 直接读文件，不经字节缓存 |
| 观看记录 | 播放中每 10 秒一次小文件原子写（同 QoE 的 `active.json`） |
| 服务端导出 | 一次一路，硬件转码，降优先级。进行中的下载从页缓存读，同档同片全家共用 |

## 11. 扩展

- **Mac**：`Shared/` 同时编进 Mac 目标。离线模块放在 `Shared/Offline/`，用 `#if !os(tvOS)` 隔开；以后开放 Mac 版只需要做界面。Apple TV 不做离线。
- **智能下载**（自动下后 N 集、看完自动删）：只是往「期望状态」里加减单元的策略，其余交给对账。
- **新档位、HEVC 导出**：在服务端清单里加，客户端不用发版。
- **安卓手机**：用同一套服务端接口和打包格式。
- **流式播放的进度**：目前上报失败就丢（PlaybackAPI.swift:190），以后可以迁到同一条观看记录通道。
- **原盘下载**：把导出的输入接到 `transcode_disc_source` 的 concat 输入即可，接口不变。

## 12. 分期与验收

共三期。D2、D3 互不依赖，可以调换或并行。

### D1 基础：原画下载、本机播放、观看记录、删除

范围：
- 服务端：`instance_id`、`allow_video_download`、清单接口、原画内容接口、观看记录补传。
- 客户端：
  - 存储与对账、后台下载；
  - 详情页和分集卡的下载与删除，海报卡长按删除；
  - 下载与存储页；
  - 本机播放、观看记录；
  - 取数层（含在线时本机秒开、请求失败回落本机）、图片回落。

D1 做完，飞行模式下就已经能用：冷启动显示首页快照，点进已下载的片子时取数层回落到本机，可以播放。只是首页还会显示全部条目。

端到端验收（模拟器 + 本地服务端 + 真实片源）：
- 下载途中杀掉服务端再拉起，续传完成，md5 与原文件一致。
- 停掉服务端，播本机副本、拖动、看到一半退出；再起服务端，等补传完成后，网页端的续播点正确，观看统计的开始时间是实际观看的时间。
- 从各个入口删除后，空间释放、目录清空、进度保留。

### D2 码率档：导出作业 + 边转边下

第一步：真机复验 AetherEngine 打开本机分片 MP4 的时长与拖动。

端到端验收：
- 点下载整季后 App 退到后台、锁屏，下载照常推进，直到全部完成。
- 导出途中重启服务端，代号改变，客户端从头重下，文件能正常播放。
- 两个账号下载同一集同一档，服务端只转一次。

### D3 离线模式：网络判断 + 离线首页、海报墙、只读详情、各页占位

单元测试（用事件序列驱动可达性状态机）：
- 慢但成功的请求永远不会判成不可达；
- 只有超时类失败时，要满 30 秒且三次探测失败才判不可达；
- 两次硬失败即判不可达；
- 通路断开立即判不可达；
- 回前台前发出的请求报 -1005 不计入。

端到端验收：在本机起一个 TCP 代理夹在 App 与服务端之间，可以调延迟、限速、丢包、黑洞、返回 HTML。
- 3 秒延迟 + 50 KB/s 限速 + 间歇丢包，连续浏览 10 分钟，不得进入离线。
- 代理改成黑洞后冷启动，40 秒内进入离线首页。
- 代理返回 HTML（模拟机场门户）后冷启动，几秒内进入离线。
- 恢复后自动回到在线，并补传观看记录。

真机验收：飞行模式开关往返；后台下载锁屏过夜。

## 13. 不做

- 没下载的内容不支持离线浏览，只有首页快照照旧显示。
- 不用系统 HLS 下载（`AVAssetDownloadTask`）。原因：
  - 它只能配系统播放器，而本机播放走 AetherEngine；
  - 服务端 HLS 会话 180 秒不用就回收；
  - 字幕和片头片尾段带不进去。
- 不做 DRM 和远程擦除。
- Apple TV 不做离线。

### 复查修复（2026-10-13）

逐项先在台子上复现、再修、再跑同一用例转绿（用例 `MovieClawUITests/OfflineReviewReproUITests.swift`；服务端的在 `tests/api/test_offline_download.py`）：

| 问题 | 修法 |
|---|---|
