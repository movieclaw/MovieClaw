# AI 字幕：无字幕片从音轨识别（本地语音模型，一期）

> 状态：**一期已实施（2026-10-29）**，实施记录见 §13。
> 前置：[subtitle-ai-translate.md](subtitle-ai-translate.md)。该稿 §1② 与 §8 已给语音识别（ASR）留好位置：
> 识别出原语言字幕，再交给同一条翻译管线。本文就是那一级来源的落地方案。
> 依据：2026-10-28 在 NAS（AMD V1500B，4 核 8 线程，有 AVX2、无核显，32 GB）上实测了
> SenseVoice-Small、Parakeet-TDT-0.6B v3 和 Whisper small，数据见 §10。

## 0. 结论

- **一期只做本地模型**：用 sherpa-onnx 2.0.1 跑 SenseVoice-Small（官方 2024-07-17 int8），
  覆盖中文、粤语、英语、日语、韩语。
- **产品形态不变**：AI 字幕入口、确认框、任务中心、外挂落盘全部沿用。唯一的新东西出现在
  选不到任何字幕源（没有文本字幕，也没有 PGS）的时候：预检不再报「没有字幕」，而是选中
  「从音轨识别」，确认框里讲清楚会用本地语音模型识别台词、比较慢、预计要多久。
- **接口形状不变**：请求沿用 `source_candidate_key`（新增取值 `audio:<k>`），说明文字放在
  `reference_notice`，不能识别的原因走 `blocker`。旧版 iPhone / Mac / 安卓 App 不升级也能用：
  这些字段在三端都按字符串处理，且有兜底，已逐端读过代码（§5）。
- **识别结果是一份独立的外挂**：先存成 `<视频名>.asr.<语言>.srt`（做法与 `pgs-ocr` 相同），
  再进现有翻译管线。目标语言恰好就是台词语言时，不调用大模型。
- **要换镜像**：新增 sherpa-onnx（55 MB）和模型（230 MB），`docker/runtime-version` 由 24 升到 25。

## 1. 范围

| 一期做 | 一期不做（原因） |
|---|---|
| 本地 SenseVoice 识别 + 现有翻译管线 | 云端或远端转写、Whisper 档（放二期，见 §12） |
| 管理员手动发起（现有入口） | 入库自动生成走识别：每集要几分钟 CPU，不能静默批量跑；自动生成仍只用文本字幕 |
| 中文、粤语、英语、日语、韩语 | 其他语言：模型不支持，明确提示 |
| 本地视频文件 | 网盘（strm）条目：要整片下载，一期不提供 |
| 本机转码时暂停；可停止；重启后能续上 | 分段断点：整片重识别只需十几分钟，一期不做 |
| 网页确认框和进度文案；旧版 App 兼容 | iPhone / 安卓的文案美化：随两端各自的下个版本发 |
| — | 改动 L1 同步检测所用的 VAD（现有能量法兜底不动） |
| — | 说话人区分、音效标注、画面硬字幕检测 |

## 2. 产品流程

1. 管理员在版本详情点「AI 字幕」，预检秒回（照旧只读数据库，不读视频）。
2. 选源顺序不变：
   - 有可用的文本字幕：走原流程；
   - 只有 PGS：走原有的 OCR 确认流程；
   - **两者都没有**：预检选中「音轨识别」候选，确认框显示一段说明（`reference_notice`），例如：

     > 这个文件没有可用的字幕。将用本地语音模型从第 1 条音轨（英语 5.1）识别台词，再翻译成简体中文。
     > 识别在本机进行、不产生费用，但比较慢：这部 2 小时的影片预计需要约 15 分钟；
     > 本机正在为播放转码时会自动暂停。识别出的英语字幕会另存为 xxx.asr.eng.srt，可以单独使用。

   - 成本估算：沿用「按片长粗估 token」。台词语言就是目标语言时显示 0，并说明不调用 AI 模型。
3. 确认后进任务，进度依次为：
   读取音轨（「已读到 01:12:33」）→ 识别台词（百分比和剩余时间）→ 术语 → 翻译 → 校验 → 写入。
4. 完成后多出两个外挂：`<视频名>.asr.eng.srt`（原文）和 `<视频名>.ai-chs.chi.srt`（译文），
   台账即时刷新，播放器里马上可选。

新增三个不能识别的原因（`blocker.code`）。旧客户端对不认识的原因码会原样显示服务端给的标题、说明和建议：

| code | 场景 | 说明要点 |
|---|---|---|
| `asr_language_unsupported` | 已知台词语言不在中、粤、英、日、韩之内 | 「本地语音模型暂不支持法语」，建议放入外挂字幕 |
| `asr_unavailable` | 运行环境缺识别组件（旧镜像，或源码运行没装依赖） | 「当前镜像不含本地语音识别组件，更新 Docker 镜像后可用」 |
| `asr_remote` | 网盘（strm）条目 | 「网盘文件暂不支持从音轨识别」 |

## 3. 选源：把音轨当作最后一级候选

- **新候选种类 `audio`**：`key` 是音轨序号（对应 ffmpeg 的 `0:a:<k>`），中性引用写作 `audio:<k>`；
  `provenance` 为 `asr`，`format` 填音轨编码，`reasons` 写明音轨语言、声道和「本地语音模型识别」。
- **只在三种情况下出现**：
  1. 手动预检或执行时，文本字幕和 PGS 都选不到（`_select_reference` 返回空）；
  2. 文件识别过（已有 `asr` 外挂）：列出音轨供用户主动选它重新识别，但标为 `on_request`，
     不参与默认选择，也不改变「为什么没有默认参考」的结论；
  3. 请求里显式指定了 `audio:<k>`（CLI、Agent 与测试）。
- **不进 `rank_candidates`**：自动生成（`auto._has_reference`）和一键校准
  （`_subtitle_reference_intervals`）都调用它。放进去的话，自动生成会对所有无字幕的文件跑识别。
  音轨候选改由新增的 `source.audio_candidates()` 产出，只在 `tasks.preview` 和 `tasks._run` 里追加。
- **选哪条音轨**：
  1. 原语言优先：轨道语言标签或元数据 `original_language` 与之一致；
  2. 排除评论音轨（标题含 commentary、评论、导评）；
  3. 跳过 ffmpeg 解不了的轨（沿用 `sync.audio_index` 的经验，例如 Audio Vivid）；
  4. 其余按顺序。
- **台词语言**：
  - 判定顺序：轨道语言标签 → 元数据原语言（TMDB 的 `cn` 表示粤语）→ 都没有时自动判断（任务里取前 20 段的多数结果后锁定）；
  - 映射到 SenseVoice 的 `zh / yue / en / ja / ko`，不在其中就排除候选（`asr_language_unsupported`）；
  - 片库里缺字幕文件的音轨标签大多是 `und`，所以元数据原语言是主要依据。
- **识别产物的世代**：`_external_provenance` 增加 `asr`，排在 PGS OCR 之后、AI 成品之前。
  以后这份外挂被当作其他语言任务的参考时，按这个顺序参与排序。

## 4. 执行管线

```
预检（不读视频）
  └ 选中 audio:<k>：reference_notice 给出识别说明和预计时长
任务
  ① 读取音轨：media_extract 读盘闸门 + -progress，产出 cache/<file_id>.a<k>.16k.wav
  ② 识别台词：asr_worker 子进程（sherpa-onnx：silero VAD 切段 → SenseVoice）
  ③ 断句成字幕条（纯函数）→ 质量门（assess_events）
  ④ 写 <视频名>.asr.<语言>.srt，刷新台账
  ⑤ 台词语言 = 目标语言 → 结束，不调模型
     否则 → 进现有翻译管线（跳过 L1 同步检测）
```

### 4.1 读取音轨

- 在 `media_extract` 新增 `extract_audio_async(file, audio_index, out_path)`，与内封字幕抽取共用：
  - 同一个全局读盘闸门；
  - 同一套进度登记，所以 `read_progress`、`tasks._reading`、`_follow_read_progress` 不用改，「排队中」「已读到」直接能显示；
  - 同样按体积估超时、可取消、原子落盘。
- 命令：`ffmpeg -i <视频> -map 0:a:<k> -ar 16000 -c:a pcm_s16le`。
  - 立体声加 `-ac 1` 下混；
  - 5.1 / 7.1 改用 `-af pan=mono|c0=FC` 只取中置声道：对白基本都在中置，实测英剧字错率由 17.6% 降到 16.7%。
- 产物是 16 kHz 单声道 PCM WAV，约 1.9 MB/分钟，2 小时片约 230 MB。
  - 任务成功就删；失败时保留给重试复用，视频 mtime 变了即作废；
  - 所在目录已在缓存登记表里，缓存管理面板能统计和清理。
- 实测从 NFS 读出音频：46 分钟剧集 16 秒，80 分钟电影 13.5 秒（约 220 MB/s），不是瓶颈。

### 4.2 识别子进程

- **启动方式**：`subtitle_gen/asr_worker.py` 是独立脚本，用 `sys.executable -I <脚本>` 启动，与 `pinyin_worker` 同一做法，避免同目录模块盖住标准库。
  它只依赖 sherpa_onnx 和 numpy，不 import movieclaw。
- **输入输出**：
  - stdin：一行 JSON 参数（模型路径、wav 路径、语言、线程数、VAD 参数）；
  - stdout：每识别完一段输出一行 JSON（起止时间、文本、token 及其时间戳、识别出的语言），夹带进度行；
  - 最后一行给出检出的语言和语音总时长。
  - 启动后先 `os.nice(19)`。
- **参数（按实测定）**：
  - 线程数 2：2 线程已有 7.9 倍实时，只占约 2 个核；4 线程 9.8 倍，8 线程反而降到 8.2 倍。核数不足 4 的机器用 1 线程。
  - silero VAD：阈值 0.5，最短静音 0.25 秒，最短语音 0.25 秒，单段上限 20 秒。
  - 每段前后各补 0.3 秒余量，不越过相邻段的中点。不补会切掉句首的词（实测整句「Is he already here?」丢失），补了以后各语种字错率降 0.4–3 个百分点。
- **内存**：主进程只等子进程，不加载模型，内存预算（< 500 MB，#918）不受影响。子进程峰值约 0.5 GB，任务结束即释放。
- **进程纪律**：子进程起在独立进程组；`process.py` 增加一个能逐行读输出的变体，回收逻辑（SIGTERM 后 SIGKILL）复用现有代码。
  `transcribing` 加进 `_STOP_AT_ONCE_PHASES`，点停止秒级生效。
- **为播放让路**：每秒看一次 `skip_segments.playback_load()`（延迟导入，不破坏分层守护）。
  - 本机在转码时给子进程组发 SIGSTOP，转码结束发 SIGCONT。这与片头识别「本机转码就停」是同一口径；
  - 暂停期间进度文案改为「本机正在为播放转码，识别已暂停」；
  - 暂停中被取消时，先发 SIGCONT 再发 SIGTERM，因为停住的进程收不到 SIGTERM；
  - Windows 源码运行没有 SIGSTOP，不暂停。
- **全局单飞**：识别任务的 Job 资源里加 `ResourceRef("asr_engine", "local")`，同一时间只跑一个识别，其余排队。
  Job 调度器默认最多并行 4 个任务，翻译任务不受这把锁影响。

### 4.3 断句成字幕条（`subtitle_gen/asr.py`，纯函数）

- 输入是 VAD 段和段内带时间戳的 token，输出现有的 `SubEvent` 列表。
- **切分规则**：
  - 句末标点处必切；逗号、顿号，以及 token 间停顿 ≥ 0.3 秒的地方作为候选切点；
  - 单条不超过 7 秒；字数不超过两行 × `validate.line_limit(语言)`；
  - 起点提前 0.1 秒，终点延后 0.3 秒，不压到相邻条，条间留 80 ms；单条至少 0.8 秒。
- **拼接**：中日韩直接相连；拉丁语种按 SentencePiece 的 `▁` 还原空格。
- **清理**：
  - 去掉只有标点或符号的条；
  - 同一 token 连续重复 3 次以上时折叠；
  - SenseVoice 的事件标签（BGM 等）不写进文本。
- **质量门**：整段音频识别成功后只要求断句结果非空；对白条数与首末对白跨度不能代表识别是否完成。
  ASR 外挂复用或再次作为翻译参考时同样按 `provenance=asr` 评估。普通字幕轨与 OCR 仍要求 ≥ 50 条、覆盖 ≥ 50%，
  识别异常和空结果仍在翻译前失败（#1121）。

### 4.4 与翻译衔接

- **提示词**：`FilmContext` 加一个「原文来自语音识别」标记。`system_prompt` 据此多一条：
  原文是语音识别结果，可能有同音错字和断句偏差；按上下文理解，明显的识别错误先按语境纠正再翻译。
- **跳过 L1 同步检测**：音轨来源的时间轴本来就出自这条音轨。
- **同语种**（例如英语片要英语字幕）：
  - 不组装 chat，也不要求配置模型；
  - 预检的 `estimated_tokens` 为 0；
  - `_prepare_generation` 和 `enqueue_generation_job` 里「先组装 LLM 路由」那一步跳过，Job 输入里的模型字段留空。

### 4.5 复用、重新识别与恢复

- **识别结果就是一份外挂字幕**：`<视频名>.asr.<语言>.srt` 写在视频旁边并刷新台账，播放器里能直接选，
  标成机器生成（`is_ai_generated` 认 `asr`）。之后生成别的语言时它就是默认的文本参考，不再识别。
- **复用**：选中音轨（默认或显式）时，识别外挂比视频新、读得出来且非空就直接复用；
  识别成功后才原子写出外挂，半截结果留在断点中。空外挂、洗版前的旧外挂都不复用。
- **重新识别**：只有用户选中音轨并勾「重新识别」（`retranscribe=true`）才重跑。入队时把此刻已有的识别外挂
  （文件名 → 大小与修改时间）和识别断点（创建时间）记进 Job 输入（`asr_stale`），执行时不复用它们。
  记身份而不当场删除：重新识别失败旧外挂还在；任务重启时这次自己写出的新结果身份不同，照常复用。
- **识别断点**：识别时主进程把锁定的语言和逐段结果追加到 `<文件号>.a<音轨>.asr.jsonl`（字幕缓存目录），
  约每 10 秒 fsync 一次。身份是同一视频文件（路径、大小、修改时间）、音轨、声道取法、台词语言、模型与切段参数。
  重启、崩溃或断电后，Job 框架把任务重新排队（kill -9 / 断电等租约 45 秒过期，优雅停机立即），识别从最后
  一段的终点接着跑；最后一行写了一半就丢掉，身份不符整份作废。识别外挂落盘后才删断点与 WAV。
- **续跑与不中断逐段一致**：子进程收到 `start` 后 VAD 仍从片头跑（只切段、不识别，本机约 300 倍实时），
  起点在断点之前的段丢掉，之后照常识别。silero VAD 的 LSTM 状态从第一个样本一路带下来：直接从断点
  冷启动，窗口网格错开 18 ms，之后 82 段一段都对不上；往回预热 30～125 秒能对齐网格、收敛大部分状态，
  也只保住接缝后约 200 秒；从片头重放则 82/82 逐段相同（2026-10-29 用《幸福伽菜子》第 1 集实测）。
  识别器每段独立解码，没有跨段状态。
- **落盘**：音轨 WAV、识别外挂、翻译断点都先写临时文件、fsync 后再改名，断电后要么没有、要么完整。
  读音轨前先清掉上次没写完的 `.part` 临时文件。
- **子进程不留孤儿**：识别子进程设 `PR_SET_PDEATHSIG(SIGKILL)`，主进程被杀时内核直接结束它，
  因转码暂停（SIGSTOP）中的也一样；其他平台靠写管道失败退出。
- 翻译阶段的断点续传沿用现状。
- **Job 输入固化**：`source_candidate_key=audio:<k>`、识别语言、模型标识（`sensevoice-small-2024-07-17`）、源文件指纹；
  `handler_revision` 升到 `subtitle.generate.v2`。
- **结果**：同语种时 `filename` 指向识别外挂，否则指向译文外挂。完成文案带上两份外挂的文件名。

## 5. 接口与兼容

- **请求**：预检与发起各加一个可选的 `retranscribe`（默认 false，§4.5）。老客户端不传，行为就是复用；
  一期只有网页提供「重新识别」勾选框，App 以后跟进。
- **预检响应**：没有新字段。
  - `candidates` 里多一种 `kind="audio"`；
  - 识别说明放在 `reference_notice`；
  - 新增三个 `blocker.code`（§2）。
- **任务进度**：
  - 新阶段 `transcribing`，`phase_index` 为 1，与读取同属第一步；
  - `details` 可选地新增 `transcribe_position_seconds`、`transcribe_paused`，老客户端会忽略。
- **三端核对**（2026-10-29 读代码）：
  - **网页**：`kind`、`provenance` 在 TypeScript 里是联合类型，但运行时不校验。不认识的阶段会落到「准备」和通用的「生成中」。
    一期顺手把候选名改成「音轨识别 · 英语 · 第 1 条音轨」、进度改成「识别台词 23%」。网页随服务端一起发布，没有兼容问题。
  - **iPhone / Mac**：`SourceCandidateView.kind` 和 `provenance` 都是 `String`，不认识的来源世代原样显示，不认识的阶段走兜底。
    旧版会把候选显示成「英语 · EAC3 · asr · 外挂 0」，但功能完整可用。
  - **安卓**：`kind` 和 `provenance` 是带默认值的 `String`，同样有兜底。
  - **结论**：旧版 App 能看到提示、能发起、能看进度，只是候选名和阶段名不够好看。两端的文案补丁随各自下个版本发。
- **CLI / Agent**：响应形状不变；请求多一个可选参数，CLI 内嵌的基线 spec 构建时现导，不入库。
  Agent 可以用 `audio:<k>` 显式发起识别，加 `retranscribe` 重新识别。

## 6. 打包与部署

- **依赖**：pyproject 加 `sherpa-onnx==2.0.1`，同步更新 uv.lock。
  - 锁死版本，因为 2.x 刚升过大版本；
  - 它提供 Python 3.7–3.15 的轮子，覆盖 Linux x86_64 / aarch64、macOS、Windows；
  - 安装后约 55 MB。同类的 faster-whisper 连依赖要 456 MB。
- **模型**：Dockerfile 新增 `asr-model` 阶段，和 NER、PP-OCR 一样烧进镜像，用户开箱即用、不用联网。
  - 从 sherpa-onnx 的 Release 下载 `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17`，
    只取 `model.int8.onnx`、`tokens.txt` 和一段测试音频，约 230 MB；
  - 另下载 `silero_vad.onnx`（632 KB）；
  - 两者都校验 sha256，放进 `/app/models/asr`，由 `MOVIECLAW_ASR_DIR` 指过去，随附 NOTICE。
  - **只能用 2024-07-17 版**：同系列的 2025-09-09 版是用 2.18 万小时粤语数据微调的版本，
    实测日语字错率 85%、韩语 99%，普通话也略差（10.5% 对 9.7%）。
- **许可**：FunASR Model License v1.1 允许使用、复制、修改、分享，要求注明来源与作者、保留模型名。
  该条款可由发布方单方修订（§11）。
- **镜像与运行时版本**：
  - 镜像约增大 290 MB；`docker/runtime-version` 24 → 25；
  - changelog 要提示 Docker 用户重新拉取镜像；
  - 旧镜像配新应用包时，能力探测会报不可用，预检给出 `asr_unavailable`，其他功能不受影响。
- **构建期冒烟**：在目标架构上用模型自带的测试音频跑一次 worker，断言识别出预期文本。
  这与 PGS 冒烟同一纪律（[docker-subtitle-runtime.md](docker-subtitle-runtime.md)），amd64 和 arm64 两个 digest 都通过才发布。
- **能力探测**：照 `pgs._Environment` 的做法，启动时后台起一次子进程，`import sherpa_onnx` 并检查模型文件。
  - 预检只查这份缓存结论，探测结果写一行启动日志；
  - 同时记下 CPU 是否支持 AVX2，供预计时长选系数（§7）。

## 7. 性能与资源预算

| 项 | 预算 | V1500B 实测 |
|---|---|---|
| 识别速度（2 线程） | ≥ 6 倍实时 | 7.9 倍（4 线程 9.8 倍） |
| 2 小时影片（读取 + 识别） | ≤ 20 分钟 | 约 15 分钟 |
| 45 分钟剧集（读取 + 识别） | ≤ 8 分钟 | 约 6 分钟 |
| 识别子进程峰值内存 | ≤ 700 MB | 约 0.5 GB |
| 主进程内存 | 不增加 | 不加载模型 |
| CPU | ≤ 2 核、nice 19、本机转码时暂停 | 约 2 核 |

- **预计时长**：按片长 ÷ 速度系数估算。有 AVX2 时系数取 8；没有 AVX2 的 J4125、N5105 等老 CPU 还没测，先取 3，确认框里写「约」。
- **整库不现实**：片库缺字幕的部分约 3,400 小时，即使 8 倍实时也要 400 多小时 CPU。这也是一期只做按需手动发起的原因。

## 8. 文案（i18n）

新增的用户可见文案全部走 `stored_fields`，中文和英文两套，并按项目流程登记源文哈希。主要有：

### 9.1 单元测试（不需要模型）

- **覆盖**：
  - 主流程：预检说明 → 发起 → 读取 → 识别 → 写识别外挂 → 翻译 → 写译文外挂；
  - 识别中停止：子进程几秒内退出，没有孤儿进程；

- **部署**：
  - runtime 25 镜像沿用 2026-10-26 的做法在 NAS 上原生构建；

- **素材**：用只读查询从片库挑一部完全没有字幕的英语片和一部日语片。电影优先；日语没有合适的电影时用动画剧集。

- **通过标准**：
  1. 两部都完整跑通，播放器里能选到识别原文和简中译文两条外挂；
  2. 识别阶段 ≥ 6 倍实时，子进程峰值 ≤ 700 MB，主进程内存没有明显增长；

## 10. 选型实测（2026-10-28，NAS V1500B）

**测法**：
- 6 段 10 分钟的片段，参考答案用片子自带的同语种字幕；
- 中日韩按字计错误率，英法按词计；
- silero VAD 切段，补 0.3 秒余量，4 线程；
- 速度包含 VAD；
- 运行时装在容器的临时目录里，测完已删。

| 片段 | SenseVoice-Small | Parakeet-TDT v3 | Whisper small |
|---|---|---|---|
| 普通话剧《大江大河》 | **9.3%** | 不支持 | 13.1% |
| 日语动画《间谍过家家》 | **19.5%** | 不支持 | 22.0% |
| 韩剧《非常律师禹英禑》 | 36.3%（有叠字） | 不支持 | **24.2%** |
| 英剧《王冠》 | 17.6%（只取中置声道 16.7%） | 18.0% | 13.2%（beam 1 为 **10.3%**） |
| 英语儿童动画《汪汪队立大功》 | 28.9% | **21.4%** | 27.0% |
| 法语电影《蝴蝶》 | 不支持 | 42.9% | 41.8% |
| 速度 | **8.8–12.8 倍实时** | 4.3–5.8 倍 | 2.5–3.7 倍 |
| 峰值内存 | **约 0.5 GB** | 1.1–1.4 GB | 1.1–1.35 GB |
| 字幕起点误差中位数 | **中 49 ms / 英 53–69 ms / 日 201 ms** | 英 81 ms | 100–150 ms |

**说明**：
- 法语那份参考字幕做过压缩，不是逐字稿，只能比较相对高低。
- Parakeet 在长片段中途会提前收尾、整句丢失：9.4 秒的段只识别出第一句。单段上限改 8 秒能缓解，但不能根治。
- 所有输出里都没有出现「Thank you for watching」「请不吝点赞订阅」这类典型的编造句子，VAD 只把语音段送进模型这一点起了作用。

**结论**：SenseVoice 在速度、内存、普通话、日语和时间戳上都是最好的，适合当默认引擎。
韩语和英语 Whisper 更准，但慢约 3 倍、依赖大 8 倍，放到二期作为可选档。

**实测中踩到的坑**（实现时同样会遇到）：
- 用 `ffmpeg -ss` 加 SRT 输出导字幕时，字幕流不会被精确裁剪，第一条还会被挪到 0 秒，整体偏移几秒。要加 `-copyts`。
- 有的 SRT 里残留 ASS 硬空格 `\h`，处理前要清掉。
- 抽 FLAC 时要加 `-sample_fmt s16`，否则会编成 24 位。本方案的缓存直接用 PCM WAV，不涉及这一点。

## 11. 风险与开放问题

1. **韩语质量**：SenseVoice 的韩语会出现「받으으려려면」这类叠字，字错率 36%。翻译阶段的大模型能理解过去，但识别外挂本身观感差。
   一期照常提供，二期加 Whisper 档。是否一期就对韩语加提示，待定。
2. **许可**：FunASR 模型许可可由发布方单方修订。万一改成限制再分发，退路是改为首次使用时下载，而不是烧进镜像。
3. **老 CPU**：没有 AVX2 的机器速度没测过，一期的预计时长系数是估的。
4. **配乐重的内容**：儿童动画、歌舞片的识别率偏低（实测 29%），歌词基本识别不准。
5. **原盘 ISO / BDMV**：能否读出音轨，取决于 `media_extract` 现有的读取能力。读不出时给出原因，不做特殊支持。
6. **粤语**：模型支持，但这次没实测；输出是口语字，目标为简中时交给翻译处理。

## 12. 二期方向（不在本期）

- 远端转写（OpenAI 兼容的 `/v1/audio/transcriptions`）和 Whisper 档：韩语、英语更准，也能覆盖更多语言；
- 入库自动识别（单独开关，默认关）；
- 网盘条目、画面硬字幕检测、说话人区分；
- 用 silero VAD 升级 L1 同步检测（需要重新标定阈值）。

## 13. 实施记录（2026-10-29）

### 13.1 一期实现

代码：`subtitle_gen/asr.py`（能力探测、规划、驱动子进程、断句）、`subtitle_gen/asr_worker.py`
（识别子进程）、`media_extract.extract_audio_async`（读取音轨）、`process.spawn`（可暂停的
逐行子进程）、`source.audio_candidate`、`tasks` 的兜底 / 预检 / 任务分支，网页确认框与进度文案。

实施中定下的细节：

- **断句的停顿阈值改为 token 起点相隔 ≥0.6 秒**：SenseVoice 只给 token 起点，没有终点，
  按 0.3 秒判会把慢语速当成停顿；
- **同一 token 连续出现 3 次以上折叠为 2 次**：单元测试里一串相同单词被折叠掉，正说明这条
  规则会吃掉真实的叠词（如「哈哈哈哈」只留两个），这是有意的取舍；
- **识别子进程以 `-I` 启动会忽略 `PYTHONPATH`**：sherpa-onnx 必须装在运行主程序的那个 venv
  里（镜像是 `/venv`）。只往 `PYTHONPATH` 里加包的做法在镜像外测试时行不通；
- **启动预热并进现有的 PGS 预热任务**：识别能力探测只是找包、看文件，不单开内置插件；
- **弹窗顶部提示**：同语种识别不调用 AI，「确认后才调用 AI」改为「确认后在后台用本地语音
  模型识别，不调用 AI」。

验证：

- 单元测试 `tests/api/test_subtitle_asr.py` 33 条（含真实模型 1 条，本机放了模型才跑），
  相关的现有字幕、PGS、文案、抽取测试全部通过；
- 本地端到端 `scripts/perf/e2e_subtitle_asr.py`：29 项检查全部通过（英语片识别后翻译、复用
  识别外挂、同语种零请求、日语片、识别中停止 0.8 秒生效且无残留进程）；
- 浏览器：确认框显示音轨候选、识别说明与预计时长；发起后字幕行显示「英语 · 识别 xx%」，
  完成后自动出现「英语 SRT」。

### 13.3 第二轮：复用、重新识别与崩溃恢复（§4.5）

起因：用户确认三件事——反复生成要复用已经识别出的结果；识别结果要登记成一条自动生成的外挂字幕；
只有主动选音轨并勾「重新识别」才重跑；重启、崩溃、断电时任务要可靠。

核对与补齐：

- **复用**：一期已经成立（识别外挂成为默认文本参考；选中音轨时外挂比视频新就复用）。补了完整度校验：
  半截外挂（断电）、洗版前的旧外挂不复用。
- **自动生成标记**：一期漏了。`is_ai_generated` 认 `asr` 后，三端播放器菜单都标机器生成；网页详情页的字幕
  列表标「语音识别」；按库语言自动选字幕时与 AI 字幕同等对待。
- **重新识别**：新增 `retranscribe`（§4.5）。识别过的文件在来源下拉里多出音轨一项（`on_request`，不参与默认
  选择）；网页选中它时出现「重新识别」勾选框。拿识别外挂当文本参考时，翻译提示同样说明原文是语音识别结果。
- **可靠性**：识别断点 + 从片头重放 VAD 的确定性续跑；WAV、识别外挂、翻译断点先 fsync 再改名；读音轨前清掉
  `.part` 残留；子进程 `PR_SET_PDEATHSIG`；复用时排队文案不再说「先读取音轨」。

验证：

- 单元测试 `tests/api/test_subtitle_asr.py` 46 条：断点的有效前缀 / 半截尾行 / 身份作废，假子进程崩溃后续跑，
  重新识别作废旧结果且任务重启不重复识别，半截外挂不复用，识别外挂当参考时提示模型，`on_request` 不改变默认选择与
  拦截结论，缓冲区不越过已读位置，真实模型续跑与不中断逐段相同；Linux 专用的「暂停中主进程被杀」用例在 NAS 上正反
  各跑一次（去掉 `PR_SET_PDEATHSIG` 时 5 秒内明确失败）。相关的现有字幕 / PGS / 文案 / 播放测试全部通过。
- 本地端到端 50 项全部通过，新增：A6 默认复用、勾选才重新识别并替换外挂；A7 识别到 30% kill -9 后端，子进程随即
  退出、断点 243 段，按租约自愈后从断点续跑，800 条与不中断一致、接缝无重复，不消耗重试次数；A8 优雅重启立刻续跑。

  - 识别到 42% 时先 SIGSTOP 子进程再 kill -9 后端：子进程被内核当场结束（0.00 秒），断点 91 段；约 30 秒后租约过期
    恢复，从 08:05 续跑，结果与不中断完整识别逐条相同（200/200，时间轴 + 文字）；
  - 识别到 40% 时 SIGTERM 优雅停机：重启后立刻续跑，结果同样 200/200 逐条相同。
