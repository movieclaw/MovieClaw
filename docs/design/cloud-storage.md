## 0. 起因与结论

用户反馈「不支持上传网盘」。网盘玩家的真实诉求是：**115 里已有的几十 TB 能直接看；新片不占 NAS 硬盘；在外面能看；
订阅到能看要快。** 上传只是手段。

同类工具（LitePan、SmartStrm、CloudDrive2 + MoviePilot……）的形态是「网盘 → strm 文件 → Emby」：strm、nfo、定时
扫网盘、刷新 Emby，都是因为下游媒体服务器是黑盒、只认文件。MovieClaw 从订阅、下载、入库到播放器全是自己的，这层
间接可以拿掉。

**结论（用户决策 2026-10-17）：**

1. **一个心智模型：媒体库的位置可以是本地文件夹，也可以是 115 上的文件夹。** 建库时根目录可以选 115 上的文件夹，和选本地文件夹一样
   ——选了 115 文件夹，里面已有的片子自动纳管进库（§4），以后订阅下载的新片自动上传到这里、本地自动腾空（§5、§6）。
   用户不需要理解「导入」「上传」「释放」「strm」这些概念。
2. **网盘是文件的存储位置，不是另一种条目。** 同一条台账（`library_file`）的字节可以在本地、在云端、或两边都有；
   条目、观看进度、规格、派生数据、订阅对账都不变。
3. **能在本地做的先在本地做。** 新片在本地时把规格、关键帧、字幕、缩略图、片头片尾都做完再上传；上云后全部保留。
   纳管来的片子没有本地字节，规格按预算在后台慢慢补，起播时还没补到就当场探（§4.4）。
4. **取流默认安全**（§7）：家里设备一律由 NAS 从网盘拉流再转发；在外面默认也走家里转发，只有自家 App、且同一时间
   只有一处在外面直连时才直连网盘（「自动」）。用户可改为「总是转发」或「总是直连」。
5. **不扫网盘**：纳管时列一次目录；之后靠 115 的操作动态增量感知变化，每周一次低频复查兜底（§4.3）。台账是事实来源。
6. **首期包含「上传后释放本地」**，也包含存量纳管。
7. **不考虑 Emby / Jellyfin 兼容**：不生成 strm、不写 nfo。（Jellyfin 兼容接口照常工作，取流走同一个入口，§7。）
8. **分两部分实施**：内核扩展（本文）在主仓库；每个网盘一个**存储后端插件**，放插件仓库。宿主管机制与安全底线，
   插件只管「怎么跟这家网盘说话」——与下载器适配器同一个形状。
9. **先让存量能看，再做上传**（§13）：里程碑一「115 里的片子能看」不涉及任何不可逆操作，还能先用真实播放把直链、
   转发、风控摸清；里程碑二再做上传与释放本地。

strm 不废弃：外部工具生成的 strm 照旧能导入、能播放（strm-playback.md），只是 MovieClaw 自己的 115 库不走 strm。

## 1. 与现有设计的关系

- **取代** plugin-extension-model.md §2.2 的推演（插件经 `ingest.staged` 上传后写 `.strm` 回库）。那条路规格和派生数据
  全丢，等于在自己的产品里重做一遍 Emby 玩法。`ingest.staged` 槽位保留，服务其他「整理后交给外部流转」的场景。
- **复用** strm-playback.md 的远程读取（直链作 ffmpeg 输入、按 Range 稀疏读、服务端转发、直链缓存与并发合并），以及
  plugin-strm-prefetch.md 的后台预探调度（补探顺序、按观看信号插队）。区别只在「直链从哪来」：strm 从文件内容来，
  115 库从存储后端来。
### 1.1 这是扩展点，主程序里没有 115

主程序新增的是一个**领域中立的扩展点「远端存储」**，形状与下载器适配器（downloader-adapters.md）一样：主程序管机制与
安全底线，插件管「怎么跟这家网盘说话」。

| 主程序（通用，不认识任何网盘） | 存储后端插件（每家网盘一个，放插件仓库） |
|---|---|
| 存储后端注册表与契约（§11）、账号与凭据加密、限速 / 预算 / 连接名额 | 登录（扫码、Cookie）、列目录、操作动态 |
| 文件的字节可以不在本地：台账、读源入口、转发 / 直连（§7） | 秒传、分片上传、核验用的哈希 |
| 库的位置可以是远端文件夹：纳管（按虚拟目录树识别）、变化处理（§4） | 取直链、移动、改名、删除、容量 |
| 上传与释放本地的编排、闸门、删除护栏、对账（§5、§6、§9、§10） | 能力声明（§11.1） |

- **没装任何存储插件时，产品与今天完全一样**：「115 网盘目录」入口、设置里的「网盘」页都不出现，取流、扫描、删除的行为不变
  （§14 的改动在 `local_bytes` 恒为真时都是原路径）。
- 界面上的网盘名、登录方式、登录端列表都来自插件声明，主程序不写死。
- **为什么这几块不能放进插件**：
  - 「字节在本地」是媒体库各处的默认假设（§14 列了几十处：取流、转码、字幕、扫描判缺失、回收站、删除）。插件改不了
    主程序的这些路径，只能绕开——绕开就是 strm 那条路（plugin-extension-model.md §2.2 的推演），规格与派生数据全丢。
  - 释放本地、删除云端是不可逆操作。按 library-boundary.md §1 的标准，安全底线归宿主，否则每个网盘插件各写一遍、
    迟早有人写错（#722 合集种子误删就是判断放在插件里的反例）。
  - 编排（何时上传、何时释放、怎么限速、播放优先）对所有网盘一样，放进插件就是每家重写一遍。
- 先例：下载器——订阅投递、做种、删种、路径映射在主程序，qBittorrent / Transmission 只是适配器插件。

### 1.2 领域归属

按 library-boundary.md §1 的标准：

| 部分 | 归属 | 理由 |
|---|---|---|
| 115 库、纳管、副本台账、指纹、取流、释放闸门、核验、删除护栏、对账 | 媒体库（宿主） | 不可逆数据操作与安全底线；所有端的核心流程都要用 |
| 存储账号、凭据加密、限速与配额、连接名额、调度、错误分类 | 宿主（新模块 `storage`） | 同上；对所有网盘一致 |
| 各家网盘协议 | 存储后端插件 | 对接外部第三方，名单长、变化快、每人只用一两家 |
| 本地释放后删种 | 获取领域（下载模块） | 媒体库不认识种子；下载模块订阅媒体库事件自己决定（§6.3） |

## 2. 用户看到的样子

**第一次用（两分钟）：**

1. 设置 → 存储 → 添加 115：扫码（登录端已默认选好，避开浏览器），或在已登录 115 的网页上点一下 MovieClaw 浏览器扩展。
2. 新建媒体库 → 根目录点「＋ 115 网盘目录」→ 在弹出的 115 目录树里勾选已有的文件夹（如 `影视/电影`）。沿用现有规则
   「第一个为主根，新内容落在这里」：主根是 115 文件夹，新片就上传到这里、本地自动腾空。
3. 库卡片显示「正在纳管：已识别 1,820 / 2,400」，几分钟后海报墙出现，点开就能播。

**之后什么都不用管：** 订阅下载的新片入库后立即能看（还在本地），后台上传到 115（多数秒传），传完核验、本地自动腾空；
用户在 115 App 里转存、移动、删除的片子，几分钟内反映到库里。

**已有的本地库**：编辑库时把主根换成 115 文件夹（二次确认迁移规模），存量按从新到旧逐个上传、逐个腾空，进度显示在库卡片上。

**只有三个选择，都有推荐默认值：**

| 在哪 | 选项 | 默认 |
|---|---|---|
| 库的根目录 | 本地文件夹 / 115 文件夹，可混用；主根在哪新片就去哪 | 建库时选；「本地也保留一份」在编辑库里 |
| 设置 → 播放 → 在外面播放 115 上的片子 | 自动 / 总是经家里转发 / 总是直连网盘 | 自动 |
| 存储账号卡片 → 同时播放数 | 数字 | 2（插件声明） |

限速、每日预算、上传上限都在账号卡片的「高级」里，默认值够用。

**界面影响面与样稿**：[mockups/cloud-storage-demo.html](mockups/cloud-storage-demo.html)（新增 2 处：设置 → 网盘、115 目录选择器；
修改 10 处：添加 / 编辑媒体库、库管理行、纳管报告、文件区、删除确认、任务中心、播放与下载器设置、播放器；海报墙、首页、搜索、
订阅不变）。根目录可以来自 115，沿用「第一个为主根，新内容落在这里」：主根在 115 即新片上传、本地腾空，建库时不再多问
「存储模式」；「本地 + 115 两边都留」只在编辑库里出现。

**界面一律陈述事实，不讲玩法**：文件位置标「本地」「本地 + 115」「115」；上传中显示进度与「秒传」；本地腾空后说明做种状态
（「38 GB 仍在做种，做种结束后自动删除」）；纳管不了的给原因（「原盘目录暂不支持」）。

## 3. 数据

### 3.1 存储账号 `storage_account`

| 列 | 说明 |
|---|---|
| `id`、`backend`（存储后端类型，如 `115`）、`name`、`remote_user_id` | 同一网盘用户只能有一个账号（扩展重复推送时更新它） |
| `credentials` | 加密 JSON（Cookie 或令牌、登录方式、登录端），只经宿主读写，不进任务输入、不进日志 |
| `status` | `ok` / `auth_expired`（要重新登录）/ `rate_limited`（带恢复时间）/ `api_broken`（接口异常，提示更新插件）/ `disabled` |
| `capabilities` | 插件声明的能力快照（§11.1），插件不在时界面仍能解释 |
| `qps`、`daily_budget`、`read_slots` | 限速、每日预算、同时播放数（服务器读网盘的连接名额），默认取插件声明，用户可改 |
| `change_cursor` | 操作动态的游标（§4.3） |
| `quota_total`、`quota_used`、`profile_at` | 容量与昵称，按天刷新 |

### 3.2 库的存储位置

不新增「存储模式」字段，由根目录推出：**主根是 115 文件夹** = 新片上传到它、本地释放（下文记作「115 库」）；主根是本地、
另有 115 根目录 = 新片留本地，115 目录纳管；全是本地 = 现状。唯一的开关 `library.keep_local`（默认假）：主根在 115 时本地
也保留一份（两边都留、当备份，不释放）。

**库的 115 文件夹** `library_cloud_folder`：`library_id`、`account_id`、`remote_dir_id`、`display_path`、`is_primary`
（新片上传到这里，每库一个）、`listed_at`（上次列目录时间）。一个库可以挂多个 115 文件夹，与本地库可以有多个根目录对应。

**本地暂存目录**：主根在 115 的库仍有一个本地根目录（沿用现有的库根），用途只有两个：新片入库后、上传完成前的落脚处
（硬链接入库时不占额外空间）；海报、字幕等旁车文件。建库时默认填好（与下载目录同盘的建议路径），用户一般不用管。

### 3.3 文件

- `library_file.local_bytes`（布尔，默认真）：本地 `file_path` 上有没有字节。**不新增 `state` 值**：「在位」的含义从
  「文件在本地」放宽为「我们拥有它」，库存、海报墙、订阅对账、观看统计的口径照旧。
- 纳管的文件 `file_path` = 本地暂存目录 + 它在 115 文件夹里的相对路径（一个本地不存在的「虚拟位置」），旁车文件放在这里，
  目录结构与 115 上一致；`local_bytes` 为假。
- 上传后释放的文件 `file_path` 不变，`local_bytes` 置假，另记 `local_released_at`。

### 3.4 文件指纹 `library_file_fingerprint`

`library_file_id`、`size_bytes`、`sha1`、`md5`、`head_sha1`（前 128 KB）、`source`（`local` 本地读出 / `cloud` 网盘列表给出）。
本地文件一次顺序读算齐（§5.1）；纳管的文件取 115 列表里自带的 SHA1，不读字节。用途：秒传、核验、重复判定、订阅判
「库里已有」、副本丢失时按指纹秒传恢复（§9）。

### 3.5 云端副本 `library_file_replica`

| 列 | 说明 |
|---|---|
| `library_file_id`、`account_id` | 一期每个文件最多一个副本 |
| `remote_id`、`remote_path` | 网盘文件 id（一切操作只认它）；路径只用于展示 |
| `origin` | `uploaded`（我们传的）/ `imported`（纳管来的） |
| `state` | `uploading` / `verified` / `lost` / `deleting` |
| `verified_at`、`checked_at` | 核验时间（纳管的以列表给出的大小与哈希为准）；最近一次对账时间 |

## 4. 网盘库与纳管（以 115 为例）

### 4.1 挂上一个 115 文件夹 = 纳管

用户在目录树里勾选文件夹（插件 `list_dir` 按需展开，不预先遍历）。确认后建纳管作业 `storage.import`：

1. **列目录树**：插件 `list_tree(dir_id)` 一次拉回整棵树的文件（文件名、相对路径、大小、SHA1、文件 id），115 有整树列举
   接口，几千个文件只要几次调用。
2. **识别**：按文件名与目录名走现有识别链（片名、年份、季集、TMDB），输入是「虚拟目录树」而不是本地文件系统——这是
   纳管里最大的一块改动（现有扫描直接读文件系统）。识别不了的进现有的「待识别」清单，用户在库里认领。
3. **入账**：直接写台账（`local_bytes` 为假）+ 副本（`origin = imported`、`verified`）+ 指纹（SHA1）。订阅对账、洗版基线
   立即把它们算作「库里已有」。
4. **报告**：「纳管 2,400 个文件：已识别 2,310，待认领 62，跳过 28（原盘目录 21、非视频 7）」。

- 外挂字幕（同目录的 `.srt` / `.ass`）记为待取，第一次播放或后台预算有余时取到本地暂存目录，之后就是本地旁车。
- **原盘（BDMV 目录、ISO）一期跳过并在报告里计数**：服务端原盘播放依赖本地按文件读取，远程读取未验证。
- 网盘上的目录结构和文件名**不动**：纳管只记账，不整理、不改名。

### 4.2 新片放哪

上传到库的主文件夹，按库的命名规范建子目录（与本地库一致：`片名 (年份)/…`、`剧名/Season 01/…`）。

### 4.3 变化感知：动态增量，不扫目录

- **操作动态**：插件 `changes(cursor)` 拉 115 的操作动态（上传、转存、移动、建目录、目录改名、删除），每 5 分钟一次、
  一次调用。只处理落在库 115 文件夹里的变化：新文件 → 识别入账；移走 / 删除 → 副本 `lost`（§9）；目录改名 / 移动 →
  更新 `remote_path`。我们自己的上传、移动按文件 id 认出来，跳过。
- **动态有盲区**：115 不记「复制文件」「文件改名」，第三方上传有时也没有记录。所以**每周一次低频复查**：对每个库 115 文件夹
  `list_tree` 一次，与台账按文件 id 对比补差。库卡片上另有「立即同步」按钮。
- 插件不支持操作动态时，只靠每周复查与手动同步。

### 4.4 纳管文件的规格与派生数据

- **规格**：后台按每日预算的一小部分逐个远程探测（复用 plugin-strm-prefetch.md 的调度：按播放下一集 → 收藏 → 打开详情
  插队）；起播时还没探到就当场探（与 strm 首播探测同一套）。
- **按需补的**：内封字幕、字体、关键帧索引、缩略图——第一次用到时按 Range 远程读，做完落本地缓存，以后不再远程读。
- **默认不做**的：片头片尾识别、刷片预切——要读大量字节，对只在云端的文件默认关闭（设置里可开，受预算约束）。

## 5. 上传

### 5.1 指纹

一次顺序读同时算 SHA1、MD5、前 128 KB SHA1。50 GB 在 NAS 机械盘上约 5～6 分钟，相对真传（50 GB 在 50 Mbps 上行要两个多
小时）可以忽略；秒传命中时省掉全部时间。读取走宿主的磁盘读限速，低优先级，不与播放抢盘。

### 5.2 任务

- 触发：主根在 115 的库有新文件入账（`library.file.created`）；主根从本地换到 115 时建回填作业，
  按入库时间从新到旧逐个建任务。
- 任务 `storage.upload`：指纹 → 建目录 → **秒传**（按指纹，可能要回答区间挑战）→ 不中则**分片续传** → **核验**（网盘返回的
  大小与哈希 == 本地指纹 → 副本 `verified`）。
- 去重键 = 文件；资源锁 = 存储账号（并发取能力声明）；**不持有媒体库资源锁**（几十 GB 的上传不能堵住扫描、整理、转移）。
- 续传状态（插件给的不透明 JSON）存任务状态，重启后续传。
- 结局：网络或限流 → 重试（限流按插件给的等待时长）；认证失效 → 阻塞（带「重新登录」动作，同账号任务一起阻塞）；
  空间不足 → 阻塞（带容量说明）；本地文件已变化（洗版、被删）→ 放弃，不算失败。

### 5.3 上行让路

上传读取经宿主的顺序读取器，**限速在宿主这一侧**：全局上传上限（默认不限）；有外网播放正经家里转发时，上传自动降到上限的
20%，播放结束 30 秒后恢复（依据播放会话的取流登记，不额外采样、不碰盘）。进程外插件读本地文件用路径授权（只读），每读一块
先向宿主领令牌（4 MB 一批），限速不可绕过。

## 6. 释放本地

主根在 115 的库自动释放；`keep_local` 为真时不释放。

### 6.1 闸门（全部满足才释放）

1. 副本 `verified`。**这是唯一不可逆的一步，任何一环没确认都不释放。**
2. **本地派生活都已完成**：派生活登记表（新注册表，各功能登记 `pending(file) -> bool`）里没有一项还在等这个文件——规格、
   关键帧索引、内封字幕、缩略图、片头片尾识别、刷片预切（开启时）。等太久（默认 24 小时）照常释放，没做完的按 §4.4 远程补。
3. 没有会话正在读这个本地文件（播放、转码、离线导出）。
4. 释放前再核一遍：本地大小与指纹记录一致；`stat(remote_id)` 仍在且大小一致。

### 6.2 动作

**先记台账、再删文件**：先提交 `local_bytes = false` 与 `local_released_at`，再删库内文件（旁车不删）；删失败就改回。
顺序反过来不行——实时监控收到删除事件会立刻触发范围扫描，看到还标着本地在的行就会把它标成缺失（§14.3）。
然后发事件 `library.file.local-released`（文件 id、释放的字节数、是否仍有其他硬链接）。

### 6.3 空间什么时候真正回来

- **复制入库**：删了就回来。
- **硬链接入库**：库文件与下载目录是同一份数据，还在做种。下载模块订阅 `library.file.local-released`，对来源种子尝试删种，
  条件复用删除参与方的判断（`services/remove_source.py` 的 `_skip_reason`，执行时重新校验）：是 MovieClaw 投递的、种子不再
  供着库里其他本地文件、删种否决钩子不反对、不是 H&R 种子。下载设置里一个开关「文件上传到网盘后自动删除下载任务」（默认开）。
- **H&R 现在只是一个布尔值**，没有做种时长、分享率的达标判断：一期 H&R 种子一律不自动删，库卡片列出「因 H&R 保留 N GB」；
  做种达标策略另起设计。

## 7. 取流

### 7.1 统一读源入口

现在读字节的地方都按扩展名分叉本地与 strm（`streaming.media_input` / `parse_strm` / `open_strm_range`）。改为按**台账**判断：

```
file_source(file) ->
    Local(path)                                     本地字节在
  | Cloud(account_id, remote_id, capabilities)      只在云端，副本 verified
  | Strm(...)                                       外部 strm（现状）
  | Unavailable(reason)                             副本 lost / 账号要重新登录 / 插件没在运行 …
```

**不能借用 `is_strm`**：strm 分支按「路径以 `.strm` 结尾、本地有这个 strm 文件」判断，115 库的文件一个都接不住（§14.1）；
strm 的那些规则（不探规格、不挑字幕）也是为「没有规格和派生数据」设计的，对上传的文件不合理。

### 7.2 三种取流方式

| 方式 | 字节怎么走 | 网盘看到 | 代价 |
|---|---|---|---|
| **家里转发** | NAS 从网盘拉，再发给播放器 | 只有家里一个 IP、一个可控的连接数 | 在外面看时受家宽上行限制，超过时按现有远程播放规则降码率转码——与在外面看本地片完全一样 |
| **直连网盘** | 302 到网盘直链，播放器自己去拉 | 播放器所在的 IP | 不占上行；但多地 IP 有被判共享的风险，第三方播放器跟随跳转时可能丢 UA 导致 403，连接数不可控 |
| 本地 | 本地文件（现状） | — | — |

**家里的设备一律走家里转发**（本地有就读本地）：同一个出口 IP，不占上行，UA 由服务器统一。

**在外面**按设置：

- **自动（默认）**：本地有字节就读本地；没有时，**只有自家 App（iPhone / Mac / Apple TV / Android / Android TV）**、且
  **这个账号此刻没有别处在外面直连**，才直连网盘；其余一律家里转发。效果是任何时刻最多「家里 + 一处在外」两个 IP 访问网盘，
  第三方播放器永远不直连（不会出 403）。
- **总是经家里转发**：从不 302，网盘只见家里。
- **总是直连网盘**：除离线下载外都 302（本地也保留了一份的文件，在外面也优先直连网盘，换取不受上行限制的码率）。

**直连失败的平滑降级**：302 之后播放器直连网盘，服务器看不到它的失败，所以只有自家 App 能降级——直连起播失败（403、
连接被重置、超时）时，App 带 `relay=1` 重新请求同一个取流地址，服务端改走转发并在这个会话里不再给直链。第三方播放器做不到，
所以「自动」不给它们直链。

- 内网 / 外网按请求对端地址判断（经 nginx 前门取受信的转发地址）：环回、私网、链路本地、IPv6 ULA 算家里；其余（含 Tailscale
  的 100.64/10）算在外面——字节都要走家宽上行。
- 网页播放器：浏览器 `<video>` 跟随 302 跨域是否可播【待实测】，测过之前按第三方处理（转发）。
- 离线下载（iPhone）一律转发：后台下载跟跳转会把设备令牌带给网盘。
- 插件声明直链不是原画（`original_link = False`）时不直连。

### 7.3 转发的效率

- **连接名额**：服务器读网盘的并发连接按账号封顶（`read_slots`，115 默认 2），播放、转码、字幕、离线导出共享，播放优先。
  一路播放占一个连接、顺序读并预读（8～32 MB 缓冲），拖动进度复用这个名额重开连接，不额外开。
- **满了怎么办**：后台读排队；新起播等几秒仍没有名额就报清楚的原因——「115 同时播放数已满（2），可在存储设置里调整」，
  不让用户面对莫名其妙的失败。
- **直链缓存**：服务器取链用插件默认 UA，按（账号、文件）缓存插件给的时长（最长 1 小时），同文件并发只取一次；给播放器
  直连的链接按（账号、文件、UA 类别）另存。删除、移动、洗版时主动作废。
- 多人同看一部片**不做**数据块共享：播放位置几乎不重合，命中率低；连接名额已经解决了「同片并发」的风险。

## 8. 配额与调度

所有对存储后端的调用都经宿主的包装（主进程与进程外运行一致）：

- **超时**：每次调用有硬超时（取直链 8 秒、元数据 30 秒、列目录树 120 秒；上传按分片大小放宽）。插件卡死拖不住宿主。
- **按账号限速 + 每日预算**，三个优先级：① 播放（取直链、起播探测）② 用户操作（删除、移动、手动同步）③ 后台（纳管、
  上传、规格补探、动态拉取、复查）。后台用量到预算的 70% 就停，余量留给播放；限流时后台整体推迟，播放照常尝试。
- **为什么不生成 strm 反而更不容易被风控**：风控看的是接口调用的量和形态。strm 玩法里最耗调用的——定时全量扫网盘目录、
  媒体服务器对每个 strm 取链探测、远程抽字幕和缩略图——这里要么没有，要么按预算摊开：

  | 来源 | 量级 | 对策 |
  |---|---|---|
  | 纳管 | 每个文件夹几次（整树列举） | 一次性；后台优先级 |
  | 变化感知 | 每 5 分钟 1 次 + 每周每文件夹几次 | 动态增量，不扫目录 |
  | 纳管文件规格补探 | 每文件 1 次取链 + 几次 Range | 每日预算的一小部分；起播插队 |
  | 上传 | 每文件 1～3 次 | 后台优先级、目录 id 缓存 |
  | 播放 | 每次起播 1 次取链 | 缓存、并发合并；转发时网盘只见家里 |
  | 对账抽检 | 每天预算的一小部分 | 30 天轮一遍 |

## 9. 对账

- 台账是事实来源；纳管与复查以外不列目录。
- 低频抽检：每天用后台预算的一小部分对 `verified` 副本逐个 `stat`，30 天轮一遍；播放或读取遇到 `NotFound`、或操作动态
  报告删除时立即处理。
- 发现不见了：副本 `lost` →
  - 本地还在：重新上传；
  - 只在云端：**先按指纹秒传恢复**（网盘去重池里多半还有）→ 失败则文件标 `missing`（现有语义：缺失提醒，用户可在缺失清单
    里重新下载）。用户若从 115 回收站还原了文件，下次复查会认回来。
- 用户在 115 里移动、改名库里的文件不影响播放（只认文件 id），动态或复查更新显示路径。
- **库扫描要认只在云端的行**（§14.3）：判缺失、库根移除时批量标缺失、自动清除缺失行都跳过 `local_bytes` 为假且副本
  `verified` 的行；**改名归并（`_try_relink`）不得把这些行当候选**——否则重新下载同一版本时，新文件会按「同尺寸、旧路径
  不在」被认成改名，劫持这一行。

## 10. 删除、回收站、转移、洗版

**语义与本地库一致**：本地库里删片会删本地文件，115 库里删片会删 115 上的文件。不论是上传的还是纳管的，都一样。

- **只按台账里的文件 id 删**，绝不按路径、按目录删；只有两种情况会删云端：用户在删除对话框里确认的删除、回收站清理
  （到期或手动）。纳管、同步、复查、对账**永远不删云端文件**。
- 删除对话框写清楚「将从 115 删除（进入 115 回收站）」；115 有回收站，这是第二道保险。
- **回收站**：库文件进回收站时云端不动；清理时删云端。
- **批量护栏**：一次涉及的云端文件超过 50 个或 200 GB 时，暂停并在任务中心等管理员确认（SmartStrm #37：改顶层目录名触发
  同步删除，批量删掉一大片）。
- **把 115 文件夹从库里移除**：只删台账，不动 115 上的任何东西。
- **条目转移 / 整理改名**：本地在时照现状搬本地，云端跟着 `move` / `rename`；只在云端时只改台账与云端。纳管的文件不主动整理。
- **洗版**：新版本照常入库、上传、核验；旧文件按现有规则进回收站，清理时删云端。
- 现有代码有几处把「本地不存在」当成「已经删掉了」然后删台账行，会让云端文件变成孤儿；§14.2 列了位置，都要先看副本。

## 11. 存储后端契约（`movieclaw_sdk.storage`）

### 11.1 登记

注册表 `storage-backends`（`EXPERIMENTAL`），登记项 `StorageBackendAdapter`：`type`（全局唯一）、`title`、`factory(account_context)`、
`login`（登录方式：`qrcode` 扫码 / `cookie` 浏览器扩展导入或粘贴 / `oauth_redirect` 跳转授权；可多种）、`login_options`
（如 115 的登录端列表与默认值）、`cookie_domains`（接收浏览器扩展推送的域名，如 `115.com`）、`capabilities`：

| 能力 | 说明 |
|---|---|
| `writable` | 能不能写（不能写的盘一期不支持） |
| `rapid_upload_hashes`、`range_challenge` | 秒传用哪些指纹；会不会要求回答任意区间的哈希 |
| `list_hashes` | 列目录时给不给哈希（纳管的文件能不能直接带指纹） |
| `change_feed` | 有没有操作动态（§4.3） |
| `original_link`、`link_needs_ua` | 直链是不是原画；是否按取链时的 UA 签发 |
| `recycle_bin` | 删除是否进网盘回收站 |
| `default_qps`、`default_daily_budget`、`default_read_slots`、`upload_concurrency`、`max_file_bytes` | 默认值与上限 |

### 11.2 方法（`BaseStorageBackend`）

| 方法 | 用途 |
|---|---|
| `login_start(method, options)` / `login_poll(handle)` / `login_complete(params)` | 扫码或跳转授权；成功交回凭据与网盘用户 id |
| `login_with_cookie(cookie_header)` | 扩展推送或粘贴的 Cookie：挑出需要的几项、校验，交回凭据与网盘用户 id |
| `account_info()` | 昵称、会员、容量 |
| `list_dir(dir_id)` | 目录选择器按需展开（只列子目录与数量） |
| `list_tree(dir_id)` | 整棵树的文件：相对路径、大小、哈希、文件 id（纳管、复查） |
| `changes(cursor)` | 操作动态增量（可选） |
| `ensure_dir(rel_path)` | 逐级建目录，返回目录 id |
| `rapid_upload(dir_id, name, fingerprint, size, challenge)` | 秒传；不中返回 None，可附带续传状态 |
| `upload(dir_id, name, source, resume_state, on_state, on_progress)` | 真传，断点续传 |
| `stat(remote_id)` | 大小、哈希、名字（核验、对账） |
| `direct_link(remote_id, user_agent)` | 地址、可复用秒数（不带请求头） |
| `move` / `rename` / `delete(remote_ids)` | 删除有回收站就进回收站 |

插件拿不到数据库、拿不到别的账号；本地文件只能经宿主给的读取器（或路径授权的只读库根）读。

### 11.3 凭据

宿主创建实例时注入解密后的凭据。插件刷新令牌后**把新凭据作为调用结果的一部分交回**，宿主先落库再交给调用方——滚动刷新的
令牌用一次就换新，先用后存会在崩溃时丢失登录态。

### 11.4 错误分类

| 异常 | 宿主怎么处理 |
|---|---|
| `RateLimited(retry_after)` | 该账号后台推迟；任务重试 |
| `RiskControl` | 同上，推迟更久（默认 1 小时），设置页提示 |
| `AuthExpired` | **只有这一种**要求重新登录：账号 `auth_expired`，相关任务阻塞 |
| `ApiChanged` | 接口不认识了（网盘改版）：账号 `api_broken`，提示更新插件 |
| `NotFound` | 副本 `lost`（§9） |
| `QuotaExceeded` | 上传阻塞，提示容量 |
| `Conflict` | 同名已存在：插件先按内容判同（同大小同哈希视为已传） |
| `Transient` | 重试 |

### 11.5 浏览器扩展导入 Cookie

MovieClaw 浏览器扩展本来就能读当前网页的 Cookie（含 httpOnly）推给宿主（`POST /api/v1/extension/cookies`），现在只认 PT 站点，
其他域名返回「未匹配到任何受支持的站点」。**扩展本身不用改**，宿主侧：

- **推送分发**：先按 PT 站点匹配；没匹配上时查存储后端的 `cookie_domains`，命中就交给存储模块（领域中立的「Cookie 接收方」
  分发，以后别的插件要收 Cookie 也走这里）。
- **存储模块**：调 `login_with_cookie` 校验，得到网盘用户 id。已有同一用户的账号 → 更新凭据（扩展开着自动同步时，浏览器里
  重新登录后会自动推过来，账号自己恢复）；没有 → 新建账号，扩展弹窗显示「已添加为存储账号：昵称」。
- 只存插件挑出的那几项，不存整页 Cookie；加密、不进日志。

### 11.6 进程外运行

照下载器适配器（downloader-adapters.md §4）：子进程按（登记 id、账号）缓存实例；宿主登记代理逐方法转发；读取器在子进程侧
用路径授权直接读，限速令牌经 IPC 领取。

## 12. 不在一期

- 原盘（BDMV 目录、ISO）纳管与远程播放。
- 按看过与否、空间水位的本地淘汰；只在云端的片子按需回拉本地。
- 网盘离线下载当下载器（订阅公开资源先交网盘离线）。**PT 私有种子永远不能交给网盘离线**（会把 passkey 交出去，违反站规）。
- 多副本（两个网盘互为备份）、跨盘转存；纳管文件的整理改名。
- 多人同看的数据块共享缓存。
- 开放平台登录（先走 Cookie）。115 开放平台用设备码 + PKCE，只要 AppID、不要密钥，不需要令牌中转服务；资质以后再办。
