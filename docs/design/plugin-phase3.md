# 插件体系第三阶段：第三方插件（进程外运行）

> 状态：实施中（2026-10-09）。C0～C4 已合并；§9 决策已拍板，C5～C8 待做。总体模型见 `plugin-extension-model.md`，内核见
> `plugin-kernel.md`（§3.1 插件分层、§5.3 可跨进程约束、§8 开发体验目标形态），底座见 `plugin-phase2a.md`、
> `plugin-phase2b.md`。第四阶段（客户端界面扩展）不在本文范围。

## 0. 目标与验收

第三方开发者写的插件，用户下载一个包、看清它要什么权限、点同意就能装上；插件**默认在独立进程里运行**，崩溃、
卡死、内存泄漏都只伤它自己；升级失败自动回滚；连续把应用拖垮会被自动隔离。

**验收（沿用扩展模型 §5）：二 A / 二 B 的验收插件（删片联动、片单订阅、关键字规则、网盘上传）原封不动改成进程外
运行，端到端测试参数化跑两遍（进程内 / 进程外），行为一致。**「运行位置对插件透明」是这一阶段唯一的硬指标。

## 1. 现状要点（调研结论）

| 事实 | 位置 | 影响 |
|---|---|---|
| 实验级以上契约已满足可跨进程约束：方法 async、载荷是冻结模型 / 基本类型，有自动检查 | `plugin-kernel.md` §5.3、`tests/kernel` | 宿主侧可以**通用地**为监听器、钩子生成代理，不必逐个手写 |
| 插件凭证 `mcpl_` 只存在内存、绑定条目生命周期 | `services/auth.py:813` | 进程外插件沿用：宿主每次拉起进程现签一枚，经环境变量交给子进程，进程退出即作废 |
| 宿主操作走 ASGI 进本进程；对进程外插件就是普通 HTTP | `services/host_ops.py` | 进程外直接打 `http://127.0.0.1:<端口>/api/v1`，鉴权、按操作授权、归因全部复用 |
| 可靠事件是库表 + 每消费者游标 + 重试 + 死信 | `services/durable_events.py` | 宿主侧代理监听器把事件转给进程、等它确认；进程挂了代理抛错 → 原有重试 / 死信语义原样生效 |
| 钩子单个监听器 2 秒、整链 5 秒超时，超时走默认实现 | `hooks.py` | 进程外钩子多一次往返（本机 WebSocket，毫秒级）；进程卡死 → 超时 → 默认实现，决策不被拖住 |
| 插件路由挂在宿主路由器、鉴权由宿主注入 | `services/plugin_routes.py` | 进程外插件的路由由宿主反向代理到插件进程（Unix 套接字），鉴权仍在宿主 |
| 容器以 root 运行；NAS 内核 4.4（没有 landlock，多半不能用非特权用户命名空间）；镜像 Python 3.12 | NAS 实测 | 文件系统隔离只能靠「换 uid + 宿主文件接口」，见 §6、§9 |
| 本地受信插件已能从 `data/plugins/` 加载单文件或包，按 `plugins.yaml` 显式开启 | `plugins/local.py` | 第三方包的安装目录与之并列；`plugins.yaml` 继续作为「用户批准」的落点 |

## 2. 插件包

```
acme-group-blocklist-0.1.0.mcplugin      ← zip
├── movieclaw-plugin.toml
├── group_blocklist/…                    ← 插件代码
└── vendor/…                             ← 依赖（纯 Python 或 cp312 对应平台的 wheel 解包）
```

```toml
[plugin]
id = "acme.group-blocklist"     # 全局唯一，小写；路由、数据、日志都按它隔离
title = "发布组黑名单"
version = "0.1.0"
entry = "group_blocklist:plugin"
runtime = "process"             # 默认；"inline" 需要用户单独批准（等同本地受信插件）
sdk = ">=1.0,<2"                # movieclaw_sdk 版本区间

[requires]                      # 用到的契约与版本区间（服务、注册表、事件、钩子）
"subscription.candidates.filter" = "^1.0"

[permissions]
operations = ["search.titles", "subscriptions.create"]   # 宿主操作；危险操作必须逐个列出
paths = [{ path = "staging", mode = "read" }]            # 路径授权，见 §6
network = true                                           # 是否需要直连外网（仅声明、提示用户）
```

- **依赖只能随包携带**（`vendor/`），安装时不跑 pip：NAS 外网不稳定、装出来的环境不可复现、pip 本身就是
  任意代码执行。打包工具负责把依赖解包进去并校验平台标签。
- 包内不许出现绝对路径软链、`..` 路径、设备文件；单包上限（建议 50 MB）。

## 3. 安装、升级、回滚、卸载

目录：`data/plugins/packages/<id>/<version>/`，`data/plugins/packages/<id>/current` 指向当前版本（与应用自身的
overlay 更新同一套「版本目录 + 原子切链」做法）。

1. **上传 → 校验**：清单字段、id 与版本格式、`sdk` 区间与宿主的 SDK 版本、`requires` 里的契约是否存在且版本兼容
   （复用内核 `check_requires`）、权限声明是否合法（操作在目录里、路径别名已定义）。不兼容直接拒绝并说明原因。
2. **展示权限 → 用户批准**：批准结果写进 `plugins.yaml`（`grants`、`paths`、`runtime`），与本地受信插件同一个落点。
   升级时权限扩大必须重新批准，否则保持旧版本。
3. **解包 → 切链 → 挂载**：先解到 `<version>.partial` 校验后改名；切 `current`；运行中挂载（二 B 的运行中启停）。
4. **激活失败自动回滚**：新版本在宽限期内（建议 2 分钟）进入 `FAILED` 或进程反复崩溃 → 切回上一个版本并重新挂载，
   系统通知说明原因；坏版本打标记，不再自动尝试。
5. **卸载**：释放条目、删版本目录；插件数据（`plugin_data`、签名密钥）默认保留，「连同数据删除」需要单独确认。

接口：`app.plugins.packages.{list,upload,approve,discard,rollback,uninstall}`（管理员；批准、回滚、卸载是危险操作，
命令行逐次确认），CLI 自动获得 `mclaw app plugins packages …` 命令（上传走 `--file`）；网页入口在 C8。

C5 实现要点：

- 批准结果与安装记录存在 `data/plugins/packages/state.json`，不写用户手写的 `plugins.yaml`；上一版以完整快照保存，回滚不依赖再解析清单。
- 批准时宿主操作须与插件申请的**完全一致**（显式同意，不能多也不能少）；申请进程内运行须额外 `allow_inline=true`。批准前重新做一遍兼容检查。
- 自动回滚两条路径：挂载即失败（启动报错、读不出声明）；或挂上后 2 分钟宽限期内进入失败 / 进程崩溃到停止重启。回滚后坏版本记入 `bad_versions`、目录删除、发一条待处理事项；首次安装失败则撤销安装记录。
- 只保留当前版与上一版两个目录。进程内运行的包按 `movieclaw_packages.<条目 id>.<模块>` 导入，避免与别的包重名；`vendor/` 加入导入路径。
- 启动时加载已安装的包（来源记为 `package`，按第三方对待），计入安全模式；安全模式退出时一并挂回。

## 4. 进程外运行器

### 4.1 拓扑

```
主进程（宿主）                                         插件进程（每个插件一个）
  RemoteEntry（内核里的普通条目）                         python -I -m movieclaw_sdk.runner
    ├─ 拉起 / 监管子进程（退避重启）                       ├─ 导入 entry，调用 apply(RemoteContext)
    ├─ WebSocket 会话 ◀──────────────────────────────▶  ├─ RemoteContext：on / contribute / use / task / effect
    ├─ 为插件的每个 on / contribute 在真实 ctx 上登记代理  ├─ 宿主操作：直接 HTTP（mcpl_ 令牌）
    └─ 反向代理插件路由 ──Unix 套接字──────────────────▶  └─ 插件路由：进程内 ASGI，监听 Unix 套接字
```

- **宿主侧是一个普通内核条目**：`RemoteEntry.apply` 拉起子进程、等握手、把插件声明的监听器和贡献项**以代理的形式**
  登记到真实的 `ctx` 上。于是事件分发、钩子超时与熔断、可靠事件的重试 / 死信、注册表覆盖栈、卸载回收——全部是
  现成的内核行为，进程外只是「代理背后是另一个进程」。
- **插件侧的 `RemoteContext`** 与内核 `Context` 同名同签名：插件代码不分运行位置（§0 的硬指标）。

### 4.2 协议（每行一条 JSON；本机子进程走标准输入输出）

传输与协议分开：本机子进程用标准输入输出管道（私有、不占端口、不需要凭证出进程，测试里也能跑）；
将来 `mclaw plugin dev` 远程开发用 WebSocket（`mcpl_` 令牌鉴权）承载同一套消息。插件的 `print` 被改到标准错误，
宿主按行收进日志。C2 已实现的消息：

| 方向 | 消息 | 说明 |
|---|---|---|
| 插件 → 宿主 | `hello{sdk, entry, title}` | 握手；宿主核对与安装记录一致 |
| 插件 → 宿主 | `on{event, id, mode}` / `contribute{registry, id, item}` / `ready` | `apply` 期间的声明，`ready` 之后宿主才把条目标为 ACTIVE |
| 宿主 → 插件 | `call{call_id, kind, target, payload}` | 投递事件、调用钩子、执行任务、请求路由以外的回调 |
| 插件 → 宿主 / 宿主 → 插件 | `next{call_id, payload?}` / `next_result{call_id, ok, result}` | 钩子里调用 `next()`：宿主替它跑下游（可带改过的载荷），结果再送回去——与进程内语义完全一致 |
| 插件 → 宿主 | `reply{call_id, ok, result \| error}` | 结果按契约的结果类型校验；非法 = 当作监听器出错 |
| 插件 → 宿主 | `log{level, message}` / `health{key, ok, message}` / `progress{job_id, …}` | 日志带条目 id 进宿主日志；健康走 `PLUGIN_HEALTH` |
| 双向 | `ping` / `pong` | 15 秒无响应视为卡死 → 杀进程、重启（C2 先靠单次调用时限兜底：钩子 2 秒、普通事件 30 秒） |

载荷就是契约里的冻结模型 `model_dump(mode="json")`，两端用同一个模型类校验（SDK 与宿主同源）。

### 4.3 各类贡献怎么代理

| 插件里写的 | 宿主侧代理 |
|---|---|
| `ctx.on(LIVE 事件 / 钩子)` | 在真实 ctx 上登记一个 async 监听器：发 `call`、等 `reply`；钩子里插件调 `next()` 时经 `next` 消息让宿主跑下游 |
| `ctx.on(可靠事件, id=…)` | 登记到 `DURABLE_EVENTS`，代理等插件确认才算成功；进程不在 → 抛错 → 原有重试 / 死信 |
| `ctx.contribute(JOB_HANDLERS, …)` | 代理处理器：发 `call{kind: job}`，插件侧拿到一个 `JobContext` 代理（进度、取消、`JobRetry` / `JobBlocked` 以结构化错误回传） |
| `ctx.contribute(INGEST_STEPS / SITE_DATA_PACKS / …)` | 纯数据项，原样贡献（数据包目录换成插件包内的路径） |
| `PLUGIN_ROUTES.mount` | 插件在进程内建 ASGI 应用并监听 Unix 套接字；宿主按区挂一个代理路由（鉴权、验签仍在宿主），OpenAPI 取插件进程导出的片段合并 |
| `PLUGIN_DATA` / 签名链接 | 宿主端点 `/api/v1/plugin-runtime/data/*`，按令牌限定到本插件 |
| `ctx.task(...)` | 就在插件进程里跑；进程退出即全部结束（天然无泄漏） |

**内部契约**：第三方本来就碰不到；进程外再加一道——代理只为实验级以上契约生成。

### 4.4 监管

- 拉起：`python -I -m movieclaw_sdk.runner`，工作目录是插件版本目录，`PYTHONPATH` = 包根 + `vendor/`，环境变量只给
  宿主地址、令牌、条目 id、数据目录（插件专属），**不继承**宿主的环境（主密钥、数据库地址、代理凭据一律不给）。
- 资源上限：`RLIMIT_AS`（默认 512 MB，可在清单申请、用户批准）、`RLIMIT_NOFILE`、CPU 不设硬限（NAS 上 nice 19）。
- 崩溃：指数退避重启（1 s → 2 s → … → 60 s）；10 分钟内崩溃 5 次 → `FAILED`，系统通知，停止重启，等用户处理。
- 卸载 / 重载：发 `dispose`，5 秒宽限后 `SIGTERM`，再 5 秒 `SIGKILL`；令牌作废、代理全部撤销（内核 effect 自动完成）。
- 「进程内代码热重载不可靠」在这里不存在：重载 = 重启进程。

## 5. 安全模式

与镜像入口脚本的「坏版本」判定配合（`docker/entrypoint.sh`：overlay 启动后 60 秒内退出、1 小时内连续 2 次 → 标坏回落）。
两者判断的对象不同：入口脚本判应用版本，安全模式判插件。**安全模式的阈值必须比入口脚本低一级**，诊断顺序才对：

1. 生命周期开始时在数据目录写一条「启动中」记录（时间、本次加载的本地 / 第三方插件）；应用就绪并稳定运行 60 秒
   后清掉；正常停机（收到停止信号、走完关闭流程）也清掉。
2. 启动时发现上一条「启动中」记录还在（1 小时内）、且那次加载过插件 → **本次跳过全部本地 / 第三方插件**，进入
   安全模式：系统通知「已进入安全模式」，诊断页可见，并列出被跳过的插件。
3. 跳过插件后应用稳定了 → 问题在插件，保持安全模式直到用户在诊断页「退出安全模式」（当场挂载被跳过的插件；
   再崩就再进安全模式）。跳过插件后应用还是起不来 → 不是插件的问题，入口脚本的第 2 次失败照常把坏版本回落。
4. 断电、OOM 这类不洁关机若恰好发生在启动后 60 秒内，下次会误进安全模式；代价是用户点一次「退出」，可以接受。
5. 手动入口：环境变量 `MOVIECLAW_SAFE_MODE=1`（只能改环境变量退出），或数据目录放一个 `SAFE_MODE` 文件。

## 6. 路径授权与隔离（方案 A，§9 决策 1）

### 6.1 NAS 实测约束

容器里数据目录 `/app/data` 是 `0700`、属主 1026（NAS 用户），主进程靠 root 的 `CAP_DAC_OVERRIDE` 才能访问；overlay 部署的代码
也在它下面（`/app/data/updates/versions/...`）。换成非特权 uid 的插件进程**什么都读不到**，而改数据目录权限会影响 NAS 宿主上的共享目录，
不做。所以：

- 代码：启动插件进程前，把宿主正在运行的那份后端源码（约 22 MB）与插件代码复制到一个对插件 uid 可读的运行目录
  （`/tmp/movieclaw-plugins/`，按内容指纹缓存，同一次启动只复制一次）；`/venv` 本来就对所有用户可读。
- 插件**没有**可直接写的持久目录：持久状态用插件数据（`PLUGIN_DATA`），文件一律经宿主文件接口；另给一个本次运行有效的临时目录。

### 6.2 文件接口 `PLUGIN_FILES`

- 授权：插件包清单 `[permissions] paths = [{ path = "library", mode = "rw" }, …]`，本地插件在 `plugins.yaml` 的 `paths`；用户批准后生效。
  别名：`library`（全部媒体库根目录）、`library:<id>`、`staging`（导入规则的自定义目录）、`plugin`（`data/plugins/data/<条目 id>/`，
  总是可读写、只属于它自己）；本地插件与批准时还可以写绝对路径（例如网盘挂载点）。
- 检查：先 `realpath` 再判断落在哪个授权根之下、读写模式是否允许（软链接逃逸无效）；每次调用现算别名（库根路径改了立即生效）。
- 进程外：`open` 由宿主检查后打开文件，经一条专用的 Unix 套接字把**文件描述符**递给插件（`SCM_RIGHTS`），插件直接读写，
  大文件没有中转与拷贝开销；`stat / listdir / makedirs / rename / remove` 走普通 RPC。进程内运行的插件用同一个接口、同一套检查。
- 取流：插件路由返回 `files.response(path)`——进程内就是带授权检查的 `FileResponse`；进程外是一个
  `X-MovieClaw-Sendfile` 响应头，宿主代理拦下后检查授权、自己发送文件（支持 Range），插件进程碰不到字节。

### 6.3 进程（宿主是 root 时生效；开发机 / CI 非 root 时跳过并记日志）

- 以非特权 uid 运行（默认 65534 `nobody`，`MOVIECLAW_PLUGIN_UID` 可改），不带附加组；工作目录是运行目录里的插件代码。
- 资源上限：`RLIMIT_NOFILE` 1024、`RLIMIT_CORE` 0、`nice` 10；内存上限（`RLIMIT_AS`）默认不设（多线程的虚拟地址空间远大于实际占用，
  设小了会误杀），插件清单可申请、用户批准后再加。
- 环境变量与 C2 一样只给最小集合；不继承任何文件描述符（除协议管道与文件套接字）。

### 6.4 拆分

- C6a：`PLUGIN_FILES`（授权、检查、进程内实现、进程外描述符传递、`files.response`）；示例插件改用文件接口与插件数据。
- C6b：非特权 uid、运行目录复制、资源上限；NAS 上验证「读不到未授权路径、拿不到主密钥文件、超限被限制」。

## 7. 开发者工具链

- `movieclaw_sdk`：宿主镜像自带；= 内核公开 API（`plugin`、`Context`、`Event`、`KernelHarness`）+ 实验级以上契约
  （钩子模型、领域事件、服务键）+ 进程外运行器。契约目录与表面快照（二 B 留下的 §5.4）在这里落地，CI 比对。
- `mclaw plugin dev ./my-plugin`：在开发机上以进程外方式把插件连到正在运行的 MovieClaw（本机或 NAS），用管理员
  现签的开发令牌；文件一改就重启插件进程。
- `mclaw plugin pack`：校验清单、解包依赖进 `vendor/`、检查平台标签、产出 `.mcplugin`。
- 示例插件全部改为可打包的形态，作为样板。

| C3 | 可靠事件、宿主操作、插件数据、健康经运行器 | 删片联动、关键字规则参数化进程外跑通 |
| C4 | 任务处理器（进度 / 取消 / 重试 / 阻塞）、纯数据注册表、路由反向代理与签名链接 | 片单订阅、网盘上传参数化进程外跑通 |
| C5 | 插件包：校验、安装 / 批准 / 升级 / 回滚 / 卸载接口与 CLI | 坏包拒装；升级激活失败自动回滚；卸载保留数据 |
| C6 | 隔离：路径授权与宿主文件接口（C6a）；独立 uid、运行目录、资源上限（C6b），见 §6 | 未授权路径读不到；拿不到主密钥文件；示例插件在隔离下照常跑通 |
| C7 | 开发者工具链：`movieclaw_sdk` 契约快照、`mclaw plugin dev` / `pack` | 外部目录里的插件经 `plugin dev` 连上 NAS |
| C8 | 「模块」页演进为插件管理页：上传、权限批准、升级 / 回滚 / 卸载 | 浏览器里走完安装 → 批准 → 运行 → 卸载 |

C3 的实现要点：主进程不导入插件代码，启动前用子进程跑一次 `runner --describe` 读出插件声明（标题、注入的服务、
宿主操作），据此构造精确的内核条目（依赖顺序、授权都与进程内一致）；插件发起的服务调用带上「正在处理的宿主调用」，
宿主在那次调用的上下文里执行，发起方、因果链、可靠事件的投递信息原样沿用。

C4 分两部分：先做注册表贡献（任务处理器跨进程执行，进度 / 取消查询经协议交给宿主的真实 `JobContext`，
`JobRetry` / `JobBlocked` / `JobFailed` / `JobCancelled` 原样还原，进程不在时转为「稍后重试」；入库槽位步骤、站点数据包
这类纯数据项原样贡献）；插件路由需要流式反向代理（网盘取流是几 GB 的 Range 请求，不能走逐行 JSON）：
插件在子进程里把路由器挂进自己的 ASGI 应用（uvicorn 监听宿主分配的 Unix 套接字），宿主按插件声明的路由清单挂代理路由，
鉴权 / 验签照常由 `PLUGIN_ROUTES.mount` 注入，请求体与响应体按块转发；插件进程不在或连不上时返回 503。
签名链接由宿主签发（密钥不出主进程）。至此 §0 的验收全部达成：五个示例插件的端到端测试都参数化为进程内 / 进程外各跑一遍。

C1 与 C2 互不依赖，可以先做 C1；C3、C4 依赖 C2；C5 依赖 C2；C6 依赖 C3（文件接口）；C8 依赖 C5。

## 9. 决策记录（2026-10-09 用户拍板）

1. **隔离强度：方案 A**。插件进程以独立的非特权 uid 运行，除它自己的数据目录外，文件一律经主进程的文件接口按路径授权访问。
   这是 NAS 内核 4.4 上唯一能真正强制的边界；C6 按此实现。
2. **依赖只能随包携带**（`vendor/`），安装时不联网、不跑 pip；打包工具负责解包依赖并校验平台标签。
3. **安装来源只支持手动上传插件包**（管理页或 `mclaw`）；第三阶段不做插件市场 / 远程仓库 / 填网址安装。
4. **成员区路由暂不开放**：第三阶段进程外 / 第三方插件只能挂管理员区与验签公开区；等成员权限 v2 能表达「插件操作」再开。
5. **允许第三方包申请进程内运行**（`runtime = "inline"`），但安装时以「拥有与主程序相同的权限」红色警告单独批准，
   与本地受信插件同等对待。
