## 0. 范围

- **做**：iOS App（含自研引擎的三个补丁）与服务端的打点、分析日志、存储与查询。
- **不做**：
  - 优化本身；
  - NAS 环境（文件缓存、磁盘、负载）——我们只对客户端与服务端程序负责，用户家里的环境控制不了；
  - 界面：统计只经接口与 CLI 查看，不改产品功能；
  - 网页播放器与经 Jellyfin 接口播放的第三方客户端（Infuse 等）：沿用现状，字段设计与客户端无关，留好接入位置。
- 数据只存在用户自己的服务器上，不外发（硬边界 3）。

## 1. 目标与口径

### 1.1 北极星：无打扰播放率

一次播放从头到尾没有打扰用户，就算一次「无打扰」。以下任一条都算打扰：

| 打扰 | 线 |
|---|---|
| 起播慢 | 点下到首帧出画 > 2 秒 |
| 跳转慢 | 任一次跳转到画面出现 > 1.5 秒 |
| 没出画就结束 | 起播失败，或用户在出画前退出 |
| 非自愿中断 | 卡顿 ≥ 0.5 秒、冻帧 ≥ 1 秒、报错、闪退或被系统杀掉 |
| 可避免的规格损失 | 见 §5.6 规则表：当前设备和音频输出本来能呈现、却被我们丢掉的规格 |
| 猜错 | 首帧后 30 秒内用户把音轨或字幕改成别的；续播后 30 秒内往远处（> 120 秒）跳，说明续播位置错了 |

**目标：局域网 ≥ 99%，外网 ≥ 95%。**北极星用的是「用户开始觉得被打扰」的线；追求的速度写在 §1.2 的核心指标里。
两条线必须一致：起播 p99 不超过 2 秒、跳转 p99 不超过 1.5 秒，北极星才可能达标。

### 1.2 三项核心指标

| | 指标 | 目标 |
|---|---|---|
| **稳**（最重要） | 每观看小时的非自愿中断次数（卡顿、冻帧、报错、闪退，按原因拆开）；起播失败率 | 局域网 ≤ 0.1 次；不闪退的播放 ≥ 99.99% |
| **快** | 用户动作到画面出现的时长（p50 / p90） | 起播首帧：局域网中位 ≤ 0.5 秒、p90 ≤ 1 秒，外网 p90 ≤ 2 秒；跳转：缓冲内 p90 ≤ 0.3 秒、缓冲外 p90 ≤ 1 秒；换音轨 / 字幕 / 画质、切回前台 ≤ 0.5 秒 |
| **对** | 可避免损失率；猜错率 | 可避免损失率 ≤ 1%；猜错率暂定 ≤ 5%，拿到基线后收紧 |

**护栏**（不追求更低，只要求不越线）：被系统杀掉 0 次；硬解通路室温连播 2 小时不进「严重」发热；
掉电另测基线后再定线；流量冗余率（实际下载 ÷ 片源码率 × 观看时长）≤ 1.05。

### 1.3 计时口径

一律从**用户动作**算到**画面出现**，用单调时钟，毫秒：

| 计时 | 起点 | 终点 |
|---|---|---|
| 起播首帧 | 点下播放（`Router.play`）；自动下一集为触发时刻；深链为打开时刻 | 首帧可上屏：引擎的 `hasFirstFrameReadyForDisplay`（主力通路与服务端流是 `AVPlayerLayer.isReadyForDisplay`，软件通路是显示层就绪） |
| 起播开始走 | 同上 | 引擎报 playing |
| 跳转（播放中） | 松手 / 点下快进快退键 / 锁屏或耳机控制 | 主力通路：AVPlayer 在落点处恢复播放（`timeControlStatus` 变 playing 且位置在目标 ±0.5 秒内）；软件通路：落点帧交到显示层（补丁 P32） |
| 跳转（暂停中） | 同上 | 主力通路：跳转完成且渲染位置等于目标；软件通路：落点帧交到显示层 |
| 换音轨 | 点选 | 新音轨开始出声（引擎换轨或重载完成、恢复 playing） |
| 换字幕 | 点选 | 新字幕可上屏（不需重载的记 0） |
| 换画质 | 点选 | 新会话首帧 |
| 切回前台 | 回到前台 | 引擎重建后首帧（没重建记 0） |

- **扣除用户自己的等待**：确认转码的弹窗、换画质提示等停在用户手里的时间，单独记为 `user_wait_ms`，不算进起播。
- **卡顿不含起播与跳转**（CTA-2066）：起播中、跳转中的等待分别记进起播与跳转，不重复记成卡顿。
- **连续拖动**：以第一次拖动为起点、最后一次松手的落点出画为终点，中间被取代的跳转只计数。

### 1.4 为什么改掉 web-player.md §8 的两条决定

- **北极星从「直通率」改为「无打扰播放率」**：直通率只覆盖「对」的一部分。自研引擎之后，App 上几乎所有片子都直出，
  直通率接近 100% 也挡不住起播慢、跳转慢、冻帧这些真实打扰。直通率保留为「对」的一个分项。
- **跳转耗时要上报**：跳转是「快」的一半，只进诊断面板就只能等用户报障，无法统计分布，也无法判断优化有没有用。

## 2. 数据流：一次播放一条记录

- **播放编号（`attempt_id`）**：App 在用户动作那一刻生成（UUID）。
  - 一次播放 = 打开播放器到离开这一集。
  - 断线重连、原位重开、降级、换画质都算同一次播放，编号不变。
  - 自动下一集是新的一次播放。
- **开始**：会话请求带上播放编号。
  - 服务端**先返回响应，再在后台建「已开始」记录**，不给起播加延迟。之前「取流接口占满数据库连接池、全站卡 30 秒」的事故就是在这条路径上。
  - 服务端把编号写进取流令牌。之后引擎的每个取流请求都带着令牌，服务端据此把取流统计归到这次播放，不用改引擎发请求的方式。
- **服务端耗时回传**：会话接口与决策接口在响应头 `Server-Timing` 里带各段耗时（决策、准备、ffmpeg）。App 记下来，
  起播分段就能分出「网络往返」与「服务端处理」。
- **结束**：App 离开这次播放时上报完整记录，**所有结局都报**：看完、中途退出、没出画就退出、失败。
  - 先写本机队列（App 容器内），发送失败就在下次启动或下次播放时补发。
  - 服务端按播放编号合并，重复上报只保留最后一份。
- **异常退出**：播放期间在本机写「正在播放」标记（编号 + 最近状态，每 10 秒刷新）。下次启动发现标记还在，
  就补报一次「异常退出」（闪退或被系统杀掉）。
  - 服务端把开始后 6 小时仍没收尾的记录标为「未收尾」。
  - 系统的 MetricKit 退出与崩溃诊断只作补充：是否依赖用户开启「与开发者共享」说法不一，而且数据一天才来一次。

## 3. App 打点

### 3.1 快

- **起播分段**：沿用 `StartupTrace` 的各段，改为从点下算起，并补上：
  - 自研引擎的首帧标记（`onFirstFrame` 已有，只是没接进 `StartupTrace`，属于 App 的 bug）；
  - 引擎 `startupProgress` 的 8 个检查点（打开片源、打开容器、探测、准备显示、选通路、建会话、出画）；
  - `Server-Timing` 回传的服务端各段；
  - `user_wait_ms`。
- **每次跳转**一条，记录这些字段：
  - 序号、来源（按键 ±10 / 拖动 / 章节 / 锁屏 / 自动）；
  - 起止位置、预判是否在缓冲内、是否暂停中；
  - 结局（落地 / 被取代 / 失败）、到画面的毫秒数；
  - 分段（引擎重启生产、首次读源、首个分片产出）**第一阶段没做**：现场记录只有总耗时，缓冲外跳转慢在哪一段
    暂时看调试日志（`[HLSSegmentProducer] first source read …`、`seg…: served … wait=…`）。
- **换音轨 / 换字幕 / 换画质 / 切回前台**：各记起止与毫秒数（App 没有自动连播，下一集由用户点）。
  音轨原地换要等引擎重载后的首帧，换会话式的等新会话首帧；不用重载的即刻生效记 0；15 秒还没结果的作废。

### 3.2 稳

- **卡顿**：按**播放头**判，不看引擎报不报缓冲：用户想看、画面出过、不在后台、没在跳转或换轨，播放头 0.5 秒不走就是一次卡顿。
  这样两条通路同一口径——软件通路本来就不对外报缓冲（P27 / P30 停钟时播放头不走，正好被这里抓到），断线重连、原位重开期间
  画面停着也算。原因在卡顿开始时判：重连中 / 换会话中 / 前方缓冲 ≥ 3 秒（解码跟不上）/ 没在收数据（网络）/ 在收但不够快。
  离开播放器时还在卡顿，已经卡住的时长照算。
  **跳转落地后的起步宽限**：落地到播放头第一次走动之间最长 1.5 秒不判卡顿，过了还不走从落地起算。软件通路的播放时间 250 毫秒
  发布一次、App 也 250 毫秒采一次，加上时钟放开后音频预滚约 0.3 秒，画面照常在出、播放头却要 0.6～0.8 秒才看得出在走；
  没有宽限时真机全量每批有 2～3 次这样的误报（§9.4）。
- **冻帧**：播放头在走、画面 1 秒没有新帧。软件通路用引擎公开的逐帧回调（`setSoftwareVideoFrameTimeObserver`）计数；
  主力通路的画面由 AVPlayer 出，与时钟一体，暂不检测（真实数据显示需要时再加）。
- **断线重连**：开始、结束、原因、重试次数、结果。
- **报错**：
  - 引擎错误类型（`PlaybackErrorKind` 原值，`NativeEngine.lastFailureKind` 补上了）、归类（网络 / 片源不在 / 服务端 / 拒绝 / 解码……）、
    发生阶段（协商 / 起播 / 播放中）。落到错误页的记为 `error`（计入中断）；引擎报了失败但被重连、原位重开接住的记为
    `engine_failure`（不计入，看得见的部分会表现为卡顿）。底层错误域与错误码第一阶段没带（在引擎日志尾巴里）。
- **降级**：从哪到哪、原因。
- **看门狗**：提示、判定解码卡死、判定断线的次数。
- **系统打断**：来电 / Siri 等音频会话打断、耳机拔出等路线变化，记下是否正确恢复。这些不算我们的中断，但要看恢复得对不对。

### 3.3 对

- **规格快照**：首帧时记一次，之后有变化再记。
  - 通路：主力 / 软件 / 服务端流 / 服务端转码；档位与降级来源。
  - 源：容器、视频编码、分辨率、帧率、HDR 格式、杜比视界配置、码率；音频编码、声道、是否无损、是否全景声；字幕类型。
  - 输出：实际视频格式、杜比视界转换与增强层是否保留、音频交付方式（原样 / 桥接成什么格式 / 解码）与声道、全景声是否保留、字幕呈现方式（原生 / 叠加层 / 服务端压制）。
  - 设备：当前音频输出（扬声器 / 蓝牙 / 有线 / 隔空播放 / HDMI）、屏幕是否支持 HDR。
  - App 只报事实，损失判定在服务端按规则表算（§5.6），规则改了不用改 App。
- **猜错**（进北极星）：首帧后 30 秒内把音轨或字幕改成别的，记下「自动选的 → 用户选的」；续播后 30 秒内的远跳（> 120 秒）。
- **诊断用的行为**（不进北极星）：改画质、其他拖动、首帧后 10 秒内退出、60 秒内又进同一部、点重试。

### 3.4 上下文与资源

- **环境**：
  - App 版本（引擎随 App 内置，版本与补丁由 App 版本确定）、系统版本、机型；
  - 网络（在家 / 在外 / 分不清）、接口（Wi-Fi / 蜂窝 / 有线）、是否计费网络；
  - 实测下载吞吐的峰值（引擎的带宽读数）；
  - 实验室标签（§3.6）。
- **资源**：发热状态（开始、最高）、低电量模式、电量（开始 / 结束）、内存峰值、本进程平均 CPU。
  - Release 包也采（`DeviceVitals` 改为 Release 可用）；10 秒一次，只保留汇总，不保留曲线。
  - 下载字节与片源缓存命中第一阶段没记（服务端取流统计有服务端视角的字节数）。

### 3.5 分析日志

- **时间线**：每次播放一份，是上面所有事件按时间排成的列表，每条带距起点的毫秒数，最多 200 条。随结束记录上报，
  用来还原「这一次到底发生了什么」。
- **失败时附引擎日志尾巴**：Release 包里给引擎日志装一个环形缓冲（`AetherPlayback.installLogHandler`：最近 300 行、每行 ≤ 400 字，
  上报时取最近 ≤ 32 KB，引擎自带脱敏；开发期 `-mcAetherLog` 同时打到控制台）。
  - 这次播放以失败、异常退出或冻帧告终时，随记录一起上报；平常不报。
  - 引擎本来就会拼好这些日志字符串，环形缓冲只是多存一份，开销可以忽略。
- **客户端事件日志**（`/playback/client-log`，服务端按天日志）一律带上播放编号，与服务端的「播放会话就绪」「首片供给」「转码会话结束」
  「播放记录」等行串起来。
- **Debug 包**：现有控制台标签保留。`[SeekTrace]` 改由播放记录打，每次跳转一行，终点按 §1.3（带来源、是否换会话、是否暂停中）；
  离开时多一行 `[PlaybackRecord]` 摘要。

### 3.6 实验室标签

- 启动参数 `-mcLab <场景名>`：真机批量验收、故障注入、外网测试台产生的播放都打上它，统计默认排除。
- 实验室脚本改为读服务端的记录接口出结果，不再解析控制台日志，保证实验室与真实使用同一套口径。

## 4. 引擎：第一阶段不打补丁

原计划的 P32 ～ P34 核实后都不需要，信号全部来自引擎已公开的接口，只在 App 的包装层（`AetherCore/AetherPlayback.swift`）接出来：

| 信号 | 来源 |
|---|---|
| 起播检查点 | `startupProgress`（8 个 `StartupCheckpoint`）→ `onStartupStage` |
| 跳转终局 | `seekEvents`（landed / stalled / superseded / rejected）→ `onSeekOutcome` |
| 软件通路跳转后的出画 | `setSoftwareVideoFrameTimeObserver`：每帧带显示代数，跳转清空队列就换代，新一代第一帧交到显示层即出画 → `onSoftwareFrameGeneration`；同一个回调顺带计数（冻帧） |
| 主力通路跳转后的出画 | 跳转落地后：暂停中即出画，播放中等 AVPlayer 恢复播放（`NativeEngine` 组合两者，发 `EngineEvent.seekPresented`） |
| 首帧（每次） | `hasFirstFrameReadyForDisplay`（起播、换音轨重载、回前台重建都会再来一次） |
| 规格事实 | `videoRoute`、`sourceVideoFormat` / `videoFormat`、`sourceDVProfile`、`dolbyVisionConversion`、`audioDelivery`、`activeAudioDecoder`、当前音轨 → `deliveryFacts()` |
| 日志尾巴 | `EngineLog.handler` → 环形缓冲 |

原计划里补丁才能拿到、现在用近似的：
- 卡顿改按播放头判（§3.2），不再需要引擎发布软件通路的卡顿、原盘读取器的网络状态；
- 全景声、DTS-HD MA 按轨名与解码器说明识别（「Stream-copy (EAC3+JOC Atmos)」「truehd → EAC3 bridge」），桥接输出格式也从说明里取；
- 杜比视界只记转换（P7 → P8.1 即完整增强层被丢，iPhone 上是设备上限，不算损失），不区分完整 / 最小增强层；
- HDR 主列表被拒回退到基础层后 `videoFormat` 不更新的问题没修，规格快照在这种情况下会偏乐观。

## 5. 服务端

### 5.1 存储：扩展 `playback_metric`

一次播放一行，按 `attempt_id` 合并。网页播放器仍按旧字段上报，新字段都可为空。迁移只加列，向前兼容。

| 类别 | 字段 |
|---|---|
| 身份 | `attempt_id`（唯一）、`status`（已开始 / 已收尾 / 未收尾 / 异常退出）、`outcome`（看完 / 中途退出 / 出画前退出 / 失败 / 异常退出）、`origin`（点下 / 自动下一集 / 深链）、`client`（ios / web / jellyfin）、`lab_scenario`、`metric_version`、`media_item_id`、季、集 |
| 分组 | `source_class`（UHD 原盘 / 蓝光 / DVD / 杜比视界 / HDR / 4K / 1080p / 标清）、`route`、`network_class`、`interface`、`app_version` |
| 快 | `first_frame_ms`、`playing_ms`、`user_wait_ms`；缓冲内 / 缓冲外跳转的次数、p90、最大值 |
| 稳 | 卡顿（沿用 `rebuffer_ms` / `rebuffer_count`）、冻帧次数与时长、重连次数与时长、错误类型 / 归类 / 阶段 |
| 对 | 沿用 `tier` / `degraded_from` / `engine` / `hw_backend`；`avoidable_loss`（是否有可避免损失）、`misguess_count` |
| 明细（JSON） | 起播分段、跳转列表（≤ 50）、换轨与回前台、中断列表（≤ 50）、规格快照、损失判定、猜错与行为、环境与资源、服务端统计（§5.3）、时间线（≤ 200 条）、失败时的引擎日志尾巴（≤ 32 KB） |

- 分组要用的放标量列，其余放 JSON 列（SQLite 自带 JSON 函数）。
- `source_class` 在写入时由 `library_file` 算好存下，文件删了也不丢。
- **保留期改为按时间**：默认 90 天，`core/config.py` 新增配置项，不再是「超过 3000 条删到 2000」。不新增 `data/` 下的目录。
- **上报校验**：数值有上下界、枚举有白名单、JSON 有大小上限。超限截断并记一行警告，不拒收。

### 5.2 会话接口

- 请求可带 `attempt_id`；响应头带 `Server-Timing`。
- 原文件直出也会经过会话接口（在那里签发取流令牌），所以每次播放服务端都能建「已开始」记录。
  - 记下服务端视角的事实：决策、档位、原因，转码计划（视频 / 音频怎么处理、有没有色调映射、有没有压字幕），请求头里的客户端信息。
  - 都在后台写，不阻塞响应。

### 5.3 取流统计

按播放编号在**内存里**累计，这次播放结束（或会话结束）时写一次，**从不逐请求写库**：

- 原文件、原盘目录、服务端转码分片：请求数、字节数、首字节耗时 p50 / p90 / 最大、慢请求清单（> 1 秒，最多 20 条）、客户端中途断开次数。
- 转码会话：首片耗时、分片等待 p90 / 最大、超时、重启、ffmpeg 失败。

### 5.4 分析日志

- 每次播放结束写一行摘要：`播放记录 attempt=… 结局=… 起播 首帧 N 毫秒（分段…）· 跳转 n 次 缓冲外 p90 … · 中断 … · 规格 … · 猜错 …`。
- 现有播放相关的日志行统一带上 `attempt=`，用来串起一次播放：会话就绪、首片供给、分片等待、会话结束摘要、客户端日志。
- 错误与降级各写一行警告。

### 5.5 查询

- `GET /playback/stats/qoe`（管理员）：
  - 参数：时间窗口，按片源类型 / 网络 / 通路 / App 版本 / 客户端分组，默认排除实验室。
  - 返回：北极星、三项核心指标（p50 / p90 / p99）、护栏、打扰按原因的帕累托排序、最差 20 条播放。
  - 少于 30 条的分组直接列明细，不算分位数。
- `GET /playback/attempts/{attempt_id}`（管理员）：一次播放的完整记录与时间线。
- 两个接口按项目约定返回 `success / code / message / data`，并在 CLI 里可用，便于排查与后续自我迭代时直接读取。不做界面。

### 5.6 规格损失规则表

在服务端判定，**以「当前设备 + 当前音频输出能呈现的最好效果」为准，而不是以源片为准**：

| 情形 | 判定 |
|---|---|
| 设备解不了的（如 iPhone 解不了杜比视界 P7 的完整增强层） | 设备上限，不算损失 |
| 输出听不出差别的（如经蓝牙输出时，无损音轨转成有损） | 设备上限，不算损失 |
| 本机能直出却走了服务端转码 | 可避免损失 |
| 用户主动限画质 | 用户选择，不算损失，单独统计 |
| 服务端压制图形字幕 | 可避免损失（本机可以画） |
| 有线 / HDMI / 隔空播放输出时丢了无损或全景声 | 可避免损失 |

规则会随实测调整；App 只报原始事实（§3.3），规则改了历史记录可以重算。

## 6. 外网测试台

- **一根 USB 线不够**：iOS 不会经 USB 用 Mac 上网，手机的应用流量仍走 Wi-Fi。
- **方案 A：Mac mini 当手机的网关**（推荐，能脚本切换档位）。
  - Mac mini 已用网线接家里网络（en0），把这条有线网络经「互联网共享」共享给手机：
    - 用 Mac 的 Wi-Fi 开热点，不用买东西；
    - 或者给手机接 USB-C 网卡、用网线直连 Mac（Mac 另接一个网卡）。iPhone Air 的 USB-C 是 USB 2，有线约 300 Mbps，外网测试够用。
  - Mac 上用系统自带的 `dnctl` + `pfctl` 限带宽、加延迟、加丢包，脚本切档。
  - 手机与服务器不在同一网段，App 会判为「在外」，外网逻辑被真正执行。
  - 需要你做一次：打开互联网共享；给 `dnctl` / `pfctl` 配免密 sudo，或每次输入管理员密码。
- **方案 B：iPhone 开发者设置里的「网络链接调节器」**。
  - 可以自定义档位，但只能在手机上手动开关；
  - App 仍判为「在家」，外网专属逻辑（按网络记画质等）不会被执行。
- **建议档位**：
  - 典型外网：下行 50 Mbps、往返 40 毫秒、丢包 0.5%；
  - 差：10 Mbps、100 毫秒、2%；
  - 很差：3 Mbps、200 毫秒、抖动。

  「外网」在这里指的是家庭宽带上行受限的远程访问，限的是服务器 → 手机方向。

### 9.1 第一轮（2026-09-29 凌晨，iPhone Air 连 NAS）

  首帧后约 0.8 秒卡一下 → 引擎补丁 P33（点播分片 2 秒）。

| 乙 P32 | 1494 / 1755 | 291 / 541 | 706 / 1425 | 2 次 |

### 9.2 第二轮（同夜）：原盘读取窗口快速放大——否决

**假设**：原盘缓冲外跳转后读取器从 256 KB 起每次翻倍（256K → 8M 六次请求，约 0.56 秒）才读到落点关键帧（约 16 MB），
每次请求都付一遍往返；按 8 倍放大（256K → 2M → 8M）能省两三百毫秒。

**分段计时**（调试构建临时加 URLSession 取数计时）：连接一直复用，发请求到首字节 11～15 毫秒；慢在新位置的冷读传输
（跳转后 256 KB 传 31～43 毫秒、2 MB 132 毫秒、8 MB 185 毫秒，顺序读热了以后 8 MB 约 100 毫秒）——瓶颈是片源盘，不是请求次数。

**交替对照**（6 部原盘 / DVD × 2 组 × 3 轮）：旧 / 快涨 首帧中位 1165 / 1110、p90 1432 / 1564，缓冲外跳转 p90 1060 / 1196，
卡顿 5 / 8 次。读到关键帧早了约 150 毫秒，但淹没在后续分片产出与 AVPlayer 的波动里，p90 反而变差。**不改，代码已撤回。**

**顺带查清的小头**（下一轮候选，都在 100 毫秒以内）：服务端决策 13～28 毫秒；App 建引擎约 30 毫秒（每部片都有，可在等会话时预建）；
原盘目录多一次拉清单往返 40～80 毫秒（可由会话响应直接带上清单，要改接口）。

桥接自己开解码器。真机验证：切到这条音轨（中文 TrueHD）桥接照常初始化、读回确认在放中文，切回英语也正常。

**交替对照**（2 部 TrueHD 片 × 2 组 × 3 轮）：《变形金刚4》探测 630 → 32～144 毫秒，首帧中位 1335 → 812（三轮每轮都快约 500 毫秒）；

是否在低存储重试前退避几秒，留给用户定。

### 9.4 打点修正（同夜）：软件通路跳转落地后的卡顿误报

三批全量（q1～q3）里软件通路（VC-1、DVD、VP9）每批 2～3 次「卡顿」，都在缓冲外跳转落地后约 0.6 秒、持续约 0.8 秒。
引擎诊断同一时段时钟每秒走 0.94～1.00 秒、每秒约 50 帧上屏——画面没停，是量化误差（两个 250 毫秒定时器不同步）加音频预滚
叠过了 0.5 秒线。按 §3.2 加起步宽限，单测覆盖「起步慢不算」「落地后真冻住从落地起算」。它们原来把这些播放判成「有打扰」，
软件通路的北极星会被低估。

**通宵结果**（22 部全量，q1 基线 → q3 三轮改动后）：首帧中位 1000 → 816、p90 2125 → 1605 毫秒，一秒内出画 11 → 15 部；
缓冲外跳转中位 378 → 334、p90 1164 → 999 毫秒，超过 1 秒 13 → 7 次；缓冲内 p90 345 → 450（4K60《他是谁》的零容差逐帧解，
见 §9.1）。22 部无降级、无报错，记录与本机日志全部一致。离目标（首帧 p90 ≤ 1 秒）还差的主要是：长 GOP 的《权力的游戏》2.4 秒、
UHD 原盘 1.1～1.8 秒（新位置冷读）、4K60 / HLG 1.3 秒左右。

### 9.5 第四轮（09-29 早晨）：软件通路时间轴错位 600 秒（引擎补丁 P35）

**缺口**：q1～q4 每批《戴珍珠耳环》（VC-1 原盘，软件通路）都记「有打扰」，原因是冻帧中断。本机日志显示跳回 300 秒后
时钟停在 300、解码一帧不出，直到退出。

**定位**：这张盘 raw PTS 从 600 秒起。软件通路原来只在「首样本晚于起播点 2 秒以上」时才得出 session zero（给直播中途加入用）：
续播 600 秒时首样本 600 对起播点 600，不触发，整条时间轴按 raw 发布——续播点其实是片头、片尾 600 秒够不着，
往 600 秒之前跳，EP map 落回片头（首包 600），时钟停在 300 等不到画面。主力通路按 AE#270 以容器起点为 0，两条通路口径不一。

**改动**：点播片源容器起点超过 2 秒时，装载即预设为 session zero（起播定位与锚时钟加上起点，发布时间减去起点）；
首样本重锚叠加在预设值上；光盘章节跳转基准扣掉已折算部分。字幕仍按 raw 源时间对齐。

**真机验证**：续播 600 → 源 1200、跳回 300 → 源 900，5 次跳转 187～394 毫秒全部落地；从头播、开 PGS 字幕（raw 1800.95 的字幕
在内容 1201 秒准时上屏、1802.27 清空）都对；DVD ×3、VP9、MPEG-4 ASP 起点在容差内，不触发、读数与 q4 同水平。
8 条记录全部无打扰，与本机日志一致。

**遗留**：修复前这张盘（以及其他起点大的软件通路片源）存下的续播点在 raw 轴上，比实际位置多 600 秒；不迁移数据，
用户下次打开会续播到偏后的位置，手动拖回即可。

### 9.6 第五轮（09-29 上午）：跳转按代价吸附关键帧（引擎补丁 P36）

**缺口**：用户手测《抓特务》（4K HDR10 60 帧 WEB，14.5 Mbit/s）拖进度条、点 ±10 秒都慢：缓冲内 8 次 p90 2426 毫秒。
ffprobe 量出关键帧按场景 2～10 秒不等，耗时与「落点离前一关键帧的距离」成正比（每秒约 0.27 秒）——主力通路零容差跳转，
AVPlayer 从前一关键帧逐帧解到落点，4K60 手机硬解约 3.7 倍速。数据早在本机，不是网络。

**改动**：估精确落点的逐帧解码耗时（距离 × 帧率 × 按像素折算的单帧耗时），超过 0.2 秒才落到最近的关键帧（方向不反）；
解得快的片子照旧精确。落点是用户看得见的行为，用户拍板「按代价自适应吸附」。第一版落在关键帧 + 0.01 秒，B 帧 MP4
（《他是谁》索引首个关键帧 −0.067 秒）仍回退解码，改为关键帧后 0.2 秒。

**真机交替对照**（ab4 两轮 + ab5 修正版一轮）：缓冲内中位 541 → 215、p90 2053 → 665 毫秒；《抓特务》1.2～2.3 秒 → 全部 ≤ 0.37 秒；
4K60 MP4 缓冲内 2.2 秒 → 0.29 秒；《大空头》这类解得快的片两组相同（不吸附）。

**第二批语料**（09-29，按片库格式普查补 40 部，见 §9.7 待办）暴露的其余问题：《黑豹2》UHD 原盘开头约 20 秒有声无画；

### 9.9 第七轮（09-30 凌晨，iPhone Air 连 NAS）：常见格式起播与引擎装载

### 9.10 第七轮续（09-30 清晨）：MKV 索引提前取、缓存记账补漏与启动整理，几个否定结论

**P48（撤回）：首帧到开播约 100 毫秒是 AVPlayer 自己的管线时间。** 历史日志里 P28（缓冲过线直接开播）七成在条目就绪之前触发，
这些起播就绪到开播中位 40、p90 423 毫秒，看上去像「放行被吞掉」。试了就绪那一刻再放行一次：交替对照首帧到开播中位
102（关）对 113（开）毫秒，补发的放行同样不起作用——《权力的游戏》照旧等第二个分片（25 MB）送达才开播。换个角度看数据：
不论就绪早晚、放行几次，首帧到开播都稳定在约 100 毫秒，就绪只是落在这段时间里的某一刻。已撤回，不再从放行时机上找。

**P49：MKV 索引提前取。** libavformat 把 Cues 的解析推迟到第一次跳转（引擎的索引预热），那时才按 SeekHead 去读。
mkvmerge 产物的 Cues 离文件尾 7.7 万～93 万字节，落在尾部预读（64 KB）之外：语料 14 部 MKV 有 10 部要为它单独再发一次请求
（每次 40～120 毫秒），还会掐掉正在读文件头的连接、之后再重连一次。现在文件头第一块数据一到就解析 SeekHead，
与开容器、探测流并行把「Cues 到文件尾」一次取回，解复用器读索引时直接从内存给。（开头的 SeekHead 只指向文件尾附近的
完整目录时，试过盲取文件最后 1 MB：真机上这 1 MB 要 90～180 毫秒，索引预热反而多等，已改回按需读。）解析器在片库随机 40 个 MKV 的真实文件头上逐个核对过 Cues 位置，全部一致。
从头播交替对照（13 部 × 2 轮，两组都关跨启动缓存模拟第一次播，含 1 部 MP4 对照）：首帧中位 419 → 363、p90 590 → 540，
开播 p90 941 → 838 毫秒；分片计划就绪距装载 158 → 105、首个分片送达 285 → 212 毫秒；按片配对差值中位 −72 毫秒，10/13 部变快。
只看适用的 10 部 MKV，首帧中位 454 → 367 毫秒（《变形金刚4》670 → 498、《三体》529 → 366、《权力的游戏》460 → 351）。
没变快的 3 部：MP4 对照（不适用）、次级目录布局的那部（见上，这种布局不提前取）、一部噪声（+17）。

**P50：片源缓存记账补漏。** 片源字节缓存每个 1 MB 块原来只记一段连续范围、不相连时留长的：尾部预读先写了文件最后 64 KB，
moov（尾部 moov 的 MP4）或 Cues 再从最后一块中间顺序写过来时，每一小段都比已记的短、全被丢账，下次启动整块重下——
跨启动续播 12 部里 7 部开流时仍要向文件尾最后一块发请求，尾部 moov 的 MP4 开容器因此多等 43～176 毫秒。
现在每块另记一段暂存范围，接上就并。跨启动交替对照（10 部 MP4，热身前清空缓存、每组从零填，续播 600 秒）：
关掉时 5 部开流要向文件尾重新请求，开着 0 部；首帧中位 303 → 241、p90 499 → 333 毫秒。受影响的几部开容器 48～128 → 11～21 毫秒，
《他是谁》4K60 首帧 362 → 217、《大江大河》364 → 226。

**P51：启动整理不再整条删掉要续播的那份。** 对照里有一次 4K60 片的缓存整份没了：跨启动缓存的保留上限是运行预算的一半
（至多 512 MiB），启动时超了就按最近使用整条删——高码率片热身 18 秒就写了 398 MB，下次启动整理赶在装载之前跑完，
正要续播的这一份连 moov 一起被删，开容器重下 10 MB 的 moov（415 毫秒，首帧 1047）。真实使用里看一个多小时，缓存早涨到上限，
下次续播几乎必然撞上（整理与装载谁先谁后是竞速，装载先打开就躲过）。现在超额时先从旧到新缩：每份丢元数据区
（P46 的文件头 8 MiB、文件尾 32 MiB）以外的块，按块的最近使用从旧到新丢、丢够超额就停（续播点附近最后看的那段留着），缩完仍超才整条删；缩的时候先写记账再打洞，保留记账原来的修改时间，并且持缓存的锁、
锁内再确认这份没被装载打开——整理与第一次装载几乎同时，恢复要是夹在两者之间，会把刚打成洞的块当成数据读出全零。单测覆盖。

**页面预连与播放器弹出**：首页出现时预连后，开会话从 126 降到 66 毫秒，但首帧持平——会话回来时主线程还在搭播放器界面，
要到约 100 毫秒才轮到处理会话（`[StartupDiag]`「会话处理开始」）。服务端开会话本身只要约 20 毫秒（其中决策 16）。
试了把全屏播放器的呈现挪到独立小视图（点播放时不再让整个页签容器重算）：交替对照（8 部 × 2 轮，同一动线）建引擎距点击
97 对 97、首帧中位 309 对 311 毫秒，无差，已撤回——视图出现后那约 70 毫秒是播放器内容视图第一次搭建（`PlayerScreen` 在
onAppear 里才接上控制器，控制层、手势层、菜单这时才建），与页签容器无关。要省这段得让内容视图首建变轻（起播期间用不上的
控制层、菜单晚点建），或在页面预连动线下重测之前撤回的界面空闲预热；只在会话回来得快（热连接）时才吃到，收益约 10～30 毫秒。

**起播预热（试过、撤回）**：系统播放器那条路在会话回来时就先建资源开读，自研引擎要等主线程空出来才装载。试了会话一回来就在后台
并行取文件头（512 KB）与文件尾、引擎打开时接管（在途就等）。交替对照半程（首页停几秒再点播放的动线，10 部）反而更慢：首帧中位
314 → 357、首个取流数据距装载 42 → 91 毫秒——预热要整段收齐才交出来（69～129 毫秒），而这一轮会话只比装载早约 10 毫秒回来，
读取器自己的流式连接反而先到。要有效得把「正在进行的取流连接」整条交给读取器接着用，而不是交一段收齐的字节，改动大，留待以后。

**播放器界面空闲预热（试过、撤回）**：模拟器上剖析第一次弹出播放器的主线程开销，约四成是 Swift 运行时的协议一致性查找（关掉调试动态库
重编无差）；照页面预热的做法在启动后空闲时把播放器内容视图在背后画一遍。模拟器上会话处理开始约 185 → 110、首帧约 450 → 360 毫秒，

−2 毫秒——模拟器把这段开销放大了好几倍，真机上会话约 90 毫秒才回来，主线程那时本来就快空了。已撤回。
