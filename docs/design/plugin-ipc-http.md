# 插件进程间通信改走 HTTP

> 状态：**设计稿**（2026-10-11）。前置阅读：`plugin-phase3.md`（进程外运行器）、`plugin-kernel.md` §5.3（可跨进程约束）、
> `plugin-phase2a.md` §3（插件主体与宿主操作）、`plugin-callbacks.md`。文中 `文件:行号` 均指 `7c6d19ec`。
> 相关：#774（路由套接字只许宿主连接）。

## 1. 背景

进程外插件与宿主之间现在有三条通道：

| 通道 | 承载 | 实现 |
|---|---|---|
| 标准输入输出，每行一条 JSON | 宿主调插件（事件、钩子、任务、回调、通道、下载器、定时任务）与插件调宿主（宿主操作、插件数据、健康、任务进度、签名、网络代理、通道收消息） | 自制协议：`movieclaw_sdk/protocol.py`、`runner.py`、`plugin_runtime.py` |
| HTTP over Unix 套接字 | 用户请求经宿主反代到插件路由 | 插件进程里的 uvicorn；宿主 `_route_proxy` |
| socketpair + SCM_RIGHTS | 宿主把授权过的文件描述符递给插件 | `plugin_files.py` |

第一条是问题所在：

- **不是计划中的设计**：`plugin-phase3.md` 原本写的是「宿主操作直接打 HTTP、插件数据走 HTTP 端点、控制通道走 WebSocket」。
  C3（#675）改成全部复用管道，理由只有一条：服务调用要在所处理事件的上下文里执行。这个需求用一个请求头就能满足。
  文档 §4.1、§4.2 至今仍按原计划描述，与代码对不上。
- **违背了内核的初衷**：`plugin-kernel.md` §5.3 立「可跨进程约束」，是为了「进程外代理能对任何契约**通用生成**，不需要逐个手写」。
  实际实现是手写的：宿主侧 25 个 `rpc` 方法逐个分支（`plugin_runtime.py:985-1113`），插件侧 7 种调用逐个处理
  （`runner.py:714-731`），`RemoteContext` 里每个服务各有一个手写代理类。每加一个契约，两边各写一遍。
- **没有流式**：一问一答。`x-cli-stream` 的操作（如 `session.follow`）插件调不了；§5.3 只好规定「流式改分页」。
- **高并发下的隐患**：
  - 插件端同步阻塞写管道（`runner.py:658`），宿主读得慢时插件整个事件循环冻结，连它的路由一起停；
  - 所有调用挤在一根管道里，一个大载荷（上限 16 MB）挡住后面所有消息；
  - 没有按插件的并发上限；
  - 插件调宿主没有超时（`runner.py:662`）。
- **只能用 Python**：消息格式只存在于代码里，没有成文规范。

## 2. 目标与非目标

目标：

1. 两个方向都是**标准 HTTP over Unix 套接字**：取消就是断开连接，超时、流式、反压、并发全部用 HTTP 栈的现成能力；
2. **契约即协议**：调用按契约的类型定义自动分发、自动出 OpenAPI，新增契约两端都不用写传输代码；
3. **对插件透明**：`Context` / `RemoteContext` 的接口不变；现有的进程内、进程外参数化端到端测试原样通过；
4. 不退步：吞吐和延迟不低于现状（§8）；没有入站声明的插件不开服务；
5. **协议与语言无关**：为 §9 的非 Python 插件打基础。

非目标：每插件独立 uid（§7.3，单独立项）；改动开放给插件的契约本身（除 §5 放开流式外）。

## 3. 模型：两端各导出一张调用表

进程外插件和宿主之间只有一种交互：**调用对方导出的一个方法**。区别只在谁导出：

| 方向 | 导出方 | 导出内容 | 地址 |
|---|---|---|---|
| 插件调宿主 | 宿主网关 | 插件注入的服务（插件数据、健康、回调端点、签名、网络代理、任务上下文、通道账号……） | `POST /plugin-runtime/v1/{service}/{method}` |
| 宿主调插件 | 插件控制服务 | 插件 `apply` 里声明的监听器与贡献项（事件 / 钩子监听器、任务处理器、通道驱动、下载器、回调处理器、定时任务……） | `POST /_mc/{target}/{method}` |

这是 Twirp / Connect 一类「RPC over 普通 HTTP」的做法：

- 请求体是参数（JSON）；
- 响应 200 是返回值；失败时返回统一错误体（§4.3）；
- 返回类型是异步迭代器的方法，响应是 `application/x-ndjson` 流，一行一个元素。

分发和校验都按契约的类型定义**自动生成**：

- **服务契约补上方法签名**：每个开放服务定义一个 `Protocol` 类（如 `PluginDataApi`），`surface.json` 记录方法签名。
  注册表项现在已经有签名记录（如 `im-channels` 的 `ChannelDriver`）。
- **宿主侧网关**：一个通用端点。按 `{service}` 找到本插件实际注入的服务对象，按签名校验参数后调用，序列化返回值。
- **插件侧控制服务**：一个通用端点。`{target}` 是插件声明时分配的编号（一个监听器、一个贡献项各一个），`{method}` 是该对象的方法；
  监听器只有一个方法 `call`。
- **SDK 的远程代理**：按 `Protocol` 动态生成。服务的每个方法就是一次 `POST`。
- **OpenAPI**：从同一份签名导出两份文档（`gateway.json`、`control.json`），测试守护代码与文档一致。

通用调用覆盖不到的只有三个，它们各自有更合适的标准做法：

| 特例 | 做法 |
|---|---|
| 宿主操作（`HOST_OPS`） | 插件直接用令牌调标准的 `/api/v1/…` 接口，鉴权、按操作授权、审计都走现有链路；流式操作照常用 SSE |
| 插件路由（`PLUGIN_ROUTES.mount`） | 路由声明在 `ready` 里上报；用户请求由宿主反代到插件，与现在一样 |
| 文件（`PLUGIN_FILES.open`） | 通用调用返回令牌，描述符仍经 socketpair 递送；HTTP 递不了描述符 |

## 4. 运行时

```
宿主进程                                                      插件进程（每个插件一个）
  主应用 uvicorn（TCP，对外）
  网关 uvicorn（Unix 套接字，同一个 FastAPI 应用） ◀──HTTP── SDK：服务代理、宿主操作客户端（令牌 mcpl_…）
    · /api/v1/…                    标准接口（宿主操作）
    · /plugin-runtime/v1/{svc}/{m}  服务的通用调用（不进接口目录）
  Session（每个插件一个，一个 httpx 连接池） ──HTTP──▶ 插件的 uvicorn（宿主绑定的套接字，#774）
    · 调用监听器 / 贡献项                                   · /_mc/{target}/{method}  控制服务（最简 ASGI）
    · 反代用户请求                                          · 其余路径                插件路由（按需加载 FastAPI）
    · socketpair ──fd──▶ 文件描述符
  stdin：启动时写一行引导信息后关闭；stdout 合并进 stderr，只收日志
```

### 4.1 生命周期

1. **引导**：宿主拉起进程后往 stdin 写**一行** JSON，然后关闭 stdin。

   ```json
   {"protocol": 1, "entry_id": "…", "token": "mcpl_…", "gateway": "/tmp/mcp-xxxx/gateway.sock",
    "listen_fd": 4, "fd_socket": 3, "config": {…}, "data_dir": "…"}
   ```

   令牌不放环境变量，因为所有插件是同一个用户，能读彼此的 `/proc/<pid>/environ`。

2. **就绪**：插件跑完 `apply`，调 `POST /plugin-runtime/v1/session/ready`，一次性上报全部声明（导出表、路由、回调端点）。
   失败调 `…/session/failed`。导出表非空或有路由时，插件先在 `listen_fd` 上起服务再报就绪；否则不起服务（§4.5）。
3. **释放**：`SIGTERM`。运行器捕获后执行 `ctx.dispose()`、退出；宽限 5 秒后 `SIGKILL`。没有专门的释放消息。
4. **存活**：
   - 进程退出靠 `proc.wait()` 发现，在途请求随连接断开立即失败；
   - 宿主退出靠 `PR_SET_PDEATHSIG`（`runner.py:1125`）；
   - **不做定时健康探测**：插件卡死时，发给它的调用会超时，再触发内核现有的熔断；空闲时卡死不影响任何人。
     比起再加一套探测和判死规则，这样更简单，也不会误杀。

### 4.2 调用上下文

- 宿主调插件时带请求头 `X-MovieClaw-Call: <调用号>`，宿主侧登记「调用号 → 上下文快照」（现在 `Session._contexts` 的做法），
  调用结束即删除。
- SDK 在处理这次调用期间发出的所有请求都带上同一个头。网关按调用号恢复发起方、因果链、可靠事件投递信息；
  任务上下文类方法按它找到真实的 `JobContext`。
- **上下文只存在宿主这边，插件只交调用号，不自报发起方或因果链**。否则插件能伪造因果链，绕过递归限制
  （例如 `plugin-agent.md` 里「Agent 引起的调用不能再调 Agent」）。调用号只对发起它的那个插件有效。
- 插件路由收到的用户请求也分配调用号（反代注入同一个头）。现在路由里发出的宿主调用是 `call=None`，会丢上下文，这样就补上了。

### 4.3 错误

统一错误体 `{"code", "message", "details"?}`，与主应用的错误响应同构。现在的 `error_kind`（`JobRetry` / `JobBlocked` / `JobFailed` /
`JobCancelled`、`permission` / `not_found` / `value` / `ops`）映射成 `code`，SDK 原样还原成异常。连接失败统一为 `PluginProcessGone`；
内核的超时、熔断、重试、死信语义不变。

### 4.4 超时、取消、并发

- **宿主调插件**：沿用现有时限（钩子单监听器 2 秒、普通事件 30 秒、任务和通道 `run` 不限），由 httpx 超时实现。
  超时或宿主侧取消都表现为断开连接；控制服务是纯 ASGI，处理任务与 `receive()` 并行，收到 `http.disconnect` 就取消处理任务。
  不能用 `BaseHTTPMiddleware`，它会让断连检测失效（PR #172 的教训）。
- **插件调宿主**：SDK 默认连接超时 5 秒、读超时 60 秒，流式不限；可以按次覆盖。
- **并发**：网关按插件限制在途调用数（默认 32），超出的**排队等待**，不拒绝。排队时间计入调用方自己的超时，
  插件作者不用写 429 重试。带调用号的请求（钩子里的 `next()`、任务进度）不占名额，避免嵌套调用把自己卡死。
- 每个 Session 持有一个 httpx 客户端（连接池），调用和路由反代共用，不再每个请求新建客户端。

### 4.5 控制服务按需启动

- 只在插件有导出（监听器、贡献项）或路由时启动。只跑后台任务、只往外调宿主的插件不开服务。
- 控制服务用最简 ASGI 应用，不依赖 FastAPI。本机实测常驻内存：
  - 运行器基线 44.7 MB；
  - 加 uvicorn 和最简应用 46.3 MB（+1.6 MB）；
  - 加 FastAPI 57.0 MB（+12.3 MB）。

  FastAPI 只在插件挂路由时按需加载，和现在一样。
- 控制服务与路由共用一个 uvicorn，按路径前缀分发。宿主只反代插件声明过的路由路径，用户请求到不了 `/_mc/`，不需要额外的拦截规则。

### 4.6 网关

- 宿主在插件运行时条目激活时，在同一事件循环里多起一个 uvicorn `Server`，挂**同一个 FastAPI 应用**，监听 Unix 套接字
  （0660，属组为插件组）。开发热重载模式同样适用。
- **令牌只在网关上有效**：网关给 ASGI scope 打一个标记，`_plugin_principal` 只认带标记的请求。主应用经 nginx 对外，令牌就算泄露也用不了。
- 插件请求走完整的中间件链（审计、安全头），不计入前台压力（现有规则）。

## 5. 放开流式契约

§5.3 的「需要流式数据的场景改成分页」只是管道协议的限制。通用调用天然支持流（§3 的 ndjson 响应），所以这一条改为：

> 方法可以返回 `AsyncIterator[冻结模型]`；跨进程时是 ndjson 流，迭代器关闭即断开连接。

自动检查测试同步放开。插件调 Agent（`plugin-agent.md`）因此可以直接返回事件迭代器：进程内直接迭代，进程外是一条流，不需要长轮询。

## 6. SDK 结构

```
movieclaw_sdk/
  runner.py     引导、降权、信号、起服务；不再含协议
  rpc.py        通用调用：服务代理生成、控制服务（纯 ASGI）、调用上下文、错误映射、ndjson 流
  remote.py     RemoteContext：on / contribute / use / task / effect（从 runner.py 拆出）
```

删掉：`protocol.py` 的消息格式、`runner.py` 里 7 种调用处理和 `_Remote*` 手写代理、`plugin_runtime.py` 的读取泵和 25 个 `rpc` 分支。

## 7. 安全

### 7.1 边界

| 方向 | 谁能连 | 身份 |
|---|---|---|
| 插件 → 网关 | 所有插件进程（同一用户） | 令牌：每次拉起进程现签，进程退出即作废，只在网关上有效 |
| 宿主 → 插件 | 只有宿主（文件 0600、目录 0700，#774） | 不需要 |
| 用户 → 插件路由 | 经宿主反代（鉴权、验签在宿主） | 不转发 `Authorization` / `Cookie`（#774） |

### 7.2 令牌泄露面

令牌只在 stdin 引导行和插件进程内存里，不进环境变量、不进日志。

### 7.3 已知限制：插件之间没有隔离

所有插件同一个 uid，能互相 `ptrace`、读彼此的临时目录。插件和宿主之间的边界成立，插件和插件之间不成立。
每插件独立 uid 单独立项，不阻塞本稿。

## 8. 验证

**一致性测试（新增）**：遍历 `surface.json` 里的全部开放契约，每个方法用最小合法参数经 HTTP 往返一次，比对与进程内调用结果一致。
契约新增或改签名时自动覆盖，不靠人记得补测试。

**端到端**：现有参数化测试（进程内 / 进程外）原样通过；NAS 上用真实插件包（企业微信通道、网盘示例）验收。

**压测**：`scripts/bench_plugin_ipc.py`，用真实应用生命周期拉起假插件进程。迁移前后、本机和 NAS 各跑一次，结果写进 §11：

1. 事件投递：N 个监听器 × M 并发，吞吐与 p50 / p99 延迟；
2. 钩子：带 `next()` 的瀑布链，单次往返延迟；
3. 插件调宿主：插件数据读写、宿主操作，K 路并发；
4. 路由反代：并发 QPS、1 GB 流式下载吞吐；
5. 背压：插件故意慢消费时，其他调用是否被拖住（现状预期被拖住，迁移后不应被拖住）；
6. 内存：有服务 / 无服务插件的常驻内存。

验收：1～4 不低于现状，5 解决，6 符合 §4.5 的实测量级。

## 9. 非 Python 插件（下一期，本稿只定接口）

- **协议**：§3 的通用调用 + `gateway.json` / `control.json` + 引导行（§4.1），版本号 `protocol`。
- **清单**：`runtime = "exec"`、`command = "bin/acme"`、`platforms = ["linux/amd64", "linux/arm64"]`、`protocol = 1`；
  安装时校验 NAS 架构与协议版本。
- **声明**：约定 `<可执行文件> --describe` 输出 JSON（标题、注入的服务、权限、配置表单的 JSON Schema）。
- **可信启动器**：宿主先拉起 `python -m movieclaw_sdk.launch`，由它降权、清空附加组、设资源限制、设父进程退出信号（须在降权之后），
  再 `execve` 插件二进制。不可信的二进制不能自己降权。
- **验收**：用 Go 重写一个示例插件，过 §8 的一致性测试和端到端测试。
