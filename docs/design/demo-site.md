# 公开演示站：只读守卫、公开账号与合规内容——设计

> 状态：已实施（2026-09-28，分支 `feat/demo`）。部署手册见 [demo/README.md](../../demo/README.md)。
> 关联文档：[member-management.md](member-management.md)（超管 + 成员体系、路由分区）、
> [login-devices.md](login-devices.md)（登录设备）、[in-app-update.md](in-app-update.md)、
> [library-photo-kind.md](library-photo-kind.md)（图片库）。

## 0. 目标

一台任何人都能进去点的 MovieClaw：给潜在用户体验、给 App Store 审核用。三条要求：

1. **自带账号、登录页直接提示**：一个超管 + 几种典型成员角色，账号密码公布在登录页；
2. **写操作一律禁止**：改密码、增删改成员、删片、改设置都不行——尤其是成员相关的写与删；
3. **内容合规**：媒体库里只有开放授权的影片与图片，站上不出现任何访客生成的内容。

## 1. 威胁模型：公开的超管等于公开的服务器

正常产品里，超管持有的是服务器控制权：Agent 带 bash、`/fs` 浏览任意目录、可接 PT 站点
与下载器、可应用内更新与重启。演示站把超管密码贴在登录页上，所以不能按「挡住几个危险
接口」来想，而要按「访客就是超管」来想：

| 访客想做的事 | 后果 | 对策 |
|---|---|---|
| 改超管 / 成员密码、停用成员 | 其他访客全部进不来 | 写接口默认拒绝（§2） |
| 配 LLM 后用 Agent 的 bash | 拿到服务器 shell | 不接真实模型、不挂 bash：AI 助手是预设回复的演示模型，只带卡片与只读查库两个工具（§7） |
| 在 AI 助手里输入不当文字 | 出现在下一位访客的会话列表里 | 会话按登录设备隔离，别人的会话一律 404（§7） |
| 接 PT 站点、下载器、订阅 | 演示站变成盗版下载机 | 同上；PT 站点目录与种子搜索连读都拒绝；确认订阅被拒并说明原因（§4） |
| 改片名简介、建合集、传头像 / 背景 / 封面 | 站上出现违规文字或图片 | 同上；上传全部是写 |
| 搜索框输入不当文字 | 出现在下一位访客的「最近搜索」里 | 影视搜索在演示模式下不写历史；资源站搜索被拒 |
| 故意输错公开账号的密码 | 按用户名限速，全体访客被锁 5 分钟 | 公开账号不限速（§3） |
| 看「我的设备」「活动」 | 看到其他访客的 IP、设备名 | 输出时脱敏（§3） |
| 浏览目录、翻系统日志 | 服务器结构、其他访客的访问记录 | 这两类读接口也拒绝 |
| 把图片代理当免费中转 | 流量与滥用风险 | 演示模式下图片代理只认 TMDB / 豆瓣 / Fanart.tv 图床 |
| 点「应用内更新」 | 演示站被换成没有守卫的正式版 | 演示模式下应用内更新整体失效 |

## 2. 只读守卫：按 operation_id 默认拒绝

`services/demo.py` + `api/deps.demo_guard`，挂在 `app.py` 总装业务路由的那一层，
每个请求实时读 `MOVIECLAW_DEMO_MODE`（未开启时只多一次布尔判断）。

- **写请求**（非 GET/HEAD/OPTIONS）：只放行 `ALLOWED_WRITE_OPERATIONS` 里登记的
  operation_id，其余一律 `403 DEMO_READ_ONLY`。白名单只有三类：登录态本身（登录、
  退出、App 设备登录、Apple TV / Mac 扫码登录、多账号切换）、播放链路（起播、心跳、进度、收藏 / 已看、诊断上报）、
  只读语义的 POST（发现页的影视搜索、订阅面板的预检、媒体库管理里的各类「预览」）。新增写接口不登记就自动被挡——与路由
  分区的「默认拒绝」同构，漏登记只会少个功能，不会多个口子。
- **读请求**：默认放行，`BLOCKED_READ_OPERATIONS` 里的拒绝（目录浏览、系统日志、
  插件令牌明文、PT 站点目录、种子搜索、完整接口清单 `system.spec`、带服务器路径的
  转码诊断）。网络设置里的代理地址可能带账号密码，演示模式下置空再返回。
- **接口文档**：`/docs`、`/redoc`、`openapi.json` 在演示模式下一律关闭，不看 `APP_ENV`；
  登录后能取完整 OpenAPI 的 `system.spec` 同样被拒——否则公开账号一登录就绕开了。
- 影片分享（`share.*`）整组不放行：演示站建不了分享，访客通道留着只是多一个口子。
- 用 operation_id 而不是路径正则：它是全站稳定的接口标识（CLI 与 MCP 也靠它），接口
  挪路径不影响判定。守卫放在路由级依赖而不是 ASGI 中间件，因为依赖里拿得到已匹配的
  路由，抛出的业务异常也走统一错误格式；它先于参数校验执行，哑参数请求也会被拦。
- 拒绝理由按 operation_id 前缀给出具体文案（「演示账号的密码不能修改」「演示站不能
  新增、修改、停用或删除成员」……），客户端原样展示后端 `message`，网页与 iOS 零改动
  就有明确提示；业务码 `DEMO_READ_ONLY` 与权限不足的 `FORBIDDEN` 区分开。
- MCP 工具调用经 ASGITransport 回到同一个 app，同样过守卫；唯一的 WebSocket 路由
  （转码 Worker 控制面）在演示模式下直接拒绝握手。
- Jellyfin 兼容层不在守卫范围内：它的写接口只有播放状态与转码协商，没有账号与媒体的写。

守护测试（`tests/api/test_demo_mode.py`）以超管身份遍历 OpenAPI 里全部写接口，白名单
之外必须 403 DEMO_READ_ONLY；另一条断言两张表里的 operation_id 都真实存在。

## 3. 公开账号与访客隐私

- **登录页提示**：`MOVIECLAW_DEMO_ACCOUNTS_FILE` 指向 `demo/accounts.json`，`GET /auth/bootstrap`
  在演示模式下多返回 `demo: {notice, accounts}`。网页登录卡片只保留「演示账号 / App」入口，
  点开「App 登录信息」弹窗后，可切换四种身份、查看可见范围，并复制对应的账号、明文密码和
  当前服务器地址；尚未选择时默认展示第一个公开身份。点击「填入网页登录」才更新表单，
  不自动提交。弹窗支持关闭按钮、遮罩与 Esc，关闭后恢复入口焦点，不撑高主登录卡片。
  这些密码本就要公开，放进公开接口不算泄露。`GET /auth/me` 等会话视图多一个 `demo: true`，
  网页据此：改密卡片直接说明「密码不能修改」；隐藏资源站搜索的入口（超管也一样，
  影视与媒体库搜索照常）；更新页只显示版本、不给更新 / 回退 / 重启按钮；登录后在角落
  显示一条可关闭的「全站只读，数据每天自动还原」提示；超管登录后先落在媒体库，AI 助手
  留在侧栏（§7）。
- **主干新功能**：成员权限沿用分区授权（影视搜索按订阅能力、媒体库搜索按可见库），
  PT 搜索、下载与订阅手动选种在演示站对所有账号关闭；片段浏览和 `reels.events` 上报放行。
  更新页不展示 GitHub 令牌输入。新播放质量上报照常接收，但 `playback.attempt.get` 和
  `playback.stats.qoe` 含访客日志或自报文字，演示站拒绝读取；活动页的观看与档位汇总仍开放。
- **限速**：公开账号不计失败、不锁定（密码公开，防爆破无意义）；其他用户名照常限速。
  但每次登录都要跑一次刻意很慢的密码哈希、成功后还会建登录设备与一套预置对话，所以演示
  模式对**全部**登录（网页、App 设备登录、Jellyfin）再按来源地址限频：同一地址 10 分钟
  30 次，超了 429。取不到可信地址时所有人共用一个桶（上限 600）。要让服务端看到访客真实
  IP，`docker-compose.yml` 固定了网段并用 `FORWARDED_ALLOW_IPS` 信任 Caddy 转发的
  `X-Forwarded-For`（Caddy 默认不信访客自带的这个头，伪造不了）。
- **脱敏**：「我的设备」里除当前这台以外的设备，名字换成「其他访客的 iOS 设备」这类中性
  称呼、去掉 IP 与机型；活动页与播放记录里，服务端按 User-Agent 认出的客户端（网页、原生
  App）原样展示，Jellyfin 客户端在请求头里自报的名字换成「第三方播放器 / 访客设备」。
  演示数据的几台设备按完整标识认（不看 `demo-` 前缀），并且一律显示预设文案：访客在
  Jellyfin 登录时自报一个演示设备的标识，也只能让页面显示预设的「Infuse / 客厅 Apple TV」。
- **不落用户生成内容**：能写文字的接口（改名、简介、合集、设备名）本来就被守卫挡住；
  影视搜索在演示模式下不写搜索历史，资源站搜索被拒。

## 4. 内容合规

- 影片：13 部 Blender 开放电影（CC BY 2.5 / 3.0 / 4.0），授权以 Blender 官方声明与
  Wikimedia Commons 的授权审核为准。刻意排除含自杀情节的 *Cosmos Laundromat* 与恐怖
  血腥向的 *Sprite Fright*；排除授权说法不一的 *Agent 327*。
- 图片：58 张 Wikimedia Commons 精选图片，全部 CC0；避开可识别的人像、裸体雕塑、商标、
  地图、宗教与政治题材；下载前重新向 Commons 核对授权，EXIF 去掉 GPS。图片库按拍摄月份
  分组，原图的拍摄时间横跨十几年、几乎每月一张，所以按分类归到 2026 年的五个月份
  （日与时刻不变），原始拍摄时间记在 `CREDITS.md`。
- 发现页照常开放（TMDB / 豆瓣榜单，元数据展示）。订阅面板能打开、能预检，确认时后端
  拒绝并说明「演示站不会真的订阅和下载」。刻意不做「假装订阅成功」：假数据要同时骗过
  订阅列表、详情、活动、取消等十几个接口，而且所有访客共用账号，别人「订」的商业片会
  出现在你的订阅页里——比一句明确的提示更容易被误解成真能下载。
- 署名：每部影片的简介末尾写明授权、署名、来源与「只做了技术性转换」，详情页一定看得到；
  完整清单见 `demo/CREDITS.md`。
- 可复现：来源地址写死在 `content.json`，来源字节指纹锁在 `content.lock.json`，镜像站内容
  被替换时下载直接中止。
- 播放不触发服务器转码：影片统一整理成 H.264 + AAC 的 MP4（faststart），网页与 iOS 都直接
  播放。演示站的「软件转码」开关保持关闭，播放页也无法把它打开（改播放策略是写操作）。

## 5. 建站与还原

建站必须在演示模式关闭时进行（守卫会拒绝建库、建成员）：普通模式启动 → `provision.py`
建超管、库、成员角色与合集，等扫描刮削完成 → 停服务，把 `data/` 打成黄金快照 → 打开
演示模式启动。之后每天用快照整体替换 `data/`，访客留下的播放进度、收藏、登录设备随之清空。

媒体目录只读挂载进容器，建库时关闭「往媒体目录写海报与 NFO」：守卫之外再加一道，
即便哪条路漏了也改不了演示内容。

HTTPS 入口两种形态：独占的服务器用本目录的 Caddy（自动申请证书）；已有 nginx 占着
80/443 的服务器不起 Caddy（`DEMO_PROXY=external`），演示站作为 nginx 的一个站点接入
（`demo/nginx-site.conf.template`，证书走 acme.sh）。后者建站时换一个 nginx 不转发的
端口，保证非演示实例任何时候都不经 nginx 暴露；域名经 Cloudflare 代理时只信 Cloudflare
回源网段带来的 `CF-Connecting-IP`，服务端才拿得到访客真实 IP。

## 6. 订阅与观看数据

演示站没有真实的家庭在看片、追片，活动页、「我的订阅」「继续观看」「我的收藏」会全是
空的。`services/demo_activity.py` 用媒体库里真实的片子造出一个家庭的数据：

- **什么时候造**：每次以演示模式启动时按「今天」重建。统计窗口、「刚刚入库」「最近播放」
  都相对当前时间，建站时造一次几天后就过期；每日还原会重启容器，于是每天都是新的。
  随机数按日期播种，同一天重启结果一致；只替换演示数据（播放记录按 `demo-` 设备标识
  区分），演示站访客不能建订阅，订阅表整体重建。
- **订阅**：库里每部片一条已收齐的订阅，最近 7 天「刚刚入库」三部，家庭成员发起或关注
  了其中几部。时间线只有「订阅 → 入库 → 收齐」，不出现站点与种子信息。
- **观看**：超管与三个成员按各自习惯（几点看、用什么设备、能看哪些库）造出近 180 天的
  播放记录与档位统计（上一周期对比也有数据），回填已看、续播点、收藏。约束：入库之前
  看不到、不造未来或「疑似仍在播放」的记录、超管没看过刚入库的片（否则他的「刚刚入库」
  是空的）。
- **正在播放**：实时会话只在进程内存里，不往注册表塞假会话（会过期、会被同设备的真实
  会话覆盖、还会被取流鉴权读到），而是按当前时间确定性地算出几路，由活动接口并进快照：
  每路按「片长 + 空档」轮播，进度随时间推进，路数有起有落。
- 这些数据的客户端名是写死的（Infuse、MovieClaw iOS……），不经访客脱敏。

## 7. AI 助手：预置对话 + 预设回复

演示站不接真实大模型（没有 Key，也不该让公开访客消耗额度），但 AI 助手是产品的门面，
不能是空的。`services/demo_agent.py` 顶替模型路由，Agent 运行时其余部分（转录落盘、
SSE 事件流、工具执行、卡片渲染）原样工作：

- **演示模型**：`DemoLlmRouter` 按关键词判断意图（推荐、新入库、字幕、观看统计、订阅、
  播放转码、片名），用媒体库里的真实数据拼出回复，逐字流式输出，中途调用工具、画卡片，
  看起来和真模型一样。认不出的问题如实说明「这是演示站的预设回复」并送几张卡片。模型名
  就叫「演示模型（预设回复）」，`llm.providers.list / llm.models / llm.defaults.show`
  在演示模式下只报这一个，不冒充真 AI。
- **工具**：只挂媒体卡片与一个名为 `mclaw` 的只读查库工具（输出是演示模型生成计划时就
  算好的文本，不执行任何命令）。没有 bash、文件读写和真命令行，工具校验层也不认它们。
- **预置对话**：六个用例（和孩子看什么、本周新入库、《钢铁之泪》的中文字幕、家里谁看得
  最多、Blender 出新片能否自动收、流量看会不会卡），由同一个演示模型对真实数据跑一遍
  生成转录。提到片名一律附原名，例如「钢铁之泪（Tears of Steel）」「Sintel（寻龙记）」——
  后者原名在前，免得和商业片《寻龙诀》混淆。
- **按设备隔离**：公开账号下所有访客共用同一个超管，而会话本来是全局的。每台登录设备
  第一次打开会话列表时得到一套自己的预置对话（会话编号由「设备 + 用例」推导，重启后
  仍对得上）；访客自己新开的会话只记在进程内存里，只对发起它的设备可见，重启后隐藏，
  每日还原时随 `data/` 清掉。列表、读取、跟随、停止、重试、续聊都按这个口径判定，
  别人的会话一律当不存在（404）。
- **守卫**：`session.start / stop / retry` 放行；改名、删除、分叉、压缩上下文、上传图片
  仍被拒绝。
- **配额**：每台设备最多新开 20 个会话、10 分钟最多发 40 条消息，超了 429 并提示在已有
  会话里继续聊；运行历史（逐字事件）在演示模式下只留 10 分钟（正常产品 24 小时）——
  否则访客不停发消息会让内存一直上涨。已结束的对话重新打开读的是转录文件，不受影响。

## 8. 已知边界

- iOS App 没有改：登录页的账号清单只在网页上（审核备注里写明账号密码即可）；App 里被拒的
  操作显示后端给的中文说明，订阅面板确认时也是如此。
- Apple TV / Mac 扫码登录沿用主干配对协议，仅允许 `tvos` / `macos` 类型；命令行和转码器配对继续拒绝。
  配对码查看不返回来源 IP，令牌继承批准账号的媒体库范围和演示限制。
- 演示站没有剧集内容：开放授权、TMDB 上有条目的剧集几乎没有（能找到的 *Pioneer One* 是
  CC BY-NC-SA，带非商业条款），剧集相关页面在演示站上是空的。
- AI 助手的预设回复不理解语言：换个说法可能就落到兜底回复。这是有意的——兜底回复会说明
  原因并引导到能回答的问题上，而不是假装听懂。
- 带宽与并发播放没有在应用层限流，只能靠 VPS 带宽兜底（影片码率 1～6 Mbps）；被刷流量时
  可在 Caddy 前再加一层限速，或换更低码率的片源。
- 播放打点、客户端日志只限了单条大小（字段长度、Caddy 请求体 2MB），没有限条数：刷量
  只会让当天的日志变大，第二天随 `data/` 一起还原；容器标准输出日志另有轮转。
- 影视搜索没有按地址限频，被刷时可能被豆瓣按服务器 IP 封几个小时（发现页的豆瓣榜单
  随之失效，TMDB 不受影响）。
