# 刷片：沉浸式竖滑看片段

> 状态：一期开发中（2026-09-29 起，分支 `feat/reels`）。入口先放在 iOS 媒体库顶栏做试验，页名「片段」。

## 1. 要解决什么

在自己的片库里像刷抖音一样上下滑：每滑一下，出现一部电影或一部剧里的一段 30～60 秒的片段；
看得有意思就横过手机或点「接着看」，**同一个播放器**直接往下放正片。目的是帮用户决定「今晚看
什么」「想重温哪部」，不是让人在信息流里消磨时间。

同类产品：Netflix Fast Laughs（2021，15～45 秒）、Tubi Scenes（2024，60～90 秒）、
Disney+ Verts（2026-03）、Netflix Clips（2026-04，横过手机直接看）。它们靠人工策展或海量
行为数据挑片段；我们两样都没有，所以靠**容器索引里的免费信号 + 硬护栏**。

## 2. 一期的决定（用户拍板）

| 问题 | 决定 |
|---|---|
| 预先剪好小文件，还是实时从原片放 | **实时**：挑好位置，用现有自研引擎从原片中间起播。预渲染要先把全库跑一遍（估算 5～18 小时）才好用，首日体验差 |
| 看没看过要不要区别对待 | 不区别，一期不看观看状态 |
| 剧集怎么抽 | **按剧抽**（一部剧一个名额），固定放最早一季的第二集（2026-09-30 由剧内随机改，理由见 §4） |
| 入口 | iOS 媒体库顶栏一个按钮，点开全屏沉浸页 |
| 网络 | 不限制；蜂窝网络进入前确认一次「可能很耗流量」 |
| 接口 | 要能轻松兼容将来的预剪模式（见 §5） |

## 3. 挑哪一段（服务端，零解码）

实现：`movieclaw_playback/container_index.py`（读索引）+ `services/reels/picker.py`（挑点）。

**只读索引，不解码、不通读文件**：

- MKV：SeekHead 定位 Info / Tracks / Chapters / Cues。Cues 里有每个视频关键帧的 Cluster
  字节位置，mkvmerge 还默认给**每条字幕事件**（包括 PGS 图形字幕）写索引点。
- MP4：只读 moov 的样本表（stts / stss / stsz / stsc / stco）。**不能用 ffprobe 列包**——它会
  顺带读出每个包的数据，等于通读 mdat（NAS 实测 15.7 GB 的 MP4 读了 60 秒、5.7 GB 仍未完）。
- 原盘目录与蓝光镜像（2026-10-05 放开）：主播放列表（MPLS）给剪辑序列与章节，各剪辑 CLPI 的 EP_map
  是天然的关键帧表（PTS + 源包号 × 192 当字节位置，只用来估码率），挑点规则与 MKV / MP4 完全一样。
  镜像里的这些小文件经服务端的 UDF 读取器读（`services/library/udf.py`，照搬 App 引擎的实现，
  NAS 49 个蓝光镜像全部读得出，冷读首个 11 秒、之后每个 0.05～0.1 秒）。实现：`services/reels/disc_index.py`。
- DVD（目录或镜像）：按与引擎相同的规则选主标题（VIDEO_TS.IFO 标题表列出的标题集里内容 VOB 最大的），
  片长取它 IFO 里最长的节目链（ffprobe 对整个镜像猜出的片长不可信），按时间挑。
- 其余读不出索引的片源（TS、AVI、WMV、MPG、网盘 strm……，以及读不出索引的 MKV / MP4）：按台账片长与
  章节挑（区间前三分之一处的章节起点或固定位置），没有码率信号、不对齐关键帧，起点交给 App 引擎定位。
  连台账片长都没有才算挑不了。
- 光盘与读不出索引的片源不给预取范围（光盘的字节位置是拼出来的，不是取流地址上的位置），
  不抽封面（ffmpeg 读不了光盘目录 / 镜像，用剧照），光盘也不开字幕（服务端的字幕清单与盘内轨对不上序号）。
- App 按交付方式装载（`play.disc`，与正片同一套，docs/design/disc-direct-play.md）：镜像给原字节地址，
  原盘目录先取目录清单（含服务端选的主播放列表），时间轴与挑点同一条。模拟器实测各格式引擎落点与服务端
  起点一致、引擎读到的片长与服务端相同；预起（装载到停在起点）原盘目录 1.8 秒、蓝光镜像 0.9～1.6 秒、
  DVD 0.2～0.8 秒、AVI 0.1～0.4 秒、TS 2.2～2.7 秒（按字节二分定位，最慢）。

NAS 实测（17 个文件）：MKV 每部读 0.2～2 MB、0.04～1 秒；MP4 每部读 2.5～16.5 MB（moov）、
0.14～1 秒；挑点本身几毫秒。

**规则**：

1. 区间：电影全片 5%～75%，剧集单集 10%～80%（不剧透、避开前情提要 / 片头曲 / 片尾曲 / 下集预告）。
2. 码率信号：45 秒窗口的码率 = 两端关键帧字节位置之差 ÷ 时间差。窗口最高码率比中位数高
   8% 以上才信它，取最高的窗口。
3. 信号平（网络平台的剧集常见近恒定码率，实测《黑袍纠察队》每个窗口都在 17.0～17.1 Mbps）
   就退回：区间前三分之一附近的章节起点；没有章节就取那个位置。
4. 起点：落在关键帧上；附近有章节起点就对齐章节（场景开头）；否则找前后没有台词的关键帧。
   字幕只知道事件时间，按「持续到下一条或最多 3 秒」估计台词持续期。
5. 终点：在起点后 30～60 秒里找离 45 秒最近的台词空隙。
6. 黑场：抓起点那一帧当封面，平均亮度低于 16（0～255）就把起点往后挪到下一个关键帧（每次
   至少 2 秒，最多 3 次）——章节起点常是淡入黑场。

**实测效果**（抽帧肉眼核对）：动作片、动画片命中率高（《功夫熊猫》4/4、《流浪地球2》空间站
危机、《龙族》比武）；对白为主的喜剧挑得弱；不限区间时码率峰值会集中在高潮段（《让子弹飞》
4 段全在 73%～89%），所以区间上限必须卡住。已知漏洞：韩剧这类片头曲在 15%～20% 处的，片头
可能被挑中（《机智的医生生活》），一期接受；零解码比对两集找片头试过、不成立（码控使同一内容
字节数不同，恒定码率片处处假匹配），要精确识别得上音频指纹。

**缓存**：`data/cache/reels/<文件id>.json`（登记为 `cache.reels`，可清空，重建几乎无感），
按「文件大小 + 修改时间 + 算法版本」认账；封面随条目图片存放
（`<条目id>/reels/<文件id>/<起点毫秒>.jpg`，经 `/images/assets` 提供，沿用条目可见性校验）。

## 4. 翻页与预热

- 抽样单位是「部」：电影一部一个名额，剧一部一个名额（《哆啦A梦》一部就有两千多集）。
- 第一页服务端生成随机种子，App 翻页时带回 `seed` + `offset`；同一种子顺序固定，服务端无状态。
- **按评分加权洗牌**（2026-09-30，用户要求）：Efraimidis–Spirakis 加权无放回抽样，每部片的键是
  `Exp(1) / 3^(校正分 − 池子均分)`，从小到大排——每高 1 分排到前面的机会 ×3，低分片照样刷得到。
  校正分是按评分人数往均分拉的贝叶斯平均（先验 50 人）：片库里评分人数不到 30 的有 151 部、其中
  66 部在 8 分以上，多是几个人打出的虚高分，不校正就会专挑它们。NAS 模拟（688 部、400 个种子的
  前 30 条）：8 分以上从池子占比 29% 升到 46%，7 分以下从 20% 降到 10%，「8 分以上但少人评」
  维持 10% 不被放大。
- 剧集固定放最早一季的第二集（没有就取最近的一集，一样近取后一集）。依据：Netflix 2015 年统计
  25 部剧「看完这一集的观众七成会追完第一季」的集数，没有一部是第一集，最早是第二集（7 部），
  平均第四集——试播集忙着交代设定，第二集起才进入冲突。只看早期集也不剧透。固定一集还让同一部剧
  每次刷到都是算好的那一段：剧内随机时，长剧几乎每次都抽到没算过的集。
- 现成的片段够一页就立刻返回，没算过的这一页跳过、后台照常算完落盘；不够才并行现算，等到抽样
  顺序前面的每一部都有结果、挑得出的凑满一页就返回，整页最多等 3 秒。NAS 实测（688 部、缓存
  55%）：以前每页都等满 3 秒（3.2～5 秒），其实每页 30 部候选里现成的就有十三四条，不等现算时
  整个请求 0.1～0.4 秒。返回一页后顺手在后台把下一页要用的片段算好。
- 同一文件并发请求共用一次计算；计算限 3 路，抓帧与章节图共用两路 ffmpeg 的闸。
- **全池补算**（2026-09-30）：凑够就返回之后，剩下的慢只在「一页里现成的不够」——剧集改放第二集后
  252 部剧只有 32 部算过，筛「剧集 + 没看过」一页要 3.6 秒只拿到 6 条。所以有人刷片时，后台把全部
  电影库 / 剧集库每部一个文件（`choose_file` 选中的那个）没算过的片段一部一部补齐（`_fill_pool`），
  每个进程只补这一轮（用户要求不浪费：之后新入库的片刷到时现算，现成的够一页就先跳过它、后台算完落盘；
  重启后第一次刷片再过一轮，已算过的只读缓存记录，全池一两秒）。串行算，最多占计算闸 3 路里的 1 路，另 2 路留给正在等的那一页；
  片段与观看者无关，补的是全集。没人用刷片的部署不花任何代价。不走任务框架：它不需要进度、取消与
  断点，任务页上多一条常驻任务只是噪音。
- **第一条起播**（2026-09-30）：预起好的下一条出画 0 ms、预取过的冷起播约 200 ms，慢的只有「完全没预取」
  的冷起播——进页面的第一条永远是它（Wi-Fi 中位 4.6 秒、蜂窝 1.3 秒，62 条事件）。拆开看：引擎自己的打开、
  探测、建会话约 350 ms，其余是等数据；片源在另一台 NAS 上经 NFS 挂载，取流日志里第一条的文件头、索引两次
  请求在服务端各花 300 ms 上下（冷读），而播放器是一段一段串行读的。四处改动：
  1. **服务端预读**（`_preread_in_background`）：第一页一定下来（装配之前）就在后台把前两条的文件头 /
     索引 / 起点三段**并行**读一遍进页面缓存，第一条读完再读第二条。NAS 实测冷文件三段串行 60～114 ms、
     并行 35～62 ms，预读之后播放器再读只要 2～9 ms。转码时转码器读的也是这几段，一样受益。
  2. **第一条挑起得快的**（`_quick_first`）：第一页里第一个起播字节（文件头 + 索引 + 起点后几秒）不超过
     12 MB 的挪到最前，都超过挑最小的；只动第一条。起播字节中位 9.5 MB、90 分位 22.7 MB（4K 原盘）。
  3. **客户端冷起播补两段**（`boostColdStart`）：没有任何预取的冷起播，和播放器的打开、探测并行，
     各开一个请求把索引、起点头 1 MB 下进片源字节缓存。引擎的范围预取与播放器互不等待（没下完的那段
     播放器会自己再下一遍），所以只补播放器靠后才读、且补得比它快的这两段；原文件才补（转码不补）。
  4. **预连**：进页面、第一页还在路上时就和源站建好引擎那条连接（`AetherPlayback.preconnect`，
     与正片点播放时同一做法），外网 HTTPS 省一次握手。
  另外第一页只取 5 条（服务端装配按条数算，第一屏快约 30 ms），之后每页 10 条。
- **筛选计数并行**：`/reels/facets` 二十来条 COUNT 每条 25～40 ms，串行一秒多；各用独立会话限 4 路
  并发（WAL 下读可并行），NAS 实测 19 条串行 0.57 秒 → 4 路 0.29 秒（6 路反而 0.4 秒）。
- 全部现成时一页的耗时（NAS，热缓存）：可见库 2 ms、抽样池 40 ms、选文件 78 ms、取片段 3～6 ms、
  装配 58 ms，合计约 185 ms；再往下抠收益有限，瓶颈在客户端起播。

## 5. 接口（为预剪模式留口子）

`GET /api/v1/reels?seed=&offset=&limit=10&modes=seek`

```jsonc
{
  "seed": 123, "next_offset": 10, "has_more": true,
  "items": [{
    "id": "rl_15693_1964254",                 // 片段标识：文件 + 起点，事件按它归并
    "title": { "media_item_id": 6813, "kind": "movie", "name": "…", "year": 2022, "rating": 8.1,
               "genres": ["动作"], "tagline": "…", "poster_url": "…", "backdrop_url": "…",
               "logo_url": null, "episode": null },
    "cover_url": "/images/assets/6813/reels/15693/0001964254.jpg?v=…",
    "segment": { "file_id": 15693, "start_ms": 1964254, "end_ms": 2002300, "method": "chapter" },
    "play": {                                  // 怎么放：按 mode 区分，字段都可空
      "mode": "seek",
      "stream_url": "/api/v1/playback/files/15693/stream?token=…",   // 按文件签发，12 小时
      "size_bytes": 64200000000, "audio_ordinal": 1,
      "subtitle": { "ordinal": 2, "language": "chi", "title": "简体", "codec": "hdmv_pgs_subtitle" },
      "prefetch": [ { "offset": 0, "length": 180000, "purpose": "head" }, … ]
    }
  }]
}
```

兼容规则：

1. App 用 `modes` 声明自己会放哪几种，服务端只发它会放的——老 App 永远收不到 `clip`。
2. `segment` 永远是原片时间轴：「接着看」= `start_ms` + 已播时长，事件、封面在两种模式下
   逻辑都不变。
3. 存储也拆开：一期只有挑点结果；将来预剪只是再加一份「渲染产物」指向它，挑点不用重做。
   `play` 是一个带 `mode` 的模型、各模式字段可空（生成的 Swift 模型最稳）。

**筛选**（2026-09-30 由单个类型名扩成多维）：`GET /reels` 与 `GET /reels/facets` 带**媒体库筛选
的同一组参数**（docs/design/library-filtering.md：`g` 类型 TMDB id / `c` 地区码 / `d` 年代档 /
`rating_gte` 评分下限 / `rt` 片长档 / `w` 观看状态，维内 OR、维间 AND），另加 `kind=movie|tv`。
维度对齐发现页顶部的筛选（类型、地区、年份、评分、片长；排序不要——刷片的核心就是随机），取值口径
用媒体库的（年代、片长按档：刷的是自己几百部的片库，发现页那种单个年份一选就空），外加刷片特有的
「电影 / 剧集」与「只看没看过的」（用户拍板）。服务端复用媒体库唯一的收窄点 `_narrow`（分级约束
也在里面），抽样池只多一条 `media_item_id IN (…)`；`/reels/facets` 与抽样池同一个 WHERE，每维计数
排除本维自身条件。NAS 实测（688 部）：带筛选的抽样池 31 ms，整份计数 0.6～0.75 秒（二十来条 COUNT，
与第一页并行拉，只影响菜单里的数字）。

**「其他」库（`kind=video`，2026-09-30）**：家庭录像、自录内容这类「其他」库**不混进默认**，是筛选菜单里
一个独立的切换项。

- 为什么不混：刷片是帮人决定「今晚看什么」，而「其他」库一个文件一个条目，动辄几千个；抽样按条目均匀，
  5000 个录像 + 700 部电影时「全部」里将近九成是录像，电影、剧集被淹没。配比、份额上限都是补丁，
  分池才是根上的解法。
- 默认（不传 `kind`）= 电影 + 剧集；`kind=video` = 只刷「其他」库；`movie` / `tv` 不带录像。
- **回落**：电影 / 剧集在可见范围内**一个可刷的文件都没有**、且有「其他」库时，不传 `kind` 也刷「其他」，
  否则只建了「其他」库的用户「全部」永远是空的。判据是「有没有可刷的文件」，不是「有没有库」（建了个空电影库
  的人照样该看到录像），也不是「筛选后有没有结果」（带着条件刷空了不能偷偷改推录像）。
- **筛选**：「其他」没有 TMDB 档案，类型 / 地区 / 年代 / 评分 / 片长对它无意义，服务端一律忽略（不报错，
  老版 App 带着旧条件也不会拿到空页），**只认观看状态**（`w`）——家庭录像同样有「只看没看过的」需求。
- **菜单**：`/reels/facets` 的 `kinds` 多一项「其他」（没有可刷的文件时不给）；「其他」的计数只带观看状态、
  不带别的条件——点它会清掉那些条件，按当前条件数会让它在勾了「动作」之后显示 0 并置灰、点不进去。
  `filterable=false`（选了「其他」，或库里只有「其他」）时 App 收起类型 / 年代 / 地区 / 评分 / 片长五个菜单；
  只有「其他」库的用户 `kinds` 为空，整行「电影 / 剧集 / 其他」也不画。
- 抽样池读能力位 `profile.playable`，不列举形态：图片库不可播放自然排除。
- **补算**：`_fill_pool` 电影 / 剧集与「其他」各补各的，「其他」懒启动——第一次有人刷到「其他」池才开始补，
  没人刷它的部署零成本。挑点、封面、取流、进度沿用电影的一套（`video` 按单本、放 `(item, 0, 0)` 单元，
  区间沿用电影口径；短于 35 秒的挑不出片段，自然跳过）。

**大图预告**（2026-10-05，Apple TV 首页与详情页，docs/design/tvos-app.md §3.5）：`GET /api/v1/reels/preview/{id}?source=&season=&episode=`
返回一条同样的 `ReelItemView`（放不了为 null）。`highlight` 就是刷片这一段（剧集第二集）；`resume` 是这个人续播点往前 30 秒到续播点
（`segment.method = "resume"`，起点对齐关键帧、预取按这个起点现算），没有可用的续播点退回 `highlight`。预告不开字幕。

`POST /api/v1/reels/events`：`{"events": [{"reel_id", "kind", "mode", "media_item_id",
"file_id", "position_ms", "watched_ms", "wait_ms", "detail"}]}`，kind 为
impression / first_frame / leave / complete / continue / open / fullscreen / detail / fail（continue、open
是早先「播放」键的，App 已不再发，服务端照收）。只写 `reel_event` 表
（成员级数据，删除成员时一并清理），**不写观看记录**。

取流令牌不带 device_id：刷片的取流不登记到活动页，也不写续播点与播放次数。

    文件时间，只在显示时换算（`timelineStartMs` / `timelineDurationMs`）。跳转夹在片段之内。
  - 放到终点停下，中央键变「重播」，右侧出「片段放完了」卡片：看全片 / 重播这一段。
  - 底栏多一颗「看全片」：原地退出片段模式（同一个引擎、不重开），时间轴变回整部，从这一刻起照常记
    观看进度，返回键也恢复正片的语义（横屏先退出横屏、竖屏再退出播放）。
  - 左上返回与横屏键在片段模式下都是「退出全屏」：先转回竖屏、转好再关播放器，回到信息流从刚才看到的

    不给画中画：小窗里是系统自己的进度条，只认整部片的时长。

  - 翻页区每页始终按竖屏尺寸排版：进播放器页时整页会跟着转横，跟着横屏重排的话，转回竖屏后滚动位置

  （补丁 P39）；再往后两条只取文件头与索引。
- 预起下一条（2026-09-30 加）：原来每滑一条都要现建引擎，打开、探测、建会话、出第一帧全部重来一遍。
  - **改法**：当前这条出画 1 秒后，且下一条的预取已下完，另建一个引擎把下一条装载到片段起点。
    装载好就停在那里，并停止往前下载（引擎的暂停下载开关，补丁 P23）。滑过去只需「播放」。
    换条时旧引擎先停声，半秒后再拆。拆引擎在主线程上要几十毫秒，不能赶在滑动收尾那一刻。
  - **实测**：iOS 27 模拟器，软件解码通路，字节都已预取，各 10 次换条取中位数。
    - 停稳到开播：139 → 36 毫秒。
    - 停稳到出画：184 → 79 毫秒。
    - 改前的构成：主线程同步拆旧引擎约 50 毫秒；新引擎的装载在主线程上排队约 75 毫秒才开始；
      装载本身约 50 毫秒。建引擎对象本身不到 1 毫秒。
  - **剩下的耗时**：软件通路装载好停着时不解第一帧（要播放后才解，约 45 毫秒）；旧引擎停声要调
    音频同步器，约 35 毫秒。
  - **真机主力通路（换封装进 AVPlayer）模拟器量不了**：模拟器硬解不了测试片，全走软件通路。
    作为参照，NAS 日志里真机正常播放从建好引擎到首帧是 0.23～0.7 秒（片中起播、含网络）。
    预起后 AVPlayer 停在起点通常已有第一帧，预期接近「滑过去立刻动」，**待真机验证**。
  - **代价**：同时多一个引擎（4K 杜比视界约 135MB 内存）。往回滑、一次跳过好几条时没有预起，
    退回现建引擎。
- 事件：攒一批报 `/reels/events`，含「滑到出画面」的等待时间。
  first_frame 的 `detail` 还带起播方式（2026-09-30 加）：`start` = standby（预起好直接播）/ cold（现建引擎），
  `prefetch` = 这一条起播时的预取进度（full / light 已下完，*_running 还在下，none 没预取）；cold 时再带
  `load_ms`（停稳到发出装载）与 `stages`（装载后引擎各起播阶段在第几毫秒，阶段名同播放器页）。
  起因：真机蜂窝下冷启动 1.4～47 秒、Wi-Fi 下也有一条 9.8 秒，只有总时长拆不出慢在哪一步。

## 8. 预切片段（`mode=clip`，2026-10-10 立项）

### 8.1 为什么做

预告、刷片一直从原片中间直推原画。网络本身没问题，但在电视上太卡：4K 原盘一段 45 秒的预告要从片库
（NFS）读 90～340 MB，TV 端要开完整的自研引擎（4K 杜比视界一个约 135 MB 内存），首页大图背后同时解 4K
HDR，焦点动画跟着掉帧。NAS（Ryzen V1500B，**无核显**）实时转码撑不起「停留 2 秒就开播、好几台同时开」，
所以把转码挪到离线：后台把每部片挑好的那一段切成一个小文件，预告和刷片放它。小文件起播只要头 1 MB，
「停留 2 秒」本身就够把它拉完，客户端不用另做预加载。

### 8.2 用户拍板（2026-10-10）

| 问题 | 决定 |
|---|---|
| 剧集 | 不再做续播点回忆（`source=resume`）；首页、详情都放精彩片段，一部剧只切一段（最早一季第二集，同 §4） |
| 开关 | 设置 → 播放「片段预切」，**默认关**，文案讲清开启的好处；关掉时若已有切好的，问要不要删 |
| 范围 | 全库切；顺序要保证「马上要看到的」先切好（§8.5） |
| 没切好时 | 电视只显示剧照，不原地轮询，下次划回来切好了就放；手机刷片只出切好的 |
| 提醒 | 简洁：一个都没有时提示「正在预切，已完成 N / M」；刷到底提示没有更多 |
| 电视播放器 | 小片换系统播放器（Apple TV 用 AVPlayer，Android TV 用 ExoPlayer），不再开自研引擎 |
| 720p | 首版不切。以后要省移动流量，从 1080p 小片再转一份（不读原片，全库几分钟） |

### 8.3 规格与依据

| 项 | 取值 |
|---|---|
| 画面 | 宽不超过 1920、保持比例（不放大）；帧率超过 30 的减半（60→30、50→25） |
| 编码 | H.264 High，`-preset faster -crf 23 -maxrate 5M -bufsize 10M`，关键帧 2 秒，`yuv420p` |
| 色彩 | SDR BT.709。HDR / 杜比视界走封面抓帧同一套色彩决策（`thumbs.build_filter_chains`，`tonemapx`）：P5 只给映射链，映射不了就不切 |
| 音频 | 与刷片同一条音轨（`choose_audio`），AAC-LC 立体声 128 kbps；响度统一到 -23 LUFS（`loudnorm`，LRA 9，接近电影原片的对白响度，「接着看」切回原片不突兀），首尾 0.15 / 0.5 秒淡入淡出；切完实测小片响度，偏差超过 1 LU 就补一次增益并限峰（单遍 loudnorm 在 45 秒片段上 NAS 实测偏差到 3 LU） |
| 封装 | MP4，`+faststart`（索引在文件头） |
| 字幕 | 不压进画面。文字字幕沿用片段字幕窗口（`ReelSubtitleView.url`），App 按 `segment.start_ms` 换算到小片时间；图形字幕（PGS）没有——与外网转码刷片同一口径 |
| 体积 | 一段 45 秒约 14～28 MB；全库（电影 + 剧集约 940 部）约 20 GB |

实测（2026-10-10，本机 VMAF 0.6.1，参照为同尺寸无损 SDR，电视模型 / 手机模型）：

| 样片 | 码率 | 45 秒 | 电视 | 手机 |
|---|---|---|---|---|
| 雄狮少年（动画，4K） | 2.5 Mbps | 14 MB | 95.9 | 100 |
| 八佰（4K HDR10 → SDR） | 3.8 Mbps | 24 MB | 96.9 | 100 |
| 127 小时（1080p 原盘，颗粒重） | 3.3 Mbps | 19 MB | 93.3 | 99.8 |
| 长津湖之水门桥（4K 60 帧 → 30 帧） | 4.5 Mbps | 28 MB | 90.4 | 99.2 |

- **为什么定质量 + 封顶，不定码率**：同样 VMAF 93～95，动画只要 1.8～2.5 Mbps，颗粒重的片要 3.2～6.5 Mbps，
  差好几倍。这正是 Netflix 放弃固定阶梯、改按片定码率的理由（固定阶梯 1080p 5800 kbps，动画用不完，
  复杂内容仍有色块）。封顶 5 Mbps 落在 Apple HLS 规范 H.264 1080p 档（6000 / 7800 kbps，峰值不超过平均
  两倍）之下：预告是背景画面，不是正片。
- **为什么降帧**：水门桥保持 60 帧，4.7 Mbps 只有 85.8；降到 30 帧同码率 90.4。
- **为什么不用 HEVC**：x265 同画质省 25%～37% 码率，但编码慢 10 倍以上，NAS 只能软编；H.264 所有设备都能硬解。
- **为什么只切 1080p**：手机模型下 720p 1.3～1.9 Mbps 已有 99 分，省一半流量，但首版只有外网刷片受益；
  720p 能事后从 1080p 小片补，不用现在决定。
- **为什么用 `faster` 档**：实测 CPU 大头是编码不是解码（八佰 45 秒：只解码 53 CPU 秒，加 1080p `medium` 编码共 300 秒）。
  `faster` 比 `medium` 省 31%～37% CPU，VMAF 平均只低约 0.3、码率基本不变；`veryfast` 再省约 15%，但低约 1 分、码率多约 15%。
- 顺带测过「一次解码同时出 1080p + 720p」：CPU 多 34%～41%；单独再压一遍 720p 多 64%～69%。以后要 720p 从 1080p 小片转最省。

### 8.4 存储与失效

- 文件：`data/cache/reels-clips/<文件 id>/<起点毫秒>-v<CLIP_VERSION>.mp4`，旁边一份同名 `.json` 记大小、
  时长、来源文件的大小与修改时间。挑点结果（§3 的缓存）变了起点，名字就变了；切新的时删掉同目录旧的。
- 规格变了（`CLIP_VERSION` +1）全部重切；洗版换文件（大小 / 修改时间变）重挑重切。
- 台账里已经没有的文件，补切开始时顺手清掉目录。
- 关开关时有切好的：设置页问「已有 N 个片段（X GB），要删除吗」，删就整目录清掉；不删留着，再开即用。

### 8.5 先切谁：四档队列

单路串行（一次只跑一个 ffmpeg，`nice 19`）。新活按档入队，同档去重：

| 档 | 内容 | 顺序 |
|---|---|---|
| 0 眼前 | 预告 / 刷片请求到了、但还没切的那部 | 后到先切，只留最近 3 部，更早的降到档 1 |
| 1 首页会出现的 | 近 30 天有观看记录的、最近入库的 40 部、新入库 / 洗版换了文件的 | 最近的先 |
| 2 其余电影与剧集 | 全库剩下的 | 按刷片同一套评分权重从高到低（只切一部分时，刷片也是高分片先有） |
| 3 「其他」库 | 家庭录像等 | 有人刷过「其他」才开始，沿用 `_fill_pool` 的懒启动 |

- **插队**：档 0 来了，正在切的是档 1～3，就停掉 ffmpeg、放回原档（最多浪费几十秒算力）。
- **让路**（复用片头识别的 `skip_segments.playback_load()`）：本机在转码 → 全停；有人在看 → 只切档 0；空闲 → 全切。
  **预告与刷片自己的取流不算「有人在看」**：刷片令牌本来就不带设备标识、不登记播放活动（§5），小片路由同样不登记，
  否则在首页浏览反而会把预切停掉。
- **进度**：不进任务中心（那套持久化作业为可恢复的一次性任务设计，切片队列是常驻、要实时插队的），设置页开关下方直接写
  「已切 N / M」，因播放暂停时写原因。队列在内存里，重启后由下一轮补排恢复。
- 开关打开时排一轮全库；之后入库、换文件时补排；服务重启后第一次有人要片段时再排一轮（已切的只查一下记录）。

### 8.6 接口

- `GET /reels?modes=seek,clip`：开关开着且 App 声明会放 `clip` 时，**只出切好的**，`play.mode = "clip"`，
  `play.clip_url`（`/api/v1/reels/clips/<文件 id>/<起点>.mp4?token=…`，支持 Range）、`play.size_bytes` 是小片大小；
  `segment` 仍是原片时间轴（「接着看」照旧用它）。响应加 `clips: {ready, total, state}`（可空，开关关着为 null）。
- `GET /reels/preview/{id}?modes=seek,clip`：开关开着、App 会放 `clip` 时，一律放精彩片段（忽略 `source=resume`）；
  切好了返回 clip 条目，没切好返回 null 并把这部排进档 0。
- 老 App（`modes=seek`）行为完全不变，开关开着也照旧放原片。
- 设置：`playback.reel_clips_enabled`（默认 false）。`GET /reels/clips/stats` 给 `{count, bytes}`（关开关前问删不删用），
  `DELETE /reels/clips` 清空（管理员）。

### 8.7 各端

- **Apple TV**：预告条目是 clip 时用 AVPlayer 放小片（淡入、声音渐入、放完淡回剧照的节奏不变），不开引擎、不切显示模式；
  返回 null 保持剧照。
- **Android TV**：clip 时 ExoPlayer 直接放小片（不再 `ClippingConfiguration`），光盘条目不再跳过。
- **iPhone 刷片**：开关开着只出切好的。一个都没有：空状态写「片段正在预切，已完成 N / M」；刷到底（`exhausted`）
  末尾一页写「没有更多了」，没切完时补一句「其余还在预切」。小片不需要预起第二个引擎与字节预取。

### 8.8 验收

- 服务端：队列档位 / 插队 / 让路 / 失效 / 开关的单元测试；本机夹具起服务，真切几段片子（HDR、60 帧、原盘），
  ffprobe 核对规格，Range 取流、播放活动不登记。
- 各端模拟器：TV 首页停留出预告、没切好只剩剧照、切好后划回来能放；手机刷片空状态、刷到底提示。
- NAS：开关打开后的整库补切耗时、CPU、读盘，播放时让路生效。
