# 图片尺寸统一设计：母版、派生与各端取图

> 状态：已拍板（2026-10-04）。
>
> 起因是 Apple TV 上的图片不够清楚。排查下来，问题不在某一档设得太小，而在三层各定各的：
> 刮削存多大、服务端派生多大、客户端要多大。这三层都只按「网页 2 倍屏」考虑过。
> 本文把三层统一成一套口径，并据此重做刮削的图片设置。
>
> **用户决策（2026-10-04）：**
> - 默认画质给原图，体验优先，不为磁盘做规整。
> - 头像要本地化，详情页能看到的演职员全部落本地，同一个人只存一份。
> - 老用户升级后自己点「刷新元数据」生效，不另做升级任务。
> - 保留「自定义」档位。
> - 附录 A 的问题按最佳实践处理，处理状态见附录。
>
> 相关文档：`metadata.md` §6（图片资产）、`scrape-customization.md` §2.2 / §14（档位设置）、
> `cache-management.md`（图片缓存）、`tvos-app.md`（电视首屏与卡片）。

## 1. 现状（排查时，2026-10-04）

### 1.1 三层各管各

```
TMDB / 条目目录图 / 抓帧 / 用户上传
   │  刮削时下载一次（要联网）
   │  档位来自设置页三个下拉，默认：海报 w780 · 背景 original · 剧照 w300
   ▼
母版  data/metadata/images/<条目 id>/
   │  断网可读的事实源，同时镜像进媒体目录给 Emby / Kodi
   │  请求时按 variant 生成 WebP：8 个预设，按「设备 × 场景」命名（poster-card、tv-poster……）
   ▼
客户端  Web · iPhone · Apple TV · Jellyfin 客户端
        各自假设屏幕倍率，挑一个预设名
```

### 1.2 哪里糊、哪里浪费

- 显示尺寸按布局代码推算。
- 「够不够」= 实际给到的像素宽 ÷ 需要的像素宽，低于 0.9 时肉眼能看出发虚。
- 电视按 4K（2 倍）算，获得焦点时卡片放大约 1.1 倍；iPhone 按 3 倍算。

| 端 | 场景 | 显示宽 | 需要（px） | 实际给到（px） | 够不够 |
|---|---|---|---|---|---|
| Apple TV | 详情页分集剧照 | 416 点 | 832，焦点 915 | ≤300（母版 w300） | **0.33～0.36** |
| Apple TV | 媒体库海报墙 | 333 点 | 666，焦点 732 | 540（tv-poster） | 0.74～0.81 |
| Apple TV | 演员头像 | 210 点 | 420，焦点 470 | 300（远程 w300） | 0.64～0.71 |
| Apple TV | Top Shelf（剧集） | 908 点 | 1816 | ≤300 | **0.17** |
| Apple TV | 播放器「下一集」 | 256 点 | 512 | ≤300 | 0.59 |
| iPhone | 媒体库海报墙（2 列） | 174.5 点 | 523 | 328（poster-card） | 0.63 |
| iPhone | 「刚刚入库」横卡 | 264 点 | 792 | 480（landscape-card） | 0.61 |
| iPhone | 分集剧照 | 200 点 | 600 | ≤300 | 0.50 |
| iPhone | 视频墙（单列） | 361 点 | 1083 | 480 | **0.44** |
| Web 手机 | 海报墙 | 173 CSS px | 519 | 328 | 0.63 |
| Web 桌面 2x | 海报墙 | 164 CSS px | 328，悬停 348 | 328 | 0.94 |

另一头是浪费：

- **iPhone 详情页大图**：显示框 393×452 点，取的是母版原图（最大 3840 宽），解码后约 33MB。
- **1080p 电视**：只需要 4K 电视一半的宽度，现在按 4K 取，像素量是需要的 4 倍。
- **电视首屏亮度分析**：为了算一个 24×24 的亮度值，解了一整张 4K 位图（`TVStageCornerScrim`、`TVStageEdgeColor`）。
- **Web 详情页 Logo**：显示 420 CSS px，取的是原图 PNG。

### 1.3 根因

1. **母版：剧照只存 w300。**
   - 本地开发库 4441 张剧照里，4195 张是 300×169，平均 8.8KB。
   - 母版只缩不放，后面怎么派生都救不回来。
   - TMDB 的剧照档位只有 w92 / w185 / w300 / original，中间没有档。要清楚只能下原图。
2. **母版：头像根本不落本地。**
   - 演员、导演头像一律是 TMDB 远程地址（`items.py` 注释：「头像不入本地资产」），断网就空。
3. **派生：预设按设备命名，尺寸按网页定。**
   - `poster-card` 328 宽，是按网页 2 倍屏 164 CSS px 定的。iPhone 墙要 523，也拿它。
   - `tv-poster` 按首页 266 点的卡定，333 点的海报墙也拿它。
   - 每加一种布局，后端就得加一档、发一版。旧服务器不认识新名字，直接回 422。
4. **客户端：写死倍率，也不认「铺满」。**
   - tvOS 没有一处读屏幕倍率。
   - Web 不用 `srcset`。
   - 详情页大图「要不要原图」的闸门只看宽度。竖框铺满 16:9 背景其实要按高度算，见 §6。
5. **库内还有「永远远程」的图**，断网就空：
   - 头像；
   - 「接着看」的原图剧照；
   - 订阅卡片，包括「刚刚入库」；
   - 系列面板里已入库的部分；
   - 推送图片。
   - 远程图缓存是 2GB 的 LRU，不是离线保证。

## 2. 目标与非目标

**目标：**

1. **库内场景的每一张图都来自本地母版。** TMDB 不通或服务器断网时，媒体库、详情页、首页和电视端照样完整。
2. **每端每个场景拿到「刚好够」的像素。** 4K 电视上卡片获得焦点放大也不糊；手机不白下 4K 原图。
3. **加设备、改布局不改后端。** 客户端自己算需要多少像素，服务端只认一套通用的宽度阶梯。
4. **刮削设置说人话。** 用户选的是「画质与空间」，TMDB 档位收进「自定义」。

**非目标：**

- 发现、搜索、订阅前预览这类**未入库内容**的离线。它们天然依赖 TMDB / 豆瓣。
- 换图片格式（AVIF、HEIC）。
- 进度条预览图（trickplay），见附录 A 第 10 条。

## 3. 三层分工

| 层 | 回答的问题 | 由谁决定 | 不变量 |
|---|---|---|---|
| 母版（刮削落盘） | 这张图**最多**能有多清楚 | 刮削画质设置 | 每个资产一份；默认存原图；断网可读 |
| 派生（请求时生成） | 这次**传**多少像素 | 请求里的 `w` | 只缩不放、不裁切；档位有限（缓存键有界）；可删可重建，断网也能重建 |
| 客户端 | 这个位置**需要**多少像素 | 布局 × 屏幕倍率 × 放大系数 | 向上取到阶梯；不写死倍率 |

「本地优先」和「各端尺寸」由此协调：

- 刮削只负责存一份**足够大**的母版。默认就是原图，不设上限。
- 各端要多大，在服务端本地派生。派生只用 CPU，不联网。
- 所以无论哪一端、取什么尺寸，都不需要联网。

## 4. 母版

### 4.1 每类资产要多大

| 资产 | 各端最大需求场景 | 需要宽（px） | 原图能否满足 |
|---|---|---|---|
| 海报（含季海报） | 电视海报墙焦点 732；iPhone 墙 523；Web 手机 519 | ~730 | 能（原图多为 2000×3000） |
| 背景 | 电视全屏 3840；iPhone 竖框铺满约 2400～2800；Web 4K 全屏 3840 | 3840 | 能（原图多为 1920～3840 宽） |
| 片名 Logo | 电视详情页 860 点 → 1720 | 1720 | 能 |
| 分集剧照 | 电视横卡焦点 915；iPhone「刚刚入库」792 | ~920 | 能（原图多为 1920×1080） |
| 演员 / 导演头像 | 电视 470；iPhone 与 Web 约 312 | ~470 | 能 |
| 库封面、合集封面 | iPhone 管理页全宽 1083；电视 720 | ~1080 | 本地拼图 1260×600，够 |

「原图」等于 TMDB 上传的那一张。少数剧照原图本身只有 480×270，这种情况任何档位都没法让它变大。

### 4.2 改动

**默认画质给原图**：海报、背景、剧照、头像都存 TMDB `original`，不设宽度上限、不在本地规整。

**下载要原版字节**（已修复，附录 A 第 3 条）：

- 下载时点名要扩展名对应的格式：Logo 要 PNG，其余要 JPEG。
- 原因：图片代理默认按浏览器发 Accept，TMDB 的 CDN 会据此回有损 WebP。这样存下来的「原图」并不是原图，镜像给 Kodi / Emby 的 `.jpg` 也是 WebP 冒充的。

**抽帧剧照**（TMDB 缺剧照时从视频抽一帧）：上限从 640 提到 1920，与 TMDB 原图剧照常见的尺寸对齐。

**头像落本地**：

- **范围**：详情页能看到的全部演职员，即演员表（最多 40 位，`_MAX_CAST`）加导演 / 主创（最多 5 位）。各端都是整排展示，所以全部下载。
- **存储结构**：

  ```
  data/metadata/people/              ← 新目录，按发布规范第 4 条在 storage/registry.py 登记、声明为 Settings 字段
    original/                        ← 档位一层：换档位整层替换，旧层整体作孤儿清理
      kj/                            ← TMDB 文件名前两位分桶，单个目录的文件数可控
        kjz9dl25oi1stWmb7TVnBSBP51y.jpg
  ```

  - **按 TMDB 头像路径命名**：TMDB 的图片路径即内容身份，换图就是换路径，所以同一个人在多少部片里出现都只存一份。本地开发库 4059 条带头像的演员记录，去重后是 3094 张。
  - **不需要数据库列**：有没有下载过，看文件在不在就知道；人物换了新头像，按新路径下载，旧文件变成孤儿。
- **下载时机**：跟随条目刮削，`download_item_assets` 下完条目图之后下载。文件已在就跳过，所以刷新不会重复下载，`force` 也不必重下（路径不变，内容就不变）。
- **NFO 头像**：NFO 里 `<thumb>` 是 TMDB 地址的，换算成头像路径，走同一套；其他来源的地址保持远程（少见）。
- **清理**：头像路径没有被任何条目的演职员表或人物表引用时，算孤儿，在缓存管理里清理。
- **出图**：新增 `/images/people/…` 路由，需要登录，同样支持 `w`。接口里有本地文件的就给本地地址，没有就给远程兜底地址。

**加锁的图也随档位重下**（已修复，附录 A 第 1 条）：锁保护的是「用哪张图」，不是「用多大的分辨率」。

### 4.3 磁盘账

以本地开发库为例：525 张海报（含季海报）、274 张背景、5220 集、约 3200 张头像（去重后）。

| 方案 | 海报 + 季海报 | 背景 | 剧照 | 头像 | 合计 |
|---|---|---|---|---|---|
| 现状（w780 / original / w300，WebP 协商，无头像） | | | | — | 0.28GB（实测目录） |
| **原图（默认）** | 398MB | 347MB | 981MB | 874MB | **约 2.6GB** |
| 标准（w780 / original / original / h632） | 161MB | 347MB | 981MB | 147MB | 约 1.6GB |
| 节省空间（w500 / w1280 / w300 / w185） | 78MB | 79MB | 57MB | 35MB | 约 0.25GB |

单张均值按 TMDB 原版 JPEG 计，取自 2026-10-04 抽样（剧照 12 张，海报、背景、头像各 8 张）：

| 资产 | 档位：单张均值 |
|---|---|
| 海报 | w500：148KB · w780：306KB · original：759KB |
| 背景 | w1280：288KB · original：1265KB |
| 剧照 | w300：11KB · original：188KB |
| 头像 | w185：11KB · h632：46KB · original：273KB |

量级换算：

- 每 1000 集剧照约 190MB。
- 每 1000 张头像：原图约 270MB，h632 约 46MB。
- 每 1000 部的海报加背景约 2GB。

两点说明：

- **原图档的磁盘大约是现在的 9 倍。** 这是体验优先的取舍。
- **头像原图对显示几乎没有增益。** 最大需求约 470 像素宽，h632 已经够用，但原图占了头像磁盘的约 85%。日后如果在意磁盘，「标准」档去掉的主要就是这一块。

## 5. 派生：一套宽度阶梯

### 5.1 规则

- **请求**：任何服务端图片地址后加 `w=<需要的像素宽>`。
- **取档**：服务端把 `w` 向上取到阶梯 `160 · 240 · 360 · 480 · 720 · 960 · 1280 · 1920 · 2560 · 3840`。
  - 相邻两档之间不超过 1.5 倍。
  - 超过 3840 按 3840 算。
- **母版宽不超过该档**：直接回母版文件，不重新编码。
- **母版宽超过该档**：
  - 等比缩到该档宽；
  - 高度不超过宽的 2 倍；
  - 不裁切、不放大，输出 WebP q80。
- **缓存键**：`image-variant:v3:w<档>:<来源>:<版本>`，每张母版最多 10 个派生，缓存键有界。
  - 远程来源只认 URL，不带原图版本（已修复，附录 A 第 7 条）。
- **解码提速**：母版改存原版 JPEG 后，可以用 Pillow 的 `draft` 在解码阶段直接按 1/2、1/4、1/8 缩小。原图做默认后，派生的 CPU 开销主要在解码 4K 原图上，`draft` 能把它降一个量级。

### 5.2 所有出图路由一视同仁

现在只有 `/images/assets` 和 `/images/proxy` 认 `variant`。下面这些路由收到参数会悄悄丢掉：

- 条目目录图
- `-thumb` 旁挂图
- 库封面、合集封面
- 账号头像

改成：这些路由加上新的头像路由，统一认 `w`，照片原图也用 `w` 取代 `?size=screen`。客户端的规则随之简化为一句话：**凡是服务端给的图片地址，都可以带 `w`。**

### 5.3 兼容

| 情况 | 处理 |
|---|---|
| 旧客户端的 `variant=` | 已经发布过的 6 个预设原样保留，行为不变。`tv-poster` / `tv-landscape` 没进过任何发布版本（v0.30.0 之后才加），映射成 `w=960` |
| 新客户端连旧服务器 | 旧服务器不认识 `w`，FastAPI 会忽略未声明的查询参数，直接回母版原图：大一点，但清楚。iOS 现有的 422 兜底保留 |
| Jellyfin 客户端 | `maxWidth` / `width` / `fillWidth` 取到同一阶梯，走同一个派生服务，输出 JPEG（带透明的输出 PNG），取代现在接受任意宽高的 `_render_scaled` |

**过渡期提醒**：P1 落地之前，不带派生参数取图的地方会拿到更大的原版 JPEG，比如电视首屏、iPhone 详情页大图、Jellyfin 不带缩放参数的请求。背景原图平均 1.2MB，过去协商出来的 WebP 约 0.56MB。所以 P1 应该与本分支一起或紧随其后发布。

### 5.4 否决的方案

- **刮削时按设备各存一份**：磁盘翻几倍；出新设备、改布局就得整库重刮。
- **继续加设备预设**：每个新布局都要后端发版，旧服务器回 422。
- **任意宽度**：缓存键无界。
- **客户端直接按 TMDB 档位取远程图**：违背本地优先。

## 6. 客户端：按公式要像素

**公式：需要宽 = 有效宽 × 屏幕倍率 × 放大系数，再向上取到阶梯。**

- **有效宽**：
  - 等比装下（contain）取框宽。
  - 铺满（cover）取 `max(框宽, 框高 × 图片宽高比)`。竖框铺满 16:9 背景要按高度算：iPhone 详情页 393×452 点，按宽只算出 1179，按高要约 2410。
  - 图片宽高比未知时按资产类型取：海报、头像 2:3；背景、剧照 16:9。
- **屏幕倍率**：tvOS 和 iOS 读 `displayScale`（接 1080p 电视为 1）；Web 交给 `srcset`。
- **放大系数**：电视卡片焦点 1.1、电视头像焦点 1.12、首屏慢推 1.06～1.1、Web 海报悬停 1.06。
- **统一取整**：各端内置同一张阶梯表，先取整再拼地址，同一档就是同一个 URL，缓存可以复用。

**各端落点：**

- **Apple TV**
  - 首屏和详情页大图改成 `w=屏宽像素`。
  - 亮度和边缘色分析改取 `w=240` 的小图。
  - 预载器预载实际要显示的那一档。
  - Top Shelf 统一取背景图的 1920 档。
- **iPhone**
  - 3 倍屏按 3 倍取，海报墙从 328 升到 720 档。
  - 全屏大图按公式取，详情页约 2560 档，不再取原图。
- **Web**
  - 卡片用 `srcset` + `sizes`。
  - 大图区用 JS 按公式算一个 `w`。
  - `upgradedTmdbOriginalUrl` 只留给发现页的远程图。

## 7. 本地优先：库内场景只读本地母版

**规则**：凡是描述**库内条目**的图片字段，取图顺序一律为：条目目录图 → 本地母版 → 远程。远程只在母版还没下好时才用。

| 现在永远远程的字段 | 改法 |
|---|---|
| 详情页演员和导演头像、影人页头像、刷片导演头像、Jellyfin 人物图 | 头像落本地（§4.2） |
| 「接着看」的 `episode_still_original_url` | 剧照母版改存原图后就不再需要；字段保留给旧客户端，新客户端只用 `episode_still_url` + `w` |
| 订阅 `MediaBrief` 的海报、背景、Logo（包括「刚刚入库」） | 订阅对象已在库里时用本地资产 |
| 系列面板里**已入库**的部分 | 用本地资产 |
| 推送图片 | 服务端取图时先找本地资产 |
| 管理类列表 | 有本地资产就用本地，优先级低 |

**统一远程兜底档**：现在各接口各写一档（墙 w500、详情 w1280、「接着看」背景 w780……），改成一个构造函数，按**当前母版档位**生成远程地址。图床地址走设置页配置的镜像，这一条已在本分支统一（附录 A 第 5 条）。

**远程图缓存的定位**随之收窄为「未入库内容的加速」。它被淘汰或清空时，媒体库不会缺图。

## 8. 刮削设置：选画质，不选 TMDB 档位

### 8.1 界面

「设置 → 刮削与整理 → 图片」里，原来的三个 TMDB 档位下拉改为一项单选：**本地图片画质**。

| 档 | 界面文案 | 海报 | 背景 | 剧照 | 头像 | 本地开发库估算 |
|---|---|---|---|---|---|---|
| **原图（默认）** | 所有图存 TMDB 原图，各设备都最清楚 | original | original | original | original | 约 2.6GB |
| 标准 | 各设备都清楚，头像与海报不存原图，省约四成空间 | w780 | original | original | h632 | 约 1.6GB |
| 节省空间 | 手机和网页够用；电视上剧照、头像会发虚 | w500 | w1280 | w300 | w185 | 约 0.25GB |
| 自定义（默认收起） | 展开四个下拉（现有三个，加头像） | … | … | … | … | 实时计算 |

- **估算**：每一档旁边显示「按当前媒体库估算约 X GB」，服务端用条目数、季数、集数、头像数乘以 §4.3 的单张均值算出来。
- **作用范围不变**：全局默认，加上按条目「刮削归属库」的库级覆盖。库级覆盖里留空就是跟随全局（附录 A 第 2 条已修复）。
- **「最低分辨率门槛」不动**：它管选哪张图，不是存多大。
- **存量配置**：
  - 以前显式保存过档位的，视为「自定义」，行为不变。
  - 留空的跟随新默认「原图」。
  - 环境变量 `TMDB_*_SIZE` 显式设过的，同样视为「自定义」。
  - 全程走 SettingStore，不需要数据库迁移。

### 8.2 换档怎么生效（不做升级任务）

- **立即生效**：在媒体库点「刷新元数据」，所有图片强制按当前档位重下。手动选定的图也随档位重下，选的还是那一张。
- **自然追平**：不点也会慢慢跟上。定时刷新轮到哪个条目，就按溯源记录（`sources.json` 里的「档位 + 路径」）发现档位变了而重下。
  - 在播的订阅剧 8 小时一轮，未订阅的条目 30 天一轮。
  - 早先落下的 WebP 冒充 `.jpg` 的资产，也在这时按格式不符重下。
- **老用户升级**：默认变成原图之后，存量图片靠上面两条生效，不另做后台任务。保存设置后的提示文案维持现状：「存量条目在媒体库页执行『刷新元数据』后按新配置更新」。

### 8.3 刷新进度要看得见明细（本分支已实现）

原图做默认后，图片下载量大约是原来的 9 倍，长剧刷新一次要几分钟。原先任务中心有三个问题：

- 整库刷新只显示「已刷新 X / Y」，每 3 部才跳一次；
- 单条目刷新的「下载图片」是一个不动的黑盒；
- 单张图下载失败只写日志。

现在的做法：

- **图片逐张记账**（`AssetTally`）。
  - 先数清这一轮要处理的图床图片张数，每张结算成三种结果之一：新下载、沿用（档位与来源没变、文件完好）、失败（保留旧图，下次刷新自动补下）。
  - 从视频抓帧补的剧照单独计数。
  - 刮削的阶段文案随之变成「下载图片 120 / 480 · 已下 230 MB」，详情页和媒体库卡片沿用的旧阶段文案也自动带上张数。
- **单条目刷新**：
  - 进度带上「第几步 / 共几步」（拉取档案 → 写元数据 → 读本地 NFO → 下载图片 → 写媒体目录）；
  - 下载图片那一步按张数显示确定进度；
  - 完成摘要示例：「新下载 312 张（1.2 GB）、沿用 168 张、3 张失败，下次刷新自动补下」。
- **整库刷新**：
  - 每完成一部就推进计数，不再等一整批；
  - `details.active` 列出正在处理的几部和各自阶段；
  - `details.images` 是全库汇总的记账；
  - 进度条按「已完成部数 + 正在处理的各部完成到几成」来走。
  - 断点续跑的位置单独存在 `details.checkpoint`，仍然按整批前移，与展示用的计数互不干扰。
- **任务卡**（Web 和 iOS 同一套规则，最多 4 个标签）：
  - 依次显示：正在处理的那部及其阶段、「另有 N 部进行中」、未完成的条目数（琥珀色）、未下载的图片数（琥珀色）、新下载张数和体积、沿用张数。
  - 有失败时，完成后的任务卡保持展开，不收成一行。
  - 进度单位区分：单条目刷新是「张图片」，整库刷新是「个条目」。
- **控制写库频率**：内存里的进度随时更新，写进任务表最多每秒一次（`_ProgressWriter`）。内容没变不写；检查点和收尾时立即写。
- **端到端验证时发现、已修的两处**（2026-10-04，隔离后端 + 真实 TMDB + Web 截图）：
  - **默认主题的「活动」页根本不显示明细。** 它用的是时间线（`task-center-view.tsx`），不走任务卡的标签逻辑。
    - 所以整库刷新的摘要一句话就写出正在处理哪部：「正在刷新「XX」：下载图片 4 / 9 · 已下 2.0 MB（另有 1 部同时进行）」。片名用「」，因为时间线会把《》里的内容当成任务标题。
    - 进行中的元数据刷新行补上图片标签。
    - 已结束行在有未下载的图片或未完成的条目时，用黄色对勾代替绿色。
    - Web 和 iOS 两端一致。
  - **任务事件流（`/jobs/stream`）缺 `no-transform`。** 经 Next 代理时被 gzip 攒住，一条事件都到不了浏览器，活动页只能等 60 秒一次的兜底轮询，进度看着不动。补上之后实测每秒一条（同 agent 和 search 的 SSE）。
- **不做的事**：
  - 不显示剩余时间。图片大小相差几十倍，估出来的时间会来回跳。
  - 失败的图片不单独给「重试」按钮。任务本身算成功，失败的图在下次刷新时会自动补下，摘要里已经写明。
