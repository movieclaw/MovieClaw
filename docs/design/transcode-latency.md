# 转码链路时延：起播与跳转

> 状态：**测量手段（§2、§3）与前两轮优化（§4.1 回拖、§5 边产出边送）已实施，连真实 NAS + Mac Worker 验证中**（2026-10-01）。
> 前置阅读：[remote-transcode.md](remote-transcode.md)（远程 Worker 的协议与命令形态）、
> [playback-qoe.md](playback-qoe.md)（播放器的打点口径与迭代方法，本文照搬）、
> [player-pipeline-optimization.md](player-pipeline-optimization.md)（VOD 会话、闭环节流、缓存复用；§D 当年判「边写边发」不可行的理由）。

## 0. 范围

- **做**：远程硬件转码这条链路——客户端开会话 → NAS 派单 → Mac Worker 上的 ffmpeg 取源、转码 → 回传 NAS → 客户端取分片——
  从用户动作到画面出现的时延；以及这条链路上 NAS 侧的会话逻辑（重启判定、分片交付）。
- **不做**：直出 / 换封装（App 自研引擎那条路见 playback-qoe.md）；NAS 环境本身（盘、网络挂载、负载）。
- 测量用的客户端是 macOS 上的系统 AVPlayer——与 iOS App「限画质 → 服务端转码流」同一套 AVFoundation（自研引擎的
  remoteBypass 就是 AVPlayer 直接取服务端 HLS）；hls.js 的口径（整段到齐才喂解码器）另有 `segments` 模式近似。

## 1. 指标与目标

### 1.1 口径

一律从**用户动作**算到**画面出现**，单调钟、毫秒，与 playback-qoe.md §1.3 一致：

| 指标 | 起点 | 终点 |
|---|---|---|
| 转码起播首帧（续播 / 从头） | 发出开会话请求（`POST /playback/sessions`） | 第一帧可上屏（`AVPlayerLayer.isReadyForDisplay` 或第一个像素缓冲，取早的） |
| 缓冲外跳转出画（前跳 / 回跳） | 发起 seek | 落点那一帧（显示时间在目标 −0.25～+3 秒内）可上屏 |
| 缓冲内跳转出画 | 同上 | 同上（分片已在 NAS 上，只看客户端） |

前跳 = 跳到转码头前方 10 分钟；回跳 = 跳回续播点前 4 分钟（转码头后方）。两者都要重启远程任务，是转码链路最慢的路径。

### 1.2 目标（局域网，Mac Worker）

北极星沿用 playback-qoe.md：起播 > 2 秒、跳转 > 1.5 秒就算打扰。转码链路的目标：

| | p50 | p90 |
|---|---|---|
| 续播首帧 | ≤ 1.0 秒 | ≤ 1.5 秒 |
| 从头首帧 | ≤ 0.8 秒 | ≤ 1.2 秒 |
| 缓冲外跳转（前跳 / 回跳） | ≤ 1.0 秒 | ≤ 1.5 秒 |

原盘（UHD 蓝光目录）另算：源 50～90 Mbit/s、多剪辑 m2ts，取源本身就重，目标是 p90 ≤ 3 秒。

### 1.3 护栏

- 不出现起播后的卡顿（AVPlayer 等缓冲，`timeControlStatus` 回到等待）；
- 远程任务失败率、补片重启次数不升；
- NAS 的取源读量不升（时间线里 `src` 的 `kb` 总和）。

## 2. 时间线：把一次起播拆开

以前只有「播放会话就绪」（派单前）与「首片供给…距会话创建」（交付后）两行日志，中间一秒多全在 Worker 上，看不见。
现在会话带一份**时间线**（`TranscodeSession.timeline`），诊断接口 `GET /playback/sessions/{id}/diagnostics` 的 `timeline`
字段原样返回；首片交付时「首片供给」日志后面附一句分段（`_startup_breakdown`）。每条是距会话创建的毫秒数（NAS 单调钟）：

| 事件 | 记在哪 | 含义 |
|---|---|---|
| `prep` | 开会话 | 目录与台账就绪（认领缓存要 stat 源文件，媒体在网络挂载上时不一定便宜） |
| `dispatch` / `accepted` | 派单 / Worker 回 `job.accepted` | 每一轮远程任务各一对（`prog` 标出是不是边产出边送） |
| `spawn` | 本机 ffmpeg 拉起 | 只有本机转码才有 |
| `src` | 取源请求结束 | `mb` 从哪读起、`kb` 读了多少、`ttfb` 首字节、`dur` 整个请求、`cut` 是否被掐断；每轮最多 40 条 |
| `put` / `frag` / `landed` / `put_fail` | 产物上传 | 开始收、边产出边送的第一块落盘、整个产物落盘 |
| `req` / `served` / `miss` / `gone` | 客户端取分片 | 请求、交付（`wait` 等了多久，`partial` 是边产出边送的半截）、没给出、客户端等不及断开 |
| `restart` | 重启直奔 | 目标分片、原因、当时的转码头与已产出到 |
| `w_*` | Worker 报来（`job.timeline`） | 以这一轮 `dispatch` 为零点换算，`wt` 是 Worker 自己的毫秒数 |

Worker 侧（`JobTimeline`）以收到 `job.start` 为零点：`proxy`（上传代理就绪）、`ffmpeg`（进程起来）、`input`（读完源文件头、
探测完流——stderr 的 `Input #0`）、`init_open`（第一帧过完滤镜、编码器起好）、`seg_open`（一段编完开写）、`recv`（代理收齐
ffmpeg 交来的产物）、`up`（传到 NAS）。要认出这几个节点，Worker 把 NAS 下发的 `-loglevel warning` 换成
`-loglevel level+info -nostats`，info 行只拿来认节点、不进 stderr 尾巴（尾巴里仍只有 warning 以上，也不会留下带令牌的源地址）。
首片传到 NAS 时整份发一次，任务结束前补发一次；旧版服务端按未知消息忽略。

一次真实的续播（4K HDR10 MKV，25 Mbit/s，生产 Mac mini，整段落盘）读出来是这样（毫秒）：

```
72 派单 → 76 接单 → 103～339 取源（文件头 6 MB 掐断、跳文件尾读 SeekHead、回文件头、文件尾读 Cues 649 KB、回文件头、
跳到续播点） → 1313 init 落盘 → 1323 首片开始回传 → 1333 落盘 → 1344 交付（客户端 1519 收完、1538 出画）
```

首片从「读到续播点」到「编完回传」用了 985 毫秒，之后每片 615 毫秒（6.5 倍速）——多出来的约 370 毫秒是硬解 / Metal /
编码器的冷启动和精确 seek 从前一个关键帧解到起点；而客户端要等**一整段**（4 秒内容）编完才拿得到第一个字节。

## 3. 实验台

`scripts/perf/transcode_lab.py` + `scripts/perf/transcode_probe.swift`（详见脚本头注释）：

- **语料**：`corpus` 子命令从 NAS 片库（只读、只取电影 / 剧集库）按格式挑：4K HDR10 / 杜比视界 MKV 与 MP4、4K SDR MP4、
  4K H.264 长 GOP 高码率、1080p H.264 MKV / MP4、1080p HEVC 10-bit、UHD 原盘、HLG TS，每类两部（`quick` 每类一部）。
  语料写在 `~/.config/movieclaw/transcode-lab-corpus.json`，不入库。
- **客户端**：探针以 iOS App 系统播放器的能力申报 + 限画质（4K → 1080p、1080p → 720p）开会话，AVPlayer 直接放；
  所有取流经本机的记录代理，逐请求记发出、首字节、收完（含客户端中途掐掉的请求）。慢线路档经 `netem_proxy.py`。
- **服务端 / Worker 视角**：每次播放结束前取诊断接口的时间线（§2），之后取 NAS 日志。
- **场景**：`resume`（37% 处续播 → 看 6 秒 → 前跳 10 分钟 → 看 5 秒 → 回跳到续播点前 4 分钟 → 看 4 秒）、
  `head`（从头播 → 看 6 秒 → 缓冲内跳 +12 秒）。
- **对照**：`--arms seg=no-progressive,prog=` 在同一台 Mac 上切换开发版 Worker 的开关，每部片各组都跑、先后轮换（AB / BA）；
  `report` 出中位 / p90 与按片配对的差值。

几条纪律（踩过才写下的）：

- **只在 Worker 空闲时开播，开出来不是「档 3 + 目标 Worker」就作废**：Worker 只有一个并发槽，被别人占着时会话会落到 NAS
  本机软件转码（档 4），既测错了东西，又把 NAS 的 CPU 打满（第一次冒烟就撞上了）。
- **每次播放前清掉这部片的转码缓存**，否则第二轮直接读上一轮转好的分片；占位会话（`--block-worker`）同理。
- **NAS 会被别的会话重新部署**：同一台 NAS 上还有别的会话在部署开发版（网页播放器那条线），部署前合并对方分支，批次里核对时间线字段
  是否还在。2026-10-01 下午就有一批跑到一半被换了服务端，后半批作废。
- 开发版 Worker 跑在 MacBook（Wi-Fi）上：绝对数字与有线的 Mac mini 不同，组间差值成立；占住 Mac mini 的唯一槽位后任务才会
  落到它身上（选 Worker 的规则是「任务最少、先连上的优先」）。
- **每次起播前把片源赶出 NAS 页缓存**（`--cold`，默认开，`posix_fadvise(DONTNEED)`）：不赶的话同一部片两组对照里先跑的读冷盘、
  后跑的读页缓存（文件尾小读首字节 20～30 毫秒对 2 毫秒），配对差里混进了先后顺序。真实用户打开一部片也多半是冷的。
- **等本机安静再起播**（`--max-load`，默认 1 分钟负载 6）：探针总在本机，本机当 Worker 时 ffmpeg 也在本机。2026-10-01 一批
  对照撞上别的会话打包（负载 14），Worker 起 ffmpeg、ffmpeg 发第一个请求、播放器要分片全慢了几百毫秒，那一组的结论整个
  反了过来；每次起播前后的负载记在结果里（`load`）。
- **环境事实**：MacBook 到 NAS 是 Wi-Fi（802.11ax）。空闲时往返 3～95 毫秒、平均 34（省电休眠，AWDL 开着）；有流量时
  p50 4 毫秒、p99 11 毫秒。NAS 的片库在另一台存储上（192.168.1.80，NFSv3 挂载，两台之间 0.5 毫秒、约 85 MB/s）：
  冷读一次要过两跳，NAS 侧首字节 20～90 毫秒（热缓存 2 毫秒）。

## 4. 基线与迭代

### 4.0 基线（生产 Mac mini Worker，客户端 MacBook Wi-Fi，19 部 × 2 场景 × 2 轮）

| | n | p50 | p90 | max |
|---|---|---|---|---|
| 从头首帧 | 38 | 1253 | 2281 | 4054 |
| 续播首帧 | 38 | 1778 | 3343 | 15795 |
| 前跳出画 | 38 | 1557 | 3691 | 6068 |
| **回跳出画** | 38 | **5111** | 5489 | 13330 |
| 缓冲内跳 | 38 | 96 | 113 | 142 |
| 开会话 | 76 | 59～71 | 189～252 | |

各类续播首帧中位：1080p 1.0～1.5 秒、4K HDR / DV 1.35～1.5 秒、4K H.264 长 GOP 2.3 秒、UHD 原盘 2.9 秒（冷读 6～8 秒）。

### 4.1 回拖不再熬探测宽限；等分片时客户端断开即注销

**缺口**：回跳中位 5.1 秒，几乎每次都是 4～5 秒。逐请求记录与 NAS 日志对上：

- 落后于转码头的分片请求要熬 `_PROBE_GRACE_S`（3 秒）才有资格重启——当年为了挡 iOS 在 JS seek 落地前从列表头狂打的
  seg00000；如今播放列表有 `EXT-X-START`、网页那次 JS seek 也去掉了，**真正的回拖却每次都白等 3 秒**；
- AVPlayer 一个分片请求等满约 4 秒就自己掐掉重发：3 秒宽限 + 1.5 秒转出 > 4 秒，于是先白等 4 秒、重发后才拿到；
- 客户端掐掉的请求，uvicorn 并不取消应用协程：没人要的旧请求一直挂在「在等的分片」表里直到 30 秒超时，重启判定把它当成
  客户端还要的分片。生产日志里就有跳转瞬间在途的旧请求熬过宽限后把转码拽回旧位置、紧接着又被新请求拽回来的重启来回。

**改动**：

- 宽限只给「像探测」的落后请求（`_behind_request_ready`）：列表头（第 0 段）且会话开出来不到 10 秒；或已经过时——挂号之后
  客户端又去要了别处（不是它往后几段的顺序预取）。客户端最新要的就是转码头后面的一段，就是回拖，立刻重启直奔。
- 分片等待挂一个后台 receive 盯断开（`await_unless_disconnected`），客户端掐掉就取消等待、注销挂号。

**结果**（同一台 Mac mini，前半批，NAS 中途被别的会话换了服务端，后半批作废）：回跳中位 5111 → 1482 毫秒，配对差值中位
−3.5 秒、26/28 次变快；其余指标在噪声内。

## 5. 边产出边送

**为什么**：时间线里首片最大的一块是「一整段编完」。ffmpeg 的 HLS muxer 把整段（4 秒）攒在内存里、转完才写出
（player-pipeline-optimization.md §7.4 实测过，加 `frag_duration` 会把切段搅乱），所以 §7.4 当年判「边写边发」不可行。
iOS 引擎的 P57 证实了另一半：AVPlayer 能边收边解一个还没写完的分片，收到第一个完整片段（moof + mdat）就能出画。

**方向先在本机验证**（4K HEVC → 1080p，本机 ffmpeg + 本机 HLS 服务 + AVPlayer，`progressive_exp.py`，三轮一致）：

| 起播点在分片里的位置 | 整段落盘 | 边产出边送（0.5 秒片段） |
|---|---|---|
| 分片起点 | 887～891 毫秒 | **403～410 毫秒** |
| 分片中间（+2 秒） | 893～919 | 706～712 |
| 分片末尾（+3.5 秒） | 932～936 | 926～938 |

播放器要解到起播点那一帧，起播点越靠后要等的片段越多——所以要与「起播点吸附到分片起点」配套。

**做法**：

- **命令**（`ffmpeg_args._progressive_args`）：Worker 申报了 `progressive_segments` 的远程 fMP4 点播任务，不用 HLS muxer，
  输出一整条分片化 MP4 PUT 给 Worker 的上传代理：`-f mp4 -movflags +frag_keyframe+delay_moov+default_base_moof+frag_discont
  +skip_sidx -frag_duration 500000`。`frag_discont` 让每个 moof 写真实时间（不写的话片段时间从 0 起算）。
- **Worker 切段**（`FragmentSegmenter`）：ftyp + moov 就是 init.mp4；片段按与 HLS muxer 一模一样的规则归段——第一段是 NAS 给的
  起转分片号（`start_segment`），之后从这一轮第一帧起每满一格（4 秒）后的第一个同步帧开新的一段。**不能**用时间戳除以 4：
  `force_key_frames expr:gte(t,n_forced*4)` 的 t 从这一轮第一帧起算（实测从 41 秒起转，关键帧在 41、45、49……），片源
  start_time 不为零时第一帧还会比格点早一点点——第一版就这样把第 344 段算成了 343，播放器要的那一段永远不来（冒烟测出来的）。
- **分块回传**（`ProgressiveUpload`）：init 整个传；每个片段作为所属分片的第 n 块 `PUT seg?part=n`，下一段的第一个片段到了
  （或 ffmpeg 正常收尾）补一个空的收尾块 `part=n&final=1`。某一块传不上去（重试用尽、NAS 回 409 说中间缺了一块）就不再分块，
  等这一段转完把内存里的整段一次传上去——与老路完全一样。任务被叫停（seek 重启）时没转完的那一段不补收尾块。
- **NAS 追加落盘**（`_append_progressive_part`）：按序追加进 `.segNNNNN.m4s.partial`，收齐原子改名成正式分片。块号小于已收到
  的是重传（幂等认下）；跳号回 409；新一轮从第 0 块重写同一个分片时旧的作废；一块没收完连接断了就把文件截回这一块之前。
- **NAS 流式交付**（`_PartialSegmentResponse`）：客户端 UA 带 `AppleCoreMedia`（iOS App 放服务端流、Safari 原生 HLS）且这一轮
  在边产出边送时，分片第一个片段一到就开始分块下发，跟着文件增长往下送；分片作废或 10 秒不长就**不发结束块**直接中断，客户端
  丢掉半截重新请求。不进浏览器缓存。hls.js 要整段收完才喂解码器，提前下发对它没有好处，反而让网页按传输期算的带宽读数偏低，
  照旧等整段。
- **起播点吸附**：同样只对 AVFoundation 客户端、只在边产出边送时，`EXT-X-START` 吸附到续播点所在分片的起点（最多往回 4 秒，
  与 iOS 引擎 P39「起播点吸附前一个关键帧」同一取舍）。

### 5.1 对照结果

开发版 Worker 跑在 MacBook（M2 Max，Wi-Fi）上，`--arms seg=no-progressive,prog=` 每部片两组都跑、先后轮换，
19 部 × 续播 / 从头（2026-10-01 下午，批次 ab-prog）：

| | 整段落盘 p50 / p90 | 边产出边送 p50 / p90 | 按片配对差值中位 |
|---|---|---|---|
| 从头首帧 | 1171 / 1569 | **638 / 939** | 起播两种合计 −506 毫秒，36/36 变快 |
| 续播首帧 | 1435 / 2644 | **904 / 2076** | |
| 前跳出画 | 1354 / 3433 | **967 / 2566** | −397 毫秒，18/18 |
| 回跳出画 | 1372 / 2367 | **915 / 2174** | −345 毫秒，17/18 |
| 缓冲内跳 | 92 | 93 | 持平 |

按类（续播首帧中位）：1080p H.264 1011 → 546、4K HDR10 MKV 1419 → 684、4K DV 1236 → 755、4K SDR MP4 1290 → 728、
HLG TS 2106 → 1507、UHD 原盘 2854 → 2030 毫秒。p90 降得少，是原盘与 TS 的取源本身慢（§6 第 1 项）。

**对照里撞出的两个兼容问题**（都已修，见 `_progressive_args` 注释）：

- 一部带章节的 4K Remux 两个场景都报 -11801「Cannot Complete Action」：mp4 muxer 把片源章节写成 init 里的一条
  文本轨，AVPlayer 不认。HLS muxer 不把章节交给内部的 mp4 muxer，老路从没撞上。加 `-map_chapters -1`，本机复现后确认，
  修好后这部片续播 2878 → 1216、从头 1373 → 740 毫秒。
- `empty_moov` 要求开头就写出 moov，音轨直通 E-AC-3 / AC-3 时 dec3 / dac3 得从第一个包里解析，ffmpeg 直接报错退出
  （本机复现）。改成 `delay_moov`（HLS muxer 内部也是这么配的），首帧不受影响（init 与第一个片段一起到）。

**iOS App**：自研引擎放服务端流时挂引擎会显式 seek 到会话给的起播点，服务端只改播放列表的 `EXT-X-START` 不够——
所以开会话的响应 `start_ms` 对 AVFoundation 能力（原生 HLS、没有 MSE）同样吸附到分片起点，App 续播时直接用它。

**还没做 / 没验证**：

- 生产 Mac mini 还是旧版转码器（不申报 `progressive_segments`，NAS 照旧派整段落盘的任务），要发新版转码器才生效；
- 真机 iOS App 没验证（模拟器 / 真机的 AVPlayer 与 macOS 同一套，预计一致）；
- App 跳转仍是精确落点：落在分片中间时要等转到落点那一片，可以按代价吸附到分片起点（§6 第 5 项）。

### 5.2 网页渐进解码（2026-10-06）

网页现在也能消费半成品：开会话的 `progressive_segments` 为真时，hls.js 启用
`progressive`，FetchLoader 用 `partial=1` 选择流式分片；整段输出、缓存复播与不支持
流式 Fetch 的浏览器继续整段请求。能力声明不增加网络往返。编码端仍是现有的 0.5 秒
MP4 片段、4 秒 HLS 分片，没有为了快首帧缩短 GOP 或降低画质。

不能只开配置：hls.js 1.7.1 的渐进续块重复映射时间起点，实测 30 秒压成 8.5 秒。
固定版本并通过 pnpm 补丁让续块及 flush 沿上一块的结束时间推进；完整播放显示
720/720 帧，音频、续播、seek、小分片与 XHR 回退都有实际浏览器端到端守卫。
流式响应不进入线路带宽估算，避免把编码等待误认作网络慢。

M2 Max、回环 HTTP、两个真实内核（共享一台物理设备），4K SDR HEVC → 1080p H.264：
8 组单路交替对照中位 **953 → 532 ms**，3 组三路并发中位 **1931 → 705 ms**，
新版全部 17 次低于 1 秒、最慢 828 ms。口径从播放 API 请求到浏览器显示首帧，
HLS 缓存未命中，页缓存和播放器 JS 已热身。编码命令相同，整片吞吐持平。
详见 [对照数据](../reports/remote-transcode-startup-optimized-2026-10-06.json) 与
[远程转码验证说明](remote-transcode.md)。

现有 SMB 挂载上的完整 MP4/MKV 片源也做了每类三组对照，GPU 全链路输出 1080p：
4K SDR HEVC 首帧中位 490 ms，4K HDR10 + TrueHD 601 ms，4K H.264 484 ms；
新版 9/9 在 1 秒内，观察首帧后 5 秒均无卡顿或丢帧。
[真实片源数据](../reports/remote-transcode-real-source-startup-2026-10-06.json) 区分完整
原文件与裁剪样本；API 仍是本机隔离服务，尚未部署至生产 NAS。

这解决了网页等待整段的问题；下节所列原盘 / TS 的输入探测仍是独立瓶颈，不能
由这组结果推断家中所有格式都已在 1 秒内。

## 6. 取源

边产出边送之后，p90 剩下的大头是原盘、TS 的「ffmpeg 打开输入」：时间线里 `w_ffmpeg` → `w_input` 原盘 0.85～3.5 秒、
TS 约 1.5 秒，MKV / MP4 只要 0.1～0.4 秒。

### 6.1 起转时 ffmpeg 怎么读片源

NAS 时间线的 `src` 事件（每个取源请求：到达时刻、起点 MB、读走多少、首字节、持续、是否被掐断）把一次起转拆得很清楚。
以一张 UHD 原盘续播为例（星际穿越，单段 85 GB m2ts，热缓存），`w_input` 前 1.48 秒里有 35 个请求：

| 阶段 | 请求 | 用时 | 说明 |
|---|---|---|---|
| 探测 | 1 | ~150 ms | 从文件头读 27 MB（不封口的 Range，读够了掐断） |
| 估时长 | 2 | ~85 ms | 文件尾倒着读 244 KB、488 KB（`estimate_timings_from_pts`） |
| 找最后一个时间戳 | 16 | ~480 ms | `-ss` 的二分查找要先知道文件尾的时间戳：从尾巴往前 1、2、4……1022 KB 地试，再往回收 |
| 找第一个时间戳 | 6 | ~150 ms | 回到文件头 |
| 二分查找 | 6 | ~330 ms | 31501 → 31688 → 31653.7 → 31653.1 MB…… |
| 主读 | 1 | — | 从落点起一直读下去 |

每个请求都要新开一条 TCP 连接（ffmpeg 的 HTTP seek 只在剩余字节很少时才复用连接），在 Wi-Fi 上是两个往返；
二分查找每一步只要几 KB，NAS 却推出 12～20 MB 才发现对面已经断开（NAS 这一层还要先从 NFS 上把这十几 MB 读过来）。
TS 文件同理；MKV 有 Cues、MP4 有 moov，直接定位，请求少得多。

### 6.2 ffmpeg 自带的选项够不够

- `skip_estimate_duration_from_pts`：跳过「估时长」那两到十几个请求（时长 NAS 早就知道），对 MKV / MP4 无害。**保留**。
- `initial_request_size` + `multiple_requests`（jellyfin-ffmpeg 8.1）：读 8.1 的 `http.c` 才弄清，「initial」只管到第一次顺序读
  越过区间末尾为止，之后全部恢复不封口；原盘、TS 的探测第一下就读过了 1 MB，二分查找照样不封口、照样新开连接。连接复用
  也只在「当前区间剩余字节小于 short seek 阈值」时发生。对照里看不出收益（ab-read 批次撞上本机负载，作废），**不再申报**。

ffmpeg 没有「先小后大」的自适应取法，也不缓存读过的块。

### 6.3 Worker 侧取源代理

`SourceReadProxy`（`macos/MovieClawTranscoder/.../SourceReadProxy.swift`）：Worker 在回环口起一个 HTTP 服务，把 ffmpeg 的
`-i`（单文件 `.../source`、原盘 `.../source.ffconcat`，清单里的剪辑是相对地址，跟着一起走代理）换成本机地址，替它向 NAS 取：

- **连接复用**：所有任务共用一条 URLSession，到 NAS 的连接 keep-alive；跳读不再握手。
- **按块取、按需放大**：块 256 KiB。一个请求先取 1 块；ffmpeg 读过第一块还在读（顺序读）才放大到 4、16、32 块（8 MiB），
  并提前取下一段。读几 KB 就跳走的二分查找，NAS 只多送一两块，而不是十几 MB。
- **块缓存**：整个 Worker 共用，按会话的取源路径记（不含令牌），128 MiB。文件尾那串越读越大的小请求大多落在已取的块里；
  **seek 重启的新一轮 ffmpeg 再探一遍文件头尾，直接命中上一轮留下的块**。一个请求顺序读过 16 MiB 之后取的块（转码主读）
  标成过路块，容量满了先淘汰，头尾索引留到最后。
- **出错**：NAS 的错误码原样转给 ffmpeg（404 会话已结束、403 令牌失效），stderr 归因不变；中途取数失败就断开这条连接，
  ffmpeg 的断线续读接手。代理起不来就直连，转码不受影响。

### 6.4 对照结果

开发版 Worker（MacBook，Wi-Fi），`--arms direct=no-source-proxy,proxy=`，8 部 × 续播 / 从头 × 2 轮，每次起播前片源赶出
NAS 页缓存（冷启动），全部 64 次有效（2026-10-01 17:00 前后，批次 ab-srcproxy）：

| | 直连 p50 / p90 | 取源代理 p50 / p90 | 按片配对差值中位 |
|---|---|---|---|
| 从头首帧 | 919 / 1636 | **784 / 1091** | 起播两种合计 −199 毫秒，23/32 变快 |
| 续播首帧 | 1552 / 3471 | **1216 / 2810** | |
| 前跳出画 | 1557 / 3089 | **1150 / 2594** | −382 毫秒，14/16 |
| 回跳出画 | 1551 / 2636 | **1028 / 1620** | −433 毫秒，16/16 |
| 缓冲内跳 | 102 | 105 | 持平 |

按类（首帧 / 前跳 / 回跳中位，毫秒）：

| 类别 | 直连 | 取源代理 |
|---|---|---|
| UHD 原盘 | 2314 / 2706 / 2570 | **1629 / 1686 / 1539** |
| HLG TS | 1277 / 1767 / 1719 | **881 / 858 / 952** |
| 4K H.264 MKV | 1284 / 2996 / 1551 | 1182 / 2614 / 1118 |
| 1080p H.264 MP4 | 1087 / 1511 / 1429 | 999 / 1192 / 996 |
| 4K SDR MP4 | 785 / 1061 / 1266 | 759 / 1005 / 1057 |
| 4K HDR10 MKV | 816 / 1203 / 1126 | 892 / 961 / 954 |

- 原盘、TS 收益最大：二分查找每一步从「新连接 + NAS 推十几 MB」变成「复用连接 + 取 1.25 MB」，文件尾那串小读
  十六个请求变成五次取数。
- **跳转普遍变快，是跨轮次块缓存的功劳**：MP4（moov 在文件尾）的前跳、回跳两轮，代理一次都没再向 NAS 要文件头和
  moov（直连每轮各读一遍 1 MB + 16～23 MB 文件头、5.4 MB moov），只取新落点的数据。
- 代价：多一个回环跳。缓存命中的读几乎零成本，没命中的多一次本机拷贝，量不出来；4K HDR10 MKV 的首帧中位略慢
  （816 → 892），配对差在噪声内。

**冒烟里撞出的两个问题**（都已修，见 `SourceBlockCache` 注释）：

- 初版只有一个总量、淘汰时一律先挤过路块：起转跳读的块攒满后，主读刚取回的块马上被挤掉，读不到就断开、ffmpeg 重连，
  一个任务向 NAS 取了 400 MB、只交给 ffmpeg 210 MB。改成两类块各有份额，并且一个请求攥着自己在取、预取的那几段，
  不依赖缓存还留着它们（新增用例：缓存远小于文件时每块只取一次，修前取了 6.6 倍）。
- 回环口两头的缓冲能吞下约两块（实测客户端只读 4 KB，代理送出 512 KiB 才停住）：「送出第二块」不等于 ffmpeg 读了，
  初版这时就预取 4 + 8 MB，原盘二分查找每一步白取 12 MB。改成送出 6 块后才预取。

**预取时机对照**（ab-prefetch，5 部 × 2 场景 × 2 轮，`eager=eager-prefetch` 对 `lazy=`）：起播 −21 毫秒（13/20）、前跳 −38、
回跳 −15，都在噪声里；跳转 p90 略好（前跳 2223 → 1988、回跳 1641 → 1372），且不白取，保留「送出 6 块后才预取」。

**逐请求日志看原盘**（`source-log`）：星际穿越续播打开输入 1.3 秒、32 个请求——文件头探测顺序读 8 MB 400 毫秒（等网络三次），
文件尾那串大多命中缓存，二分查找四步每步 100～290 毫秒：每步 ffmpeg 读 0.6～1.2 MB，加上回环缓冲多送的 512 KB，
正好跨过 256 K → 1 M 两次取数、等到第三次（4 MB）。每次等的都是冷读（NAS 上 NFS 读另一台存储，首字节 30～100 毫秒）。

**首次取量的两次尝试，都没留**：

| 批次 | 做法 | 续播首帧 | 前跳 | 回跳 | 从头首帧 |
|---|---|---|---|---|---|
| ab-firstrun（4 部 × 2 × 2） | 首次直接取 1 MiB | −216（6/8） | −174（7/8） | +24（4/8） | **+82（1/8）** |
| ab-companion（5 部 × 2 × 2） | 首块单取 + 并行取后 3 块 | −51（6/10） | +81（3/10） | −66（7/10） | +30（5/10） |

取数整段到齐才交出，首次 1 MiB 让每个新请求的首字节都晚到，从头起播稳定变慢；并行多取后几块确实把原盘 / TS 二分查找
每一步的等待从 2.23 次降到 1.55 次、中位 217 → 196 毫秒，但两路冷读并发时互相拖慢，p90 从 393 涨到 521 毫秒，端到端
看不出收益。都按「简洁优先」撤掉，首次只取 1 块。再往下得让一次取数边到边交（URLSession 流式回调），或者减少二分查找
本身（§7 第 3 项）。
