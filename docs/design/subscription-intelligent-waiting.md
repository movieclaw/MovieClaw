# 智能订阅模式与等待策略

状态：需求草案。产品方向已确认，执行细节待评审。尚未实施。

更新日期：2026-10-07。

订阅提供原有规则模式和新增的智能选择模式。智能选择模式独立定义设置和选择策略，不要求用户先配置规则组。用户分别为电影和剧集完成一次智能设置。后续同类型订阅直接复用对应设置。

智能选择以分辨率和片源为主要品质依据。剧集优先保持可靠、统一的版本。系统根据实际发布记录决定是否等待。用户接受洗版时，现有洗版机制负责后续品质提升。

本文面向产品、开发和测试人员。本文定义模式入口、首次设置、剧集等待流程、功能需求和验收场景。电影的专属等待流程仍需补充。

技术拆解与验证方案见[智能订阅技术方案](subscription-intelligent-implementation.md)。

## 1 写作约定

本文按“80% 采用 ASD-STE100”的要求使用受控表达。这里的 80% 表示写作取向，不表示正式符合率。ASD-STE100 是受控技术英语标准。本文是中文设计文档，不执行英语词典和英语词数检查。

本文采用以下写法：

- 一个术语只表示一个概念。
- 一条需求只规定一个主要行为。
- 一条流程步骤只执行一个主要动作。
- 先写条件，再写动作。
- 明确动作的执行者。
- 使用短句和主动表达。
- 将要求、示例和待定事项分开。

“必须”表示实现和验收要求。“不得”表示禁止行为。“可以”表示允许行为。需求编号用于开发和测试追踪。这些编号和约束用语是本项目的约定。

规范参考：[ASD-STE100 官方说明](https://www.asd-ste100.org/about_STE.html)。

## 2 产品目标和范围

### 2.1 已确认的方向

1. 用户主要表达分辨率和片源偏好。
2. 系统优先保持追剧版本的可靠性和一致性。
3. 系统根据作品的实际供给调整选择。
4. 用户通过少量设置表达等待耐心。
5. 用户接受洗版时，系统可以等待更好的资源并执行替换。
6. 系统必须说明等待对象、等待原因和停止等待的时间。
7. 订阅时新增智能选择模式，与原有规则模式并存。
8. 用户分别为电影和剧集设置一套智能偏好。
9. 每类设置只需首次完成，后续同类订阅直接复用。

字幕语言、播放兼容性和体积上限不作为智能设置的核心入口。原有规则模式继续使用原有高级限制。智能模式不隐式继承某个规则组的限制。AI 字幕生成不属于本文范围。

### 2.2 本次设计范围

模式入口和首次设置覆盖电影与剧集。两类设置分别保存、分别读取，不互相覆盖。

本文已展开的等待流程处理连载剧集的首次下载和后续追更。决策单位是单集。版本跟随的范围是同一部剧的同一季。

智能模式可以复用身份匹配、下载投递、入库核验和洗版等底层能力。它不必建立在原有规则组模型或评分方式上。本文不规定数据库结构或接口字段。

电影的资源发布阶段、等待起点和等待预算需要独立定义。不得直接套用剧集的单集计时和版本跟随流程。跨季继承和同档位修复版本的替换规则不在本次范围内。

第 3 至第 10 节是建议的执行规则。第 11 节列出实施前必须确定的参数和语义。

## 3 固定术语

| 术语 | 定义 |
|---|---|
| 规则模式 | 通过原有规则组筛选和选择资源的订阅模式。 |
| 智能模式 | 根据类型设置、作品供给和等待策略选择资源的新增订阅模式。界面名称为“智能选择”。 |
| 类型设置 | 电影或剧集对应的一套智能模式设置。同类型智能订阅复用该设置。 |
| 品质偏好 | 用户对分辨率和片源的优先顺序。偏好不等于最低要求。 |
| 最低要求 | 用户明确禁止系统突破的限制。等待结束后仍然有效。 |
| 合格候选 | 通过身份检查和全部有效硬性过滤的资源。 |
| 版本系列 | 同季内由制作组、分辨率、片源等属性识别的一组连续发布。相同制作组不一定属于同一系列。 |
| 跟随版本 | 系统当前优先延续的版本系列。 |
| 等待预算 | 用户允许系统为本集推迟下载决策的最长时长。 |
| 等待起点 | 系统为本集确定的计时基准。 |
| 等待截止时间 | 等待起点加等待预算。到达此时间后，系统不得继续为品质偏好延迟下载决策。 |
| 预计到达窗口 | 系统根据发布记录估算的资源出现时间范围。它不是承诺。 |
| 当前最佳候选 | 系统在本轮合格候选中，按当前策略选出的下载对象。 |
| 洗版 | 已有资源入库后，通过现有机制验证和替换更高品质版本。 |

等待预算约束开始下载的决策时间。它不保证下载完成时间，也不保证可观看时间。

## 4 用户输入与系统责任

### 4.1 模式入口

订阅入口必须让用户识别并选择当前使用的模式。

| 模式 | 配置来源 | 选择行为 |
|---|---|---|
| 规则模式 | 原有规则组 | 沿用原有自动选组、过滤和选优行为 |
| 智能选择 | 电影或剧集的类型设置 | 根据作品供给和等待策略执行智能选择 |

REQ-M01：智能订阅不得要求用户创建、复制或选择规则组。

REQ-M02：规则模式不得消费智能模式的等待预算。

REQ-M03：系统必须记录订阅采用的模式，并在详情中显示。

REQ-M04：已有订阅必须保留原有行为，不得自动迁入智能模式。

Web 的普通新订阅默认选中智能选择。不记忆上次模式。旧客户端省略模式时继续使用规则模式。已有订阅不迁移。

### 4.2 首次设置与复用

1. 用户在订阅时选择智能模式。
2. 系统识别作品是电影还是剧集。
3. 系统检查该类型是否已有智能设置。
4. 如果尚未设置，系统展示该类型的首次设置。
5. 用户保存该类型的设置。
6. 系统使用对应设置继续创建智能订阅。

如果第 3 步发现已有设置，系统直接进入第 6 步。系统不得要求用户再次完成设置。

首次订阅电影时，只需完成电影设置。首次订阅剧集时，只需完成剧集设置。系统不得要求用户预先完成另一类设置。

“只第一次”表示不重复展示首次设置。它不限制用户以后主动修改设置。界面必须提供查看和修改两类设置的入口。

类型设置只保存用户偏好。某部剧的跟随版本和历史证据属于该作品。系统不得将它们应用到其他剧集。

### 4.3 设置内容

电影和剧集各自提供以下三类输入。两类的选项和默认值可以不同。

| 输入 | 用户表达 | 系统解释 |
|---|---|---|
| 品质偏好 | 优先选择什么分辨率和片源 | 决定候选的品质顺序 |
| 等待耐心 | 为合适版本最多愿意等多久 | 转换为有明确时长的等待预算 |
| 洗版选择 | 是否接受后续替换 | 使用本类型的洗版设置，对接现有洗版执行能力 |

等待选项可以使用“尽快下载”“可以等一段时间”等自然语言。界面必须同时显示实际时长。“当天”或“次日”不能单独作为计算规则。

系统不得要求用户按制作组、分辨率和片源分别设置等待计时器。

### 4.4 系统责任

系统负责观察发布节奏、识别版本系列、选择跟随版本和执行到期决策。

智能模式必须区分“偏好 4K”和“只接受 4K”。最低要求应在智能模式中明确表达，不从旧规则组推断。旧规则中的分辨率白名单在规则模式中继续作为硬性过滤。

## 5 主流程

本节及第 6、7 节适用于剧集智能订阅。订阅创建先执行第 4 节的模式选择和设置流程。

### 5.1 建立本集决策

1. 系统确认本集属于有效订阅范围。
2. 系统读取剧集类型设置中的品质偏好、最低要求和等待预算。
3. 系统确定本集的等待起点。
4. 如果起点已确定，系统计算并保存等待截止时间。
5. 系统读取本季的跟随版本。
6. 系统根据已观测资源生成本集决策。

如果本集已过等待截止时间，系统直接执行第 5.4 节。

### 5.2 选择首次跟随版本

1. 系统排除不合格候选。
2. 系统按品质偏好比较剩余候选。
3. 系统检查相关版本的可用发布和入库记录。
4. 系统按第 6 节判断是否等待。
5. 如果无需等待，系统提交当前最佳候选。
6. 入库核验成功后，系统建立跟随记录。

首集的成功入库可以建立跟随记录。它不能证明该版本以后会稳定更新。系统必须保留“证据不足”的判断。

### 5.3 延续跟随版本

1. 系统检查跟随版本是否已有合格候选。
2. 如果存在，系统优先提交该候选。
3. 如果不存在，系统检查预计到达窗口。
4. 系统按第 6 节选择继续等待或使用替代版本。

其他候选的做种数更多或处于免费期，不单独构成切换理由。更高品质候选的出现，也不自动中断正常的版本跟随。

### 5.4 结束等待

1. 系统结束本集的主动品质等待。
2. 系统重新检查当前合格候选。
3. 如果存在候选，系统提交当前最佳候选。
4. 如果不存在候选，系统显示“等待已结束，暂无符合要求的资源”。

没有候选时，系统继续使用现有同步和搜索机制。后续首次出现合格候选时，系统不再增加品质观察窗口。

### 5.5 处理下载和洗版

1. 系统通过现有下载与入库流程处理已提交资源。
2. 系统记录入库核验结果。
3. 如果用户已开启洗版，系统将后续品质提升交给现有洗版机制。

投递失败或下载失败不重置等待截止时间。现有重试、换源和退避机制继续生效。

### 5.6 洗版停止条件

洗版目标直接来自订阅保存的分辨率和片源偏好。界面必须显示目标，例如“达到 4K 蓝光后停止”。用户不必再配置另一套洗版规则。

分辨率和片源必须同时满足目标。系统不得用一个维度的提升补偿另一个维度未达标。

系统在资源入库并完成目标核验后停止洗版。电影按整部判断。剧集按每集判断。已达标单集不再自动替换，其他单集继续独立处理。

系统不得将同品质的制作组变化视为品质升级。系统不得因出现新资源而自动提高目标。只有用户明确修改目标，系统才重新评估已停止的洗版。

目标资源始终未出现时，系统保留当前资源并低频观察。首次下载的等待预算不作为洗版的截止期限。

分辨率可以通过文件探测核验。片源还依赖来源声明和证据。系统不得把名称解析结果描述为文件实测结果。证据不足时，系统不得声称已确认达标。

## 6 等待决策

### 6.1 等待起点

系统按以下顺序确定等待起点：

1. 使用可信的本集上线时间。该时间必须包含可解释的时区。
2. 如果没有可信时间，使用系统首次发现本集合格候选的时间。
3. 如果两者都没有，显示“等待资源出现”，不编造倒计时。

仅有播出日期时，系统不得把零点当成可信上线时间。首次发现时间只表示本系统已经看到资源，不表示资源在全网的最早发布时间。

系统保存起点后，不得因刷新预测、发现新候选、重启或恢复订阅而向后移动起点。

如果后续证据表明本集更早上线，系统可以提前截止时间。系统必须记录调整原因。系统不得因此延后截止时间。

### 6.2 决策顺序

系统必须按表中顺序检查条件。命中一行后，执行该行的动作。

| 顺序 | 条件 | 动作 |
|---|---|---|
| 1 | 订阅暂停、取消，或本集已有在途任务 | 停止本轮自动选种，不重复投递 |
| 2 | 没有合格候选 | 继续发现资源；如果已到截止时间，显示暂无合格资源 |
| 3 | 已到等待截止时间 | 提交当前最佳候选 |
| 4 | 跟随版本已有合格候选 | 提交跟随版本 |
| 5 | 跟随版本尚未到达，且有效预测窗口尚未结束 | 等待至窗口结束或截止时间，以较早者为准 |
| 6 | 尚未建立跟随版本，且有证据支持更优版本在预算内出现 | 等待至预测窗口结束或截止时间，以较早者为准 |
| 7 | 尚未建立跟随版本、缺少有效历史，且本集尚未使用有限观察窗口 | 使用一次有限观察窗口；窗口不得超过截止时间 |
| 8 | 其他情况 | 结束等待，提交当前最佳候选 |

有限观察窗口只用于首次选择。系统不得因窗口内出现新候选而重新计时。窗口长度属于第 11 节的待定参数。

窗口结束后，系统必须重新决策。系统不得仅因预测仍然存在而继续等待。继续等待必须有新的有效证据，且不得超过等待截止时间。

### 6.3 到期后的候选顺序

存在合格跟随版本时，系统优先延续该版本。

没有合格跟随版本时，系统按分辨率和片源偏好选择替代版本。同品质先延续现有跟随；无跟随时，依次比较本季所需集的版本覆盖、独立成功核验集数、单资源覆盖和做种数。仍相同时按规范化系列、站点及资源标识稳定决胜。覆盖取集合，镜像不累计；没有核验记录时保持未知。

系统必须使用确定的最终排序。相同输入不得因数据库返回顺序不同而选择不同资源。

### 6.4 截止时间的执行边界

系统必须让截止时间触发一次决策。系统不得仅等待下一次新种子到达。

如果服务在截止时间不可用，系统在恢复后的首次有效调度中执行到期决策。界面必须区分“等待超时”和“服务未执行”。

用户可以主动延长等待或立即下载。系统必须记录操作前后的截止时间。只有用户明确延长等待，系统才可以向后调整本集的截止时间。

剧集类型设置中的等待预算修改，默认只影响尚未建立截止时间的单集。若要修改正在等待的单集，界面必须明确说明影响范围。品质与洗版设置修改对已有订阅的影响范围仍需确定。

## 7 发布证据与版本稳定性

### 7.1 发布证据

REQ-E01：系统必须区分资源发布时间和首次发现时间。

REQ-E02：系统必须记录预测使用的历史单集和版本系列。

REQ-E03：系统不得把同一发布的跨站转载计为多次独立履约。

REQ-E04：系统不得使用尚未发生的记录生成历史预测。

REQ-E05：系统不得把站点访问失败直接解释为版本停更。

REQ-E06：历史不足或发布波动过大时，系统必须降低预测可信度。

预计到达窗口必须附带证据摘要。系统不得在没有校准数据时显示精确的到达概率。

### 7.2 版本跟随

REQ-V01：系统必须结合版本属性识别系列，不得只使用制作组名称。

REQ-V02：缺失属性不得作为“已确认相同”的证据。

REQ-V03：单集使用替代版本，不得自动改写整季的跟随版本。

REQ-V04：持续迟到、缺集或核验失败，可以触发整季跟随版本的重新评估。

REQ-V05：系统切换跟随版本时，必须记录原因和证据。

REQ-V06：系统不得因一次普通延迟就反复切换跟随版本。

下载器故障与资源本身的品质问题必须分开记录。系统不得用本地磁盘故障降低制作组的可靠性评价。

## 8 与现有系统的衔接

| 现有能力 | 本次衔接要求 |
|---|---|
| 规则组自动选择 | 仅服务规则模式。智能模式读取类型设置，不经过自动选组。 |
| 规则过滤 | 规则模式沿用原有逻辑。智能模式独立定义合格条件，可以复用通用检查能力。到期不得突破本模式的最低要求。 |
| 发布预测 | 复用现有观测与调度能力。增加版本维度前，必须验证样本口径。 |
| 被动匹配与主动搜索 | 两条入口必须按订阅模式执行。智能模式共用等待决策，规则模式保留原有行为。 |
| 下载投递 | 继续使用现有认领与防重复机制。等待到期不等于创建第二个任务。 |
| 洗版 | 智能模式从类型设置取得洗版意图，对接现有品质比较、入库验证和旧版本处置能力。不得要求用户额外配置旧规则组。 |
| 活动记录 | 保存首次下载、继续等待、到期替代和跟随切换的理由。相同理由不得每轮重复写入。 |

现有发布时间预测主要使用同季较早单集的最早发布记录。它回答“本集资源何时可能出现”。它尚不能直接证明“指定 4K 版本何时出现”。

本次设计不得为等待策略额外建立无上限的站点轮询。现有限流、退避和熔断继续有效。

整季包会覆盖多个单集。系统不得借用“整季包优先”绕过尚未到期单集的等待决策。系统必须先决定各集是否允许下载，再只选择包内相应文件。文件核验失败必须保持暂停，重试同一任务，不得回落全量。

关联设计：[规则组适用范围](rule-set-scope.md)、[发布时间预测](subscription-release-forecast.md)、[洗版机制](quality-upgrade.md)。

## 9 用户可见说明

电影智能设置已保存时，后续电影订阅可以显示“智能选择 · 使用电影设置”。剧集同理。界面提供设置摘要和修改入口，不重复展示首次设置流程。

每个等待中的剧集单集必须显示四项内容：等待对象、证据摘要、停止等待时间和到期动作。

有历史证据时，使用以下形式。时间仅为示例：

> 正在等待本剧跟随的 2160p WEB-DL。前 3 集的该版本通常晚约 2 小时出现。预计今晚 21:00 至 22:00 到达。最晚等待至 22:00。届时若仍未出现，将下载当前合格的 1080p WEB-DL。下载完成时间取决于资源和网络。

没有历史证据时，使用以下形式：

> 本剧暂无足够的发布记录。系统正在观察是否有更合适的版本。最晚等待至 22:00。系统不能确认更好版本会在此之前出现。

到期且没有合格候选时，使用以下形式：

> 等待已结束。当前没有满足最低要求的资源。系统将继续查找，并在发现合格资源后开始下载。

开启洗版时，界面可以补充“入库后继续按洗版设置查找升级版本”。未开启洗版时，不得显示自动升级承诺。

| AT12 | 一个整季包覆盖已到期和仍在等待的单集。 | 系统不绕过任一单集的等待约束。 |
| AT13 | 同一发布在三个站点出现，其中一个站点访问失败。 | 系统不计为三次独立履约，也不直接判定版本停更。 |
| AT14 | 只有播出日期，没有可信上线时刻。 | 系统不从当天零点生成倒计时。首次发现合格候选后按发现时间计时。 |
| AT15 | 用户明确延长本集等待，随后修改共享偏好。 | 显式延长有记录。共享修改不再次推迟本集截止时间。 |

| AT19 | 电影设置已保存，用户首次通过智能模式订阅剧集。 | 展示剧集首次设置。保存后两类设置各自保留。 |
| AT20 | 用户修改电影设置，然后通过智能模式订阅剧集。 | 剧集继续使用剧集设置，不受电影设置影响。 |
| AT21 | 部署新增智能模式，已有订阅仍使用原有规则组。 | 已有订阅的选组、过滤和投递行为不变。 |

| AT25 | 当前版本为 1080p 蓝光，候选为 4K WEB-DL。 | 系统不把跨维度取舍直接当作已达标；替换行为必须服从技术方案的升级判定。 |

单元测试必须覆盖起点选择、截止时间、候选顺序和预测证据处理。

端到端测试必须覆盖“模式选择 → 首次设置或复用 → 资源发现 → 等待 → 投递 → 入库 → 可选洗版”。跨站访问和下载器调用可以模拟，但业务链路必须真实执行。

## 11 首版实施决策（算法版本 1）

本节确定首版参数。参数是保守起点，不是对真实发布行为的统计结论。

| 事项 | 首版决定 |
|---|---|
| 模式默认值 | Web 普通新订阅默认智能。旧客户端省略模式时使用规则。原有单次洗版入口保持原行为。 |
| 设置归属 | 与全局共享订阅一致，由管理员分别保存电影、剧集设置。成员可以复用，不能修改全局设置。 |
| 设置更新 | 只影响新建订阅。订阅保存类型、设置版本、算法版本及完整偏好快照。保存设置不等于订阅成功。 |
| 模式切换 | 首版不支持原地切换。重复订阅返回原有模式和快照，不静默覆盖。 |
| 品质优先轴 | 首次选择先分辨率，再片源，再独立单集成功记录，最后比较做种和稳定 ID。4K WEB-DL 在 1080p 蓝光之前。洗版不得降低任何一个品质轴。 |
| 品质目标 | 默认 4K WEB-DL。可选 1080p/4K 和 WEB-DL/蓝光/Remux。默认允许后续洗版。 |
| 最低要求 | 可识别的至少 720p、至少 Rip 档片源；排除无做种及超过所选分辨率的资源。用户可开启“只接受所选分辨率”。身份检查继续由共享管线执行。 |
| 等待档位 | 电影与剧集共用：尽快下载（0）、最多 3 小时、最多 1 天、自定义 1–7 天。保留「等待耐心」下拉框及「尽快下载 / 可以等 / 更有耐心 / 自定义」文案。自定义用带「天」单位的数字输入框及 − / + 按钮，步长 1 天；不显示范围及加减操作说明；空值、非整数和越界值不能保存。首次设置剧集默认 3 小时，电影默认 1 天；已有设置原值保留，非整天旧值回显为「原有设置 · N 小时」。0 表示不主动等待。 |
| 首次观察 | 剧集 30 分钟，电影 6 小时，均不得超过预算。满足目标可立即选择。没有可信预测时，观察结束即可选择。 |
| 起点 | 现有元数据没有可信的资源上线时刻。首版从智能模式首次观察到合格候选开始，不使用播出日零点。导入旧索引不把后来修正的属性假装成历史事实。 |
| 系列识别 | 同作品、同季、制作组、分辨率、片源档；已知编码族及平台进一步区分。未知不作为通配符。制作组仅去除首尾空格和忽略大小写，不猜别名。 |
| 可靠性证据 | 以已核验入库的独立单集计成功，不按跨站镜像次数累加。一次成功可以确认系列，但不能证明长期可靠。 |
| 整季切换 | 至少 3 个不同单集出现实测品质问题，且替代系列至少 3 集已核验成功。切换后重新累积证据。单集缺席、站点离线、下载器失败不计为品质失约。 |
| 整季包 | 按本次允许下载的集数选择包内文件，保护已入库、在途和等待单集。暂停添加、核对清单、选文件、回读一致后恢复；失败保持暂停并重试同一任务，不回落全量。 |
| 预测 | 同季较早的至少 3 集，最多取最近 8 集。近期加权中位数和向前误差给出窗口。历史证据等待默认开启。至少 3 个独立单集，最近 8 集成熟样本按时出现比例至少 80%；最近两集连续缺席或误差半径超过 3 小时则不预测。合包与跨站镜像不增加样本。没有依据时使用有限观察；旧发布时间已超过窗口时直接选择。 |
| 调度 | 每 30 秒扫描有索引的到期单元。参考负载要求决策延迟不超过 60 秒，不承诺下载或入库在 60 秒内完成。 |
| 片源证据 | 分辨率来自探测；来源标为声明一致、人工标注、光盘结构、冲突或未知。仅前 3 类可用于达标判断，不能称来源声明为探测证明。 |

### 11.1 电影专属流程

1. 读取电影设置，不读取剧集设置或制作组跟随记录。
2. 首次观察到合格正片时保存起点和截止。未见资源时不计时。
3. 已满足目标时立即选择。否则最多观察 6 小时，并受用户选择的等待预算约束；预算为 0 时不主动等待。
4. 观察结束或截止时选择当前合格资源。没有资源时保留缺口。
5. 用户可以延长 1 天，或立即下载当前候选。两项操作均校验状态版本。
6. 入库后，允许洗版的电影继续低频查找。分辨率与片源都核验达标后停止。

首版不预测跨作品的蓝光发售时间。电影上映日期不作为资源上线证据。

| 编号 | 补充验收 |
|---|---|
| AT26 | 电影首次设置独立保存；电影订阅不建立剧集系列记录。 |
| AT27 | 未见合格电影资源时不倒计时；目标片源到达可立即选择；电影观察窗口不使用剧集的 30 分钟。 |
| AT28 | 电影设置变更不影响旧订阅快照；重复订阅不改写模式。 |
| AT29 | 电影洗版同样要求两个品质轴同时达标，并在入库核验后停止。 |

## 12 完成标准

本功能完成时，用户可以在订阅时选择智能模式。用户只需分别为电影和剧集完成一次设置，表达品质偏好、等待耐心和洗版选择。后续同类型订阅直接复用设置。

系统必须能回答：“正在等哪个版本”“为什么值得等”“最晚等到何时”“到期会做什么”。

第 11 节固定首版决策及电影流程。验收证据见 [实现与验收记录](subscription-intelligent-acceptance.md)。测试必须通过第 10 节的场景。现有规则组、下载和洗版回归测试必须继续通过。


## 2026-10-07 等待证据修订

1. 等待预算是上限，不是必须消耗的时长。先检查本集所有匹配且合格资源的最早站点发布时间。时间缺失或不可信时，使用系统首次发现时间。保留这两种时间及其来源。
2. 新订阅、转载和合包不能重置等待。发现更早的发布证据只能缩短自动等待。用户手动延期优先；刷新和重启不得撤销延期。
3. 同季独立单集的发布延迟分别支持目标品质等待或同组跟随等待。不能用下一集的播出频率预测 4K。样本必须在当前决策时已经可见，且集号早于当前集。
4. 有证据的到达窗口超出预算时，选择当前合格资源。窗口失效、到期或近期连续失约时，重新选择，不续开窗口。目标品质与严格分辨率约束保持不变。
5. 尚无合格资源时不启动品质计时。页面区分未到播出日期和已播但暂无合格资源。系统不把播出日期的零点当发布时间。
6. 已入库、在途、单集等待保护与整包选文件核验保持不变。先逐集决定是否可选，再由共同投递链路只认领可下载单元。

新增验收：NAS 34 旧资源直接选中两集合包；旧状态被新证据缩短；手动延期不被缩短；目标版本延迟到达；预测超预算立即回落；连续失约撤回预测；跨站镜像不增加样本；未来事件不可见；正式链路单次选中整包，重复触发不增加任务。

## 2026-10-07 分集信息归并

1. 订阅详情只保留原有分集明细。待播出、待搜索、下载、入库与洗版使用原行状态及里程碑，不在智能区域重复展示。
2. 页头配置区显示智能目标与后续洗版设置。不新增分集数量汇总。
3. 智能模式有当前候选或提交核对任务时，在原分集行显示选择状态。用户仍点击原行展开。
4. 等待依据、版本跟随、候选、时间来源、截止时间及延期/立即下载操作放在该集原有「搜索」节点内。无候选时不增加一段智能说明。
5. 达标停止由该集入库核验状态表达。已入库但未达标时，沿用原洗版节点。
6. 仅智能设置异常、执行关闭或仅记录决策时，显示独立全局提示。保留按季折叠、一次展开一集与电影正片常展开的原交互。
