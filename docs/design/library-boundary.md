# 媒体库边界与删除参与方

> 状态：**已定稿，实施中**（2026-10-10 评审通过）。起因是 issue #622（删条目时可选同时删下载任务和源文件）。
> 讨论中定下的方向：**媒体库保持纯粹，不认识种子；「删片时一起腾空间」是官方功能，但由下载模块提供**。
> 相关：`plugin-extension-model.md`（§1 扩展形态、§2.1 删片联动）、`plugin-phase4.md`（§4 删除对话框选项）、
> `plugin-kernel.md`（§4.2 注册表、§4.7 事件模式）、`identity-confidence.md` §5.3。

## 0. 结论先行

1. **先定标准，再分功能**（§1）。事实与安全底线归宿主，「拿事实做什么」的策略才交给插件；大多数人要、做法唯一、
   要在各端核心流程里出现的，是官方功能。官方功能不等于写进某个模块：**放在它所属的领域里，通过别的领域开的口子接进去**。
2. **媒体库只管文件、条目、库、回收站。** 种子、下载器、订阅都是「内容从哪来」（获取领域）的事。依赖只许单向：
   获取领域认识媒体库，媒体库不认识获取领域（§2）。
3. **媒体库开一个领域中立的口子：删除参与方**（§3）。别的模块在删除时可以：给一个勾选项、按这次要删的文件给一段
   只读预览、在用户勾选后接一个后续任务。媒体库只知道「有人给了个选项、用户勾了没」，不知道它是什么。
4. **#622 由下载模块作为第一个参与方实现**（§4）：「同时删除下载任务和源文件」，默认不勾，预览写清楚会删什么、
   为什么不能删；执行走任务中心，库侧和下载器侧结果分开报告。
5. **「哪个文件来自哪个种子」迁出媒体库**（§5），归下载模块自己的表；**谁的数据谁清理**，媒体库删文件不级联删别人的记录。
   其余牵扯（入库桥、身份认领、命名变量、做种提示）按同一原则分批迁，本轮不做。
6. **第四阶段相应修订**（§7）：删除选项不再是第四阶段的通用界面贡献点，而是媒体库自己的扩展点，先给系统模块用、
   稳定后开放给插件；第四阶段由真正属于插件的需求驱动（插件配置页、插件操作、订阅详情区块）。

## 1. 什么该是官方功能，什么该是插件

**先分机制与策略。** 事实与安全底线只有宿主看得全、错了不可挽回，归宿主：文件来自哪个种子、种子还供着谁、删了能不能
恢复、删除前的确认与预览。拿这些事实做什么——删片后删不删订阅、H&R 没达标拦不拦、删不删网盘备份——各人不同，交给插件。
#722 修的「合集种子被误删」就是反例：判断放在插件里，每个插件都得自己查一遍，迟早有人查错。

| 问题 | 是 → |
|---|---|
| 它没装或坏了，用户会觉得「MovieClaw 本身坏了」？ | 官方 |
| 大多数人需要，且做法只有一种明显正确？ | 官方 |
| 涉及不可逆的数据操作或安全底线？ | 官方（至少底线部分） |
| 要在所有端的核心流程里出现？ | 官方（插件界面目前只有网页） |
| 对接外部第三方（IM、网盘、站点、片单源），名单长、变化快、每人只用几个？ | 插件 |
| 不同用户会想要不同做法？ | 插件 |
| 小众、实验性、个人自动化？ | 插件 |

中间档是**官方插件**（随应用提供、可替换）：对接外部系统但大多数人要（四个 IM 通道），或提供默认策略、允许替换。

**官方功能放在哪：** 放在它所属的领域，通过别的领域开的口子接进去。「删片时一起删种」属于下载领域，接进媒体库的删除流程；
媒体库只负责开口子。这样各模块保持纯粹，口子稳定后插件也能用同一个。

## 2. 领域边界与现状

### 2.1 边界

| 领域 | 管什么 | 不该知道 |
|---|---|---|
| 媒体库（`library.*`） | 库、条目、文件、回收站、扫描文件系统、元数据、整理与命名 | 种子、下载器、订阅、站点、H&R |
| 获取（`subscription`、`downloads`） | 订阅、搜索、投递、下载任务、做种、入库桥（把下载完成的内容交给媒体库） | 媒体库内部表结构（只经媒体库的服务接口读写） |

依赖方向：获取 → 媒体库。媒体库需要「别人的信息」时，开领域中立的口子（参与方、提供者），由别人往里填。

### 2.2 现状（2026-10-10 调研）

媒体库对获取领域的牵扯比预想多，大致四类：

| 类别 | 例子 | 本轮 |
|---|---|---|
| 种子关联数据 | `library_file.info_hash` / `downloader_id`（2026-10-09 为删片联动加的）；`relations.py`；删除事件里的 `links` / `TorrentRef` | **迁出**（§5） |
| 删除时的种子判断 | `deletion_recorder` 拍种子快照、算 `shared` | **改为参与方**（§3、§4） |
| 入库桥与身份认领 | `ingest.py` 读订阅下载记录、手动下载意图；扫描按下载记录的保存路径反查；按 info_hash 认领身份（identity-confidence §5.3）；`site_id` / `torrent_id` 两列；`origin.py` 拼来源文案；认领改判时重开想要（`reopen_unfulfilled_wanted`） | 后续批次（§8） |
| 其它 | 命名模板变量 `{site}`；整理 / 转移前的「做种中」提示（`preflight.py`、`_seeding_root_names`）；洗版按 `site_id` / `torrent_id` 找旧文件 | 后续批次（§8） |

另有一处**过时语义**：回收站「做种保护」已在 2026-08-17 去掉（`recycle.py:9-11`），但模型注释、接口说明、网页与 iPhone
仍把 `kept_in_place`（`purge_after` 为空）叫「做种保护」。现在它只表示原盘目录或移动失败。本轮顺手改文案（§8 批次 1）。

## 3. 删除参与方（媒体库的扩展点）

### 3.1 契约

注册表 `library.delete-participants`（`EXPERIMENTAL`，先只给系统模块用；稳定后开放给第三方，见 §7）。一个参与方登记：

| 字段 | 说明 |
|---|---|
| `id` | 参与方内唯一；对外键 = `<条目 id>:<id>`（如 `downloads:remove-source`） |
| `label` / `help` | 勾选项文案；`help` 写后果（如「源文件删除不可恢复」） |
| `preview(request) -> Preview` | **只读**，按这次要删的文件说明勾上会发生什么（§3.2） |
| `job_type` | 用户勾选后要跑的后续任务类型（在 `JOB_HANDLERS` 里登记的处理器） |
| `applies_to` | `item` / `file` / 两者；删整部和删单文件都给不给选项 |

**默认值一律不勾，由宿主强制**，参与方改不了（解决 `plugin-phase4.md` §9 待决策 1）。会删数据的东西不默认勾上。

### 3.2 预览

```
DeleteRequest   = { library_id, media: MediaRef, whole_item, files: [ {id, path, season, episode, size_bytes} ] }
Preview         = { available: bool, reason?: str, lines: [ {text, tone: info|warn|danger} ] }
```

- 请求里只有媒体库自己的事实（文件 id、路径、季集、大小），没有任何种子字段；参与方按文件 id 查自己的数据。
- 必须只读、无副作用（`plugin-extension-model.md` §1：决策无副作用，副作用放到提交后）。
- 每个参与方限时 3 秒，总预算 5 秒；超时或出错时该选项显示「暂时无法预览」且不可勾。
- `available=false` 时选项置灰并显示 `reason`（例：「这个种子还供着《电影乙》的文件」「没找到对应的下载任务」）。

### 3.3 接口

| 接口 | 说明 |
|---|---|
| `GET /libraries/{lid}/items/{mid}/delete-preview?file_id=` | 新增，`library.items.delete-preview`，只读。返回媒体库自己的计划（要删的路径、可释放空间，见 §3.5）+ 各参与方的选项与预览 |
| `DELETE …/items/{mid}`、`DELETE …/files/{fid}` | 新增可选参数 `options`（勾选的参与方键，可重复）。不带 = 都不勾，旧客户端行为不变 |

- 带了不存在或当前不可用的键 → 400，不静默忽略（防止以为删了种其实没删）。
- 删除提交前（`before_commit`，与现有删除事件同一处）为每个勾选的参与方建一个后续任务（`create_job(commit=False)`，
  与订阅清理 `enqueue_cleanup_job` 同一做法），任务载荷 = `DeleteRequest` 里实际删掉的文件 + 选项键。库删除与建任务同一事务：
  要么都成立，要么都不成立。
- 响应新增 `follow_ups: [{option, job_id}]`，客户端据此跟进。

### 3.4 执行与回报

- 后续任务在提交后由任务分发器执行，失败按任务自己的重试策略；**库侧删除不回滚**（#622：「库已删除，下载器任务清理失败：xxx」）。
- 结果写在任务上（`message` + 结构化结果），出现在「活动 → 任务」；失败另发系统通知。
- 删除对话框的结果页按 `follow_ups` 订阅任务流（`jobs.stream`），当场显示「下载器：已删除种子，释放 12.3 GB」或失败原因。
- **为什么用任务而不是可靠事件**：这是用户在这次操作里明确要求的事，需要进度、结果、重试、在任务中心可见，任务都有；
  可靠事件留给「不需要用户选择的自动化」（插件监听删除事件做联动）。两者并存。

### 3.5 媒体库自己的预览也补准

现在「可释放空间」按台账 `size_bytes` 估，硬链接入库时删库文件其实不释放空间。改为按文件系统判断（领域中立：只看 inode 与
链接数）：「其中 9.8 GB 与库外的文件是同一份数据（硬链接），只删库文件不会释放这部分空间」。参与方的预览再说明它能不能把那份也删掉。

### 3.6 删除事件瘦身

`library.item.deleted` / `library.file.deleted` 去掉 `links`（订阅、种子）与 `FileRef.info_hash` / `downloader_id`，只留媒体库的事实，
另加 `options`（这次勾了哪些参与方）。需要种子关联的插件改用下载领域的查询（§5.3）。契约是 `EXPERIMENTAL`，按契约版本升一级，
示例插件 `delete_cascade` 同步改写；保留一个版本的兼容期：旧字段照填（由下载模块的数据算出），并在插件诊断里提示即将移除。

## 4. 下载模块：同时删除下载任务和源文件（#622）

参与方 `downloads:remove-source`，`applies_to = item + file`。

**预览**（只读；用 §5 的文件来源表 + 下载器只读查询）：

- 找到的任务：「qB-家里 · Test.Show.S01.1080p · /downloads/Test.Show.S01.1080p」；
- 硬链接入库：「源文件与库文件是同一份数据，删除源文件才真正释放空间」；复制入库：「将删除库内与下载目录两份文件」；
- 一律附：「源文件删除不可恢复」（`danger`）。
- 不可用（`available=false`）的情况，每条给原因：
  - 找不到对应任务（扫描入库无来源、任务已被手动删除）→ 只删库；
  - 种子还供着本次不删的文件：同条目别的集、别的条目、别的库、没识别的文件（#722 的判断移到这里）；
  - 不是 MovieClaw 投递的种子；H&R 未达标；删种否决钩子（`dl.torrent.before-delete`）说不；
  - 删单文件但种子里还有本条目的其他集（做不到只删对应源文件）。
- 订阅还在追这部片时提示：「订阅仍在追，删除后这些集会重新下载」（与现在删单文件对话框的提示一致；
  删种会把对应季集打回想要，`download_tasks.py` 的既有语义，不改）。

**执行**（任务 `downloads.remove-source`）：执行时**重新校验**一遍预览里的条件（中间可能有变化），再调
`delete_download_task(delete_files=True)`；校验不过就跳过并在结果里写原因。结果：删了哪些种子、释放多少、跳过哪些及原因。

**各端**：网页与 iPhone 的删除弹窗改为先调 `delete-preview`，在库侧说明下方渲染参与方选项（勾选框 + 预览几行 + 不可用原因）；
命令行 `mclaw library items delete --options downloads:remove-source --yes`，`mclaw library items delete-preview`
看计划。Android 只有删单文件，后补。旧客户端不传 `options`，行为与现在完全一样。

## 5. 种子关联迁出媒体库

### 5.1 数据

新表 `download_file_source`（下载领域）：`library_file_id`、`info_hash`、`downloader_id`、`site_id`、`torrent_id`、`created_at`。

- **不设到 `library_file` 的级联外键**：媒体库删文件不动别人的记录。下载模块处理完删除（后续任务或删除事件）后自己清理，
  外加每日一次孤儿清扫（文件行已不存在且超过 7 天）。原则：**谁的数据谁清理**。
- 迁移：从 `library_file.info_hash` / `downloader_id` 拷过来；本轮保留旧两列只读一个版本（兼容回滚），下一版删列。
  `site_id` / `torrent_id` 读者多（洗版、认领、命名、来源文案），本轮只**双写**到新表，读者在后续批次迁（§8）。

### 5.2 写入方

入库（`ingest.py` 的 `torrent_of()`）与扫描（`scan.py` 的 `_download_for`）现在直接写 `library_file` 的两列。改为写入后调
下载领域的 `record_sources(file_id, …)`。这两处代码本身属于入库桥，整体搬家在后续批次；本轮先改写入目标。

### 5.3 读取方

`relations.py` 搬到下载领域（`services/downloads/sources.py`），含 #722 的跨条目共享判断；
「查条目关联」接口保留路径与操作 id，实现改调下载领域（它本来就是给插件查种子用的）。

## 6. 兼容与风险

| 风险 | 应对 |
|---|---|
| 预览要访问下载器，慢或连不上 | 参与方限时 3 秒；连不上时说明「下载器暂时连不上，删除后可在任务中心重试」，选项仍可勾（执行时再校验） |
| 预览与执行之间状态变了 | 执行时重新校验；结果里写明跳过原因 |
| 删除事件瘦身影响已装插件 | 契约升版本 + 一个版本兼容期 + 诊断提示；目前已知使用者只有示例插件 |
| 旧客户端 | `options` 可选，不带 = 不勾；响应只加字段 |
| 迁移出错 | 新表从旧列拷贝、旧列保留一版；迁移有往返测试 |

## 7. 对第四阶段的影响

- `plugin-phase4.md` §4 的 `library.delete.options` 改由本文的删除参与方取代：它是**媒体库自己的扩展点**，先给系统模块
  （下载）用；契约稳定后开放给第三方插件——进程外的参与方按 `IM_CHANNELS` 的方式代理（`preview` 走一次调用，
  后续任务走已支持进程外的 `JOB_HANDLERS`）。届时各端已经会渲染，插件给的选项自动出现，包括 iPhone。
- 第四阶段的其余内容（分步流程词汇、插件配置页、插件操作、订阅详情区块）不变，配置页和操作放进已上线的插件详情页。
- 同样的「领域开口子」做法后续可以用在：整理 / 转移前的「这些文件还被谁用着」（做种提示）、命名变量、来源文案。

## 8. 实施拆分

| 批次 | 内容 | 验证 |
|---|---|---|
| 1 | 删除参与方契约 + `delete-preview` 接口 + 删除接口 `options` + 后续任务；媒体库可释放空间按 inode 算；「做种保护」过时文案清理 | 单测：参与方超时 / 出错 / 不可用 / 未知键 400；不带 `options` 行为不变；库删除与任务同事务 |

| 3 | 下载模块参与方 `downloads:remove-source`（预览 + 执行任务） | 端到端：硬链接 / 复制 / 季包共享 / 合集共享 / 非自有 / H&R / 否决钩子 / 找不到任务 / 删单文件 |

| 后续 | 入库桥搬到获取领域；`site_id` / `torrent_id` 读者迁移；身份认领、命名 `{site}`、来源文案、做种提示改为提供者；Android 删除选项 | 每项独立 PR |

每批独立 PR；批 1～3 只动服务端，批 4 动客户端。

## 9. 决策（2026-10-10）

1. 后续任务失败时推送到手机，成功不推（成功的结果在删除弹窗和任务中心里看）。
2. 删除参与方本轮只给系统模块用（契约先标 `INTERNAL`），下载模块用稳一个版本后再升 `EXPERIMENTAL` 开放给插件。
3. Android 的删除选项后补（它目前只有删单文件），不随批次 4。
