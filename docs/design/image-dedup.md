# 刮削图片防重复下载

> 状态：已实现（2026-10-04）。代码：`services/asset_reuse.py`、`media_scrape._sync_asset`。

## 1. 问题

刮削把海报、背景、Logo、季海报、分集剧照、演职员头像落成本地资产。排查下来有三处会把
「本地已有（或等价）」的图再下一遍：

1. **手动「刷新元数据」带 `force`，无条件重下全部条目图与剧照**——整部剧几百张剧照，
   每点一次刷新全部重下（端到端实测：3 部电影刷新「新下载 9 张」，真正变了的只有 1 张）；
2. **数据目录重建 / 换机后重新入库**：媒体目录里还留着当初镜像的 `poster.jpg`、
   `-thumb.jpg`，或别的刮削软件刮好的图，却全部重新下载；
3. **画质降档**：本地有原图，改成「标准 / 节省空间」后仍去图床下小图。

## 2. 关键事实

图床（TMDB / Fanart.tv）的图片地址**一图一址**：图换了地址就变，地址不变图就不变。所以
「本地这张是不是要的那张」可以不下载就判断。

但**同址不保证同字节**（2026-10-04 实测）：TMDB 图床是 BunnyCDN，边缘节点即时压缩优化
（响应头 `x-bo-compressionratio`），同一张海报在不同节点、不同缓存时刻实测给出 1016287 与
1024639 字节。沿用只比地址，不受影响；收编按字节数比对，偶尔会因此对不上，对不上就退回
下载——少省一次流量，不会错收编。

## 3. 取图顺序（`_sync_asset`）

| 步骤 | 条件 | 网络 |
|---|---|---|
| 沿用 | 资产文件在、格式对、溯源（`档位+路径` / Fanart 地址）一致 | 无 |
| 本地缩图 | 资产里是同一张图的**更大档位**（要的不是原图） | 无 |
| 收编媒体目录 | 媒体目录里的候选图与远端**字节数一致**（HEAD）；或与原图字节数一致 → 收编后缩图 | 1～2 个 HEAD |
| 下载 | 以上都不成 | GET |

- **`force` 不再重下图片**：只影响 TMDB 没剧照的分集是否重新抓帧。文件损坏由格式校验
  兜底，写盘是原子操作。「更换图片」选新图时溯源自然对不上，照样当场下载。
- **收编按需查**：只有真要下载的图才去媒体目录找候选（NAS 上媒体盘常是网络挂载）；条目
  级图一次查完，剧照按集现查。候选按 Kodi/Jellyfin 命名规则找（`find_artwork`，与详情页、
  Jellyfin 接口同一份规则）。收编后资产沿用媒体目录文件的修改时间，镜像时不会把同一份
  字节写回去。
- **收编命中率**：同一部署通常固定落在同一个边缘节点，实测连续 4 轮重建全部命中；首轮有
  5/13 张因节点压缩差异没对上、按设计退回下载。
- **HEAD 必须带与下载相同的 Accept**：TMDB 的 CDN 按 Accept 协商格式，浏览器式 Accept
  拿到的是 WebP，字节数对不上。实测 TMDB 与 Fanart 图床的 HEAD `Content-Length` 与 GET
  字节数完全一致。
- **头像**：按档位分层存放，换小档位时从更大的那层缩出来。
- 记账新增「从媒体目录收编」「本地缩图」两项，任务中心（Web / iOS）显示。

## 4. 为什么不靠 NFO 里记的图片地址判定

最初设想把图片来源地址写进 NFO（Kodi 标准 `<thumb aspect="poster">`），重建时零请求比对。
放弃的原因：NFO 只能说明「这部片的海报是某个地址」，证明不了目录里**哪个文件**是它——用户
自己放的 `logo.png`（命名规则里排在 `clearlogo` 前）、换过而没被镜像覆盖的 `poster.jpg`，
都会让记录指向别人的图。HEAD 比的是真实远端与本地文件，没有这个歧义，代价只是重建时每张
图一个几百字节的请求。
