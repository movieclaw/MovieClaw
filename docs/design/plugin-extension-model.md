## 0. 结论先行

1. **内核机制够用，缺的是领域底座。** 服务、注册表、可撤销注册、事件、子插件这些内核机制，四个场景都用得上，
   也都够用。真正挡路的是领域层：关键动作没有事件（删除、下载完成都不发任何事件），文件和种子之间的关联
   没有落库，插件没有「以谁的身份、能做哪些操作」的概念。
2. **插件要「做事」，不需要另造一套宿主 API。** CLI、MCP、Agent 已经共用同一份 OpenAPI 操作目录
   （约 25 个领域，`subscriptions.create`、`dl.torrent.delete`……），MCP 还已经实现了「进程内经 ASGI
   调用自己的接口、鉴权和校验与 HTTP 完全一致」（`movieclaw_mcp/dispatch.py`）。插件的宿主能力就是这份
   目录，加上插件身份和按操作授权。它天然可序列化、天然有版本快照、天然能跨进程，进程外插件直接调 HTTP 即可。
3. **事件要分两种。** 现有推送中枢和 Webhook 都是内存里发完即忘，重启就丢。「删了片子就删种子」这种有后果
   的自动化，必须用**可靠事件**：和业务改动在同一个数据库事务里写入，提交后投递，至少一次，失败重试，
   消费方按事件 id 幂等。
4. **第一阶段内核要因此提前定下三件事**：事件区分「实时 / 可靠」两种投递、可靠事件的监听器必须有稳定 id、
   内核贯穿「谁触发的」（发起方与因果链）。详见 §6。

## 1. 扩展模型：插件能做的八件事

| # | 扩展形态 | 插件拿它做什么 | 内核机制 | 领域侧需要什么 |
|---|---|---|---|---|
| 1 | **宿主操作** | 主动做事：建订阅、删种子、触发扫描、搜索站点 | 插件身份（§3） | OpenAPI 操作目录 + 插件令牌 + 按操作授权 |
| 2 | **可靠事件** | 对已发生的事做出反应：删片后清种、入库后同步 | 事件，投递方式 = 可靠 | 事务内写入事件表（outbox），提交后投递 |
| 3 | **实时事件** | 统计、展示、低价值通知 | 事件，投递方式 = 实时（现有 EMIT） | 在业务点发事件 |
| 4 | **决策钩子** | 改变决策：加搜索关键词、过滤候选、改排序、否决删除 | `waterfall` / `bail` | 在决策点开钩子，钩子必须无副作用 |
| 5 | **提供方** | 新增一种实现：站点、站点框架、下载器、通知渠道、元数据源 | 注册表贡献 | 把现有的硬编码表改为注册表 |
| 6 | **管线步骤** | 在流水线中插一个耗时步骤：上传网盘、转码、解包 | 注册表贡献 + 持久化任务 | 流水线声明步骤槽位，按槽位串联任务 |
| 7 | **后台服务与入站接口** | 长期监听外部系统；接收外部系统的 Webhook | `ctx.task`、路由注册表 | 插件路由挂到 `/api/v1/plugins/<id>/` 并进入操作目录 |
| 8 | **插件自有数据与界面** | 存自己的规则；在核心实体上打标记；配置页、管理页 | 插件存储、实体扩展字段 | 存储服务、声明式界面 |

一条贯穿全部形态的规则：**决策钩子里不许有副作用，副作用一律放到提交后的可靠事件或宿主操作里。**
否则一次被否决的决策（例如候选被别的规则淘汰）也会留下插件的副作用，并且核心事务里会混进插件代码。

## 2. 场景推演

每个场景按「现状 → 插件怎么写 → 缺口 → 结论」展开。

### 2.1 删除影片时，自动删种子、删订阅

**现状：**

- 删除条目走 `library.items.delete`（`api/routes/libraries.py:3041` → `services/library/items.py:3259`），
  **立即永久删除**，不经回收站，响应返回时文件行已经没了。删单文件、回收站进出、到期清除也是同样情况。
- **删除、进回收站、恢复、清除，全都不发任何事件**（推送、Webhook、订阅动态都没有）。
- 文件到种子的关联很弱：
  - `library_file` 上只有 `site_id` / `torrent_id`（站点自己的种子编号），**没有 info_hash**；
  - 原地下载（inplace）的文件由扫描入库，连这两个字段都没有；
  - 手动下载的意图记录在入库成功后被删除，info_hash 从此找不回来。
- 能用的关联：订阅的 `wanted_item.info_hash` 和 `subscription_download_attempt`（含 `downloader_id`、
  `owned_by_movieclaw`、`hit_and_run`），入库后都还保留。
- **反方向的清理已经做好了**：删除订阅时可以选「同时删种子」，任务 `subscription.cleanup` 按安全顺序
  先删种子、再把文件送回收站（`services/subscription/cleanup.py`）。
- 一个顺序陷阱：订阅还在时先删它的种子，`delete_download_task` 会把对应的剧集打回「想要」状态并重新下载
  （`services/download_tasks.py:813`）。所以必须先删订阅。

**插件怎么写：**

```python
@plugin("acme.delete-cascade", title="删片联动清理")
async def plugin(ctx: Context[Config]) -> None:
    async def on_deleted(event: LibraryItemDeleted) -> None:      # 可靠事件，至少一次
        if event.cause.is_plugin(ctx.entry_id):
            return
        if event.whole_item and event.links.subscription_id:
            await ctx.ops.call("subscriptions.delete", {          # 宿主操作；幂等
                "id": event.links.subscription_id,
                "delete_torrents": True,
                "delete_library_files": False,
            })
        else:
            for t in event.links.torrents:                        # 部分删除：只删相关种子
                if t.owned_by_movieclaw and not t.hit_and_run:
                    await ctx.ops.call("dl.torrent.delete", {
                        "downloader_id": t.downloader_id,
                        "info_hash": t.info_hash,
                        "delete_files": True,
                    })

    ctx.on(LIBRARY_ITEM_DELETED, on_deleted, id="cascade")       # 可靠事件的监听器必须有稳定 id
```

更好的交互是让用户在删除对话框里勾选「同时删除种子和订阅」，而不是全局自动执行。这需要第四阶段的界面贡献；
在那之前，插件配置里提供一个总开关。

**缺口：**

| 缺口 | 归属 |
|---|---|
| 删除 / 进回收站 / 清除要发**可靠事件**，载荷是**删除前的快照**：媒体条目、是否整部删除、每个文件的季集与路径，以及解析好的关联（订阅 id、相关种子的 info_hash / 下载器 / 是否自有 / 是否 H&R）。行删除后就查不到了，所以必须先拍快照，`cleanup.py:21-25` 已经踩过这个坑 | 二 A |
| 入库时把 `info_hash`、`downloader_id` 写进 `library_file`；原地下载的文件在扫描入库时按订阅下载记录的 `save_path` 补齐 | 二 A |
| 插件身份可以被授予危险操作（`x-cli-dangerous`）；删除类操作要支持「演练」，只返回将要做什么、不真执行 | 二 A |
| 删种前的否决钩子 `dl.torrent.before-delete`（`bail`），让「H&R 未达标不许删」这类规则成为独立插件 | 二 B |
| 删除对话框里的插件选项 | 四 |

**结论**：内核机制足够；领域侧要补「删除事件 + 关联落库 + 插件身份」。

### 2.2 订阅下载完成后先传网盘，再入库

**现状：**

- 订阅只负责把种子交给下载器；文件进媒体库靠入库任务 `library.ingest`（`services/library/ingest.py:4425`）。
- **网盘 / STRM 流程已经实现了一半**：导入规则可以设「自定义目录」（`ImportWatch.target_path`），入库任务
  识别、改名后硬链接或复制到暂存目录，不记台账。外部工具上传、生成 `.strm` 放进媒体库根目录，扫描把 `.strm`
  记账并关闭订阅的想要项。`strm-workflow.md` §6.5 明确写着「内置上传 + strm 生成：明确不做，留作独立开口……
  届时整理段与回流侧无需变更」。**这个开口正好由插件来填。**
- 播放 `.strm` 时每次都重新读文件里的地址（`movieclaw_playback/streaming.py:436`），所以 `.strm` 可以指向
  一个固定的跳转地址，由插件在播放时换出新鲜的网盘直链。
- 入库任务结束时**没有任何交接点**：没有完成回调，最终文件路径也没有收集（`_ingest_entry` 只保留了源文件的相对名，`ingest.py:1740`）。
- 持久化任务基础设施已经很完整：去重键、资源锁、进度、取消、重试 / 阻塞 / 失败三种结局、租约跨重启、凭据不入任务输入。

**插件怎么写：**

1. 用户把导入规则设成「自定义目录」，指向暂存目录（现有能力）。
2. 插件往管线槽位 `ingest.staged` 贡献一个步骤。入库任务整理完一批文件后，按槽位创建插件的持久化任务，
   并把它挂在入库任务下面（父任务 / 根任务 id，现成字段）。
3. 插件的任务处理器（贡献到 `JOB_HANDLERS`）负责：断点续传上传（仿 `_transfer_for_job` 的分块 + 旁路状态文件）、
   上报进度、网络错误 `JobRetry`、凭据失效 `JobBlocked`（带「去配置」动作）。
4. 上传完成后，在媒体库根目录用「临时文件 + 不覆盖改名」写 `.strm`，内容指向插件自己的跳转路由
   `/api/v1/plugins/acme.cloud/play/<file_id>`；然后调宿主操作触发该目录的增量扫描。
5. 扫描记账 `.strm`、关闭想要项、订阅完成——这一段完全复用现有流程。
6. 确认是硬链接时删除暂存副本（不影响做种）。

**为什么不做成「入库时的传输策略」**：传输步骤运行时持有媒体库资源锁（`ingest.py:2160`），几十 GB 的上传
会把该库的扫描、整理、转移全部堵住；同盘校验等逻辑也假设目标是本地文件。

**缺口：**

| 缺口 | 归属 |
|---|---|
| 入库任务收集最终文件路径，并在整理完成后按槽位串联下游任务；载荷包含最终路径、季集、媒体条目、info_hash、导入规则、目标媒体库（自定义目录规则是按类型的，不按库，要带上路由结果） | 二 B |
| 插件可以贡献任务处理器、创建持久化任务（第一阶段的 `JOB_HANDLERS` 注册表已覆盖处理器） | 一（处理器）/ 二 A（创建任务的宿主操作） |
| 插件凭据存储：只存引用，任务输入里不放明文（与现有 `_secret_input_path` 规则一致） | 三 |
| 插件路由；播放器访问的跳转地址要用签名链接鉴权，而不是会员令牌 | 二 B |
| 进程外插件要读暂存目录：需要「路径授权」；同一容器里的独立进程，靠文件权限做不到强隔离，真正的文件系统沙箱留到第三阶段评估 | 三 |
| `.strm` 条目没有媒体规格（不探测）：接受这一限制，或者由插件通过实体扩展字段写回规格 | 二 B（可选） |

**结论**：内核机制足够（注册表贡献 + 持久化任务 + 路由）；领域侧要补「入库管线槽位」。这是所有场景里
最能体现「管线步骤」这种扩展形态的一个，建议作为二 B 的验收插件。

### 2.3 基于关键字规则的自定义订阅

**现状：**

- 订阅永远锚定一个 TMDB 媒体条目（`subscription.media_item_id` 唯一且必填），并展开成按季集的想要项。
- 搜索关键词由内部函数从中英文和原名推导（`wanted_search.py:67`），用户不能加关键词或排除词。
- 规则集只是参数（分辨率、片源、发布组黑白名单、做种数、体积……），不能表达自定义逻辑（`movieclaw_matcher/rules.py:45`）。
- 投递路径（`dispatch.py:50`）要求有订阅和想要项；入库时按 info_hash 认领订阅身份。

「关键字订阅」其实是两类不同的需求，要分开设计：

**A 类：在现有订阅上加关键字规则**（最常见）。例如「这部剧只要某字幕组」「标题必须含『国语』」「排除『抢先版』」。

- 插件写法：两个决策钩子即可。
  - `subscription.search.keywords`（`waterfall`）：在内部推导的关键词基础上追加或替换；
  - `subscription.candidates.filter`（`waterfall`，按批）：在规则集评估之后，再按插件规则淘汰候选，
    淘汰原因写进订阅动态（与现有 `MATCH_REJECTED` 一致）。
- 插件规则存在插件自己的存储里，用实体扩展字段挂到订阅上（`subscription.ext["acme.keywords"]`）。
- 缺口：两个钩子（二 B）；实体扩展字段（二 B）；在订阅详情里编辑插件规则的界面（四，之前用插件配置页代替）。

**B 类：不锚定作品的关键字订阅**。例如「每周综艺 / 体育赛事 / 某字幕组的所有新番，只要标题匹配就下」。
这类内容常常没有 TMDB 条目，或者条目和种子对不上。

- 推荐写法：插件自己维护「关键字订阅」，复用核心的积木，而不是改造核心订阅模型：
  1. 定时任务（贡献到 `SCHEDULED_TASKS`），或订阅实时事件「站点新种同步完成」；
  2. 调宿主操作 `search.torrents` 搜索，或读同步下来的新种；
  3. 用插件规则 + 调宿主操作「按规则集评估候选」复用核心匹配器；
  4. 调宿主操作 `dl.submit` 投递，带上**下载意图**（归属 = 本插件、目标媒体库、期望身份）；
  5. 入库时按意图认领身份，文件来源记为 `plugin:acme.keyword-sub`；
  6. 订阅可靠事件 `download.completed` / `library.ingest.imported` 更新插件自己的状态。
- 缺口：
  - 匹配器没有对外操作（「用某规则集评估这批候选」）——二 A 补；
  - 现有「手动下载意图」要泛化成带归属方的**下载意图**，插件投递的下载才能在入库时被正确认领、在删除时被正确联动——二 A；
  - 下载完成事件（`download_progress.py:613` 处目前什么都不发）——二 A。
- 不推荐的写法：给核心订阅加一个「订阅来源」注册表，让插件定义新的订阅种类。这要放开 `media_item_id` 必填、
  改动想要项展开、对账、订阅页面，侵入太深。等 B 类插件真正跑起来、证明需要深度集成时再评估。

**结论**：A 类靠决策钩子即可；B 类靠「宿主操作 + 下载意图 + 可靠事件」组合实现。内核机制足够，
领域侧要补匹配器操作、下载意图归属、下载完成事件。

**长期约束（2026-10-08 用户决策）**：B 类第一步不改核心订阅模型，但**将来必须能兼容、完全扩展乃至替换整条订阅链路**。
因此订阅链路的每个环节（搜索触发、候选来源、匹配淘汰、排序决策、投递、完成对账）在二 B 开放时都按「可替换的契约」
来定义，而不只是开钩子：钩子解决「改一点」，契约解决「换一整段」。届时评估把订阅引擎本身定义为服务键
（`SUBSCRIPTION_ENGINE`），内置引擎只是它的默认提供方。

### 2.4 离线任务监听外部信号，决定触发订阅

例如：豆瓣想看列表新增、Trakt 片单变化、家庭群里有人发了片名、某个 RSS 出现新条目。

**插件怎么写：**

- **拉模式**：贡献定时任务，或用 `ctx.task` 起一个常驻循环轮询外部系统。
- **推模式**：贡献一个入站路由 `/api/v1/plugins/acme.trakt/webhook`，外部系统推过来。鉴权用插件签发的
  签名令牌，不用会员令牌。
- 拿到片名后：调 `discover.search` 解析成作品，再调 `subscriptions.create`。现有接口在豆瓣条目有歧义时
  返回 409 并附候选（`api/routes/subscriptions.py:272`），插件要处理这种情况（取最佳候选，或写待处理事项让人确认）。
  创建接口对同一作品幂等，重复信号不会重复订阅。
- 常驻循环要上报健康状态（「Trakt 令牌过期」），出现在诊断页和待处理事项里。

**缺口：**

| 缺口 | 归属 |
|---|---|
| 插件身份「代表哪个成员」：订阅有 `member_id`，成员能做什么受权限 v2 约束。插件配置里指定「以谁的身份订阅」，权限取该成员与插件授权的交集 | 二 A |
| 入站路由与签名令牌 | 二 B |
| 运行时健康上报 | 二 B |
| 外部系统凭据存储 | 三 |

**结论**：几乎不用改核心业务，主要靠宿主操作 + 路由 + 定时任务。是最容易落地的场景，适合作为
**二 A 的验收插件**。

### 2.5 站点定义与订阅链路的关键环节

**站点：**

- 现在纯 YAML 能描述「NexusPHP 形态」的站点（地址、认证方式、分类映射、全套选择器、优惠规则）。
  非 NexusPHP 的站点、JSON API 站点、特殊解析都要写 Python 子类（`mteam.py` 509 行、`sunnypt.py` 427 行）。
- 框架表、认证方式都是硬编码的封闭集合（`registry.py:308`、`registry.py:31`）。
- **安全问题**：YAML 的 `custom_class` 字段可以加载 `sys.path` 上任意可导入的类，没有白名单，也没有
  `issubclass(BaseSite)` 校验（`registry.py:97-102`、`:213-223`）。用户目录 `data/site-configs` 里的
  一个 YAML 文件就能触发任意模块的顶层代码执行。
- 插件化方案：
  - 站点定义 = **数据包插件**，贡献到 `SITES` 注册表（带 schema 校验）；
  - 站点框架 / 站点类 = **代码插件**，贡献到 `SITE_FRAMEWORKS` 注册表；YAML 只能引用已注册的框架或类名，
    不再接受任意导入路径；
  - 认证方式 = 注册表 `SITE_AUTH_TYPES`。
- 进程外的站点插件有一个特殊需求：站点访问要走宿主的出口（每站代理、限速、Cookie、熔断都在宿主里），
  所以宿主要给站点插件提供「绑定到该站点的 HTTP 客户端」能力，而不是让插件自己发请求。
  `BaseSite` 的方法都是异步、返回 pydantic 模型，本身满足可跨进程约束，只有构造参数（`HttpClient`、`AuthManager`）需要改成宿主代理。

## 3. 宿主操作：插件怎么「做事」

### 3.1 直接复用 OpenAPI 操作目录

| 方案 | 评价 |
|---|---|
| 另造一套插件专用 API | 要重新设计约 25 个领域的能力、重做鉴权和校验、单独维护兼容性，且与 CLI / MCP / Agent 割裂 |
| **复用 OpenAPI 操作目录（采用）** | 能力已经存在并被三种客户端验证过；有 `operationId` 和规格快照；天然可序列化；进程外插件直接调 HTTP；进程内插件经 ASGI 调用（MCP 已有实现） |

进程内调用路径：`ctx.ops.call("subscriptions.create", payload)` → 以插件身份签发短期令牌 → 经 ASGI 调用
本进程的 FastAPI → 与 HTTP 请求走完全相同的鉴权、权限、校验。代价是每次调用多一层 HTTP 序列化，
在插件场景（秒级以上的自动化）可以忽略。

### 3.2 插件身份与授权

- 新增一种主体：**插件主体**（`kind=plugin`，id = 条目 id）。现有令牌的作用域只有 `full` / `transcode`
  两档（`schemas/auth.py:56`），要扩展成按操作授权。
- 插件清单声明需要的操作（支持领域通配，如 `subscriptions.*`）；危险操作（`x-cli-dangerous`）必须逐个列出，
  安装时单独展示给用户批准。
- **代表成员**：需要成员语义的操作（订阅、收藏），插件配置里指定代表哪个成员；有效权限 = 该成员的权限 ∩ 插件被授予的操作。
- **审计**：插件发起的操作，在订阅动态、任务中心、日志里都标明「由插件 X 执行」。

## 4. 可靠事件

### 4.1 为什么现有机制不够

- 推送中枢：内存队列，单消费者，满了丢、重启丢（`services/push/hub.py`）。
- Webhook：提交后起一个后台任务，最多重试 3 次，没有持久队列（`services/webhook/dispatcher.py:50`）。
- 两者都适合「通知」，不适合「删种子」这种有后果的自动化：进程恰好在删除提交后、投递前重启，联动就永远不会发生。

### 4.2 设计

- **事务内写入（outbox）**：业务代码在同一个数据库事务里把事件写进事件表，事务提交即事件成立；回滚即不存在。
  不会出现「删除成功但事件丢了」或「事件发了但删除回滚了」。
- **提交后投递**：投递器从事件表按顺序读出，交给每个可靠订阅者；每个订阅者（条目 id + 监听器 id）有自己的进度，
  互不影响。
- **至少一次 + 幂等**：处理成功才前进；失败按退避重试；超过次数进入死信，在诊断页可见、可手动重放。
  事件 id 沿用现有信封的 ULID，消费方以它去重。
- **快照式载荷**：删除类事件携带删除前的快照与解析好的关联（§2.1）。
- **因果链**：每个事件携带发起方（用户 / 成员 / 插件 / 系统）和因果链。插件可以忽略自己引起的事件；
  因果链长度超过上限（如 8）时停止投递并告警，防止插件之间互相触发成环。
- **统一出口**：Webhook 出站变成一个普通的可靠订阅者，顺带获得持久重试；推送中枢继续用实时事件。
- **事件目录**：现有 Webhook 事件目录（`services/webhook/catalog.py`）扩展为全系统事件目录，每个事件标注版本、
  稳定性、投递方式。Webhook 允许订阅其中「对外」的子集。

关于「本地受信插件」放在二 A：你举的场景，很多就是你自己要用的定制。等到第三阶段的进程外运行器做完再写插件，
扩展模型要很久之后才能被真实插件检验。二 A 先允许本地受信插件进程内运行（显式开启、诊断页醒目标注），
扩展模型就能边做边被真实插件验证；第三阶段再把它们挪到进程外，验证「运行位置对插件透明」。

## 6. 对第一阶段内核的反向影响

场景推演证明，以下三件事如果第一阶段不定，第二阶段就要改内核接口。已同步修订 `plugin-kernel.md`：

1. **事件区分投递方式**：事件定义增加 `delivery = LIVE | DURABLE`。第一阶段只实现 `LIVE`（即现有 EMIT 语义）；
   `DURABLE` 事件的监听器需要可靠事件存储服务（`DURABLE_EVENTS`），第一阶段没有提供方，这类监听器停在等待状态，
   内核接口不必再改。
2. **监听器要有稳定 id**：`ctx.on(E, handler, id="...")`。可靠事件的消费进度以「条目 id + 监听器 id」为键，
   没有稳定 id 就无法跨重启续投。实时事件 id 可选（诊断里更好认）。
3. **发起方与因果链**：内核用 `contextvar` 贯穿「当前由谁发起、因哪个事件引起」，传过 `ctx.task`、事件分发、
   （二 A 起）宿主操作。插件据此忽略自己引起的事件，内核据此限制因果链长度。

另外两条只影响文档、不影响第一阶段代码：

- 决策钩子无副作用的规则写进 `plugin-kernel.md` §4.7；
- 内置插件清单里的注册表在二 B 会大量增加（站点、下载器、通知渠道……），第一阶段的注册表实现要按「会有几十个注册表」
  来写诊断输出。
