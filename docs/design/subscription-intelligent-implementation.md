# 智能订阅技术方案

状态：首版已实现，按冻结快照执行。验收结果见 [实现与验收记录](subscription-intelligent-acceptance.md)。有门槛的历史证据等待默认开启；旧资源回放已验证减少额外观察，长期等待收益仍需纵向验证。

日期：2026-10-07。

需求依据：[智能订阅模式与等待策略](subscription-intelligent-waiting.md)。

## 1 技术结论

新增独立的智能选择策略。首版使用确定性代码和可解释的统计预测。原有规则模式保持原有语义。两种模式共用身份识别、资源索引、下载、入库和清理能力。

智能模式不生成隐藏规则组，也不使用大语言模型直接选择下载对象。动态性来自作品事实、发布历史和当前状态的变化，不来自每次重新生成一套规则。

| 方案 | 结论 | 原因 |
|---|---|---|
| 将智能偏好转换为旧规则组 | 不采用 | 旧组同时表达硬过滤、加权评分和洗版阶梯，无法清楚表达等待承诺与逐集跟随 |
| 复制整套订阅引擎 | 不采用 | 会复制认领、重试、换源、入库和旧文件保护逻辑 |
| 新的确定性选择策略 | 首版采用 | 同一输入产生同一决策，可以回放、解释和测试 |
| 统计发布时间预测 | 首版采用 | 用本季实际记录估算等待窗口，证据不足时明确退回有限观察 |
| 大语言模型直接做选择 | 首版不采用 | 决策会控制下载与替换；首版需要稳定的边界、可重复结果和离线运行 |
| 学习型到达预测 | 后续候选 | 只有在数据与回放证明优于简单方法后，才替换预测部分 |

首版业务实现已落地。动态预测保留独立开关，默认不启用。工程验证与真实效果验证分别记录，不把合成场景通过写成收益提升。

## 2 现有能力与必须改动的地方

| 现有位置 | 已有能力 | 改动边界 |
|---|---|---|
| `movieclaw_enrich` | 用现有模型和解析逻辑提取资源属性 | 复用。保留未知值与识别证据，不把猜测当事实 |
| `movieclaw_matcher/identity.py` | 作品和季集身份匹配 | 复用。智能模式不得绕过身份检查 |
| `services/subscription/matching.py` | 被动匹配和主动搜索共用评估管道 | 增加模式分流。智能候选进入统一决策入口 |
| `services/subscription/release_forecast.py` | 同季发布时间预测、加权中位数和误差窗口 | 复用统计方法与观测来源，另建版本系列维度的预测 |
| `services/subscription/dispatch.py` | 工单条件认领、真实投递和活动记录 | 复用并加强智能决策版本校验，处理提交结果不确定的恢复 |
| `movieclaw_matcher/decision.py` | 旧规则组的品质阶梯、停止判断和去重比较 | 保留旧行为。智能模式提供独立的比较与达标判断 |
| `services/library/ingest.py` | 入库前判断来件是否被现有版本覆盖 | 按订阅模式选择同一套品质判断，不能继续无条件使用旧阶梯 |
| `services/subscription/upgrade.py` | 快照、洗版核验、替换和旧资源保护 | 复用执行流程。候选判断、停止判断和实测比较改为消费对应模式的策略 |

这里有三个重要事实：

1. 当前 `Subscription.rule_set_id` 非空。新模式需要正式的模式字段和数据约束，不能只在前端隐藏规则组。
2. 当前很多洗版查询通过规则组 ID 判断是否启用洗版。这些查询需要一起适配智能模式。
3. 当前同一作品只有一份共享订阅。第二个成员订阅时会成为关注者，不会创建另一份下载。

现有预测估算的是较早单集的最早资源发布时间。它不能直接回答“指定系列的 4K 版本何时到达”。

## 3 决策结构

```text
资源索引与属性识别
        ↓
共享身份检查与资源可用性检查
        ↓
读取订阅模式
        ├─ 规则模式 → 原有过滤、评分与洗版阶梯
        └─ 智能模式 → 偏好快照 + 本季跟随状态 + 单集等待状态
                              ↓
                       确定性决策函数
                              ↓
                等待 / 无合格资源 / 提交候选 / 已达目标
                              ↓
                  统一认领、下载、入库与核验
```

智能决策函数不访问数据库，不读取当前系统时间，不调用网络或模型。调用方提供 `now` 和事实快照。

建议输入包含：偏好快照、候选集合、本季跟随记录、本集等待状态、当前已入库品质、历史观测和本轮触发原因。

建议输出包含：动作、候选 ID、原因码、证据引用、下次评估时间、建议状态变更和算法版本。

输出不是执行命令。服务层必须重新检查订阅状态和决策版本，然后才能认领工单。

模式分流应收口为少量明确函数：加载策略、评估候选、判断升级、判断达标。首版不建设可插拔规则平台。

## 4 偏好和状态如何保存

### 4.1 电影和剧集偏好

新增类型偏好记录，保存品质偏好、最低要求、等待预算和洗版选择。每种类型一份有效设置。保存版本号和修改时间。

电影和剧集共用「等待耐心」下拉框：尽快下载 · 不等待、可以等 · 最多 3 小时、更有耐心 · 最多 1 天、自定义。选择自定义后显示 1–7 天的整数输入框，单位为「天」，两侧 − / + 每次调整 1 天，到边界禁用对应按钮。不展示范围或加减操作说明，不使用滑块。手机使用数字键盘；空值、非整数及越界值由表单校验阻止保存。内部仍存秒数，上限扩展至 604800；服务端保留整小时输入兼容旧偏好。首次表单为剧集预选 3 小时、电影预选 1 天。已有偏好和订阅快照不自动迁移：2 小时、6 小时、25 小时等非整天旧值以「原有设置 · N 小时」回显，原样保存或取消均不改变预算；主动选择自定义后才转为整天，向上取整且至少 1 天。输入 1 天时仍保持自定义展开。

建议首版沿用原型的管理员视角：全站电影、剧集各一套设置。成员订阅消费对应类型设置。按成员分别保存属于可选的后续扩展，不能默认推导为本次需求。

如果产品选择成员独立设置，仍须保留一部作品一份共享订阅。已有订阅的策略由创建时确定，后续关注者不得覆盖。界面需要提示“此作品已按现有设置订阅”。

订阅确认弹窗采用逐步展开。默认展示作品、品质目标、等待上限和洗版停止方式；剧集另展示已选季与是否自动追新。已有类型偏好时直接复用，用户可以一次确认。首次设置才展开偏好表单，保存后回到摘要；修改中的未保存值不能用于订阅。最低分辨率已启用时必须出现在摘要里。

季列表和自动续订开关收进「追踪范围 → 调整」。模式切换、规则组和入库位置收进「更多选项」；当前入库库名保留为一行摘要。正常下载路径和整理过程不在订阅表单解释。配置错误始终直接显示，不能藏在折叠区域。桌面和手机共用表单内容，保留各自现有的确认按钮位置。

设置页以「智能选择 / 自定义规则」两个页签组织内容。切换页签只改变当前浏览区域，不改变订阅模式，未保存的智能偏好继续保留。智能页只显示电影和剧集偏好；自定义页以规则组列表为主体，新建、编辑等原有操作保持可用。规则组匹配和入库去向的检查收进自定义页的「预览匹配」弹窗，名称为「规则与入库预览」。该预览调用原有真实规则匹配与入库路由接口，不模拟智能选种，不创建订阅或下载任务。长说明默认折叠。

### 4.2 订阅快照

订阅新增 `selection_mode`，值为 `rules` 或 `smart`。旧数据和未传模式的旧客户端都按 `rules` 处理。

智能订阅保存创建时的偏好快照、来源设置版本和决策算法版本。洗版目标也写入快照。系统不得随着可用资源变化自动提高目标。

设置修改只影响新订阅。首版不提供已有订阅的原地模式切换或策略覆盖。已有订阅继续使用冻结快照和版本。

数据库中的 `rule_set_id` 对智能订阅允许为空。数据约束必须保证：规则模式有有效规则组；智能模式有有效偏好快照。不得允许两种配置同时参与选择。

API 的订阅列表、详情和洗版报告继续使用必填整数 `rule_set_id`，兼容已发布的 Apple 客户端。智能模式返回 `0`，表示未绑定规则组；该值仅用于传输，不创建虚拟规则组、不写入数据库。新客户端按 `selection_mode` 展示。旧客户端调整或洗版时回传 `0`，沿用智能偏好快照；回传真实规则组 id 仍拒绝换绑。规则模式返回原有正整数 id，不能使用 `0`。旧版 Apple App 可恢复解码，但不会因此获得智能设置界面，规则栏可能显示 `#0`，完整展示须由 App 后续适配。

快照损坏或版本不受支持时，系统暂停该智能订阅的自动决策并显示原因。不得回退为全不限规则。

### 4.3 每季跟随状态

建议新增一张小表，以订阅 ID 和季号为唯一键。记录跟随系列、建立依据、证据状态和切换记录版本。

首次投递记录“暂定系列”。首次成功入库核验后，记录“已确认系列”。这样并发出现的前几集不会各选一个系列，也不会把一次下载成功当成长期可靠。

暂定系列投递失败时，允许重新评估。已确认系列发生单集替代时，不自动改变整季跟随。

### 4.4 单集等待状态

扩展现有 `WantedItem`，不新增另一套下载工单。

等待状态保存起点及来源、硬截止时间、观察窗口是否已消费、预测证据快照、最近决策和状态版本。需要调度查询的 `next_selection_at` 单独建列和索引。

等待属于选择状态，不增加到 `wanted → grabbed → downloaded → imported` 的现实进度中。界面从两者组合出“等待版本”等状态。

原始资源继续存于现有索引。关键决策只冻结必要事实和样本引用，不复制整站索引。索引清理后，决策理由仍应可解释。

## 5 把智能选择拆成六个具体问题

### 5.1 哪些候选可以参与

共享身份检查先排除错误作品、错误季集和明显非正片资源。智能模式再应用自己的最低要求和可下载性条件。

偏好和最低要求必须分别校验。偏好 4K 不得被转换为“所有 1080p 都拒绝”。用户只接受 4K 时，到期也不能下载 1080p。

属性缺失时保留未知。缺失片源或制作组的候选不能用于建立有把握的系列关联。系统不得为了凑齐排序字段虚构值。

### 5.2 如何识别同一版本系列

首版使用确定的属性组合：同作品、同季、规范化制作组、分辨率、片源。编码和平台在有可靠值时用于区分同组的不同发布线。

不同站点可以属于同一系列。同一制作组也可以有多个系列。缺失字段不作为通配符去合并两个已知不同的系列。

已知相同 info hash 的转载只计一份发布。缺少 hash 时，使用保守的规范化发布签名合并，并保留去重依据。无法证明重复的记录，不得因此增加独立成功集数。

可靠性按独立单集统计。记录是否观察到、何时观察到、是否被选择、是否成功入库和是否核验失败。系统只能评价已观察范围，不能把未索引到等同于全网没有。

### 5.3 首次如何选择

首版使用明确的排序规则，不使用自由配置的分数权重。

先比较分辨率，再比较片源。同品质已有跟随系列时，继续跟随。没有跟随时，按以下顺序选定本季方案：

1. 比较同版本在本季可覆盖的所需集数。取集合，不累加转载或镜像。
2. 比较本作品、本季已经成功入库并完成品质核验的独立集数。无记录保持未知。
3. 比较本资源可覆盖的所需集数。同组的完整包优先于零散单集。
4. 比较做种数。做种数只用于可下载性决胜，不代表制作组品质。
5. 比较规范化系列标识、站点 ID 和资源 ID。候选输入顺序不影响结果。

后续各集共享本季选择依据。达到用户目标的更高品质可以先于较低品质的跟随版本；同品质不会因做种数变化而切组。系统不用模型猜测制作组口碑。

首版首次选择以分辨率优先。设置页明确说明 4K WEB-DL 排在 1080p 蓝光之前。洗版仍执行两个维度均不得退步的判断。

没有历史时，系统不等待不可预测的“全网最优”。若已经满足用户目标，则直接选择。否则只使用一次有限观察窗口，并受到硬截止时间限制。

### 5.4 后续如何保持稳定

跟随系列的合格资源已出现时，优先延续系列。另一个资源免费或做种更多，不足以触发切换。

原系列未出现时，系统检查预测窗口和截止时间。到期可以为本集选择替代系列，但不直接更改整季跟随。

整季切换需要明确证据。整季切换以经核验的品质问题作为触发条件。站点故障、下载器故障和磁盘错误不计为制作组失约。

首版只使用可核验的品质问题：至少 3 个独立单集品质不符，且替代系列至少 3 集成功入库。切换后重新积累样本。单集缺席仅触发本集替代，不作为整季切换证据。参数固定在算法版本中。

### 5.5 应该等待多久

剧集先预测“等待对象是否可能在预算内到达”。对同季同系列记录，计算它相对每集首个合格资源的观测延迟。起点口径不同的样本不得直接混算。

首版使用近期样本的加权中位数作为中心，并用向前回测误差形成窗口。复用现有统计函数的适用部分，不照搬原有跨品质聚合。

少量样本只提供弱证据。波动大或监测中断时，不给精确到达承诺。有限观察结束后，无新证据就选择当前合格资源。

硬截止时间从持久化起点计算。预测只能改变截止前的评估时刻，不能推迟硬截止。新的候选、索引刷新和服务重启都不能重置预算。

首版电影不做跨作品“蓝光何时发布”的预测。优先从已匹配正片资源的可信站点发布时间计时；缺失时才从首次发现计时，目标资源到达就选，到期使用合格替代，后续升级交给洗版。正式上映日期不等于可靠的下载资源上线时间。

补订旧剧或旧电影时，历史锚点已经超过预算的，直接评估当前资源。未保留历史证据时必须说明使用了首次观测起点，不伪装为官方发布时间。

### 5.6 洗版如何升级和停止

智能模式使用独立的两个判断：`is_upgrade` 判断替换是否更好；`target_met` 判断是否停止。两者不是同一个布尔值。

`target_met` 要求分辨率和片源同时满足目标。单一维度更高不能补偿另一维度不足。分辨率按用户的接受和偏好顺序判断，不默认认为 8K 总比用户选的 1080p 更合适。

建议 `is_upgrade` 使用不退步原则：所有受保护品质维度不变或变好，至少一个维度变好。首版保护分辨率和片源。同档位换制作组不触发品质洗版。

| 当前版本 | 候选 | 目标 | 建议结论 |
|---|---|---|---|
| 1080p WEB-DL | 4K WEB-DL | 4K 蓝光 | 可以升级，但不能停止 |
| 4K WEB-DL | 4K 蓝光 | 4K 蓝光 | 可以升级；入库核验后停止 |
| 1080p 蓝光 | 4K WEB-DL | 4K 蓝光 | 跨维度有退步，不自动替换；继续等 4K 蓝光 |
| 4K 蓝光 | 同品质其他制作组 | 4K 蓝光 | 已达目标，不下载 |
| 分辨率或片源不明 | 宣称更好的资源 | 任意目标 | 证据不足，不能宣称已证明升级或达标 |

这与原有字典序洗版不同。智能模式必须在候选过滤、入库去重和入库后核验中共用这两个判断及其基础比较函数。原有规则模式继续走原有阶梯。

探测可以核验分辨率、编码等文件属性。WEB-DL 或蓝光的真实来源不能仅靠文件探测证明。系统必须保存来源证据、冲突和可信状态，并把无法确认的情况保留为未知。

候选标题不能直接推进达标状态。只有文件入库、可测属性核验完成、来源证据满足约定后，才标记该单元已达目标。旧文件处置继续服从已有所有权、H&R 和回收站保护。

## 6 时间调度与可靠投递

### 6.1 三个自动入口共享一个决定

被动发现资源、主动搜索完成、等待定时器到期，都调用同一个智能决策入口。前端仅展示服务端决策结果。

等待中的候选必须在后续评估中仍可发现。不能只消费本轮新增种子批次。到期时重新读取本作品的有效候选索引，并重查候选资格；此前出现过的合格 1080p 仍应参与兜底选择。

预测窗口结束也需要触发评估。窗口结束和硬截止是两个时间点，前者可以提前结束无收益等待，后者禁止继续延迟品质选择。

截止调度只扫描有索引的到期记录。它首先评估现有索引，不要求每个到期单集立即访问所有站点。站点访问继续复用已有预算、限流和退避。

建议首版以 30 秒为到期扫描周期。正常负载下，到期决策延迟目标为 60 秒以内。此数字是建议验收门槛，必须用目标部署规格的负载测试确认。

重启后扫描所有过期决策。数据库保存截止时间，进程内定时器不是唯一依据。服务停止期间不承诺准时，恢复后必须保留迟执行原因。

### 6.2 并发与恢复

每次人工延期、模式修改或有效决策变化，增加单集状态版本。自动决策保存所依据的版本。

执行投递前，事务内重新检查订阅未暂停、工单仍在范围内、决策版本一致、当前无冲突在途任务。然后认领工单。人工延期与到期投递并发时，以成功提交的状态变更为准；失败方刷新结果，不能假装操作成功。

现有条件认领是基础，但不是完整的外部副作用保证。需要覆盖“数据库已认领但未提交”和“下载器已接收但响应丢失”两个窗口。

建议复用下载尝试记录，补齐可恢复的提交意图、资源指纹和阶段。重启或超时后先与下载器对账，再决定是否补交。无法确定提交结果时，保留待对账状态，不立刻另选一个资源。

目标是同一单元最多有一个冲突的自动在途选择，以及提交结果可恢复。不能宣称数据库事务能让外部下载器天然实现严格一次执行。

网络调用不放在长数据库事务内。旧版换源中有明确意图的主源与试用源并存，不应被误判为重复投递。

### 6.3 整季包

整季全缺时，满足相同品质条件的完整方案先于零散方案。已入库、已有在途任务、尚在等待或已达洗版目标的单集不参与本次认领，但不因此排除整个包。制作组只发布完结包时，包内缺失集也可以参与选择。

智能剧集投递必须执行：冻结本次集数与意图标识 → 暂停添加 → 获取实际文件清单 → 精确选择本次所需集数 → 回读核验 → 再检查订阅状态 → 恢复。文件清单必须把每个所需单集对应到唯一、可拆分的视频文件。

无法识别、合并集单文件、压缩包无正片、缺少所需集、重复文件、设置失败或回读不一致时，任务保持未恢复。显示原因，重试相同意图与 hash。不得回落全量下载。未经意图标签确认的已有任务不得修改。

包内文件核验在真实投递时确认。BT 分片跨文件边界可能产生少量边界数据，不能承诺网络字节只包含选中视频。

## 7 接口与用户操作

| 接口职责 | 必要行为 |
|---|---|
| 读取与保存两类设置 | 返回是否完成首次设置、版本和有效摘要；并发编辑需要版本检查 |
| 创建订阅 | 显式传模式；智能模式引用已保存类型设置，由服务端冻结快照 |
| 读取订阅详情 | 返回模式、目标、等待对象、截止时间、依据和下一动作 |
| 立即下载 | 指定当前可见候选和决策版本；服务端重新检查资格，不绕过最低要求 |
| 延长等待 | 指定单集、延期时长和决策版本；成功后返回新的固定截止时间 |

新客户端显式选择智能模式。旧客户端不传模式时保持规则模式。智能模式请求同时携带规则组参数时，服务端应明确拒绝歧义输入。

首次设置的完成标记只在保存成功后写入。保存设置与创建订阅是两个可辨别的结果。创建失败后，已经保存的设置不应丢失。

已有共享订阅的再次订阅操作保持幂等。它返回正在使用的模式和偏好摘要，不按新的请求静默改写原订阅。

## 8 模型的使用边界

继续使用现有资源属性识别模型。识别失败时保留未知，不能放宽最低要求。记录解析器或模型版本，便于回放时解释属性差异。

首版不用大语言模型预测“最佳制作组”，也不用它决定何时下载、替换哪个文件或何时删除旧文件。活动理由由结构化原因码生成，不需要模型润色才能解释。

后续模型只能先进入预测层：估算某个系列在剩余预算内出现的可能性。必须使用已发生的观测，并处理“截至观测结束仍未出现”的样本。不能把这类样本一律当成永不出现。

模型输出只能作为证据。确定性执行层仍控制最低要求、固定截止、并发认领和洗版停止。模型不可用时，回落到统计预测或有限观察，不能无限延长等待。

只有简单统计方法在分层回放和真实观察中出现持续、可测的不足，才考虑训练新模型。

## 9 如何验证有效性

### 9.1 历史事件回放

把资源出现、属性更新、站点健康、用户操作和入库结果组织为按时间排序的事件。给三套策略输入同一条事件流：

1. 当前规则模式。
2. 简单基线：固定等待预算加同系列优先，不使用预测。
3. 新方案：同系列跟随、动态预测和固定截止。

回放使用当时可见的数据。资源宣称在 20:00 发布，但系统在 21:00 才发现，不能让 20:30 的算法看见它。当前属性可能经过后续修正；没有历史版本的字段不能假装当时已知。

历史数据不足时，只把合成场景用于验证决策逻辑，不能据此声称真实选种效果提升。先用影子观察收集带版本的决策快照，建立可信回放集。

按电影、周播剧、日播剧、新剧、旧剧补订、整季发布、稀缺资源和站点异常分别报告。不能只用一个平均数覆盖所有场景。

### 9.2 效果指标

| 指标 | 计算口径 | 防止的误判 |
|---|---|---|
| 首次品质达标率 | 首次入库后，分辨率和片源分别达标的比例，以及两者同时达标比例 | 一个维度的提升掩盖另一个维度退步 |
| 版本连续性 | 同季相邻已入库单集保持同系列的比例；另报必要替代和主动切换次数 | 把停更后的合理替代当成失败 |
| 等待代价 | 从可解释起点到提交、到入库的时间分布，分别报告 | 把开始下载误写成可以观看 |
| 到期执行延迟 | 有合格候选时，实际决策时间减去固定截止时间 | 把无合格资源导致的缺口算成计时失效 |
| 有效等待收益 | 等待后获得更合适版本的比例，以及无收益等待的时长 | 只展示成功等到的例子 |
| 重复下载代价 | 同一单元的下载次数与实际下载字节，区分首次、洗版、失败恢复 | 以更多下载换来表面品质提升 |
| 预测质量 | 到达窗口覆盖率与窗口宽度同时报告，按置信等级分层 | 用极宽窗口制造高命中率 |
| 运行成本 | 每订阅站点请求数、决策耗时和扫描积压 | 智能策略通过高频刷站获取优势 |

离线可以比较“当时可选择哪个资源”。它不能证明未下载资源一定成功。只有实际下载和入库能验证成功率、真实品质和流量代价。效果结论必须说明这种观察限制。

新策略必须同时对比简单基线。若预测没有改善品质或等待时间，就暂不启用预测，保留更简单的版本跟随与固定截止。

不预先承诺任意提升百分比。正式效果门槛需在基线测量后确定，并使用不同作品的留出数据验证。报告样本量和不确定范围，不能用少数热门剧作为全部结论。

## 10 如何验证可靠性

### 10.1 必须成立的不变量

1. 相同输入、时间和算法版本，必须得到相同决策。
2. 未经用户显式延期，截止时间不得向后移动。
3. 到期不能突破最低要求。
4. 同一单元不能产生互相冲突的自动投递。
5. 智能洗版不能在受保护品质维度上退步。
6. 未完成核验的候选不能推进停止状态。
7. 已达目标后，新资源不能自动重新开启洗版。
8. 修改电影设置不能改变剧集策略，反之亦然。
9. 智能模式关闭或失败，不能悄悄退回原有规则自动下载。
10. 规则模式的既有行为必须保持。

对候选排列、事件重复、时间推进和重启恢复进行生成式测试。测试这些不变量，不只测试几条示例输出。

### 10.2 真实业务链路与故障注入

端到端测试必须使用真实接口、数据库迁移、调度器、决策服务、投递服务和入库核验。只替换外部站点、下载器和时间源。使用少量可探测的媒体夹具验证入库结果。

| 故障或场景 | 必须验证的结果 |
|---|---|
| 截止事件和新资源同时到达 | 只确定一个有效候选，不重复投递 |
| 人工延期与自动认领并发 | 只有一个版本变更成功，另一方收到准确结果 |
| 认领后进程退出 | 恢复提交意图，不永久卡在 grabbed |
| 下载器已接收但响应超时 | 对账后恢复关联，不立即提交其他资源 |
| 数据库写入失败 | 不把未持久化决策显示为已经执行 |
| 暂停、取消或缩小季范围 | 过时决策不能继续投递 |
| 索引清理或模型更新 | 保留截止与证据摘要，不重置首次观察 |
| 候选在等待开始时出现，此后没有新种子 | 截止调度仍能重新取得候选并执行到期选择 |
| 站点不可用 | 不误判制作组停更，按现有限流与退避运行 |
| 标题宣称 4K，实际为 1080p | 不标记目标达成，不错误清理当前好版本 |
| 片源证据冲突 | 保留未知或待核实，不伪造实测结论 |
| 包含不同等待状态的整季包 | 不越过单集的等待或洗版保护 |
| 未开启洗版与已达目标 | 新资源到来不触发替换 |
| 老版本数据库升级、旧客户端请求 | 旧订阅继续按规则模式执行 |

最后在隔离环境连接真实下载器，使用项目自有或可合法分发的测试媒体，验证提交、重启对账、导入和旧版本保留。模拟测试不能替代这一段外部协议验证。

### 10.3 性能与回归

检查到期记录查询计划。确认使用索引，不每轮扫描全部种子与全部工单。检查同一作品的一批候选是否共享已加载上下文。

执行匹配、规则组、发布时间预测、洗版、入库去重、下载尝试和换源相关回归测试。原有模式的决策差异应为零，除非另有明确批准的修复。

## 11 上线和回退

先运行影子决策。影子模式只记录选择结果，不增加下载和站点请求，也不修改原订阅状态。对比相同候选和相同时间下的策略差异。

影子观察不能验证实际下载成功率。通过可靠性测试后，再对明确选择智能模式的新订阅逐步启用真实执行。保留规则模式作为对照，不能把同一作品同时交给两套执行策略。

异常时关闭智能自动决策。已有下载和入库继续完成，待选智能工单暂停并显示原因。恢复后按原有快照和截止继续，不自动迁回旧规则组。

数据库增加智能模式后，旧程序可能把空规则组错误地理解为默认或全不限。必须设置运行版本兼容检查。回退程序前要阻止智能工单被旧程序消费，不能仅回退前端。

观测期至少应覆盖完整的发布周期和多种作品。数据不足时继续观察，不以经过固定天数代替有效样本。

## 12 实施拆解与交付门槛

| 阶段 | 交付内容 | 通过门槛 |
|---|---|---|
| 1 模式与偏好 | 类型设置、模式字段、快照、迁移、权限和首次设置接口 | 设置隔离、旧客户端兼容、共享订阅幂等测试通过 |
| 2 品质与停止语义 | 智能合格条件、升级比较、目标判断、入库适配 | 选种、去重和核验对同一品质组合给出一致结果 |
| 3 可靠等待闭环 | 单集截止、到期调度、立即下载、延期、提交恢复 | 并发和崩溃场景无错误投递，重启不重置截止 |
| 4 系列跟随 | 系列识别、暂定与确认状态、替代和切换证据 | 同季连续性场景通过，站点故障不触发错误切换 |
| 5 时间预测与回放 | 系列到达窗口、历史回放、简单基线、指标报告 | 证明预测的增益；无增益时继续使用简单基线 |
| 6 页面与灰度 | 原型对应页面、准确状态说明、影子运行和逐步启用 | 完整用户流程通过，旧模式回归通过，回退演练通过 |

页面可以在前期并行制作，但真实自动投递必须等到阶段 2、3 的保护条件通过。首个可运行版本可以先使用有限观察和固定截止，再增加动态预测。

首版决策已写入需求第 11 节。运行开关为 `subscription.smart`：`enabled` 控制自动选择，`shadow_only` 只记录结果，`prediction_enabled` 默认关闭。已有任务的对账、下载进度和入库不因关闭自动选择而停止。

原始候选按订阅保存，以支持索引清理后到期执行。每个候选保存最多 16 个属性观测版本。发生决策变化时，保存去掉下载地址的输入与结果，供精确回放。回放工具支持冻结决策精确重放和单单元时间序列比较。三套策略分别推进状态；实际入库只关联匹配候选，未知字节与反事实下载结果不填成零。它不模拟整季包或未发生的下载成功。真实留出集效果报告仍属于效果验收门槛，见验收记录。

数据库有智能订阅或智能设置时禁止直接降级，使用完整备份恢复。尚未启用智能模式的数据库可以无损降级。旧程序因不认识新迁移版本而拒绝启动，不会消费空规则组的智能订阅。


### 等待证据实现修订（2026-10-07）

`smart_waiting.py` 提供纯函数时间锚点与历史延迟计算。`smart_selection.py` 从候选快照重新检查身份，按季提供独立单集发布记录。整包参与当前单元的最早发布时间，但不参与频率样本。`smart.py` 同时用于正式订阅和自动化回放。

状态增加 `anchor_source`、`first_observed_at`、`manual_extended`、`wait_explanation`，兼容现有 JSON，无数据库迁移。原偏好及算法契约版本保持 1；本修订修复时间依据，并在每份决策输入中冻结 `release_history` 和 `episode`。历史记录应用新实现后的结果可能变化，不把这些变化称为旧实现的精确重现。

预测至少需要同季较早的 3 集，最多 8 集。按单集去重；中心为近期加权中位数，半径取至少 30 分钟和向前误差最大值。半径超过 3 小时则不提供预测。只计算站点发布时间之间的差值，不混合系统发现时间。成熟样本按时比例低于 80% 或最近两集连续缺席时撤回依据。样本缺失会降低等待意愿，不推断全网不存在目标资源。

每次刷新重新验证预测。目标版本已出现则不等待历史预计时间。预测超过用户预算时不为了候选观察耗尽预算。人工延期是独立标记，不会被新时间证据覆盖。

`smart_replay_events.py` 新增 `evidence` 对照，资源只能在 `observed_at` 后进入。`fixed_wait` 明确忽略站点发布时间，用于旧等待基线。未观察到的实际下载、入库和字节收益保持未知。
