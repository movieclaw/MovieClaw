# 播放引擎：FFmpeg 负责拆，Apple 负责播

> 状态：**自研引擎就是正式版的播放器**（2026-09-28 用户拍板：应用尚未发布、没有历史包袱，不留引擎选项与强制引擎的开关）。
> 本机只有这一个播放器：自研引擎（硬解 → 引擎自己软解）解不了才改走服务端 HLS → 逐级降档 → 中文报错（§3）。
> MPV 已于 2026-09-28 整个移除（§3.6）。分支 `feat/ios-player-engine`。
> 起播链路与测量手段见 [playback-startup.md](playback-startup.md)。

## 1. 前提与原则

2026-09-27 定下的前提：**服务端（NAS）大多数时候性能弱，终端越来越强**，所以要用好终端；Apple TV 一定要做；
兜底链路不能丢。由此推出的规则：

- **终端做实时的重活**：解封装、解码、字幕、音频处理都在终端。服务端只提供文件字节与已探测的事实，
  空闲时可以做后台预计算，但客户端从不等它、不依赖它。
- **平台独占的能力交给平台**：让电视进入杜比视界模式、全景声以 MAT 2.0 透传、tvOS 画中画、帧率匹配、
  iOS 27 系统生成字幕，只有 AVPlayer 能做。所以主力通路必须以 AVPlayer 结尾，FFmpeg 只做它最擅长的事：拆容器。
- **只画平台画不了的**：AVPlayer 解不了的编码才走软件解码；不写自己的渲染器和色调映射。
- **失败按常态设计**：兜底阶梯显式建模，每次回落带原因上报。

为什么不是「自己解码 + AVSampleBufferDisplayLayer」为主：杜比视界的显示握手、全景声透传、tvOS 画中画
（sample-buffer 内容源在 tvOS 上不被接受，Apple FB9751461）都拿不到。

## 2. 架构

```
PlayerScreen（控制层 UI、手势、文字字幕叠加）
  └─ PlaybackController（会话协议、选引擎、兜底阶梯、看门狗）
       └─ PlayerEngine 协议
            ├─ NativeEngine    自研引擎（App 侧适配层）
            │    └─ AetherCore.framework（动态框架，App 与 AetherEngine 之间唯一的边界）
            │         └─ AetherEngine（LGPL-3.0 + App Store 例外）+ AetherLib* FFmpeg 动态框架
            └─ AVPlayerEngine  服务端流：HLS（只在自研引擎确定解不了时用）
```

自研引擎内部有两条通路，对控制器透明：

- **主力通路（loopback）**：FFmpeg 读 NAS 原文件 → 就地换封装成 HLS-fMP4 → `127.0.0.1` 本机服务 → AVPlayer。
  杜比视界（P5 / P8.x，P7 实时转 8.1）、HDR10+ / HLG、全景声原样拷贝都在这里；TrueHD / DTS 在本机解码后重编。
- **软件通路（software）**：VP9、VC-1、MPEG-2、MPEG-4 ASP、隔行 H.264 等 AVPlayer 不收的编码，
  FFmpeg / dav1d 解码后交给 `AVSampleBufferDisplayLayer`。

### 为什么要 AetherCore 这层动态框架

LGPL 组件的替换边界：用户可以用自行编译的同名框架替换。它的 FFmpeg 引用也在这个框架链接时就绑定到 `AetherLib*`——
一个进程里有两份 FFmpeg 时（移除 MPV 之前，MPVCore 里还静态打着一份），`avcodec_*` 绑到哪一份由链接顺序决定，
绑错了的症状像引擎 bug（上游文档「One FFmpeg」）。**App 只 import AetherCore，不得直接依赖 AetherEngine。**
核对方法：`nm -m AetherCore.framework/AetherCore | grep _avcodec_open2` 应显示 `(from AetherLibavcodec)`。

## 3. 兜底阶梯

| 级 | 通路 | 什么时候走 |
|---|---|---|
| L0 | 自研引擎主力通路（换封装 → AVPlayer） | H.264 / HEVC / 有硬解的 AV1，任意容器 |
| L1 | 自研引擎软件通路（本机 CPU 软解） | AVPlayer 不收的编码；硬件解码器报「解不了」（引擎内部自动切换，补丁 P24） |
| L2 | 服务端 HLS → 系统播放器 | 自研引擎确定解不了（原位重开一次也不行） |
| L3 | 中文报错 | 服务端也给不出 |

规则是纯函数 `FailurePolicy`（`PlaybackRouting.swift`），每条一行表驱动单测（`PlaybackRoutingTests`）。2026-09-28 用户要求
「力保不降级」后，除了「确定解不了」，其余失败一律不换播放器（故障注入测试见 §3.7）：

| 失败 | 处理 |
|---|---|
| 网络：断线、超时、令牌过期、服务端 5xx / 限流、缓冲见底 15 秒没有字节 | 等片源取得到了原地重开（新会话、新令牌），约 1 分钟取不到落错误页（§3.1） |
| 引擎报「打不开」等解码类错误 | 先探片源（`SourceProbe`，取 1 个字节）：取不到按网络处理，404 按片源不在处理，取得到才算解不了 |
| 片源不在了（404） | 错误页「服务器上找不到这个文件」，不换播放器（服务端一样读不了） |
| 手机存储写满（引擎报 `storageExhausted`，补丁 P25） | 收到最小分片窗口、关掉片源字节缓存，原位重开；重开后又写满才改走 L2 |
| 一时的解码问题：引擎楞住（缓冲够却 8 秒不走）、中途出错 | 原位重开一次（`NativeRetryBudget`，同一集 3 分钟内一次），再失败才改走 L2 |
| 确定解不了：硬解拒绝且本机软解也接不住（杜比视界 P5 在不支持的设备上）、片源格式本机不认 | 直接改走 L2 |

- **限了画质也用自研引擎**（2026-09-28 用户拍板）：用户主动限画质时仍按系统播放器的能力申报，让服务端按上限转码，
  转出的 HLS 交给自研引擎直连（引擎的 `remoteBypass`：AVPlayer 直接取服务端 HLS），画中画、诊断、暂停策略与直出
  原文件同一套。放服务端流时引擎不拆包：文字字幕由叠加层画，图形字幕由服务端压制进画面；下载量、掉帧、已播帧数与
  缓冲从 AVPlayer 的访问日志和已加载范围取，持续掉帧照旧按「这一档放不动」降档。模拟器实测切 720p 从点下到出画 1.7 秒。
- **手机存储快满不再换播放器**（原来可用空间低于 512 MB 就走服务端流）：换封装通路的分片缓存默认前方 10 段、后方 20 段，
  UHD 一段 30～45 MB，光两个窗口就 1 GB 上下；现在按剩余空间与码率把两个窗口收小（`NativeStoragePlan`，引擎补丁 P25 让后方
  窗口可设），剩余不多时不开片源字节缓存、不放大前向缓冲。分片落盘是为了不占内存（UHD 窗口放内存会被系统杀掉），不是换封装本身要磁盘。
- 自研引擎建不起来（初始化失败、原盘目录清单读不到）直接改走 L2（`nativeFallback`，`engine-fallback` 日志）。

### 3.1 网络问题不是降级信号（2026-09-28 用户拍板）

起因：用户在外网看《哪吒》（原片 76 Mbit/s，线路实测 54 Mbit/s）。缓冲跟不上被看门狗判成「缺粮」，自研引擎 → 当时的 MPV；MPV 拉服务端
HLS 一路 404 被判「文件放不了」→ 系统播放器 + 转码；之后网络好了也回不到自研引擎。改后：

- **线路慢只是缓冲，不是失败。**看门狗（`StallWatch`）只在「缓冲见底且持续没有字节进来」时判连接中断：原文件直出 15 秒、服务端流
  45 秒（等转码出片要更久）。有字节在进来就一直等，转圈下显示实时加载速度。
- **连接中断就同引擎、同片源原地重开**（新会话、新取流令牌）。原文件直出先等片源取得到：每隔 2、4、8、15、15、15 秒探一次
  （约 1 分钟），取得到立刻重开，一直取不到落错误页「连接中断，重连了几次都没成功」，点「重试」从原位置接着放——换转码要
  一样的线路，还要用户同意画质变差；服务端流按「这一档放不了」降档。
- **换不换低画质由用户定**：一次等太久或反复卡顿时提示一次（§3.3），不自动转码；也许暂停攒一会缓冲就能接着看（§3.4）。

### 3.2 画质、音轨、字幕按片记（2026-09-28 用户拍板）

- **画质**按「这部片 + 网络环境」记在本机（`QualityMemory`，最多 300 条，改回「自动」即忘掉）。网络环境（`PlaybackNetwork`）：
  服务器是私有 IPv4、且手机某个网卡与它同网段 = 家里；私有 IPv4 但网段对不上（VPN 回家、在别处）= 外网；公网地址（公网 IP，或
  域名解析出公网 IP）= 分不清——在家经路由器回流与在外面连的是同一个地址，硬猜会把在家说成外网，这时只按片记、提示里不写环境。
  不要任何额外权限（Wi-Fi 名称要定位权限）；域名在账号就绪时就在后台解析，结果 5 分钟后重查（照顾家里 DNS 把域名解析成内网地址的情况）。
- **音轨、字幕**由服务端按单元记（观看状态）。剧集的新一集没有记忆时，沿用同一部剧最近看的一集的选择，按语言换算成本集的轨
  （`services/playback/track_memory.py`：每集轨序、外挂字幕文件名都可能不同，只有「语言 + 类型」跨集稳定；换算不出来就交回默认选择）。
  只沿用**用户改过的**：那一集用的就是默认轨、或那一集本来没有默认字幕而记着「关闭」，都不沿用——否则第 1 集没字幕，
  第 2 集自带的默认中文字幕也会被关掉。本集自己有记忆时以本集为准；开会话与 decide 同一口径，换算结果随观看状态带回。
- **下次打开时提示**：出画那一刻顶部提示几秒「已沿用上次的选择：画质 720p（外网），音轨 日语，字幕 关闭」，只提**不是默认**的项——
  服务端每次进度上报都会把正在放的轨记下来，记着 ≠ 用户选过：与默认挑选一致的不提，画质上限不低于片源的不提；同语言有几条轨时
  写全称。只在打开播放器时提示，自动连播下一集不再提示。

### 3.3 换低画质的提示（`QualitySuggestion`）

只在真有必要时打扰，满足其一且线路确实跟不上才提示，每个播放单元最多一次：
- **一次等太久**：等首帧、等跳转落点、播放中卡住，连续等满 8 秒（2026-09-30 用户拍板）。起因：外网放 4K 原片时
  用户一上来就要等十几秒（真机蜂窝：首帧 18.5 秒、跳转落地 16.6 秒），人早退出了，原先只数「开播后卡了几次」永远等不到提示。
  线路看这段等待里最快的一秒——冷起播时引擎一段一段地取（索引、文件头分头取），逐秒读数时有时无（模拟器 6 Mbit/s 限速实测
  只有 0～2 Mbit/s），最快那秒最接近线路能力，它都低于片子码率的 9 成才算线路问题；
- **反复卡**：开播后 5 分钟观看时间里卡满 2 次（原为 3 次或累计 45 秒）。起播、跳转、继续播放、回到前台后各有 10 秒宽限，
  跳转的等待不算卡；卡顿时加载速度的中位数低于片子码率的 9 成。

速度够还卡、或等的时候一个字节都没有（断线、等转码），都不是线路问题，换码率没用，不提示。满足后顶部给一张卡（起播中也叠在转圈上）：
「网速跟不上当前画质——实测约 X，这一版需要约 Y。可以暂停攒一会缓冲再看，或改用 1080p（服务端转码，画质会降低）」，按实测速度
留两成余量推荐档位（1080p 约 6、720p 约 3、480p 约 1.5 Mbit/s），已在最低档不提。20 秒没理会自动收起，本单元不再提；
接受 = 选那一档画质（按片 + 网络环境记住）。回归：`scripts/faultlab.py slow-link slow-seek baseline`（共享 6 Mbit/s 慢线路下
起播 / 远跳各弹一次并接受后改走转码，正常线路不弹）。

### 3.4 暂停攒缓冲（引擎补丁 P20）

上游引擎的前向窗口在装载时定死为 10 段（约 40 秒），生产者攒满就停：线路比码率慢时，暂停多久都只攒得到 40 秒。播放中真卡住、
且当秒加载速度低于码率 9 成时，App 把窗口放大到 3 分钟内容（按本场平均段长换算段数，同一个引擎只放大一次；用户定的 3 分钟：
再长，暂停攒满后不看了白下的流量太多，76 Mbit/s 的原片 3 分钟就是约 1.7 GB）；磁盘仍受开播时算好的留存预算约束
（min(2 GiB, 剩余空间 1/4)），高码率片子窗口装不满时由磁盘停泊兜底。线路够快时不放大，免得在蜂窝网上白下几个 G。
模拟器演练（《疾速追杀4》UHD 原盘，暂停 40 秒）：不放大时恢复播放缓冲 44 秒；放大后一直下到 2 GiB 预算才停，恢复时缓冲 341 秒，
随着已播部分被清掉，下载自动续上。只作用于主力通路（换封装）；软件通路另有一套缓冲，没动。

### 3.5 流量：每个字节只下一次（2026-09-28 用户要求）

规则：视频、音轨、字幕的初次加载与切换，同一个字节只从 NAS 下一次；暂停按网络类型处理。

- **字幕不再开第二条连接**（引擎补丁 P21）。主力通路 / 软件通路本来就把所有内封字幕轨的包顺带收进字幕存储（上游 #112），
  覆盖到读取前沿（播放点后约 40 秒），画字幕、换字幕、字幕时间偏移都够用。上游那条读到 75 秒之后的旁路（#151）在 MKV / TS 上
  会把音视频整份再下一遍，现在只在画中画要把图形字幕识别成文字时才跑（系统一次预取约 240 秒原生字幕窗口）。
- **片源字节缓存**（引擎补丁 P22）。换音轨、回前台、出错恢复是整场重建，往回跳进缓存段后有空档时生产者要重产——这些重读都从
  本机拿。键是「文件 id + 大小」（`PlaybackController.sourceCacheKey`），取流令牌变了也接得上；关播放器不清，退出再进同一部片、
  断线重连换了引擎实例，续播点附近都直接从本机起播；1 GiB 预算按最久没用淘汰，App 下次启动时清掉。
- **暂停切后台被拆后要宿主重建**：引擎在后台暂停超过 15 秒会拆掉视频管线省电（上游 #127），约定由宿主回前台时在原位置重建。
  App 原来没做（`NativeEngine.setBackgrounded` 是空的），回来点播放一直转圈，要等看门狗判断线整场重连（15 秒以上）；现在回前台
  即重建（`AetherPlayback.rebuildAfterBackgroundTeardown`），保持暂停，数据从字节缓存来。
- **暂停按网络类型**（引擎补丁 P23 + `NetworkCost`）：计费网络（蜂窝、个人热点、低数据模式；系统直接给，不要权限）上按暂停
  就连下载也停，恢复播放一律解除；Wi-Fi 上照常攒到前向窗口；卡着的时候按暂停是想攒缓冲，照常下（线路慢时窗口已放大到 3 分钟）。
  暂停期间网络变了（出门从 Wi-Fi 换到蜂窝）再判一次。系统播放器（服务端流，限了画质时就是它）暂停时把预读压到 1 秒。
- 3 分钟的缓冲放大（§3.4）主力通路与软件通路都有：软件通路模拟器演练暂停 40 秒，恢复时缓冲 39 → 179 秒。

模拟器实测（`nettop` 只计外部网卡，按秒对齐 `-mcAuto*` 动作；每个动作之后 15 秒比稳态多下的量）：

| 动作 | 改前 | 改后 |
|---|---|---|
| MKV（《鱿鱼游戏》1080p，约 14 Mbit/s）换音轨 | +61 MB | 0（从缓存重开，0.11 秒恢复播放） |
| MKV 选 / 换内封文字字幕 | +118 / +109 MB | 0 |
| MKV 跳回看过的位置 | +154 MB | 0 |
| MKV 整组动作总流量 | 938 MB | 324 MB |
| UHD 原盘（《疾速追杀4》约 60 Mbit/s）选 / 换图形字幕 | +1952 / +2481 MB | 0 |
| UHD 原盘换音轨 | 整段前向缓冲重下 | 0（缓存供出 386 MB，0.65 秒恢复播放） |
| 开着内封字幕稳定播放 | 140 Mbit/s（码率两倍） | 等于码率 |
| 计费网络上放大窗口后暂停 40 秒 | 攒到约 1 GB | 34 MB |
| UHD 原盘暂停切后台 25 秒再回来 | 回来点播放一直转圈，看门狗重连后整段重下 | 回前台即重建，从缓存供出 373 MB，0 下载 |
| MKV 断线重连（新会话、新引擎实例） | 前向缓冲重下 | 从缓存重开，缓存供出 54 MB |
| MKV 退出再进同一部片 | 同首次：建引擎到出画 1374 毫秒 | 359 毫秒，前 20 多秒零下载 |
| DVD 镜像跳回看过的位置 | 重下 | 缓存供出 19 MB |

缓存内容与 NAS 原文件抽样逐字节比对一致（MKV 与原盘 m2ts；比对时要避开文件系统按块取整在数据段首尾补的零）。

### 3.6 为什么去掉 MPV（2026-09-28 用户拍板）

原先的阶梯是「自研引擎 → MPV 直出原文件 → 服务端 HLS」。用户的判断：**自研引擎要解决本机能解决的一切，本机不需要第二个播放器**。
数据也支持：

- **MPV 能接住、自研引擎接不住的情形几乎没有了。**真机两轮验证里 MPV 只救过一次场（《他是谁》手机存储写满，见 8.1 / 8.4），
  那是存储问题不是解码问题——现在本机存储不够放分片时直接走服务端流。杜比视界 P5 在模拟器上硬解不了原先回落 MPV，
  补丁 P24 让引擎自己转软解（真机硬解本来就能放）。
- **片库里没有只有 MPV 能解的东西。**引擎自带的 FFmpeg 没编 DVD LPCM（pcm_dvd）与 RealMedia 解码器，服务端台账里
  13 个 DVD 镜像（《聪明的一休》12 集、《金枝玉叶》）各列着一条 pcm_dvd；实放核对，引擎读的正片标题里并没有它
  （《聪明的一休》正片只有一条 MP2，《金枝玉叶》是三条 AC-3），台账那条来自盘上正片以外的部分。电影与剧集库里没有 RealMedia 文件。
- **代价**：MPVCore 占正式包 117 MB 里的 35 MB（移除后正式包 82 MB）；自己上屏，同片 4K 杜比视界本进程 CPU 26.2% 对 15.4%、内存 635 MB 对 135 MB（8.2）；
  销毁时关掉整个 App 的音频会话（8.3 第 6 条），还要为它维护一套能力申报、看门狗阈值、画中画接力和 LGPL 构建。

「本机解不了」的含义：自研引擎内部先硬解（VideoToolbox），不行再用引擎自带的 FFmpeg 在手机 CPU 上软解（软件通路），
都不行才请服务端转码。服务端转码不是降级通路的常态，只在这三种情况出现：本机真解不了、用户限了画质、本机存储不够。

### 7.3 发现的问题

1. **服务端取流接口在响应期间一直占着数据库连接（已修，2026-09-27 19:26 已部署 NAS）**：FastAPI 的 yield 依赖要等响应发完才收尾，
   直出长连接因此各占一个连接；本机换封装的引擎一次会开主读取、尾部预读、字幕预读几路，两三个播放器就能耗尽
   连接池（5 + 溢出 10），全站接口 30 秒超时——第一轮里《他是谁》《觉醒年代》失败、模拟器卡在「正在判断播放方式」都是它。
   修法：读完台账立即 `session.close()`；测试 `test_direct_play_releases_the_db_connection_before_streaming`
   （去掉修复时复现为占用 1 个连接）。
2. **服务端不提供 ISO 原字节直出**：`is_disc()` 把 ISO 当原盘，找不到单剪辑就 404。引擎能读解密的 BD / DVD ISO，
   要放行 ISO 原字节，并在 AetherCore 里给经 HTTP 的 ISO 提供按 Range 读取的字节源。
3. **原盘双 PID 杜比视界未识别**：UHD 原盘按 HDR10 播放。要从增强层 PID 取 RPU、注入基础层再转 8.1，引擎侧补（适合提上游）。
4. **起播时换非默认音轨要在首帧后重载一次**（主力通路约 0.5～1 秒黑屏）：原盘默认挑到的是 AC-3 核心，服务端决策要 TrueHD。
   已改：只有用户显式选过、或记着的轨不是容器默认轨时才在首帧后切换；同语言的默认挑选交给引擎（原盘不再白重载）。
   2026-09-29 起判断改成「服务端挑的是不是容器默认轨」：记着的、沿用上一集的、默认轨策略挑的原声（配音标了默认的英文片）
   都不是容器默认轨，装载前按序号交给引擎（P11），首帧就是它，不会先放配音再重载换过去（jellyfin-subtitle.md §3.4）。
   后续：服务端媒体事实带上音轨的流序号，装载时直接指定（`audioSourceStreamIndex`）。
5. **MP4 的 moov 在文件尾时起播多一次往返**：服务端媒体事实可以带 moov 偏移。
6. 服务端取流接口不支持 HEAD（405），引擎会退回 Range GET，影响很小。

### 8.3 断流演练：服务端重启时播放不该断

用 Mac 上的断流代理模拟服务端重启：掐断在途连接，停机期间新连接回 502（前端代理在后端重启时的表现）或直接拒连。
起因是 2026-09-27 真机实况：MPV 播放中 NAS 被重新部署，停机约 20 秒，App 弹出「即将播放下一集」并自动换到了下一集。

| 场次 | 引擎 / 停机 | 修复前 | 修复后 |
|---|---|---|---|
| A | MPV / 20 秒 502 | — | mpv 按 0·0·1·3·7·15 秒重连，靠 65 秒缓存无感接回 |
| B | MPV / 70 秒拒连 | 缺粮 15 秒回落系统播放器 → 服务端起转码 → 播放头停住不动 | 缓存撑到 4 秒时 mpv 接回，画面不停（B2） |
| C | 自研 / 20 秒 502 | 引擎自己接回，但重连期间报缓冲，转圈盖着正在播的画面 21 秒 | 不再报缓冲，播放头一路前进（C2） |
| D | 自研 / 90 秒拒连 | — | 缓冲吃光 16 秒后原位重开，重开被拒按退避重试，服务端恢复 1 秒内接着播，无错误页 |

对应的修复（均在 App 侧，另有一处服务端）：

1. **mpv 断线续传**（`MPVPlayer`）：mpv 默认只重连约 11 秒、撞上 502 当场放弃。加
   `stream-lavf-o=reconnect_on_network_error=1,reconnect_on_http_error=5xx,reconnect_delay_max=15`，扛过一次服务重启；4xx 不重连。
2. **离片尾还远的「播完」按断流处理**（`PrematureEndGuard`）：从当前位置重开，不进「已播完」、不弹「即将播放」；
   重开后原地附近又报播完才认定是真结尾（片长写错的文件不会在片尾反复重开）。
3. **直出缺粮先判断线**（`engineFailed`）：没有「实测带宽低于码率」的证据时同引擎原地重开，不回落别的引擎——
   服务端是同一台，换引擎、改拉服务端流于事无补，还会白起转码；线路确实太慢的照旧回落 / 降档。
4. **重开时服务端还没回来就退避重试**（`ReconnectBackoff`）：连不上 / 超时 / 502·503·504 按 2·4·8·15·15·15 秒重试，约 1 分钟仍不行才报错；
   409（管理员结束播放）、404、401 不重试。只用于已经播起来过的单元。
5. **自研引擎的 `.stalled` 不等于缓冲**（`AetherPlayback`）：源连接在重连、本地分片还够播时照实报播放；传输真吃光缓冲才报缓冲。
6. **mpv 销毁时会关掉整个 App 的音频会话**：libmpv 的 iOS 音频输出 `ao_audiounit` 在 uninit 里调 `setActive:NO`，
   异步收尾常落在下一个引擎起播之后，系统播放器 / 自研引擎被连带暂停（演练 B 回落后画面停住即此）。
   控制器在 MPV 彻底收尾后重新激活会话，并补播放被连带暂停的新引擎（`retire` / `recoverAudioAfterMPVTeardown`）。
7. **自动选引擎白起转码**（服务端 `decide_playback_route`）：决策接口不套观看记忆、开会话接口套。记住 PGS 字幕时，
   探测说「直出」、真开会话却要整片压制——App 先开系统播放器会话（Worker 转码）再改走 MPV。现在两个接口同一口径（`_with_watch_memory`）。

- **P28 VOD 提前开播真正生效**：P2 原来只在进入等待那一刻看一眼缓冲，那时总是空的（第一轮 22 部起播一次都没触发）；
  改为等待期间每 0.1 秒看一次、过 1.5 秒线就开播，每次跳转重新武装。第三轮 6 部走 AVPlayer 的片子里 5 部起播时触发、跳转时触发 6 次。
  跳转后 AVPlayer 常把缓冲判为空（`isPlaybackBufferEmpty`，此时 `playImmediately` 会变成卡住），这种等待仍交给它自己。
- **P29 原盘读取器单块预取**：全速产出分片时的读源速度，三部 UHD 原盘从 42 / 35～39 / 48 MB/s 到 58 / 36～53 / 58 MB/s。
  与 8.4.2「一条连接吃满 Wi-Fi」并不矛盾：那次测的是大块连续读，这里省下的是每 8 MB 一次请求之间约 40 毫秒的往返与处理空档。
  同晚先后两轮各跑一次，不是交替对照；第二轮读的片段第一轮都读过，可能还在 NAS 的内存缓存里（NAS 32 GB 内存），这组对比只能看方向。
- **缓冲外 +600 秒的大头不是 P29**：第一轮 UHD 原盘这一跳里，重启生产后第一次读源就等了 1.1～2.5 秒，读取器当时没有逐次计时、
  原因没查清，第三轮没再出现（跳转后首次取数 0～80 毫秒）。读取器加了仅调试构建的测速日志（等锁、取数、写缓存），再出现时能直接定位。
- **P30 / P31 软件通路跳转**：DVD 时间表粗（《哪吒闹海》137 个点、43 秒一格），跳转落在目标前几十秒；原来 0.6 秒兜底一到就走时钟，
  画面冻 2～3 秒、进度照走，追上时一次丢几十帧，`[SeekTrace]` 却只记 0.1 秒左右（软件通路在引擎报「在播」时就停表，不含出画——
  8.4.2 表里软件通路那一行同样如此）。P30 在解码器没解出落点那一帧前一直停钟，并在放开时记下真实停钟时长；P31 让追赶时跳过不被参考的帧、
  不给目标前的帧去隔行。
- **主力通路缓冲内往回跳仍慢**：《他是谁》4K60 往回 5 秒 1.5～1.6 秒。关键帧 3.5 秒一个（60 帧 / 秒），零容差跳转要从前一关键帧
  逐帧解到目标，AVPlayer 这段时间缓冲判空、本机服务器零请求——不是缺数据。改成允许落在前一关键帧可近乎瞬时出画，但落点会早最多
  几秒，属于体验取舍，待用户拍板。

- 长 GOP 4K 的首片与缓冲外跳转：瓶颈是手机 Wi-Fi 吞吐（并发读实测无收益，见 8.4.2；P29 只省掉请求间的空档，见 8.4.3）。
  能动的只有少读：跳转后头一两片切短（分片计划现在起播时一次定死），或落点靠近分片末尾时从下一片起播。UHD 原盘起播约 1.9 秒，
  其中 AVPlayer 要攒两个 27 MB 左右的分片。
