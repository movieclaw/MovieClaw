# 合并季条目：站点按两季发布时也能订阅（issue #1155）

## 问题

有人在豆瓣看到《我独自升级 第二季 -起于暗影-》（13 集，2025-01-04 首播），点进订阅。
这两个豆瓣条目收敛到同一个 TMDB 条目 `tv 127532`，而 TMDB 把这部剧登记成**一季 25 集**：

```
tmdb tv/127532
  number_of_seasons = 1
  seasons = [ {0, 特别篇, 1 集}, {1, 25 集, air_date 2024-01-05} ]

  第 1 季的集日期
  E01 2024-01-07 … E12 2024-03-31    ← 实际的第一季
  E13 2025-01-05 … E25 2025-03-30    ← 实际的第二季，中间断档 280 天
```

站点不认这套合并编号，按常规拆成 `S01`（12 集）/ `S02`（13 集）两套发布。
M-Team 同一次搜索里两种都有人发：

```
Solo Leveling 2024 S01 Complete 1080p …                12 集
Solo Leveling 2025 S02 Complete 1080p …                13 集
Solo Leveling Arise From the Shadow 2025 S02 Complete 2160p … 13 集
Ore dake Level Up na Ken S01E13-25 2024 1080p …        按 TMDB 顺延编号
Solo Leveling 2024 S01 S01E13-S01E25 1080p …           同上
```

### 现在实际发生了什么

订阅弹层只有「第 1 季（25 集）」可勾，从豆瓣「第二季」条目进来也一样——
用户找不到第二个选项，只能订这一季。

订完之后，**S02 那一批资源会被完整评估，然后无声丢弃**：

- `matching.py:830` 跑身份匹配 —— 通过（片名、年份都对得上）；
- `matching.py:834` 跑覆盖计算 —— 空。站点的 `S02` 被 enrich 解析成
  `seasons=[2]`，`_derive_units`（`movieclaw_matcher/identity.py:721`）把它写成
  `pack_seasons={2}`；而订阅在等的是 `(1, 1..25)`，两边集合没有交集；
- `matching.py:836` 跑洗版判定 —— 也空；
- **`matching.py:839-840` 直接 `continue`**。这一行没有 logger、没有活动记录，
  连 `summary.identity_hits`（`:841`）都没加。

要强调的是：`matching.py:840` 那句注释写的是「身份命中但既无缺口也无可洗单元」，
它的**设计意图本来就是不记账**——「这个包对我没用」是日常情况，全记下来会刷屏。
问题在于「**这个包我本该能收，但我读不懂它的季号**」被混进了同一个分支：
这是两件完全不同的事，却走了同一条静默的 `continue`。

手动也救不了。`manual_grab.py:221` 用的是同一个 `covered_units`，
在站点上选中那个做种 99 的 S02 完整包投递，得到的是

```
errors.subscription.unitsNotCovered
「这份资源没有覆盖你等待的集」
```

投 `S02E01` 单集同样被拒。

### 但订阅不会「卡死」

这里要说准确，因为很容易说错：**系统会继续工作**。

issue 自己列出的 `S01E13-25` / `S01 S01E13-S01E25` 两类种子会解析成
`(1, 13..25)`，`covered_units` 能正常覆盖，`_explicit_airable`
（`matching.py:628`）也过得去——E13 播于 2025-01-05，任何真实存在的
E13 文件必然在其后发布。

**前提是它通过了该订阅的规则组**（分辨率、编码、片源门槛）。
如果用户设了「只要 2160p」而顺延编号的版本只有 1080p，那它照样会被规则拒绝。

所以真实症状是：

> **系统看起来在正常干活，但只会挑那少数几条按 TMDB 顺延编号的冷门发布；
> 2160p、做种 25–99 的 S02 包一个都用不上。**

站点**只**发 S02 编号的条目（大量日漫属于这类），才是真的完全收不到。

### 用户的感受

1. 从豆瓣第二季进来，弹层只给第一季 → *我点的明明是第二季，怎么只有第一季？*
2. 前 12 集很顺利 → 挺好
3. 后面系统总挑冷门小版本下，明明有 4K 高做种就是不用 → *为什么？*
4. 去活动记录找原因 → **一条都没有** → *是站点没资源，还是软件坏了？*
5. 手动投那个 S02 包 → 被拒 → *连手动都不让下？*
6. 最后只能去找顺延编号的版本，还得碰运气它过得了规则组

比「卡住」更难受的是：系统看起来在正常工作，用户却觉得它在乱挑。

## 决策

**不做用户可配置的季映射表。**

issue 的 P1 提案是让用户填一条 `TMDB S01E13–E25 ↔ 站点 S02E01–E13` 的映射。
问题在于：用户得先发现收不到、再搞懂为什么、再自己算出「13」这个数、
再找到某个地方把它填进去——四步全靠用户。

而算这个数需要的原料（每一集的播出日期）**数据库里本来就有**
（`media_episode.air_date`）。让程序自己算，用户一步都不用做。

### 1. 后台从已有数据自己算「站点季号」

同一 TMDB 季内，相邻两集的播出日期间隔 ≥ **90 天**，就是一次播出断档。
断档把这一季切成若干 block，按首播日期排序，**序号就是站点季号**。

普通剧天然是**恒等映射**：

```
TMDB S01(10 集) + S02(10 集)  →  block1 = (季1, 偏移 0)、block2 = (季2, 偏移 0)
站点 S02E01  →  TMDB S02E01     逐字节不变
```

《我独自升级》这种：

```
TMDB S01
  block1 = E01–E12   (2024-01-07 … 2024-03-31)   站点第 1 季
  ── 断档 280 天 ──
  block2 = E13–E25   (2025-01-05 … 2025-03-30)   站点第 2 季，偏移 12

站点 S02E01  →  TMDB S01E13
```

### 2. 只在一个窄条件下启用

**只有当站点季号在 TMDB 的季列表里不存在时，才做换算。**

- 站点说 `S02`，而 TMDB 只有季 1 → `2 ∉ {1}` → 查映射 → 换算；
- 站点说 `S01`（含 `S01E13-25` 这种顺延编号）→ `1 ∈ {1}` → 走原路，一个字节都不动。

「普通剧零影响」因此是**结构性保证**，不是靠调阈值调出来的。

自洽性：映射只会在「站点季号 TMDB 没有」时被查询，而这只可能发生在
站点确实拆了季的条目上。普通剧即使在季内出现了 90 天以上的断档（比如中途停播），
也不会被误伤——因为它的站点季号本来就在 TMDB 的季列表里。

### 3. 归一化的落点只有一处

在 `_derive_units`（`movieclaw_matcher/identity.py:721`）里，把

```python
IdentityMatch(pack_seasons={2}, is_pack=True, declared_total=13)
```

改写成**显式集列表**：

```python
IdentityMatch(
    episodes={(1, 13), (1, 14), …, (1, 25)},
    is_pack=True,
    pack_seasons=frozenset(),   # 置空
    declared_total=13,
)
```

这样 `covered_units`（`matching.py:606`）**零改动**：显式集走它现成的
`key in match.episodes` 分支，上下界天然正确——`_explicit_airable` 对未定档集返回
True，所以 issue #640 的占位集行为原样保留。

**不能保留 `pack_seasons={1}`。** 一旦保留，S02 包会把第 1–12 集也标成「已覆盖」，
等于把已经下过的集再下一次。

集号上界取 `max(block_end, 偏移 + declared_total)`，让「站点声明 20 集、
TMDB 只录 13 集」这类 #640 证据链继续生效。

### 4. 两处不同步就会出真 bug

这两处不进方案，前面的都白做。

**其一：`identity.py:667` 的 `_episode_count_conflict`**

它是「包声明全 N 集，而该季发布前已播出远多于 N 集 → 判为同名另一部剧」的反证。
如果把 S02 包归一成 `pack_seasons={1}` + `declared_total=13`，而第 1 季已播 25 集，
这个反证就会**把正确资源判成错片拒掉**。

改成显式 episodes 后 `pack_seasons` 为空，该分支（要求
`len(match.pack_seasons) == 1`）自然跳过。而且这层反证在这里本来也不需要：
block 的边界就是从同一份 `media_episode` 台账推出来的，不存在「声明对不上」的可能。

**其二：`download_progress.py:1216` 的 `_verify_content`**

种子下完后，它按字面 `(季, 集)` 核对文件清单里有没有承诺的集。
如果这里不归一，站点 S02 的 13 个文件会被判成「13 集全缺」→ 工单退回 →
`_record_content_missing` 写入 `content_missing` 负面记忆 → **该来源被永久排除**，
订阅彻底废掉。

归一必须同时进 `_observed_units`（`:1163`，核验用）和 `_unit_progress`
（`:1198`，详情页的逐集进度条）。

### 5. 入库：保持 TMDB 编号

**文件落在 `Season 01/`，不新建 `Season 02/`。**

理由见下一节。实现上，`units.py::resolve_units`（`units.py:148`）加一条：

> 显式声明的季号不在台账里、且命中站点季映射 → **翻译**成 TMDB 季号，而不是否决。

这不违反该模块既有的「台账不许否决显式声明」原则（`units.py:19-23`）——
那条讲的是不拿台账去否掉发布组的明确意图；这里是**不改原意地翻译**，
翻译后它仍然落在真实存在的季里。
改这一处，三条路同时修好：

| 路径 | 调用点 |
|---|---|
| 监听导入 | `ingest.py:2261` |
| 库扫描 | `scan.py:4930` |
| 选择性下载的文件解析 | `file_selection.py:106` |

**不动 `media_episode` / `media_season`。** `media_scrape.py:1235` 在每次元数据刷新时
会删掉不在最新拉取里的集行，写进去会被冲掉（`subscription-episode-floor.md:67`
记过同一个教训：「改条目元数据：`media_episode` 随刷新增删，写进去会被冲掉」）。

分集 NFO 的 `<season>` 取自 `MediaEpisode.season_number`（`nfo.py:276`），
归一后自动正确，Jellyfin 读到的就是 TMDB 的 1 季 25 集。

### 6. 映射结果要落库

不能只在匹配时临时算。分集区要展示「这 13 集站点是按第 2 季发的」，
而详情页请求跟订阅匹配是两条独立的路径，不存下来就不知道当初怎么归的。

存**条目级**（不是订阅级）：同一部剧的多个订阅、以及库扫描，共用同一套编号常识。
这一点与 `episode_evidence.douban_ref`（订阅级）不同——那个是「这次订阅当初从哪个
豆瓣条目进来的」，是订阅历史；站点季号是条目属性。

字段设计（三种候选，实现时取一）：

- **A（推荐）**：`media_item` 新增 JSON 列 `season_mapping`，形如
  `{"site_seasons": [{"number": 2, "season": 1, "start": 13, "end": 25}]}`，
  三态语义与 `identity_twins`（`media_item.py:136`）一致：
  `NULL` = 没算过、`[]` = 算过且无需映射、非空 = 有映射；
- **B**：单独建 `media_season_alias` 表，`(media_item_id, site_season_number)` 唯一；
- **C**：复用 `MediaSeason.name`——**否决**，那是展示字段，会被 TMDB 刷新覆盖，
  且语义混淆。

选 A：一次性读、计算成本低（一个条目最多几行）、跟已有一条 JSON 列的写入路径
（`media_scrape.apply_display_profile`）共用刷新时机。

### 7. 拆开 `matching.py:840` 的无记录分支

现在的 `continue` 把两种情形混在一起：

| 情形 | 该不该记账 |
|---|---|
| 包里就是没有我要的集（正常） | 不记，保持今天的静默 |
| 身份命中、但候选季号**全都不在台账里**（我读不懂它的编号） | **记一条** |

后者新增 `_log_uncovered`：写 `MATCH_REJECTED`，`wanted_item_id=None`
（该字段本来就可空，`subscription_activity.py:97`），`reason_code`
为 `season_unmapped`。这就是「不再静默无资源」的落点。

判定要保守：只有**候选的每个季号都不在台账里**才记，避免多季包覆盖到部分季时误报。

### 8. 可见性：只有两处

**活动流水**（新增 `ActivityType.SEASON_MAPPED`）：

> 站点第 2 季对应第 1 季第 13–25 集，已纳入自动匹配

按 (订阅, 站点, 种子) 去重，照抄 `_log_rejection`（`matching.py:1195`）现成的写法。

**分集区一行小字**：

```
第 12 集  ✅
┌────────────────────────────────────────────────┐
│ 第 13–25 集：站点按「第 2 季」发布，已自动归入本季 │
└────────────────────────────────────────────────┘
第 13 集  ✅
```

实现：`EpisodeInfo`（`items.py:2720`）与 `EpisodeView`
（`schemas/library.py:1303`）各加一个可选字段，`build_season_episodes`
（`items.py:2808`）按条目映射算出来后返回。

**不加任何其他 UI**：没有新设置项、没有新弹窗、没有新开关。
订阅弹层保持原样（TMDB 确实只有一季，弹层不该凭空生出第二季）。

### 9. 阈值与残余风险

**90 天**：issue 提议值，覆盖 split-cour 的约 13 周空档（真正断档播出的两季通常
停 3 个月以上）。可调，但调低会把「中途停播三周」误判成新季，调高会漏掉紧凑的
split-cour。

两道守卫：

- **G1**：断档左侧的 block 必须已播完（`end < 今天`），不对未来开口；
- **G2**：映射只作用于 TMDB 不存在的季号（第 2 条）。

**残余风险**：TMDB 尚未登记 S02、站点已按 S02 发布时，会被映射到 S01E13+。
TMDB 补登记后，`media_season` 出现第 2 季 → 映射重算 → 站点 S02 回到字面匹配，
**自动自愈**。但此前已入库的文件留在 `Season 01/` 下，不会自动搬家。
文档记为已知限制，实现时应在映射失效时写一条活动说明。

### 10. 明确排除

- **用户可配置的映射表**（issue P1 原案）：要用户发现、计算、填写，违背
  「复杂留给后端，简单留给用户」，而它依赖的数据我们本来就有；
- **订阅弹层的提示条**（issue P0）：口径已定为只走活动流水；
- **一键确认疑似季**（issue P2）：同上；
- **把文件拆进 `Season 02/`**：见下一节；
- **季 0（特别篇）**：完全不参与推导，不进映射。

## MC 自己库里长什么样

### 分集区

季选择器的季号来源是 `meta_seasons ∪ owned_seasons`
（`libraries.py:3236`）。按本方案：

- `meta_seasons` = TMDB 的季表 = `[1]`
- `owned_seasons` = 库内文件实际落在的季 = `[1]`

所以界面是：

```
我独自升级 (2024)
[第 1 季]                      ← 只有一个选项，不出下拉

  第 1 集   ✅ 已入库
  …
  第 12 集  ✅ 已入库
  ── 第 13–25 集：站点按「第 2 季」发布，已自动归入本季 ──
  第 13 集  ✅ 已入库
  …
  第 25 集  ✅ 已入库

共 25 集 · 已收齐
```

25 集全部有集名、简介、剧照、播出日期——因为它们本来就在 `media_episode` 里，
就是 TMDB 的第 13–25 集。能播、能记进度、能续播。

### 为什么不能拆成 Season 02

假设让文件落进 `Season 02/`：

| 后果 | 具体表现 |
|---|---|
| 季下拉多出一个选项 | `owned_seasons` 含 2，`meta ∪ owned = [1, 2]` |
| **但那 13 集没有元数据** | `build_season_episodes`（`items.py:2808`）按 `(季=2)` 查 `MediaEpisode`，TMDB 没有第 2 季 → 查不到 → 只剩文件名 |
| 播出日历空白 | `build_season_air_schedule` 同样按季查，第 2 季没有日期 |
| Jellyfin 更糟 | 刮削按 `tvshow.nfo` 找 S02，TMDB 没有 → 整季认不出 |

也就是说，拆季换来的只是「第 2 季」这个标签，代价是那 13 集失去全部元数据。

**所以选保持 TMDB 编号。** 分集区那行小字负责解释「为什么 25 集都在第一季」。

## 什么时候会失效

1. **TMDB 尚未登记 S02、站点已按 S02 发布**：会被映射到 S01E13+，
   可能落到还不存在的集上。TMDB 补登记后自愈（见 §9）。
2. **断档不足 90 天**：识别不出来，站点 S02 仍然匹配不上。可用活动流水里的
   `season_unmapped` 记录观察实际发生率。
3. **站点用顺延编号**（`S01E13-25`）：本来就走原路，不受影响——这也是今天
   部分条目能「苟活」的原因。
4. **规则组过严**：即使顺延编号版本存在，只要过不了分辨率/编码门槛，仍然不会被采用。
   这是规则组的行为，不属于本方案的修复范围。
5. **季 0 特别篇**：不参与推导，行为不变。
6. **一季内被平台切成多段播出**（如中间停播一季再续）：会被识别成站点新季，
   但换算后仍指向同一个 TMDB 季的正确集号，**行为正确**；只是活动流水会多一条说明。

## 验收标准

1. 为《我独自升级》建立订阅后，站点以 `S02E01…S02E13` 发布的资源能被自动认领、
   下载、入库，最终 25/25 收齐，订阅自动完成；
2. 入库落在 `Season 01/`，文件名 `…- S01E13.mkv` … `- S01E25.mkv`，
   分集区第 13–25 集有集名、简介、播出日期，能正常播放；
3. 分集区在第 12 集与第 13 集之间出现「站点按第 2 季发布」的说明；
4. 活动流水出现 `SEASON_MAPPED` 记录，写明站点季号对应的 TMDB 集区间；
5. 未建立映射时，活动流水出现 `season_unmapped` 拒绝记录，而不是静默无资源；
6. 季号正常的普通剧（含多季剧）：订阅、匹配、命名行为**完全不变**，
   映射为空（`season_mapping = []`），无任何新增活动记录；
7. 同一部剧站点同时存在 `S01E13-25` 与 `S02E01-13` 两套编号时，去重后只入库一份；
8. 映射只作用于条目级，不改变该条目其它季的匹配；季 0 不受影响；
9. 手动选种投 S02 包不再报 `unitsNotCovered`，照常投递。
