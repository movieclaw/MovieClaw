后台接口等待可单独解释并排除；事件排队、布局、图片解码、播放器客户端工作不能因此豁免。NAS 健康接口多次返回 200（一次约 9.8 ms），这只能证明连接可用，不能代替媒体接口性能证据。当前输入和卡顿问题没有证据证明来自后端。

## 已实施的修改

1. 卡片在未做缩放/旋转的区域读取鼠标位置，消除变换坐标与悬停动画的反馈。修复前采样显示主线程持续执行 SwiftUI 动画，首页空闲约占满一个核心；修复后主线程恢复空闲。
2. 首页垂直行延迟构建；水平滚动位置写入非观察对象，仅在翻页按钮可用状态变化时更新视图。
3. 首页快照后台读取；先提交窗口外壳，首帧闸门打开后再加载首页和库目录。
4. 输入搜索时保留原页面，清空搜索不再重建整页。搜索状态仅在空/非空边界变化，空导航栈和相同联想词不重复写入。
5. 搜索 debounce 期间只显示轻量反馈，实际请求开始才建立骨架；取消旧请求不短暂撤掉新输入的反馈。
6. 隐藏页面的轮询状态纳入任务身份，搜索/播放遮住原页面时取消轮询，恢复显示时重新开始。
7. 修复合并主分支后共享类型封面对 UIKit 的依赖。主分支新增的类型色块首页行目前在 macOS 跳过，未增加这项新界面功能。
8. 修复快速改词后恢复已缓存搜索词时残留等待状态的问题；取消 debounce 后恢复缓存结果时保留分页游标，失败输入仍可重新请求。
9. 将原生搜索框、联想词和搜索焦点修饰器放到侧边栏，缩小搜索环境的作用范围。调整前 SwiftUI 录制出现大量卡片和文字属性更新，最大单次更新约 2.19 ms；该记录不能证明像素延迟来自某一个视图。调整后的代理值仍超目标，不能宣称搜索性能验收通过。

## 可复现的测量

默认关闭性能记录；仅验收时打开 `mcPerf`。不要提交包含账号信息的原始运行日志。

```sh
cd apps/apple
xcodegen generate
xcodebuild -project MovieClaw.xcodeproj -scheme MovieClawMac \
  -configuration Release -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath build-macrel ARCHS=arm64 ONLY_ACTIVE_ARCH=YES \
  ENABLE_TESTABILITY=YES test
```

```sh
python3 -m unittest discover -s scripts/perf -p test_mac_performance_report.py -v
python3 scripts/perf/mac_resource_sample.py <pid> --seconds 60 --phase idle > /tmp/mac-idle.jsonl
python3 scripts/perf/mac_performance_report.py <trace.jsonl> --resources /tmp/mac-idle.jsonl
```

最新 Release 原生 5 项测试通过，Python 6 项测试通过，`git diff --check` 通过。原生测试覆盖水平翻页边界、尺寸变化、搜索取消反馈、缓存搜索恢复及分页游标保留、搜索导航栈。缓存恢复测试使用 URLProtocol 返回固定成功响应，不依赖 NAS 速度。脚本测试覆盖分位数、缺少样本、输入排队分段、Instruments XML 引用/进程过滤，以及 Mach 时钟换算和错误旧数据的拒绝。

CPU 校准：早期脚本错误地把 `proc_pid_rusage` 的 CPU 时间当作纳秒。在此 Apple Silicon 机器上必须乘 `mach_timebase_info` 的 125/3，早期 0.527% / 0.068% 读数不可使用。修复后用本机一秒单核忙循环交叉验证：采样结果和 Python `process_time` 均为 99.69%。新数据包含 `cpu_timebase`，汇总脚本不再输出缺少换算元数据的旧 CPU 数值。[Apple 内核的资源计量实现](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/bsd_kern.c)将 task power 时间写入 rusage 字段。

原始事件 `input.commit` / `app.firstCommit` 使用主 RunLoop 的 `beforeWaiting` 回调，报告明确称为 RunLoop 空闲代理。连续输入时回调可能晚于实际显示，不能当成准确的 input-to-photon 或启动首帧。`received` 新字段区分事件投递前等待和投递后的工作；验收仍需核对 Instruments 的呈现时间。卡顿比例分母必须使用活跃交互时间，不能混入静置时间。

已验证搜索结果→详情→返回搜索结果→清空恢复首页、快速改词后恢复缓存结果、⌘F，以及 20 轮电影库→详情→返回→首页。另完成《1917》原盘的 3 次真实起播、暂停、关闭，已核对实际视频画面和播放位置推进。重新构建后运行旧进程曾出现客户端 -1009 网络错误；重启最新进程后 NAS 搜索恢复正常。

坐标滚动比逐个辅助功能元素定位更少干扰，但仍未达标。之前元素定位录制的 424 个主线程 CPU 样本中，137 个涉及辅助功能入口；不能把工具开销算成正常用户体验，也不能因此宣称应用已经达标。实际滚动是否发生已通过滚动条从 0 变为 0.2622 验证。

本轮搜索缓存恢复的界面回归已完成。撤回无稳定收益的背景延伸试验后，第十一次 Release 构建及 5 项原生测试通过；重新启动最终构建后，真实 NAS 搜索、详情和继续播放均恢复正常。

另录制 SwiftUI + Points of Interest，并将 Time Profiler 高频采样关闭。80 次按键的 RunLoop 代理值为 P95 58.43 ms、P99 61.64 ms。输入 signpost 与 JSONL 时间基准可以对齐到约 0.1 ms；应用提交通过进程、surface ID 和 swap ID 与显示帧关联。该关联尚不能证明某一帧已经包含对应输入文字，所以不能把“下一张应用帧”当作输入像素反馈验收值。[Apple 对帧生命周期的说明](https://developer.apple.com/documentation/xcode/understanding-hitches-in-your-app)也区分显示交换和完整屏幕扫描。

此输入录制的 17–31.3 秒主线程 CPU 样本累计约 1972 ms，主要涉及 AppKit 布局、文字绘制和 CA 提交，约 182 ms 样本包含辅助功能入口（分类可能重叠）。实验性地在首页隐藏时关闭背景延伸效果后，预热后的 80 次输入代理值 P95 78.51 ms、P99 139.29 ms，未证明稳定收益；已撤回该两行试验改动。试验构建的 5 项原生测试和真实搜索→详情→返回→快速改词恢复缓存→清空恢复首页均通过。

参考播放器选用本机已有 IINA 1.4.4。解锁后已播放 NAS 档 0 原片源（media 7188、file 24792，MKV、3840×2160、24 fps、HEVC Dolby Vision、约 76.3 Mbps）。临时设备登录与取流凭证仅放在内存，给播放器的测试入口仅绑定本机回环地址，转发原字节，不重新编码。临时登录在测试入口结束时注销。

初次 IINA 60 秒 CPU 均值 31.93%，但使用英文音轨和不同窗口尺寸，只作准备采样。正式对照已统一为第二条中文 TrueHD 8ch/48kHz 音轨、第一条中文 PGS 字幕、5120×2880 全屏。IINA 在约 10:00 片段的 60 秒 CPU 均值 29.21%，footprint 1247.36→1263.41 MB。客户端从约 10:03 开始的 60 秒 CPU 为 29.34%，footprint 602.36→686.25 MB、峰值 761.75 MB，采样后播放位置推进到 11:22。CPU 为进程自身计量，不包含本机转发进程；此对照不能替代总能耗或 HDR 色调映射质量的比较。

客户端另完成从约 0:27 开始的 120 秒连续播放，采样后再次核对位置已推进到 3:09。此前一组准备采样包含暂停时间，不能计入稳定播放 CPU 结论。

最终第十一次 Release 构建又完成同一 4K 文件的连续播放：600 个一秒资源样本实际覆盖约 601.4 秒，CPU 均值 25.34%，footprint 初值 400.05 MB、末值 592.81 MB、峰值 739.17 MB。每分钟均值依次为 573、601、624、636、623、596、699、592、618、577 MB，未呈持续增长。采样结束后辅助功能状态显示真实播放已推进到 10:36，关闭后详情页继续进度更新为 10:39。这是一段 10 分钟播放的证据，不能据此保证数小时播放无泄漏。

关闭这次播放后再采样 60 秒，前台空闲 CPU 均值为 0.161%，后 30 秒为 0.034%；footprint 352.19→352.17 MB、峰值 352.22 MB，播放资源释放后稳定。

能耗仍缺少有效数据：本机 Instruments 的 Power Profiler 明确报“不支持 macOS，仅支持 iOS/iPadOS”；`sudo -n powermetrics` 提示需要管理员认证。已请用户自行在终端认证并运行只读采样，认证前不能执行能耗对照，也不能用 CPU 百分比代替能耗结果。

后续仍须完成：输入像素呈现时间核对、横/纵滚动卡顿优化、冷/热可交互启动时间、同片源播放能耗对照。此前锁屏阻止了 UI 验证，解锁后已完成相同片源播放 CPU 对照和 10 分钟播放内存采样；锁屏不能作为性能达标或后端问题的解释。


## 首页滚动专项复测（15:36）

用户反馈上下、左右滚动不够流畅，真实触控板复测后确认主要剩余问题为首页整体上下滚动。生产包基线为 0.4.0 (202610051440)，第一轮优化构建为 202610051520，第二轮为 202610051550。为避免另一任务同时改动源文件和锁住 DerivedData，专项测试在附加工作树 `macos-scroll-perf` 内使用固定源文件快照与独立构建目录；工作树没有带入同时发生的播放器、侧边栏和大图高度调整。

新增两项改动：横/纵滚动及惯性期间暂停卡片悬停缩放、指针倾斜和首页悬停换大图；首页仅保留大图切换的淡入淡出，关闭每次换图后的 40 秒慢推近。停稳后恢复悬停，详情页原有慢推近保留。根据 [Apple ScrollPhase](https://developer.apple.com/documentation/SwiftUI/ScrollPhase)，`isScrolling` 覆盖 interacting、decelerating 和 animating，tracking 不作为正在滚动。

真实触控板基线 6118 的 60 秒 CPU 均值 40.94%，其中连续操作区间的 40 个一秒样本均值 57.57%、峰值 69.62%。暂停悬停后的 19479 采样连续操作区间 40 个样本均值 47.36%、峰值 68.65%。两次手势节奏与行位置没有严格统一，不能把约 18% 的下降解释为已证明的因果收益，更不能换算为帧率。优化构建在采样窗口捕获 37 次横向 interacting、36 次 decelerating，以及 18 次纵向 interacting；完整事件中没有在首页纵向或接下来继续横向活跃阶段触发 `home.stage.hover`。用户评价“有改善，仍有卡顿”。

切换相同《我不是大师》大图后停止操作的单项对照更明确：开启慢推近的 19479 前 16 个资源样本平均 CPU 26.44%，随后动画结束回到接近零；关闭慢推近的 27848 前 16 个样本平均 0.244%。两个采样窗口均晚于换图过渡完成，未使用这些样本推断淡入淡出的耗时。关闭版本后段出现真实纵向操作，因此不能把整个 25 秒样本当作空闲测试。原始数据分别为 `/tmp/movieclaw-hero-zoom-idle-aligned-19479.jsonl` 和 `/tmp/movieclaw-hero-nozoom-idle-27848.jsonl`。

第二轮真实纵向采样 `/tmp/movieclaw-real-vertical-nozoom-27848.jsonl` 覆盖 90 个一秒样本，捕获 45 次纵向 interacting 和 44 次 decelerating；按原生阶段挑选的 31 个活跃秒样本 CPU 均值 55.13%，全部样本峰值 71.08%。这组与此前混合横纵手势不构成同条件 CPU 对照。配套 45 秒 sample 在用户开始持续操作前已结束，主线程几乎空闲，不能用于判断本次卡顿热点。

第一轮优化的 30 秒 SwiftUI 诊断录制还记录了 409 次 hitch、累计 3958.05 ms、最大 30.20 ms。包含自动化定位、静置及装饰动画，未得到可靠的活跃滚动分母，不作为滚动验收值。317552 次 SwiftUI 更新累计约 1412.67 ms，Action Callback、PropertiesTransform、MacCardLabel 与布局均有开销，不能仅凭计数认定唯一原因。Animation Hitches 模板曾产生约 26 GB 输出并明显干扰进程，已停止该无效录制；其数据不计入性能结论。

第二轮 Release 的 5 项原生测试通过。第一轮真实 NAS 的首页→详情→返回、搜索→详情→返回结果→取消恢复首页通过；停稳后悬停切换大图已通过界面验证。掉帧目标仍未通过验收，不能归因于后端而忽略。

用户再次反馈第二轮仍有上下滑动卡顿。按用户要求本轮停止优化，保存已验证改动与证据；未完成性能全部达标验收。最后一项关闭首页背景延伸的试验仅完成构建与原生测试，没有完成同条件性能对照，已撤回。诊断开关 mcPerf 已恢复为缺省关闭，采样进程已结束。
