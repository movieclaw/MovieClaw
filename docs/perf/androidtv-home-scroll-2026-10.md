# Android TV 首页滑动流畅度（2026-10）

状态：优化已完成，工作量指标达标；超时帧率、每帧 CPU 等计时指标的最终验收尚未完成（测量期间宿主机被其他任务占满，见 §2 末尾与 §6）。

种子用户在真机上反馈：媒体库首页上下、左右滑动有明显卡顿。本文记录指标、目标、测量方法和每一步优化的数据。
只做端侧（不含服务端接口耗时）。

## 1. 指标与目标

每个场景都是「冷启动进首页 → 遥控器按键脚本 → perfetto 录全程」，窗口取第一下按键前 0.1 秒到最后一下之后 1.2 秒。

| 类别 | 指标 | 定义 | 目标（最佳体验） |
| --- | --- | --- | --- |
| 用户可感 | 超时帧率 | SurfaceFlinger 帧时间线判「App Deadline Missed」的帧 ÷ 全部帧（Android 官方的掉帧口径） | ≤ 1% |
| 用户可感 | 超时时长 | 超时帧比截止时间晚的毫秒数之和 ÷ 场景秒数（同 Apple 的 hitch ratio） | ≤ 5 ms/s |
| 余量 | 每帧 CPU | 主线程 `Choreographer#doFrame` + 渲染线程 `DrawFrame` 期间两条线程**实际占着 CPU** 的时间（按调度记录求交集，等缓冲区、等锁不算），p50 / p90 / p99 | p99 ≤ 8.3 ms（半帧，给比模拟器慢的电视留一倍余量） |
| 工作量 | 渲染遍数 / 帧 | 渲染线程每帧执行的 Skia `OpsTask` 个数：1 = 只画屏幕，每多一层离屏合成多一遍 | 静置与滑动中都 ≤ 1.1（没有常驻的离屏层） |
| 工作量 | 重组耗时 | `Recomposer:recompose` 合计 ÷ 场景秒数 | 比基线降一半以上 |
| 工作量 | 静置 CPU | 首屏不动时两条线程每秒占用的 CPU 毫秒 | 比基线降一半以上 |

为什么这么定：

- 模拟器跑在 Mac 的大核上，CPU 比电视盒子（Amlogic S905X4、Chromecast with Google TV 这类 Cortex-A55）快 5～10 倍，GPU 更是差两个数量级。
  所以「模拟器上不掉帧」远远不够，还要看**每帧干了多少活**：每帧 CPU 留出余量，渲染遍数和重组这类不随机器快慢变化的工作量要降到底。
- Apple TV 上踩过的坑（[tvos-home-gpu-2026-10.md](tvos-home-gpu-2026-10.md)）：主线程不慢，瓶颈在 GPU 合成——大图区两层全屏遮罩让每帧多出几遍离屏渲染。
  电视盒子的 GPU（Mali-G31 一档）填充率只有每秒几亿像素，1080p 一整屏的离屏渲染加合成就要好几毫秒，所以「渲染遍数」是这里最重要的工作量指标。
- 不用「相邻两帧呈现间隔」算掉帧：模拟器的宿主合成本身有抖动，基线包静置时也有一成的帧间隔超过 1.5 个周期，而官方口径的超时帧率三轮之间很稳。

## 2. 怎么测

### 数据

`tests/fixture/fixture.py start` 起隔离测试服务器，再跑 `tests/perf/seed_home.py` 把首页灌到真实用户的规模：
26 部电影、16 部剧，「接下来继续」17 张，收藏 12 部，首页 14 行（含按评分、上映、随便看看等自加行）。

### 被测包

`benchmark` 构建类型：与正式包同样 R8 混淆优化、不可调试，用调试密钥签名（能覆盖安装在已登录的 debug 包上），允许 perfetto 采样。
debug 包不能用来测性能：可调试的包 ART 不做优化，Compose 慢好几倍。

```bash
./gradlew :app:assembleDebug :app:assembleBenchmark
adb install -r app/build/outputs/apk/debug/app-debug.apk   # 先用调试参数登录（见 README）
python scripts/perf/home_scroll.py --apk base=/tmp/base.apk --apk new=app/build/outputs/apk/benchmark/app-benchmark.apk \
    --runs 3 --avd Android_TV_API_34 --out /tmp/atv-perf
```

- 每个场景前 `cmd package compile -m verify -f`：等同刚安装 / 刚升级、全靠 JIT 的状态。侧载安装没有云端配置，系统要等设备空闲时的后台编译才会按基线配置预编译，
  种子用户频繁升级，大多数时候就在这个状态。`--compile speed-profile` 测后台编译之后的状态。
- 多个 `--apk` 逐轮交替运行，抵消宿主机负载漂移；每条结果记下宿主机 1 分钟负载，负载超过 `--max-load` 先等。
- 遥控器按键用设备上的 `input keyevent`（Android 14 上是一次 binder 调用，几毫秒），整段按键脚本在设备上跑，节奏不受 adb 往返影响。

### 场景

| 场景 | 操作 |
| --- | --- |
| idle | 首屏静置 6 秒（慢推、预告照常） |
| v-step | 从「继续播放」逐行往下 14 下、再往上 14 下，每 0.5 秒一下 |
| v-hold | 同上，按住（系统连发 20 次 / 秒） |
| h-step-upnext | 进「接下来继续」，往右 12 下、往左 12 下，每 0.5 秒一下（每停一下大图换片） |
| h-hold-upnext | 同上，按住 |
| h-step-shelf | 进第一条海报行（选中展开），往右 10 下、往左 10 下，每 0.5 秒一下 |
| h-hold-shelf | 同上，按住 |

### 模拟器与宿主机的限制

- 模拟器的 GPU 走宿主机（gfxstream），绘制调用越多、离屏越多，宿主的渲染线程越忙，App 渲染线程就越久拿不到空闲缓冲区（`dequeueBuffer` 等待）。
  这部分数字只能当方向参考，真机上的 GPU 代价要用「渲染遍数」来推。
- 测量期间这台 Mac 上同时跑着别的任务（其他模拟器、iOS 模拟器、Gradle 构建），1 分钟负载常在 20～50、峰值上百，
  模拟器两次被自身看门狗判卡死退出。所以只比较同一时段交替跑出的结果，脚本在设备掉线时自动冷启动模拟器重跑该场景。

## 3. 基线（2026-10-08，main 0a63b47e）

模拟器 Android_TV_API_34（1920×1080，4 核），benchmark 包，JIT 状态，大核，宿主机空闲时 3 轮中位：

| 场景 | 超时帧% | 每帧 CPU p90 / p99 ms | 渲染遍/帧 | 重组 ms/s | CPU ms/s |
| --- | --- | --- | --- | --- | --- |
| idle | 1.55 | 4.6 / 15.9 | 2.0 | 0.5 | 192 |
| v-step | 3.10 | 7.1 / 16.1 | 4.42 | 45.5 | 255 |
| v-hold | 1.79 | 10.7 / 26.2 | 5.55 | 68.4 | 304 |
| h-step-upnext | 3.69 | 9.9 / 43.5 | 3.85 | 61.9 | 327 |
| h-hold-upnext | 2.33 | 7.0 / 27.8 | 2.80 | 50.9 | 253 |
| h-step-shelf | 5.06 | 6.9 / 20.6 | 2.38 | 36.1 | 225 |
| h-hold-shelf | 2.17 | 8.4 / 15.8 | 2.86 | 43.6 | 206 |

看 trace 得出的问题：

1. **大图区常驻两层全屏离屏**：整个背景层 `CompositingStrategy.Offscreen`，托字的黑再单独离屏画横向渐变、用纵向渐隐 DstIn。慢推让背景每帧都变，两层每帧都要重画（与 Apple TV 同一个坑）。
2. **TV Material 的 `Text` 每段字一层离屏**（字节码里无条件 `graphicsLayer { compositingStrategy = Offscreen }`）。首页上百段字各占一块纹理；新的一行滚进来，一帧要新建、渲染 13～20 个层。
   顺带的显示问题：大图区带阴影的几行字，阴影被层的边界截成一个硬边矩形。
3. **淡入淡出都在整块离屏**：换片时两张整屏剧照的 `Crossfade`（1920×1080，每帧两次）、片名简介的 `AnimatedContent`（1760 宽）、海报行简介（720×131）、海报卡展开（约 800×450，每帧两次）。
4. **滚动时整页重组**：首页在组合阶段读列表滚动量；「接下来继续」每张卡在每次布局时写一个状态（卡片顶边位置）；行清单每次重组重算、回调每次新建，焦点挪一下各行都跟着重组。
5. **静置也满帧重画**：慢推用逐帧动画，首页不动时也 60 帧 / 秒整屏重画。
6. 掉帧点附近渲染线程大量时间在 `dequeueBuffer` 上等宿主合成、主线程在 `postAndWait` 上等渲染线程：瓶颈在绘制量，不在主线程。

## 4. 优化

每一步都只改「怎么画」，不改画面（例外见各条）。

| # | 改动 | 画面 |
| --- | --- | --- |
| 1 | 背景层不再常驻离屏；托字的黑改成一个合成着色器（横向渐变 DstIn 纵向渐隐）一遍画完，深浅用整笔透明度 | 逐像素同（实测只有 ±1～2 的取整差：少了一次 8 位量化） |
| 2 | 首页往下滚时背景整层淡出：底下正好是纯色页面底，改为盖一层「页面底色 × (1 − 透明度)」。详情页底下是模糊图，仍按整层透明度 | 推导上逐像素同 |
| 3 | 滚动量、边缘色渐变只在图层 / 绘制阶段读；卡片顶边位置不再是状态；行清单、回调记住 | 不变 |
| 4 | 自己的 `Text`：参数与取色规则同 TV Material（`LocalTextStyle`、`LocalContentColor`），直接用 `BasicText` 画 | 普通文字逐像素同；大图区文字阴影不再被截成矩形（修掉原有问题） |
| 5 | 剧照、片名简介、海报行简介、预告画面的交叉淡入：透明度直接乘到每一笔绘制上（`ModulatedCrossfade` / `ModulateAlpha`） | 剧照、预告是单张图，逐像素同；文字只在字与自身阴影重叠处、淡入的 0.3～0.45 秒内有极细微差别 |
| 6 | 海报卡展开：背景图版在下面照常画，海报在上面按 1 − a 淡出，宽出海报的那截盖卡底色 × (1 − a) | 推导上逐像素同 |
| 7 | 慢推每秒更新 10 次（40 秒放大 6%，1920 宽的画面边缘每次挪不到 0.15 像素） | 看不出差别 |
| 8 | 基线配置：App 自己的代码全部预编译（依赖库自带规则） | — |

画面比对：通过一个挡掉预告接口的本地代理登录（首页不放预告），新旧包各在首页停 45 秒（慢推走完、停在 1.06 倍），在首屏、「接下来继续」、第一条海报行、「我的媒体库」四个状态截图逐像素比较。
同一个包截两次的噪声底：首屏、海报行两个状态完全一致（差值 0）；「我的媒体库」那一行本身渲染不稳定，同包自比也有 12% 的像素不同（最大差 81），这一张不作比较。

基线包 vs 优化后（v4）：

| 状态 / 区域 | 结果 |
| --- | --- |
| 托字黑区域（没有字的地方） | 最大差 1：单遍着色器少了一次 8 位量化 |
| 第一条海报行（整屏） | 0.5% 像素不同，最大差 3 |
| 大图区带阴影的文字 | 原版阴影被文字层的边界截成硬边矩形，现在自然散开（原有显示问题，见上） |
| 卡片暗带等其余文字 | 肉眼一致；字形边缘局部差值大（最大 216），是亚像素位置变了：原来离屏层原点对齐整像素，现在按实际坐标画 |

## 5. 结果：工作量指标

base（main 0a63b47e）vs v4（本分支），同一时段交替，各 1 轮。这些指标按「每帧」计，不随宿主机快慢变化
（v4 这轮跑在挡掉预告的代理账号上，两边条件相同）：

| 场景 | 渲染遍 / 帧 | 离屏 / 帧 | 绘制调用 / 帧 |
| --- | --- | --- | --- |
| idle | 2.0 → 1.0 | 1.0 → 0 | 60 → 54 |
| v-step | 4.04 → 2.0 | 3.35 → 0.04 | 102 → 83 |
| v-hold | 4.46 → 2.15 | 4.01 → 0.16 | 85 → 73 |
| h-step-upnext | 3.93 → 1.05 | 5.38 → 0.01 | 97 → 90 |
| h-hold-upnext | 3.15 → 1.09 | 3.21 → 0 | 91 → 87 |
| h-step-shelf | 2.28 → 0.95 | 3.15 → 0.01 | 65 → 61 |
| h-hold-shelf | 2.52 → 0.98 | 3.44 → 0.01 | 66 → 63 |

- 静置时两条线程的 CPU：300 → 35 ms/s（没有预告时；慢推降到每秒 10 次）。
- 竖滑剩下的每帧约 1 遍额外渲染，集中在「我的媒体库」卡片进画面的那几十帧（每帧 6～16 遍、伴随新建纹理）：
  库卡背后的 `blur(20.dp)`（RenderEffect）在 GPU 上多遍渲染。属于进画面时的一次性开销，换实现会改变模糊的观感，未动。

## 6. 尚未完成

1. **计时指标的最终验收**（超时帧率 ≤ 1%、超时时长 ≤ 5 ms/s、每帧 CPU p99 ≤ 8.3 ms）。
   2026-10-08 22:30 起，这台 Mac 被其他会话的模拟器（软件渲染，单个占 6～10 个核）、Gradle 构建等长时间占满，
   CPU 空闲常在 0～20%，模拟器四次被看门狗杀掉。这期间测到的计时数字连同一个基线包都比空闲时差一个数量级，没有意义。
   验收命令（交替 3 轮，开测前要求宿主机连续 1 分钟 CPU 空闲 ≥ 40%，测完复查不达标作废重测）：
   `python scripts/perf/home_scroll.py --apk base=<main 的 benchmark 包> --apk new=<本分支的 benchmark 包> --runs 3 --avd Android_TV_API_34`
2. 弱机模式（`--weak`）与后台编译后（`--compile speed-profile`）两种状态的复测，同样需要空闲的宿主机。
3. 真机验证：模拟器的 GPU 走宿主机，GPU 一侧的收益（离屏层与渲染遍数）只能在真机上看到实际帧率。
